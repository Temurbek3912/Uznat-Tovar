## 2–3. Найденные дефекты и доказательства
1. **OpenCV 5.0.0.93.** `requirements.txt` содержал `opencv-python-headless>=4.9` БЕЗ верхней границы → pip взял 5.x, а в OpenCV 5.0.0.93 нет `cv2.CascadeClassifier`
   (подтверждено выводом пользователя из контейнера: `hasattr(cv2,'CascadeClassifier') == False`). Вторая причина: `ultralytics` тянет `opencv-python` (с GUI) — обе сборки пишут в одну папку `cv2/`.
   `pip check` молчит, потому что формально конфликтов зависимостей нет. `scripts.check_imports --runtime` проверял только импорты, не возможности.
   **Исправление:** `requirements.txt` → `opencv-python-headless>=4.9,<5`; обязательный `constraints-opencv.txt` (всё `<5`); Dockerfile: установка с замком, затем удаление всех сборок OpenCV и
   установка одной headless без зависимостей, затем `python -m scripts.check_opencv` (сборка падает, если нет CascadeClassifier/каскад не загружается); общий код — `app/core/opencv_check.py`.
2. **`FaceBlurrer`:** путь к каскаду вычислялся при ИМПОРТЕ модуля (`cv2.data.haarcascades`); теперь — при создании объекта, с понятными ошибками (`FaceBlurUnavailable`, подкласс `RuntimeError`).
   Тот же класс создаётся в API (`routes_review._get_blurrer`) — сломанный OpenCV ронял бы и API-запросы обрезки; исправление общее. Размытие лиц НЕ отключено.
3. **`_init_ml_components` (воркер):** (а) `FaceBlurrer()` — первой строкой без защиты: ошибка прерывала функцию, детектор/эмбеддер/матчер оставались `None`; (б) Celery перехватывает `Exception`
   в обработчике сигнала («Signal handler raised») и всё равно пишет «ready»; (в) при сбое YOLO **молча** подставлялся `HeuristicContourDetector`; (г) healthcheck воркера — только `inspect ping` (отвечает при сломанных компонентах);
   (д) задачи при `None` молча перезапускали тяжёлую инициализацию и падали сырой ошибкой.
   **Исправление:** `app/pipeline/ml_runtime.py` (каждый компонент независимо; обязательные — face_blurrer, detector, embedder, matcher; необязательный — price_ocr; подмена детектора/эмбеддера только флагами
   `ALLOW_HEURISTIC_DETECTOR=1` / `ALLOW_DEBUG_EMBEDDER=1` и помечается «ЗАМЕНЁН»; таблица состояния в логе; файл статуса); `worker_init` → `preflight` → `SystemExit(78)` до «ready»
   (SystemExit — `BaseException`, Celery при рассылке ловит только `Exception`); `_require_ml()` в каждой ML-задаче, `MLNotReadyError` → понятный отказ (`CatalogAddError`), снимок помечается `failed`, а не висит в `queued`;
   `scripts/worker_health.py` + healthcheck compose = «статус готов» И «pong».
   **Проверено:** `tests/test_ml_runtime.py` (12), `tests/test_opencv_setup.py`, `tests/test_privacy.py`, статические проверки структуры воркера (`tests/test_worker_static.py`).
   **НЕ проверено:** что `SystemExit` из `worker_init` действительно прерывает запуск именно в вашей версии Celery (выводится из чтения кода рассылки сигналов) — проверьте, убрав файл весов: воркер должен
   завершиться с кодом 78 и перезапускаться, а в логе — критическая причина.

## 5. Штрих-коды (состояние)
Читаются EAN-13, EAN-8, UPC-A (собственный построчный декодер + запасной `cv2.barcode`, только 13 цифр от OpenCV; проверка контрольной цифры; UPC-A хранится как EAN-13 с нулём впереди — ни один ведущий ноль не теряется).
Замеры на 720 синтетических кадрах: 84%, неверных чтений 0; код ≥45% ширины кадра — 144/144. **Не читаются:** UPC-E, Code 128, Code 39, QR (QR в функциональность не входит).
`zxing-cpp`/`pyzbar` в среде Claude не установить (нет сети), поэтому как зависимость НЕ добавлены; план: опциональный движок `zxingcpp`, если он установлен (тест пропускается без него), плюс собственные декодеры Code 39/Code 128/UPC-E
с проверкой таблиц по `reportlab` (он есть в среде Claude). «Прочитан, но нет в каталоге» и «товар узнан по коду» — уже различаются в API/интерфейсе. Нет сообщения «штрих-код виден, но не читается» (идея: `cv2.barcode.detect`).

## 6. Узбекский язык — результаты аудита (исправлений нет)
* **Интерфейс:** весь интерфейс только русский; механизма переводов и выбора языка интерфейса в проекте **нет** (не «сломан» — не существует). Узбекский есть только в фразах озвучки на странице «Узнать товар» и в языках OCR ценников (`uzb`, `uzb_cyrl`, `rus`, `eng`).
* **Озвучка:** `uz-UZ` работает только если в системе/браузере есть узбекский голос (см. §7). Апострофы в фразах — `ʻ` (U+02BB).
* **Не проверено / подозрения:** (1) в `docker-compose.yml` БД `postgres:16-alpine` — у образа на musl регистронезависимый поиск `ILIKE` по кириллице/узбекским буквам может работать иначе, чем на Debian-образе (проверить на реальных названиях);
  (2) кодировка чтения CSV-импорта каталога (скрипт `scripts/import_catalog.py` / `app/services/catalog_import.py`) не проверялась — типичный источник «РѕР…» (UTF-8, прочитанный как cp1251 при работе в Windows/Excel/PowerShell);
  (3) варианты апострофа (`o'`, `o‘`, `oʻ`, `oʼ`, `` o` ``): при проверке повторов названий всё, что не буква, сворачивается в пробел (`normalize_name`), поэтому `o'zbek` = `oʻzbek`, но поиск (`ILIKE`) и артикул (`make_slug`: апостроф → «-») их не унифицируют;
  (4) STT (распознавание речи) в проекте **нет** (поиск по коду не нашёл) — только синтез.
* **План:** `app/core/uztext.py` (унификация апострофов, свёртка регистра, Кириллица→Латиница для поиска, обнаружение/починка «мojibake» БЕЗ молчаливой правки данных), поиск по каталогу с Python-свёрткой (не зависит от локали БД),
  проверка кодировки импорта, тесты на `o‘ g‘ oʻ gʻ`, «ўқғҳ», «РѕР…».

## 7. Озвучка — результаты аудита
