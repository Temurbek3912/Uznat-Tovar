# Запуск в Docker: от клонирования до работающей системы

Для Windows + Docker Desktop (WSL2). Команды — для PowerShell в папке проекта. Краткая версия — в `README.md`, раздел «Запуск через Docker».

## 1. Что запускается и в каком порядке

```
db ─────┐ (healthy)
redis ──┤ (healthy)
frames ─┤ (healthy; кадры «Узнать товар» — только в памяти)
        └─► bootstrap ──(завершился успешно)──► api       (порт 8000, сеть магазина: сотрудники)
                                          ├──► admin-api (порт 8001, только этот компьютер или VPN: управление)
                                          ├──► shop      (порт 8080, адрес из QR-кода: покупатели, без входа)
                                          └──► worker    (Celery: детекция, эмбеддинги, сверка)
```

| Сервис | Что делает | Где хранит данные |
|---|---|---|
| `db` | PostgreSQL 16 | именованный том `pgdata` |
| `redis` | очередь задач Celery | том `redisdata` (очередь переживает перезапуск) |
| `bootstrap` | одноразово: ждёт БД → создаёт таблицы → создаёт папки → создаёт первого admin | — |
| `api` | FastAPI + раздача страниц `/ui/*`; вход сотрудников, `APP_LISTENER=public` — права управления здесь не действуют | снимки — папка `data/` проекта |
| `admin-api` | тот же образ и та же база, `APP_LISTENER=admin`; порт опубликован только на `127.0.0.1` (VPN — `docker-compose.vpn.yml`). Документ 18, §4 | — |
| `shop` | вход покупателя (`APP_LISTENER=customer`, порт `SHOP_PORT`, по умолчанию 8080): только «Узнать товар» без входа и страница `/ui/shop.html`; маршрутов и страниц сотрудников нет. Адрес для QR-кода: `http://<IP компьютера>:8080/` | — |
| `frames` | Redis для кадров «Узнать товар» **без сохранения на диск** (решение D-10а): без тома, `/data` в памяти, порт не публикуется; кадр живёт не дольше 2 минут | только оперативная память |

**HTTPS для телефонов** (обязательно с 2026-11-08: пароли по Wi-Fi без защиты не передаются, документ 18, §14):
`docker compose exec api python -m scripts.make_local_tls --ip <адрес в Wi-Fi>`, затем
`docker compose -f docker-compose.yml -f docker-compose.https.yml up -d` — порт 8000 работает по HTTPS. Инструкция с установкой
центра магазина на телефоны — `docs/REMOTE_ACCESS_GUIDE.md`, п. 7.
| `worker` | Celery, `--concurrency=1` | индекс каталога — `models/index/`, кэш моделей — том `hf_cache` |

`api` и `worker` не стартуют, пока `bootstrap` не завершится успешно. Если он упал — вы увидите это сразу (`docker compose ps`, `docker compose logs bootstrap`), а не «контейнер Up, но приложение не работает».
Образ один (собирается сервисом `api`), `worker` и `bootstrap` используют его же.

## 2. С нуля

```powershell
git clone <адрес-репозитория>
cd retail-shelf-audit
copy .env.example .env      # необязательно, но так удобно задать пароль админа (шаг 3)
docker compose build
docker compose up -d
docker compose ps
```

Сборка при первом запуске долгая и тяжёлая (torch и сопутствующие библиотеки — несколько ГБ). В конце сборки Dockerfile сам проверяет, что **все импорты из кода объявлены в `requirements.txt` и установлены**, а системный `tesseract` на месте: при расхождении сборка падает с понятным списком (`python -m scripts.check_imports --runtime`).

После `up -d` подождите, пока в `docker compose ps` у `db`, `redis`, `api`, `worker` станет `healthy`. У `worker` это может занять несколько минут: при самом первом запуске он скачивает модель DINOv2 (~350 МБ, нужен интернет) — один раз, потом она лежит в томе `hf_cache`.

## 3. Первый администратор

Через API создать первого админа нельзя по построению (создавать пользователей может только админ), поэтому его создаёт `bootstrap`:

- **Способ А.** В `.env` задайте `ADMIN_USERNAME=admin` и `ADMIN_PASSWORD=<ваш пароль, от 8 символов>`, затем `docker compose up -d`. Админ создаётся, только если в БД ещё нет активного admin; пароль существующего пользователя не перезаписывается. После создания пароль из `.env` можно удалить.
- **Способ Б.** `docker compose run --rm bootstrap` — спросит логин и пароль в терминале.

Первый администратор становится **владельцем системы** (документ 18, §7). Все администраторы входят с **обязательным вторым
фактором**: перед первым входом задайте `AUTH_SECRET_KEY` в `.env` (`docker compose exec api python -m scripts.generate_secret_key --auth`),
затем откройте на этом компьютере `http://localhost:8001/ui/settings.html` и настройте второй фактор — `docs/REMOTE_ACCESS_GUIDE.md`.

Пароли из списка типичных (`password`, `12345678`, …) и совпадающие с логином не принимаются. Запасной вариант (создать ещё одного админа, если забыли пароль): `docker compose exec api python -m scripts.create_user --username admin2 --role admin`.

## 4. Первые шаги после запуска

Откройте `http://localhost:8000` → войдите. Магазины, полки и планограммы больше не нужны: проект теперь «Узнать товар», а не аудит
полок. Демо-данные **не создаются**.

| Шаг | Где | Статус |
|---|---|---|
| Войти | `/` (главная, `/ui/index.html`); вход один на все страницы одной вкладки браузера | есть |
| **Добавить товар (каталог)** | `/ui/products.html` («Товары»): название + 3–5 фото, без терминала | есть; много товаров сразу — командой (ниже) |
| **Узнать товар** (показать камере или поднести штрих-код — система назовёт на экране и покажет карточку) | `/ui/identify.html` («Узнать товар») | есть |
| Пользователи (создание, права, отключение, сброс пароля) | `/ui/admin.html` → «Пользователи» | есть |
| Состояние системы (БД, очередь, воркер, диск, настройки) | `/ui/admin.html` → «Система» | есть |

Команды для недостающих шагов (папки и файлы лежат в проекте на вашем диске и видны контейнеру):

```powershell
# Каталог ПАЧКОЙ (десятки товаров; по одному проще на странице «Товары»): фото в catalog\<артикул>\1.jpg 2.jpg … (см. docs/catalog_guide.md), затем:
docker compose exec api python -m scripts.import_catalog --dir catalog --validate-only   # проверка без записи
docker compose exec api python -m scripts.import_catalog --dir catalog
docker compose restart worker          # ОБЯЗАТЕЛЬНО: воркер держит индекс в памяти и не видит новых товаров до перезапуска
```

## 4а. Администратор: безопасные инструменты (ничего не удаляют и не пересоздают)

```powershell
docker compose exec api python -m scripts.diagnose                      # к какой БД подключено; ошибка подключения / нет таблиц / пусто; сверка кодов полок; пользователи без хешей
docker compose exec api python -m scripts.user_admin list                # пользователи, роли, статус
docker compose exec api python -m scripts.user_admin reset-password --username admin   # скрытый ввод, сессии завершаются
python scripts\backup_db.py                                              # на хосте: проверяемая копия БД в backups\ (перед ЛЮБЫМИ изменениями схемы)
```
`seed_catalog` теперь отказывается работать на непустой базе (демо-данные только в пустую, и только с флагом `--yes-add-demo-data`). `bootstrap` администратора, который уже есть, не трогает и пароль не меняет.

## 5. Как проверить, что всё работает

```powershell
docker compose ps                                  # db, redis, api, admin-api, worker — healthy; bootstrap — Exited (0)
Invoke-RestMethod http://localhost:8000/health/ready   # status = ok: БД, таблицы и очередь в порядке
docker compose logs bootstrap                      # что он сделал при запуске
docker compose exec api python -m scripts.smoke_test                # вход → токен → защищённый API → каталог → раздел «Система»
docker compose exec api pytest -q                  # весь набор тестов проекта на настоящих FastAPI/SQLAlchemy
```

`smoke_test` создаёт временного администратора и в конце удаляет его вместе с токенами — ваши данные не затрагиваются. Круг через воркер
(`--with-worker`) пока не поддерживается: прежний круг проверял снимок полки и отчёт, которых больше нет; новый будет добавлен вместе
с этапом распознавания. `pytest -q` стоит выполнить хотя бы раз: часть API-тестов проекта (`test_auth_api`, `test_stores_api`) написана
в среде без FastAPI; при падении сначала подозревайте сам тест.

## 6. Данные: что где лежит и как не потерять

| Данные | Где | Переживает `docker compose down` | Удаляется `down -v` |
|---|---|---|---|
| База (товары, пользователи; данные прежнего аудита сохранены) | том `pgdata` | да | **да** |
| Очередь задач | том `redisdata` | да | да |
| Модели HuggingFace | том `hf_cache` | да | да (скачаются снова) |
| Фото товаров и прежние снимки | папка `data/` проекта | да | нет |
| Индекс каталога, веса | папка `models/` проекта | да | нет |

Бэкап базы (формат custom, без проблем с кодировкой PowerShell):

```powershell
docker compose exec db sh -c 'pg_dump -U $POSTGRES_USER -Fc $POSTGRES_DB > /tmp/shelf.dump'
mkdir backups -Force
docker compose cp db:/tmp/shelf.dump backups\shelf-$(Get-Date -Format yyyyMMdd).dump
```

Восстановление (в **работающую** систему, перезапишет данные):

```powershell
docker compose cp backups\shelf-ДАТА.dump db:/tmp/shelf.dump
docker compose exec db sh -c 'pg_restore -U $POSTGRES_USER -d $POSTGRES_DB --clean --if-exists /tmp/shelf.dump'
```

Вместе с базой копируйте папки `data/` и `models/index/` (индекс каталога): база и индекс согласованы между собой. Автоматического бэкапа в проекте нет — настройте расписание сами (например, Планировщик заданий Windows).

## 7. Закрепить версии зависимостей (рекомендуется сделать один раз)

`requirements.txt` содержит только нижние границы (`torch>=2.3` и т.п.), поэтому сборка «через год» может подтянуть другие версии, чем сегодня. Когда образ **собрался и работает** — зафиксируйте его версии:

```powershell
docker compose run --rm --no-deps api sh -c "pip freeze > /srv/app/constraints.txt"
git add constraints.txt
```

Дальше `docker compose build` автоматически ставит ровно эти версии (Dockerfile подхватывает `constraints.txt`, если он есть). Файл создаётся внутри контейнера намеренно: `pip freeze > файл` в Windows PowerShell 5.1 записал бы UTF-16, который pip не прочитает. Обновлять версии осознанно: удалить `constraints.txt`, собрать, проверить, заморозить заново.

## 8. Заметки для большого магазина (ограничения, о которых лучше знать заранее)

- **Один воркер.** `--concurrency=1` — обязательное ограничение (индекс каталога — файл + копия в памяти процесса; `docs/HANDOFF.md`, п. 14). Снимки обрабатываются строго по очереди. Скорость на CPU внутри Docker **не измерена** — замерьте сами: `smoke_test --with-worker` показывает, дошла ли цепочка, а время обработки реального снимка видно в `docker compose logs worker`. Если очередь не успевает, масштабировать нужно архитектурой (общий индекс — pgvector), а не числом процессов.
- **Только CPU.** Образ без CUDA: видеокарта ноутбука внутри контейнера не используется. GPU работает при запуске API и воркера на хосте (`python -m scripts.start_demo`, раздел RUNBOOK) либо потребует отдельного образа на базе `nvidia/cuda`.
- **Диск.** Снимки хранятся бессрочно: параметр `raw_image_retention_days` в `configs/config.yaml` **нигде не читается** (политики хранения нет). Сотни полок × несколько снимков в день — гигабайты в сутки в `data/`. До реализации очистки следите за местом.
- **Пароль БД.** Если нужен не `postgres`, задайте `POSTGRES_PASSWORD` в `.env` **до первого `docker compose up`**: пароль применяется только при создании тома `pgdata`. База и Redis открыты только на `127.0.0.1`; наружу (в локальную сеть) открыт только API на порту 8000; административный вход 8001 — только на `127.0.0.1` (и на адресе VPN, если подключён `docker-compose.vpn.yml`).
- **HTTP, не HTTPS.** Страницы и API работают по `http://<IP-компьютера>:8000`: съёмка с телефона работает, но иконка «на главный экран» откроется во вкладке, а не на весь экран (подробно — подсказка на странице съёмки). Для HTTPS нужен reverse-proxy перед API (в проекте его нет); за прокси запускайте uvicorn с `--proxy-headers --forwarded-allow-ips=<IP прокси>`, иначе лимит попыток входа по IP считает адрес прокси.
- **Режим работы.** `ENVIRONMENT=production` в `.env` отключает `/docs` и `/redoc`. **CORS** (доступ к API с другого адреса) настраивается переменной `CORS_ALLOW_ORIGINS` (через запятую, без пути: `https://audit.example.com,http://192.168.1.50:8000`). Страницам проекта (`/ui/...`) он не нужен — они ходят на тот же адрес. Не задана: в `development` разрешён любой источник (как раньше), в `production` кросс-доменный доступ закрыт. Ошибка в значении остановит запуск api с понятным сообщением. Какой режим включён, видно в `docker compose logs api` (строка «CORS …»).
- **Нет миграций.** Alembic в проекте не настроен (пакет в `requirements.txt` не используется). `bootstrap` создаёт недостающие таблицы, но **не изменяет существующие**: если после обновления кода в моделях появятся новые колонки, `bootstrap` остановится с кодом 2 и перечислит их (api и worker при этом не запустятся — так задумано). Для рабочих данных нужен настоящий Alembic; это стоит сделать до появления данных, которые жалко потерять.
- **Зависшие снимки.** Если контейнер остановили в середине обработки, снимок может остаться в статусе `processing`/`queued`: автоматической переочереди нет.

## 9. Типичные ошибки

| Симптом | Причина и что делать |
|---|---|
| `port is already allocated` / `address already in use` | порт занят (часто свой Postgres на 5432): задайте `API_PORT`/`DB_PORT`/`REDIS_PORT` в `.env`, затем `docker compose up -d` |
| `bootstrap` завершился с кодом 1, в логе «Postgres не отвечает» | `docker compose logs db`; чаще всего пароль в `.env` не совпадает с тем, с которым создан том `pgdata` |
| `password authentication failed for user` | вы изменили `POSTGRES_PASSWORD` после первого запуска. Верните прежний пароль в `.env` — либо задайте базе новый, **не удаляя данные**: `docker compose exec db psql -U postgres -c "ALTER USER postgres WITH PASSWORD 'НОВЫЙ'"` (внутри контейнера по сокету пароль не спрашивается), затем тот же пароль в `.env` и `docker compose up -d` |
| `bootstrap` завершился с кодом 2: «схема БД устарела» | см. п. 8, «Нет миграций»; сообщение содержит точные команды |
| `api` в состоянии `unhealthy` | `Invoke-RestMethod http://localhost:8000/health/ready` — в `checks` видно, что именно не готово (БД / таблицы / очередь) |
| `worker` бесконечно перезапускается, в логе ошибка про DINOv2 / HuggingFace | нет интернета для первой загрузки модели. Подключитесь к сети и `docker compose restart worker`. Только для отладки без модели: `ALLOW_DEBUG_EMBEDDER=1` в `.env` (распознавание при этом случайное!) |
| Админ не создался, войти нельзя | в `.env` не было `ADMIN_PASSWORD`: `docker compose run --rm bootstrap` |
| При `up -d` на машине, где образ не собирали: «No such image» | сначала `docker compose build` (образ собирает только сервис `api`) |
| Сборка падает на `check_imports` | в сообщении перечислены импорты без пакета в `requirements.txt` — добавьте строку и пересоберите |
| Снимок в статусе `failed` | `docker compose logs worker` — причина там; задача сама повторяется до 3 раз |

## 10. Что проверено, а что нет

Эта конфигурация подготовлена в среде **без Docker, без сети и без FastAPI/SQLAlchemy/Celery**. Реально выполнено и проходит: 620+ офлайн-тестов проекта (включая разбор `docker-compose.yml`, логику bootstrap, создание магазинов и полок, аудит зависимостей), JS-тесты страниц (101) и статическая проверка. **Не запускалось ни разу:** `docker compose build/up`, PostgreSQL, Redis, Celery-воркер, загрузка DINOv2, реальные HTTP-запросы, API-тесты с БД. Поэтому первый запуск у вас — это и есть настоящая проверка: пройдите пункт 5 и присылайте вывод `docker compose logs` при любом расхождении.
