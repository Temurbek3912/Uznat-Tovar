# 09. Резервное копирование и восстановление

## 1. Что есть сейчас

`scripts/backup_db.py`: `pg_dump -Fc` внутри контейнера `db` → временный файл → проверка `pg_restore --list` → атомарное
переименование, SHA-256 файла. Старые копии не удаляются, база не меняется. Это хорошая основа, но:

- копируется **только база**: фото товаров (`data/catalog-uploads`), индекс (`models/index`) и конфигурация — нет;
- восстановление — ручные команды, **проверки реального восстановления нет**;
- нет расписания, ограничения числа копий, выбора места в интерфейсе;
- работает только в профиле Docker.

## 2. Две разные вещи

| | **Резервная копия** | **Экспорт** |
|---|---|---|
| Зачем | восстановить **всю** систему после сбоя диска, ошибки, неудачного обновления | перенести каталог, открыть в Excel, передать поставщику |
| Что внутри | база целиком (пользователи, права, история, каталог), фото, индекс с манифестом, конфигурация, версии | таблица товаров (CSV/Excel), по желанию — папка фото |
| Формат | служебный (дамп + файлы + манифест) | человекочитаемый |
| Восстановление | «вернуть как было на момент копии» | импорт с проверкой (документ 06) |
| Кто | владелец (`backup.create`; восстановление — `backup.restore`, документ 05, §4) | сотрудник с `catalog.export` |

## 3. Состав полной резервной копии

```text
<место копий>/
  photos/                      ← ОБЩЕЕ хранилище фото всех копий: файл назван по SHA-256 и хранится один раз (уточнено в 1.11)
  Backup-2026-11-06_2130/
    manifest.json              ← версия программы, ревизия схемы (Alembic), модели и индекса, дата, число товаров, фото, пользователей,
                                 SHA-256 каждого файла копии, результат проверки
    photos.list                ← список хешей фото, на которые ссылается эта копия базы
    db.dump                    ← pg_dump -Fc (или резервная копия SQLite через backup API)
    index/                     ← catalog.faiss, ids.json, манифест индекса (производные данные, но экономят время восстановления)
    config/                    ← настройки без секретов в открытом виде (секреты — отдельно, раздел 6)
```

**Фото в копиях (1.11, документ 05, §13.3.6).** Фото не меняются и названы по хешу, поэтому они не дублируются в каждой копии: каждая новая копия
добавляет в общее `photos/` только новые файлы, **проверяя хеш каждого при копировании** (повреждённый оригинал в копию не попадает и сразу
отмечается в отчёте). Файл в `photos/` удаляется, только когда на него не ссылается ни одна сохранённая копия. Объём — примерно объём текущих фото
плюс фото, удалённые за срок хранения копий (около 6 месяцев), а не «объём фото × число копий». Это заменяет прежнее описание «папка `photos/`
внутри каждой копии» и совпадает с рекомендацией документа 11, §2 об инкрементальном копировании фото.

**Согласованность:** сначала дамп базы (это согласованный снимок), затем копия фото (их имена с хешем, после записи не меняются;
фото, добавленные после дампа, просто окажутся «лишними» и не помешают), затем индекс. Задания индексации на время копии ставятся
на паузу, чтобы индекс не менялся во время копирования. Если индекс в копии не соответствует базе, он пересобирается из фото
и кэша эмбеддингов при восстановлении (документ 07, §8).

## 4. Функции

| Функция | Описание |
|---|---|
| Ручная копия | кнопка «Создать копию сейчас», прогресс, итог «копия проверена» |
| Автоматическая копия | по расписанию (по умолчанию ежедневно после закрытия магазина), а также **перед каждым обновлением программы** и перед восстановлением |
| Место хранения | выбор папки; по умолчанию — **другой диск** или флешка. Предупреждение, если копии лежат на том же диске, что и база |
| Ограничение числа копий | например, 7 ежедневных + 4 еженедельных + 6 ежемесячных. **Последняя проверенная копия не удаляется никогда**. Фото в общем хранилище копий живут, пока на них ссылается хоть одна сохранённая копия (§3) |
| Проверка целостности | контрольные суммы всех файлов по манифесту, чтение дампа (`pg_restore --list`), наличие фото по `photos.list`; хеш каждого **нового** фото — при копировании; выборочная проверка хешей общего хранилища фото при каждой копии, полная — при ежемесячной проверке (§5) |
| Копия после крупного импорта (1.11) | после применения импорта с большим числом фото программа предлагает «Создать копию сейчас»: копируются только новые фото и дамп — это уменьшает риск потерять день работы при поломке диска |
| Проверка восстановления | см. раздел 5 |
| Восстановление | мастер: выбрать копию → предварительная страховочная копия текущего состояния → восстановление в **новую** базу → проверки → переключение → старая база хранится N дней |
| Защита от перезаписи | имена копий с датой и временем, существующая копия не перезаписывается; восстановление — только владелец, с повторным вводом пароля и подтверждением |
| Понятные ошибки | «Нет места на диске Е: (нужно 3,2 ГБ)», «Флешка не подключена», «Копия повреждена: файл photos/… не совпадает с контрольной суммой» |
| Шифрование (по желанию) | паролем владельца; предупреждение: забытый пароль = потерянная копия |

## 5. Проверка реального восстановления

Архив ещё не доказывает, что из него можно восстановиться. Поэтому:

- **Автоматически после каждой копии** (быстрая проверка): дамп восстанавливается во **временную отдельную базу** (в Desktop — на том же
  сервере PostgreSQL под служебным именем `verify_<дата>`; в Docker — в отдельном временном контейнере). Выполняются контрольные
  запросы (число товаров, пользователей, наличие владельца, ревизия схемы), проверяется наличие фото по списку из базы. Затем временная
  база удаляется. Средство проверки **никогда не обращается к рабочей базе** — это отдельное правило кода и тест.
- **Раз в месяц** (полная проверка, по напоминанию): восстановление копии на отдельном компьютере или в виртуальной машине
  и пробное распознавание, **полная проверка хешей общего хранилища фото в копиях**. Результат записывается в журнал.

## 6. Секреты

Пароль базы, ключи (например, `CAMERA_SECRET_KEY` старых камер) **не кладутся в копию открытым текстом**.
Варианты: шифрование копии паролем владельца (секреты внутри) или отдельный «ключ восстановления», который владелец хранит отдельно.
Без ключа восстанавливается всё, кроме зашифрованных секретов. Для старых камер это не критично: функция удалена.

## 7. RPO и RTO — решение D-11 (предварительно принято владельцем 2026-11-06, подтверждается испытаниями, §7.1)

- **RPO (сколько данных можно потерять)** — **до 24 часов**. Ежедневная автокопия означает: в худшем случае потеряются изменения
  каталога за один день. Для магазина, где каталог меняется понемногу, это обычно приемлемо. Если за день вносится много изменений,
  можно делать копию чаще (каждые 4 часа: копия занимает минуты).
- **RTO (за сколько восстановить работу)**:
  - на **том же компьютере** (испортилась база, неудачное обновление) — **до 30 минут**: выбрать копию в мастере и восстановить;
  - на **новом компьютере** (сломался диск или компьютер) — **2–4 часа**: установить программу, подключить диск с копиями,
    восстановить, проверить распознавание.

Простыми словами: «потеряем не больше одного дня изменений; на старом компьютере вернёмся за полчаса, на новом — за полдня».

**Фото и RPO (1.11).** Исходный файл задания, который программа хранит 24 часа после применения импорта (документ 05, §13.3.2), лежит на **том же
диске** и защищает только от сбоев записи при отключении питания; от поломки диска он не защищает. При поломке диска до ближайшей копии
теряются и товары, и фото, добавленные после неё, — в пределах того же RPO. Восстановление фото, повреждённого позже, — из общего хранилища фото
в копиях (документ 05, §13.3.6).

### 7.1. Практическая проверка показателей (учения по восстановлению)

Принятые значения считаются выполненными только после испытаний. Каждое испытание записывается в журнал
(`docs/BACKUP_DRILLS.md`, создаётся при первом испытании): дата, копия, что делали, время по шагам, результат, что улучшить.

| Испытание | Что проверяем | Как | Успех |
|---|---|---|---|
| **И-1. RPO** | копии действительно делаются не реже раза в сутки | 14 дней подряд проверять журнал копий; найти самый большой промежуток между проверенными копиями | промежуток ≤ 24 ч, все копии с отметкой «проверена» |
| **И-2. RTO на том же компьютере** | восстановление за 30 минут | имитация: «база испорчена» (на **копии** установки или в тестовой Windows, не на рабочих данных) → мастер восстановления → распознавание работает | от решения «восстанавливаем» до первого успешного распознавания ≤ 30 мин |
| **И-3. RTO на новом компьютере** | восстановление за 2–4 часа | чистая Windows (виртуальная машина или запасной ноутбук) → установка программы → подключение носителя с копиями → восстановление → вход владельца → распознавание → проверка числа товаров и фото | ≤ 4 ч, данные совпадают с манифестом копии |
| **И-4. Повреждённая копия** | система не восстанавливает «битую» копию молча | испортить один файл в **тестовой копии** | понятный отказ с именем файла; рабочие данные не затронуты |

Ограничение на сегодня: текущая копия (`scripts/backup_db.py`) сохраняет только базу. **Полностью проверить D-11 можно после
внедрения полной копии** (§8, п. 1): база + фото + индекс + конфигурация. До этого возможно частичное испытание И-2 только
для базы — и только после отдельного разрешения владельца, потому что это действия на его компьютере.

## 9. Универсальная платформа: влияние на резервные копии (добавлено в 1.3)

- **Копия узла магазина** включает и схему каталога: категории, характеристики, правила проверки, шаблоны, изменённые владельцем.
  Всё это лежит в базе и попадает в дамп; шаблоны программы восстанавливаются установкой.
- **Журнал ИИ-помощника** (`ai_*`) — в базе и в копии. Срок хранения — по решению владельца (документ 16, §9). Удаление по сроку не должно
  противоречить сроку хранения копий: если обещан срок N дней, копии с этими данными не хранятся дольше (как для фото покупателей, документ 04, §4.3).
- **Сеть (будущее):** каждый узел делает свои копии независимо (автономность). Центр организации — свои копии и архив WAL для
  восстановления на момент времени (документ 17, §4.3). Копии узлов в центр **не отправляются автоматически** без решения владельца.
- RPO и RTO (D-11) относятся к **узлу магазина**. Для центра сети показатели будут определены отдельно.
