# 18. Удалённый вход администраторов: HTTPS, вход с разных устройств, сеансы, роли, второй фактор

**Дата:** 2026-11-08 · **Основание:** дополнительное требование владельца от 2026-11-08: централизованная удалённая авторизация
администраторов через HTTPS, вход с разных устройств, управление сеансами и ролями, двухфакторная аутентификация, без параллельной
системы авторизации.
**Статус:** решения владельца В-1…В-4 приняты 2026-11-08 09:35 (§7) и реализованы в облачной копии (§4–§5). У владельца
не запускалось; серверная часть с настоящими FastAPI и базой данных **не выполнялась ни разу** (§5). VPN не подключался, сеть магазина
не настраивалась, ничего не публиковалось и не покупалось.

## 1. Главное решение: одна система входа, а не вторая «удалённая»

В проекте уже есть **централизованная серверная авторизация**: сервер магазина — единственный источник истины. Токен — случайная строка,
в базе хранится только её SHA-256 (`api_tokens`). Пользователь, роль и права перечитываются из базы на **каждом** запросе
(`AuthService.resolve_token` → `app/api/deps.get_current_user` → `require_permission`). Поэтому:

- **вход с телефона, из дома и с компьютера магазина** проходит один и тот же путь `POST /api/v1/auth/login` → токен → тот же
  `get_current_user`. Отдельного «удалённого» входа, JWT, второй таблицы пользователей или второго механизма ролей **нет и не будет**;
- **отзыв действует сразу**: отключили пользователя, сменили пароль, завершили сеанс — следующий запрос с этим токеном получит 401.
  Самоподписанные токены (JWT) этого бы не дали без чёрных списков;
- «централизованность» для **сети магазинов** — это отдельный уровень (документ 17: центр организации) и будущее решение. Тогда
  эта же модель переедет в центр. Сейчас центр — сервер магазина.

Что добавлено (§4–§9), — это расширения той же системы: сведения о сеансе, поколение сеансов, второй фактор, коды восстановления, владелец, отдельный административный вход, HSTS.

## 2. Канал: HTTPS обязателен для входа из-за пределов магазина

Пароль, код второго фактора и токен по HTTP передаются открытым текстом. Второй фактор **не защищает канал**: украденный в сети токен
действует до завершения сеанса. Поэтому удалённый вход администратора — **только по HTTPS** (или внутри VPN). Приложение готово
к обоим вариантам. **Владелец выбрал VPN (В-1, вариант А)**; переход на свой домен и HTTPS (вариант Б) остаётся возможным без
переделки: приложение уже понимает доверенный прокси и отдаёт HSTS по HTTPS.

| Вариант | Как | Плюсы | Минусы, риски | Что нужно от владельца |
|---|---|---|---|---|
| **А. VPN-сеть (WireGuard, Tailscale и подобные)** — рекомендуется для начала | компьютер магазина и телефоны администраторов в одной зашифрованной частной сети; программа доступна только участникам этой сети | нет открытых портов в интернет; не нужен домен; шифрование канала уже есть; перебор паролей из интернета невозможен | приложение на каждом телефоне; у Tailscale и подобных — сторонний координационный сервер (бесплатные тарифы с ограничениями — проверить условия перед выбором) | выбрать сервис или свой WireGuard; установить на компьютер и телефоны |
| **Б. Свой домен + обратный прокси с сертификатом (Caddy, nginx) + проброс порта** | `https://shop.example.uz` → прокси на компьютере магазина → программа на `127.0.0.1:8000`; сертификат Let's Encrypt | настоящий HTTPS для всех, в том числе для живой камеры на телефонах (документ 04, §3.4) | открытый порт в интернет: нужны второй фактор, ограничения входа, обновления; нужен белый IP или DDNS; домен — платная услуга | купить домен, настроить роутер; решение D-08 |
| **В. Туннель облачного поставщика (Cloudflare Tunnel и подобные)** | исходящее соединение от компьютера к поставщику, вход по его адресу | без открытых портов и белого IP | трафик проходит через стороннюю компанию (данные проекта уходят во внешний сервис — нужно отдельное разрешение); зависимость от поставщика | разрешение на внешний сервис; учётная запись у поставщика |

Требования к любому варианту:
- программа слушает **только** `127.0.0.1` или внутренний адрес, наружу — только прокси или VPN;
- uvicorn запускается с `--proxy-headers --forwarded-allow-ips=<адрес прокси>`. Тогда приложение видит настоящий адрес клиента
  (ограничение попыток входа по адресу) и признак HTTPS. Недоверенный адрес подделать HTTPS заголовком `X-Forwarded-Proto` не может:
  это проверено на настоящем uvicorn (`tests/test_real_http_server.py`);
- по HTTPS приложение отдаёт **HSTS** (`Strict-Transport-Security: max-age=15552000`, без `includeSubDomains` и `preload` — решение
  при выборе домена). По HTTP заголовок не отправляется: адрес `http://192.168.x.x:8000` в магазине продолжает работать.

## 3. Сеансы и устройства

| Возможность | Как устроено |
|---|---|
| Вход с нескольких устройств одновременно | каждый вход — свой токен; ограничения на число сеансов пока нет (предел и «выбор сеанса» — документ 05, §12.10, после решения Q-20) |
| Список «Где выполнен вход» | `GET /api/v1/auth/sessions`: устройство (приблизительно, по строке браузера: «Телефон · Android · Chrome»), название, если его передал клиент (`X-Device-Name`), откуда (этот компьютер / локальная сеть / интернет), вход, последняя активность, «этот сеанс», «со вторым фактором». **Полного IP и полной строки браузера нет**: адрес хранится как HMAC с секретом сервера |
| Завершить сеанс | свой: `DELETE /api/v1/auth/sessions/{id}`; все, кроме этого: `POST /auth/sessions/revoke-others`; администратор — сеансы пользователя: `GET/POST /api/v1/users/{id}/sessions[/revoke-all]` |
| Выйти на всех устройствах | `POST /api/v1/auth/logout-all`: **новое поколение сеансов** и удаление токенов — одной транзакцией (документ 05, §12.11). Токен прежнего поколения не действует, даже если его строку не удалили |
| Смена пароля, отключение пользователя | теперь тоже одной транзакцией с новым поколением. Раньше это были две транзакции (документ 05, §1.1, оговорка) |
| Последняя активность | обновляется не чаще раза в минуту, чтобы не писать в базу на каждый запрос |

Доверенные (зарегистрированные) устройства — документ 05, §12.12, первый этап только для компьютера магазина в Desktop. Здесь
**не реализуются**: устройство не заменяет пароль и не защищает канал.

## 4. Административный вход отдельно от входа сотрудников (В-1: «снаружи VPN — нет доступа к управлению»)

**Почему не по IP-адресу.** Первый вариант (правило «администратор вне компьютера — только со вторым фактором» по адресу клиента)
отвергнут: в Docker Desktop для Windows программа в контейнере видит не адрес клиента, а адрес шлюза Docker. Правило по адресу там
не различает «этот компьютер», «сеть магазина» и «VPN» — на него нельзя опираться в защите.

**Решение — два входа одного приложения** (тот же образ, та же база, та же система входа; различается только переменная
`APP_LISTENER`):

| Вход | Порт и публикация (`docker-compose.yml`) | Что доступно |
|---|---|---|
| сотрудников, `APP_LISTENER=public` | `8000` (сеть магазина; после §14 — только HTTPS) | всё, кроме прав «только администратор»: пользователи, магазины и полки, камеры, **правка каталога** (§13; `security.ADMIN_ONLY_PERMISSIONS`) → **403 `admin_listener_required`**; администратору без настроенного второго фактора здесь не выдаётся даже пропуск настройки |
| административный, `APP_LISTENER=admin` (служба `admin-api`) | `8001`, опубликован **только на `127.0.0.1`** — с других компьютеров сети магазина недоступен | всё, включая управление и первую настройку второго фактора |
| VPN | `docker-compose.vpn.yml`: отдельная служба `admin-api-vpn`, порт 8001 на адресе компьютера **в VPN-сети** (`VPN_BIND_IP`) | то же, что административный; из интернета и из сети магазина адрес VPN не виден |
| запуск без Docker | `APP_LISTENER=all` (по умолчанию) — один процесс, `scripts/start_demo.py` слушает `0.0.0.0` | управление — только с самого компьютера (запрос на 127.0.0.1/::1, без прокси); телефонам в Wi-Fi — как входу сотрудников (§12, А-1) |

- Проверка — в одном месте: `deps.require_permission`. Права управления действуют, только если **и запрос пришёл на
  административный вход, и сеанс открыт там же** (§12, А-2), какой бы маршрут их ни требовал. Вход запроса определяется по адресу
  сокета сервера и имени в заголовке Host (`mfa_policy.listener_for_request`): чужое имя — вход сотрудников (защита от подмены DNS). Статический тест не даёт появиться проверке `role == ADMIN` в обход этой зависимости.
- `GET /auth/me` сообщает `admin_listener`; «Управление» на входе сотрудников показывает подсказку «откройте http://localhost:8001».
- **Не проверено:** публикация порта на адрес VPN-интерфейса в Docker Desktop для Windows (порядок запуска VPN и Docker, брандмауэр
  Windows). Если VPN не поднят при `docker compose up`, Docker не сможет занять адрес и сообщит об ошибке — служба не запустится,
  а не откроется шире. Это отмечено в `docker-compose.vpn.yml`.

## 5. Второй фактор обязателен всем администраторам (В-2, В-3)

- **Что это:** после верного пароля сервер не выдаёт сеанс, а просит 6 цифр из приложения-аутентификатора (Google Authenticator,
  Microsoft Authenticator, Яндекс Ключ, FreeOTP, Aegis — любое с `otpauth://totp`). SMS и почта не используются. TOTP — RFC 6238:
  SHA-1, 6 цифр, шаг 30 с, допуск ±1 шаг.
- **Правило** `auth.require_2fa_for_admins: true` (по умолчанию). Действует везде, в том числе на компьютере магазина:
  - администратор с настроенным вторым фактором: `POST /auth/login` → `{"mfa_required", "mfa_token"}` → `POST /auth/login/2fa` → сеанс;
  - администратор без второго фактора на административном входе: `{"mfa_enrollment_required", "enroll_token"}` — **пропуск настройки**
    на 10 минут. Он принимается **только** тремя маршрутами `/auth/2fa`, `/auth/2fa/setup`, `/auth/2fa/confirm` (статический тест).
    Подтверждение кода выдаёт полноценный сеанс и коды восстановления; пропуск после этого не действует;
  - на входе сотрудников — отказ 403 `mfa_enrollment_required`: первая настройка только на административном входе;
  - сотрудникам (не администраторам) второй фактор доступен по желанию; если включён — спрашивается всегда.
- **Нет обходных путей** (требование владельца):
  - сеанс без второго фактора выдаётся только функцией `_issue` во входе по паролю и только после решения политики
    (`mfa_policy.after_password`); для администратора при включённом правиле это решение невозможно;
  - **каждый** запрос проверяет сеанс в `resolve_token`: сеанс администратора без отметки второго фактора отвергается, где бы и
    когда бы он ни был выдан (старые токены до обновления, токены из консоли) — проверено тестом;
  - все маршруты, кроме входа, второго шага входа и выхода, требуют сеанс (статический тест по исходному коду маршрутов);
  - токены выдаются только в `routes_auth.py`, проверяются только в `deps.py` (статический тест);
  - администратор не может выключить себе второй фактор (409 `mfa_required_for_admins`);
  - сброс своего второго фактора через программу запрещён (`mfa_reset_self`) — только консоль на компьютере магазина.
- **Повтор кода:** запоминается последний принятый шаг (`totp_last_step`); тот же и более старые коды не принимаются — ни при входе,
  ни при подтверждении, ни при повторной проверке.
- **Перебор:** пропуск второго шага одноразовый, 5 минут, 5 неверных кодов (`mfa_attempts_exhausted`), неверные коды учитываются
  в общем ограничении попыток входа.
- **Хранение секрета:** Fernet (AES-128-CBC + HMAC-SHA256) ключом, выведенным из `AUTH_SECRET_KEY`. Без ключа настройка второго фактора
  невозможна (503 `mfa_unavailable`) — а значит, при включённом правиле администраторы не войдут. Ключ — обязательная часть установки
  (`scripts/generate_secret_key.py --auth`); в резервную копию не входит, как весь `.env` (документ 09, §6).

|---|---|---|
| любой с включённым вторым фактором | входит **кодом восстановления** вместо 6 цифр. При включении выдаются 10 кодов `XXXXX-XXXXX`, показываются один раз; в базе — только HMAC. ## 7. Владелец системы

- Признак `user_security.is_owner`. Ставится **только**: (1) `scripts/bootstrap.py` первому администратору, если владельца ещё нет;
  (2) консольной командой `scripts/user_admin owner --username … [--transfer]` на компьютере магазина. Через API назначить владельца
  нельзя: в моделях запросов нет такого поля, маршруты не вызывают `set_owner` (статический тест).
- **Первоначальное создание защищено:** первого пользователя создаёт только консольная команда bootstrap на компьютере магазина;
  в API регистрации нет. Повторный bootstrap при существующем владельце владельца не меняет (`owner_exists`).
- **Обычный администратор не может стать владельцем** и не может управлять владельцем: менять ему пароль, роль, отключать, завершать
  сеансы, сбрасывать второй фактор → 403 `owner_protected`.
- **Только владелец назначает роль администратора** (создание и повышение) и сбрасывает второй фактор администраторам → 403 `owner_only`.
  Так захваченная учётная запись обычного администратора не может создать себе соучастников.

## 8. Срок сеанса, продление, повторное подтверждение (В-4)

- **Не больше 8 часов** (`auth.admin_session_max_hours: 8`) для сеансов администраторов и для любого сеанса на административном входе,
  считая от входа с паролем и кодом (`auth_at`). Сотрудники — как раньше (`auth.token_ttl_minutes`).
- **Продление** `POST /auth/refresh`: выдаёт **новый** токен, старый сразу перестаёт действовать (украденный старый токен бесполезен);
  предел 8 часов от входа не сдвигается — после него 401 `session_max_age` и вход заново. «Управление» продлевает сеанс раз в 20 минут.
- **Отзыв:** любой сеанс завершается сразу (`DELETE /auth/sessions/{id}`, «все, кроме этого», «выйти на всех устройствах»);
  смена пароля, отключение пользователя, смена роли, сброс второго фактора — новое поколение сеансов той же транзакцией.
- **Повторное подтверждение важных операций:** создание и изменение пользователей, сброс второго фактора, удаление магазина и полки
  требуют, чтобы пароль и код вводились не раньше чем 10 минут назад (`auth.reauth_minutes`); иначе 403 `reauth_required`.
  «Управление» само показывает окно «пароль + код» (`POST /auth/reauth`) и повторяет действие.

### 13.1. Противоречие, которое было

§4 описывал порт 8001 как «административный вход», а порт 8000 — как вход, где «права управления не действуют». Но список прав
управления вёлся вручную и содержал только пользователей, магазины и полки, камеры. Право **правки каталога** (`catalog:write` —
добавление товаров и фото, правка карточек; есть только у администратора) в список не входило. Поэтому:
- администратор мог править каталог с телефона через Wi-Fi магазина, вводя пароль и код второго фактора по HTTP;
- описание «изоляции административного API» было верно только для части административных функций (§12.4 отметил это как В-5).

Причина — ручной список: новое право «только для администратора» не попадало под защиту автоматически.

## 14. Пароли, коды второго фактора и токены — только по HTTPS или через VPN

|---|---|
| Страница (до отправки) | `auth.js` перед отправкой пароля спрашивает `GET /api/v1/auth/transport` (без секретов). Канал не защищён — пароль **не отправляется**, вместо входа — защищённый адрес (`PUBLIC_HTTPS_URL`) или подсказка |
| Сервер | `auth.require_secure_transport: true` (по умолчанию): любой `/api/v1/*` по незащищённому каналу — 403 `insecure_transport` (кроме вопроса о канале и `/health*`) — для старых клиентов и прямых обращений |
| Токены | токен, полученный на `https://…`, на `http://…` не попадает сам: хранилище вкладки у этих адресов разное |
| HTTPS в сети магазина без покупок | `scripts/make_local_tls.py`: свой центр сертификатов магазина **с ограничением имён** (только частные адреса и имена компьютера; даже украденным ключом центра нельзя выдать сертификат для чужого сайта — проверено: клиент отвергает такой сертификат), сертификат сервера на 397 дней (ECDSA P-256), ключи с правами только владельца, папка `secrets/` вне git и резервных копий. `docker-compose.https.yml` переводит порт 8000 на HTTPS; `start_demo` включает HTTPS сам, если сертификат есть |
| Телефоны | центр магазина (`ca.crt`) устанавливается на каждый телефон один раз (инструкция — `docs/REMOTE_ACCESS_GUIDE.md`, п. 7). Альтернатива — телефоны в VPN |

Проверено на настоящем uvicorn через сокет: по HTTP — 403, по HTTPS с центром магазина — проходит, без центра — ошибка проверки
сертификата; режим «all» — HTTP только с самого компьютера; сертификат для чужого имени от центра магазина отвергается.
**Не проверено:** Docker (`docker-compose.https.yml`), установка центра на Android и iOS, поведение браузеров телефонов.

**Последствие для эксплуатации.** После обновления, пока HTTPS (или VPN на телефонах) не настроен, сотрудники **не смогут войти
с телефонов**: это и есть требование «не передавать пароли по незащищённому HTTP». На самом компьютере магазина и через VPN вход
работает. Временное отключение — `auth.require_secure_transport: false` (предупреждение в журнале; решение владельца).

## 15. Ограниченный режим фотографирования для телефона — проект (не реализован)

Будущее право `catalog:capture` (отдельная роль «фотограф каталога» или право для мерчандайзера — решение владельца при реализации):
- **может:** создать **черновик** нового товара (название, штрих-код, фото) и добавить фото к своему черновику — на порту сотрудников,
  только по HTTPS;
- **не может:** править и удалять существующие товары, утверждать черновики, управлять пользователями, магазинами, полками и камерами;
- черновик не попадает в поиск и индекс распознавания, пока администратор не утвердит его на административном входе (с повторным
  подтверждением, как остальные важные операции);
- ограничения: число черновиков и фото в час на учётную запись, размер файлов — как у загрузки фото сейчас;
- проверки — тем же способом: право не «только admin», значит не попадает в `ADMIN_ONLY_PERMISSIONS`, а маршруты черновиков
  отдельные; тесты «право есть — черновик создан; правка существующего — 403; утверждение вне административного входа — 403».
