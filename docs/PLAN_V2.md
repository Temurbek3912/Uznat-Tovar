## 1. Что строим

Один каталог товаров в PostgreSQL. Клиент сканирует QR камерой телефона, открывает сайт (без установки) и ищет товар по названию, штрихкоду или фото.
Владелец и администраторы наполняют каталог: пишут о товаре обычным текстом, добавляют фото, диктуют; ИИ собирает карточку и задаёт вопросы.
Отдельный ИИ-чат ищет и меняет данные **только через проверяемые серверные действия** с подтверждением и журналом. Два режима одной кодовой базы:
LOCAL (компьютер в магазине, первый этап) и SERVER (тот же код на сервере с доменом и HTTPS). Магазинов и полок в продукте нет.

## 3. Где я спорю с ТЗ и что предлагаю

**D1. HTTPS в режиме LOCAL — не «желательно», а необходимо.** Браузеры телефонов разрешают живую камеру и микрофон только на защищённом адресе (HTTPS или `localhost`).
Адрес вида `http://192.168.x.x` этого **не даёт**: живое сканирование штрихкода и съёмка в браузере работать не будут, останется «сфотографировать и отправить» (оно работает и по HTTP, и сервер штрих-код с фото читает).
Значит, «без HTTPS» — это урезанная версия. Предлагаю настоящий сертификат на домен владельца (D2).

**D2. Постоянный QR = постоянное *имя*, а не адрес компьютера.** QR содержит `PUBLIC_BASE_URL` (например `https://catalog.магазин.uz/`) и никогда не строится из IP или `localhost` (проверяется кодом и тестом).
Как это работает в LOCAL: у владельца есть домен; DNS-запись `catalog` указывает на локальный адрес компьютера (например `192.168.1.50`), адрес закреплён в роутере (резервирование DHCP);
сертификат Let's Encrypt выдаётся по DNS-проверке (он не требует открывать порты в интернет); клиент в Wi-Fi магазина открывает тот же адрес. Сменился IP компьютера — меняется одна запись в DNS (или в роутере), **QR не перепечатывается**.
В режиме SERVER запись указывает на сервер: тот же QR, тот же адрес. Ограничения, которые будут в документации прямо: нужен интернет для DNS и раз в ~60 дней для продления сертификата (между продлениями сайт работает без интернета);
часть роутеров блокирует «внутренние адреса в публичных DNS» (нужно внести домен в исключения); гостевой Wi-Fi с изоляцией клиентов не пустит телефон к компьютеру; телефон на мобильном интернете локальный адрес не откроет.
Запасные варианты (хуже): имя в роутере/`.local` без HTTPS (только фото-режим); туннель (постоянный публичный адрес и HTTPS, но нужен интернет и сторонний сервис).

**D3. Alembic вводим сейчас.** Без миграций новые колонки не добавить, а переписывать данные «пересозданием» нельзя. Порядок: начальная версия = текущая схема (помечается на вашей базе без изменений), затем версии с изменениями;
каждую версию сначала прогоняем на **копии вашей базы** (из дампа) во временной базе. `create_all` остаётся только для чистой установки тестов.

**D4. Характеристики — JSONB + шаблоны категорий.** Ключевые поля (название, бренд, категория, артикул, штрих-коды, цена, статус) — обычные колонки с индексами; специфичное (жирность, память, размер) — в одном JSONB-поле `attributes`
под схемой категории (какие поля бывают, тип, единицы). Это не «весь каталог в JSON» и не EAV (который здесь дороже и медленнее без пользы). Поиск и фильтры по характеристикам — индексом GIN.

**D5. Варианты товара.** В версии 1 — ссылка «вариант товара X» (`parent_id`) и общий «вид» карточки, без отдельной таблицы вариантов; отдельную таблицу вводим, если реальные данные покажут необходимость.

**D6. Таблицы магазинов и полок не удаляем в первой версии.** Убираем из интерфейса, API и логики; таблицы остаются до отдельной миграции после проверки данных, копии и вашего слова. Существующие учётные записи переводим на новые роли отдельным шагом (с вашим подтверждением, кого сделать владельцем).

**D7. ИИ за единым интерфейсом, по умолчанию без внешних сервисов.** Выделение полей из текста: сначала правила (объём, масса, штрихкод, бренд из справочника — работает офлайн, бесплатно, но ограниченно); поверх — языковая модель через OpenAI-совместимый адрес.
Варианты: локальная (Ollama на самом компьютере, **вне Docker**; модель класса 7–8 млрд параметров в 4-битном виде помещается в 8 ГБ видеопамяти) или платное облако **только с вашего разрешения**. Честно: русский приемлем, узбекский у малых моделей слабый, вызов функций у них ненадёжен —
поэтому ИИ у нас не «исполняет», а **предлагает** действие из закрытого списка, сервер проверяет и спрашивает подтверждение. Видеокарта RTX 5060 — новое поколение: совместимость с PyTorch и драйверами проверяется замером, а не обещанием.

**D8. Голосовой ввод (диктовка). Озвучки вслух в продукте нет** (решение владельца 2026-10-30: `voice.js` и всё, что читало ответ вслух, удалено). Про ввод: рекомендую по умолчанию **диктовку клавиатурой телефона** (работает на русском и узбекском, не требует нашего кода, не отправляет звук нам). Свою кнопку микрофона и серверное распознавание (faster-whisper) делаем позже и честно помечаем ограничения: встроенный Web Speech API ненадёжен вне Chrome, требует HTTPS и на Chrome ходит в облако; узбекский у распознавания слабее русского.

**D9. Публичный доступ без входа — только явный список.** Чтение каталога, поиск, карточка, штрихкод, поиск по фото, «сообщить о неизвестном товаре». Всё остальное — только по токену. Для анонимных запросов — лимиты по адресу (в проекте уже есть `app/core/throttle.py`),
поиск по фото идёт через очередь с ограничением размера и частоты (он самый дорогой), жалобы — с защитой от спама.

**D10. Детектор YOLO (SKU-110K) не определяет товар**, он ищет рамки на плотных полках. Оставляем его только для «выберите предмет на фото» и только если замеры покажут пользу. Карту уборки пересчитываем: `detector`, `matcher`, `embedder`, `ml_runtime`, очередь задач — **не удалять**, пока не решено по замерам.

**D11. Порядок: сначала доступ, данные и публичный каталог, потом ИИ.** На них опирается всё остальное. Версия 1 — без ИИ-чата и диктовки (но с каталогом, штрихкодом, фото-поиском, админ-панелью, ролями, QR). ИИ-черновик — версия 1.5, чат с действиями и голос — версия 2.

**D12. Разделение работы.** Серверную часть с миграциями, Docker и `pytest` быстрее и надёжнее вести там, где это можно **запускать**: Claude Code на вашем компьютере (в первом документе вы его и называли). Здесь я веду то, что проверяю сам: страницы, чистую логику, тесты, снимки Chromium, документы и контракты API, по которым серверная часть пишется без догадок.
Серверный код я тоже могу писать здесь, но каждый шаг возвращается к вам на запуск тестов. Решение за вами; по умолчанию я продолжаю здесь по плану ниже.

## 4. Вопрос, без которого фазу 1 не начать

**Готовы ли вы использовать собственный домен (или поддомен вашего домена) для адреса каталога?** Рекомендую «да»: обычный домен стоит порядка нескольких долларов в год, а даёт одновременно постоянный QR, HTTPS для камеры и тот же адрес при переезде на сервер.
Нужно знать: есть ли у вас уже домен и где его DNS (у некоторых регистраторов запись для проверки сертификата меняется по API, у других только вручную). Если домена не будет, фаза 1 делается по запасному варианту (имя в роутере, без живой камеры), и я прямо напишу, чего он лишает.

## 6. Как мы работаем

1. Серверные изменения — маленькими шагами; к каждому тест. Что я могу запустить, запускаю (JS, чистый Python, Chromium); всё, что требует FastAPI, базы или Docker, помечаю «не запускалось у меня» и прошу вас прогнать конкретную команду.
2. Файлы вам приходят выпуском с `MANIFEST.json`; применяются скриптом, который не затирает ваши правки (`INSTRUCTION_RU.md`). Папки целиком не копируем.
3. Ничего разрушительного: **не используйте `docker compose down -v` (УДАЛЯЕТ тома, то есть базу)**, не удаляем тома и базу, без восстановления дампа, без смены паролей. Миграции — сначала на копии базы.
4. ИИ не получает SQL, файловую систему и секреты; не сообщает об успехе, пока сервер не подтвердил; не выдумывает штрихкоды, составы, цены.
5. Платные внешние сервисы — только с вашего разрешения.

## 7. Версии и критерии готовности

- **v1** (фазы 0–7, 11 частично): клиент открывает сайт по QR, ищет по названию, штрихкоду, фото, видит карточку и не может править; администратор входит, создаёт и правит карточки, добавляет фото; владелец назначает администраторов, видит журнал; PostgreSQL — источник истины; миграции проверены на копии; тесты зелёные.
- **v1.5** (фаза 8): ИИ собирает карточку из текста, спрашивает недостающее, находит дубликаты, ничего не выдумывает.
- **v2** (фазы 9–10): чат с проверяемыми действиями и подтверждением; голосовой ввод в честных границах.

## 8. Риски и ограничения

- Серверную часть я не могу запустить: каждая серверная фаза проходит через ваш запуск (или Claude Code у вас); это замедляет, но не отменяет проверку.
- Качество поиска по фото зависит от ваших фото каталога; без замеров на реальных упаковках (фаза 7) никаких цифр точности не обещаю.
- Компьютер магазина — единственная точка отказа: автозапуск, резервные копии, обновления — часть фазы 12.
- Узбекский язык: интерфейс — черновик, понимание текста малой моделью и распознавание речи — слабое место; ограничения будут в интерфейсе и документации.
- Локальный режим не работает «совсем без интернета и DNS»: см. D2.
