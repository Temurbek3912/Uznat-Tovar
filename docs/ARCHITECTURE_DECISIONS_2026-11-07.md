### 5.4. Окончательная архитектура (цель — принято; размещение — запланировано на этап 6; способ — требует исследования)

Байты кадра существуют **только в памяти одного процесса**: ни файлов, ни Redis, ни временных файлов разбора.

| Вариант | Суть | Плюсы | Минусы |
|---|---|---|---|
| (б) в процессе API | проект документа 04, §4.2 (со ссылкой на документ 08, §5): распознавание и выбор — прямым вызовом в процессе API, как в Desktop | один процесс — выбор (ТК-3) естественно попадает к тому же кадру; меньше звеньев | модель в процессе API; сбой модели роняет API; воркеру модель нужна и для фоновых задач — две копии модели и индекса, если воркер не вызывает API |
| (в) отдельный процесс распознавания | `InferenceClient` (D-27, рекомендовано): API передаёт сырые байты процессу модели по локальному соединению | сбой изолирован; одна модель на распознавание | запрос выбора должен попасть в тот же процесс (D-28); передача — не `multipart` (иначе буфер на диске уже там); ещё один процесс и супервизор |

**Общие требования к любому варианту** (критерии приёмки):
1. Тело запроса — сырые байты с пределом до разбора (ВМ-1, ВМ-2).
2. Хранилище кадров для выбора — в памяти:
   - предел N кадров (например, 50 — по замеру; документ 04, §4.2);
   - удаление после выбора, после отмены, через 120 с; очистка не реже раза в 10 с;
   - переполнение — отказ, а не сброс на диск.
3. Ограничение одновременных распознаваний (семафор) и **ограниченная** очередь ожидания со сроком. Переполнение — 503 или переход
   на штрихкод (D-27).
4. Асинхронный маршрут. Синхронное ожидание держит поток из пула (по умолчанию AnyIO — 40 потоков [по памяти]) так же, как сейчас
   `task.get`.
5. Таймауты подключения и ответа. Отмена при уходе клиента — только для ещё не начатых запросов: проход модели прервать нельзя.
6. Супервизор: перезапуск, проверка готовности, прогрев модели. При падении запросы в работе получают 503, кадры в памяти теряются —
   для приватности это допустимо.
7. Журналы без тел запросов и байтов изображения.
8. Дампы памяти приложения выключены.
9. Обратный прокси (когда появится для HTTPS) — без буферизации тела на диск. Например, у nginx большие тела по умолчанию уходят
   во временные файлы [по памяти].
10. Кадры не передаются через Redis с сохранением. Общий Redis без сохранения допустим только при горизонтальном масштабировании
    (D-28, отложено).

### 5.5. Остаточный риск ОС (статус — требует решения владельца: принять ли его при толковании D-10а, вопрос 14.1-3)

Никакой вариант приложения не исключает запись памяти на диск самой ОС:

| Механизм | Профиль | Уверенность |
|---|---|---|
| подкачка ВМ WSL (`swap.vhdx` на диске Windows, по умолчанию 25 % памяти ВМ) | Docker Desktop | вероятно [вторичный] |
| файл подкачки Windows (`pagefile.sys`) для памяти процессов | Desktop (процессы Windows) | вероятно (устройство ОС; R-19) |
| гибернация (`hiberfil.sys`) | оба | неизвестно, касается ли памяти ВМ |
| аварийные дампы Windows и дампы падения процессов | оба | вероятно для процессов Desktop; для ВМ — неизвестно |
| остаток данных в освобождённых блоках диска после удаления файла | любой профиль, где кадр когда-либо был файлом | подтверждено (устройство ФС); дойдёт ли TRIM через `vhdx` — неизвестно |

**Снижение риска:**
- приложение кадр не пишет (§5.4);
- ограничение числа кадров;
- BitLocker — рекомендация владельцу (R-19);
- для Desktop — проверить, можно ли выключить дампы падения службы.

**Удаление файла не превращает запись на диск в соответствие ТК-1:** соответствие даёт только отсутствие записи.

| Что | Чем обеспечивается |
|---|---|
| устойчивый идентификатор операции | `staged_files.id` (UUID), создаётся приложением **до** первой фиксации; для загрузок пользователя — ещё и ключ идемпотентности задания (`jobs.idempotency_key UNIQUE`, документ 08, §5), его присылает клиент, так что повторная отправка узнаётся |

| атомарность «ссылки есть ⇔ операция завершена» | состояние `applied` ставится **той же транзакцией**, что создаёт ссылки `product_images` (документ 05, шаг 6) |

#### 6.4.3. Неизвестный исход `COMMIT` (рекомендовано)

**Последовательность:**
1. Запись о намерении с идентификатором операции фиксируется **до публикации файла** (состояние `writing`).
2. Файл пишется, перечитывается, хеш сверяется → состояние `stored` (отдельная фиксация).
3. Транзакция применения: ссылки `product_images` + состояние `applied` — **одна фиксация**.
4. При обрыве соединения на любой фиксации исход **не считается ни успехом, ни ошибкой**. Приложение переподключается и читает
   фактическое состояние по идентификатору операции:

| Что найдено в базе | Что это значит | Действие |
|---|---|---|
| записи нет | фиксация шага 1 не состоялась | повтор с тем же идентификатором (`INSERT … ON CONFLICT (id) DO NOTHING`); файл без записи, если успел появиться, — по правилам сборщика (§6.4.6) |
| `writing` | файл мог не дописаться | пересчитать хеш файла: совпал — `stored`; не совпал или файла нет — повторить запись из исходного файла задания (окно 24 ч) |
| `stored` | применение не зафиксировано | повторить применение. Это идемпотентно: `ON CONFLICT (product_id, sha256) DO NOTHING`, переход состояния только из `stored` |
| `applied` | операция уже успешна | вернуть результат; ничего не повторять |

5. **Незавершённая операция отличается от зафиксированной только по состоянию записи о намерении в базе.** Наличие или отсутствие файла
   этого не показывает: файл может существовать и при незафиксированной операции.
6. **Повтор не создаёт дубликат и не перезаписывает файл, на который есть ссылки:**
   - файл с совпадающим хешем уже есть — запись не выполняется (документ 05, шаг 3);
   - файл есть, но хеш не совпадает, — это повреждение, а не другой «правильный» файл. По документу 05 он уходит в карантин,
     и правильное содержимое пишется по протоколу. Перезаписи «на месте» нет.
7. **Пока исход неизвестен, файл не удаляется:**
   - сборщик мусора не трогает файлы, у которых есть запись о намерении в незавершённом состоянии (`writing`, `stored`);
   - записи, «зависшие» в таком состоянии дольше порога, попадают в отчёт для проверки, а не в удаление.

#### 6.4.4. Гонка «удаление фото ↔ запись вектора» (рекомендовано; не испытано)

**Задача.** Одной проверки статуса фото перед вычислением недостаточно: фото могут удалить после проверки, но до записи вектора.

**Требуемый инвариант:**
- в базе **никогда** нет действующего вектора для фото в состоянии `deleted`;
- в памяти поиска такой вектор может задержаться только до ближайшего обновления, и он **никогда не даёт ответа** (проверка при ответе,
  см. ниже).

**А. Векторы в базе** (если Р-5 выберет вариант 2 или кэш эмбеддингов документа 07, §8):

| Шаг | Транзакция удаления фото | Транзакция записи вектора |
|---|---|---|
| 1 | `UPDATE product_images SET status='deleted' WHERE id=:id` — берёт блокировку строки | `SELECT 1 FROM product_images WHERE id=:id AND status='active' FOR SHARE` |
| 2 | `DELETE FROM image_embeddings WHERE image_id=:id` (или пометка неактивным) + запись в журнал изменений | строка есть → `INSERT` вектора (`ON CONFLICT (image_id, model_version)`); строки нет → вектор отбрасывается |
| 3 | `COMMIT` | `COMMIT` |

**Почему это работает** — PostgreSQL, уровень `READ COMMITTED`. Это описание по документации PostgreSQL [по памяти], испытанием не проверено.

`FOR SHARE` конфликтует с блокировкой строки от `UPDATE`:
- **удаление первым:** запись ждёт, затем перепроверяет строку → статус `deleted` → вставки нет;
- **запись первой:** `UPDATE` удаления ждёт её фиксации, затем `DELETE` удаления (новый снимок оператора) видит вектор и удаляет его.

В обоих порядках действующего вектора не остаётся.

**Чего недостаточно:** условной вставки без блокировки (`INSERT … SELECT … WHERE status='active'`) в `READ COMMITTED`. Если удаление
зафиксировано после снимка вставки, а его `DELETE` выполнен до фиксации вставки, вектор останется.

**Допустимые альтернативы** (выбрать при реализации и испытать):
- при физическом удалении строк — внешний ключ `image_embeddings.image_id → product_images ON DELETE CASCADE` (проверка ключа
  блокирует строку-родителя);
- уровень `SERIALIZABLE` с повтором;
- в SQLite (если D-02 = SQLite) — проверка и вставка в одной транзакции `BEGIN IMMEDIATE`: один писатель, порядок строгий.

**Одновременные удаление и вычисление:**
- побеждает удаление;
- вычисленный вектор отбрасывается;
- задание завершается состоянием «пропущено: фото удалено», не ошибкой и без повтора;
- событие записывается в журнал.

**FAISS в памяти:**
- удаление попадает в журнал изменений той же транзакцией;
- читатели убирают id при обновлении (`IndexIDMap`);
- до обновления кандидат перед ответом сверяется с базой: фото и товар должны быть действующими. Это расширение уже сделанного в облачной
  копии правила «не возвращать товар, которого нет в базе» (этап 3) — рекомендовано.

**Б. Нынешний файловый индекс (до решения Р-5).**

Атомарности с базой нет. Безопасный порядок:
1. Путь удаления сначала фиксирует `deleted` в базе, затем **под общей блокировкой индекса** (`IndexLock`) удаляет векторы этого фото
   (по источнику вектора).
2. Путь добавления под той же блокировкой **перепроверяет статус в базе непосредственно перед сохранением** индекса.

При любом чередовании векторы удалённого фото либо не добавляются, либо удаляются путём удаления.

Если путь удаления упал после фиксации в базе, проверка по состоянию находит векторы фото в статусе `deleted` и удаляет их. Нынешний
`reconcile_index` (облако) удаляет векторы отсутствующих **товаров**; удаление по **фото** — доработка, рекомендовано. До удаления
действует проверка при ответе.

**Испытания (не выполнены):**
- пауза, внесённая между проверкой и записью, в обоих порядках — как испытания конкуренции этапа 1;
- сбой каждой стороны;
- PostgreSQL и SQLite;
- критерий — ноль действующих векторов у удалённых фото и ни одного ответа с удалённым фото.

| **Предположения (не проверено)** | открыть дескриптор каталога (`CreateFileW` с `FILE_FLAG_BACKUP_SEMANTICS`) и вызвать для него `FlushFileBuffers` — возможно, но сбрасывает ли это запись об имени файла на NTFS, документация не говорит; журнал NTFS сохраняет согласованность метаданных, но не обязательно последнее переименование после отключения питания |
| **Проверить на Windows** | испытание П-ФОТО (200 загрузок с отключением питания); сравнение «`fsync` + переименование» и «`FILE_FLAG_WRITE_THROUGH`»; влияние антивируса и индексатора; поведение на обманывающем кэш диске |

**Правила:**
- **До испытаний одинаковые гарантии устойчивости для Windows и Linux не обещаются.** Надёжность строится на порядке операций,
  самопроверяемых именах и восстановлении по записям в базе (вывод документа 05, §13.3.1).
- **`PermissionError`** (антивирус, индексатор, другой процесс):
  - ограниченное число повторов с растущей паузой — в облачной копии для индекса 6 попыток [код];
  - каждая попытка — в журнал (путь, код ошибки, номер попытки);
  - окончательная ошибка: временный файл убирается, если возможно; файл не публикуется; запись о намерении остаётся в незавершённом
    состоянии для восстановления (§6.4.3); пользователь получает понятное сообщение с кодом ошибки.
  - На Windows не испытано.

#### 6.4.6. Сборщик мусора и возраст файлов (рекомендовано)

**Источники времени — по приоритету:**
1. Запись о намерении и время операции **в базе** (создание, состояние, время перехода в завершающее состояние).

**Файл становится кандидатом на удаление, только если одновременно:**
- (а) по базе на него нет ссылок;

- (в) срок задержки удаления прошёл **по времени базы**;

недоступна, файл появился после восстановления. Выход из карантина — по проверке или решению человека.

**Во время восстановления из копии сборщик остановлен** до завершения проверки восстановленной системы.

#### 6.4.7. Резервные копии и ротация — правило документов 05, §13.3.6 и 09, §3–4 (запланировано)
- **Сначала `pg_dump`, затем фото** (новые файлы, проверяя хеш при копировании), затем индекс (документ 09, §3).

  ссылается хотя бы один сохранённый дамп.

  резервных копий она **не заменяет**.
- **Ошибка редакции 1** («удалять не раньше срока хранения копий» как замена хранения по ссылкам) исправлена ещё в редакции 2.
- **Сверено:** документ 05, §13.3.6 и документ 09, §3, §4, §8 (прочитаны в облачной копии при подготовке редакции 3) — совпадает.
- **Не описано в документе 09:** как в общее хранилище по хешам попадают нынешние файлы из папок по артикулу. В профиле Docker
  документ 09, §8 п. 1 копирует `data/catalog-uploads` целиком. Уточнить при проектировании 2А.

### 9.1. Alembic — запланировано (генеральный план, 2Б); только после успешного 2А и по отдельному разрешению

  3. Автогенерация предложит удалить таблицы старого аудита (D-13 — «оставить, не трогать»). Нужен фильтр `include_object`

  4. Миграции вперёд и назад проверяются на копии до рабочей базы (генеральный план, 2Б).

### 9.2. Цена — запланировано на этапе 4 («цена в точных единицах вместо float»); тип — требует исследования
- **Отозвано:** предложение редакции 1 перенести цену в первую миграцию 2Б. Оно противоречило П-2 и порядку генерального плана.
- **Отозвана формулировка** «`float64` точно хранит суммы до 15 значащих цифр». Верно другое: десятичное число не длиннее 15 значащих
  цифр переживает путь «десятичное → `float64` → десятичное».
- **Опыт** [облако-PG16], приведение `float8` → `NUMERIC(12,2)`:
  - 9900.1 → 9900.10; 0.1+0.2 → 0.30;
  - 12.345 → 12.35; 12.355 → 12.36; 1999.995 → 2000.00;
  - 99 999 999.99 — без потерь;
  - **`NaN` → `NaN` (проходит молча)**;
  - `Infinity` → ошибка; 1e10 → ошибка переполнения.
- **Перед любым переводом** — отчёт на копии: `NaN`, бесконечности, значения ≥10¹⁰, значения с >2 знаками, отрицательные.
  Каждую группу решает владелец.
- **API.** SQLAlchemy вернёт `Decimal`:
  - Pydantic v2 сериализует его **строкой** (`"9900.10"`) [облако-замер, Pydantic 2.13];
  - `jsonable_encoder` FastAPI — **числом** (`int` или `float`) [первичный, копия `encoders.py`].

  Маршруты со словарями (например, `/identify`) и с моделями ответа выдадут разный формат. Формат цены в API фиксируется отдельно
  и закрывается тестами контракта.
- **SQLite.** `NUMERIC` в SQLite не точный десятичный тип [по памяти]. Если D-02 = SQLite, переносимо и точно **целое число
  в минимальных единицах** (`BIGINT`).
- **Валюта.**
  - Рекомендовано — у магазина (`stores.currency`, ISO 4217), а не у каждого товара (один магазин — одна валюта, §2.1 п. 1).
  - Нужны ли дробные суммы (тийины), решает владелец. По моим сведениям, на практике цены в сумах целые [по памяти, не проверено].
- **Статус:** тип — после D-02 (D-02 по генеральному плану решается до 2Б); место валюты и дробные суммы — решение владельца к этапу 4;
  внедрение — этап 4, отдельным разрешением.

## 10. Многоязычие: ru, uz-Latn, uz-Cyrl, en

- **Принято владельцем:** четыре языковых варианта интерфейса (документ 14, §2.1 п. 4). Помощник на узбекской кириллице — требование
  владельца (О-11).
- **Коды:** `ru`, `uz-Latn`, `uz-Cyrl`, `en` (BCP 47).
  - В коде сейчас `ru`, `uz` (латиница, черновик), `en`.
  - Переход: `uz` → `uz-Latn`.
  - Цепочка замены недостающих строк (рекомендовано): `uz-Cyrl` → транслитерация `uz-Latn` с пометкой «авто» → `uz-Latn`.
    Молча показывать русский текст вместо узбекского нельзя.

### 10.1. Трудности транслитерации латиница → кириллица (вероятно; примеры — проверить носителем)
1. `e` → «э» в начале слова и после гласной, иначе «е»; `ye` → «е».
2. **Русские и международные заимствования пишутся в кириллице по-русски**, и правилами их не восстановить:
   `aksiya` → «акция», `stansiya` → «станция», `sentner` → «центнер», `oktabr` → «октябрь» (сразу «я» вместо «a» и мягкий знак).
3. ц в латинице передаётся как `s` или `ts` — однозначно не восстановить.
4. Обычный апостроф `'` после `o`/`g` формально означает либо букву (ў, ғ), либо разделительный знак (ъ). На входе встречаются
   разные апострофы: `oʻ o' o‘ o’`.
5. **Бренды, артикулы, штрихкоды** содержат латиницу вне узбекского алфавита (`c`, `w`, а также `x`, `q`, `h` с другим чтением):
   `Coca-Cola`, `XL` — их транслитерировать нельзя.
6. Имена и смешанные названия (бренд латиницей + описание).
7. Единицы и числа: `kg`, `l`, `ml` → «кг», «л», «мл»; `0,5 l`.
8. Регистр: `SH`/`Sh` → «Ш»; текст прописными.
9. **Нестандартная латиница на входе:** `poezd` вместо `poyezd`, русские слова латиницей. Качество варианта «латиница +
   транслитерация» ограничено качеством латиницы модели **и** транслитератора.

**Защищённые токены** (рекомендовано): бренды, артикулы, штрихкоды, названия из каталога не транслитерируются. Они берутся
из поля на нужном варианте или показываются как записаны.

### 10.2. Способ узбекской кириллицы у помощника — требует исследования

Ни один способ не выбран. Редакция 1 отнесла прямую генерацию к «не рекомендуется» без опыта — это нарушало П-1 и отозвано.

**Системы:**
- **A** — модель пишет сразу кириллицей;
- **B** — модель пишет латиницей, приложение транслитерирует по правилам;
- **C** — B плюс словарь исключений и защищённые токены.

**Наборы:**
- **W — слова и фразы, ≈1000 единиц, по слоям:** исконные слова с `e`/`ye`/`yo`/`yu`/`ya`; заимствования с ц, ь, ъ, ё, «я»;
  апострофы; бренды и смешанные названия; единицы и числа; регистр; нестандартная латиница.
  - Делится на **часть разработки** (словарь C строится только по ней) и **закрытую часть** — чтобы не подгонять словарь под тест.
  - Эталон кириллицы готовят два носителя независимо; расхождения разбирают.
- **S — ответы помощника:** 200 типовых запросов × 3 системы. Оценка вслепую двумя носителями:
  - смысл;
  - естественность (1–5);
  - примеси другого языка;
  - ошибки письма;
  - согласие оценщиков (каппа Коэна).
- **Q — понимание:** 100 запросов, написанных носителями кириллицей.

**Метрики:**
- ошибки на слово и на символ (W);
- сохранность защищённых токенов (цель 100 %);
- чистота письма (доля латиницы и русских форм в кириллическом ответе);
- доля ответов с примесью;
- естественность с доверительным интервалом.

**Пороги** записываются **до** опыта; выбор — по закрытой части. Ноль ошибок на n примерах означает верхнюю 95 % границу около 3/n,
а не ноль. Опыт повторяется при смене модели.

**Что нужно:** выбранная модель помощника (О-7, до этапа 10) и **два носителя языка** (вопрос 14.1-8). Проверка носителями всех
четырёх вариантов интерфейса до пилота уже есть в генеральном плане (§7 п. 7).
