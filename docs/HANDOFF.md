## Подводные камни среды (чтобы не наступать повторно)
- `cut`/`head -c` в shell режут многобайтные русские символы — вывод «не UTF-8», команда падает; читать файлы через Python.
- JS-тесты берут ПЕРВЫЙ `<script>` без атрибутов (`<script src="nav.js">` не мешает); поддельный DOM создаёт любой `id` сам — потерянный в разметке элемент они не заметят; это ловит `tests/test_frontend_pages.py`.
- В Node `assert.deepStrictEqual` не сравнит массивы из `vm`-окружения с обычными — оборачивать в `Array.from(...)`.
- Сессия SQLAlchemy у проекта с `autoflush=False`; порядок ORM-удаления идёт по `relationship()`, а не по внешним ключам — после удаления зависимых строк нужен явный `flush()` (иначе на Postgres `ForeignKeyViolation`, а на sqlite тесты этого не видят).
- Правило проекта для проверок: сломать код мутацией и убедиться, что тест падает; выжившая мутация = дыра в тесте (или объяснённая эквивалентность). Не писать «пустых» проверок (`or True`, замена на то же самое).
- Правки через `str.replace` по куску строки легко ломают комментарий/код в той же строке — после правок `node --check` / запуск тестов.
- Скриншоты: `PLAYWRIGHT_MODULE=… CHROME_PATH=… node tools/ui_screenshots/shoot.js <папка> [сценарий…]`; полностраничные снимки показывают закреплённую нижнюю панель «посреди» страницы — это артефакт.
- `pkill -f "<шаблон>"` убивает и собственную оболочку, если шаблон встречается в тексте команды — писать шаблон как `"[e]2e_demo.py"`. Вывод с бинарными данными (миниатюры JPEG) в терминал не печатать — «не UTF-8».
- Сквозной прогон в браузере: `python tools/e2e_assets.py /tmp/e2e-assets`, затем `PLAYWRIGHT_MODULE=… PLAYWRIGHT_BROWSERS_PATH=/opt/pw-browsers node tools/ui_screenshots/e2e.js <папка-вывода> /tmp/e2e-assets` (сам поднимает `tools/e2e_demo.py`; `E2E_VERBOSE=1` печатает последние ответы API при провале).

## Сессия №10 — запуск «с чистой машины» через Docker (аудит и правки)

**Контекст.** Пользователь запускает всё в Docker Desktop (Windows) и сообщил, что проект предназначен для **большого супермаркета**. После

## Что это за проект

Система автоматического учёта и классификации товаров на полках магазина
по фотографии — для розничной сети в Узбекистане. Полное ТЗ —
`docs/TZ_technical_specification.md`. Архитектурная суть: class-agnostic
детекция (YOLO) + open-set распознавание SKU через векторный поиск
(DINOv2-эмбеддинги + FAISS), а не классический classifier — потому что
каталог сети большой и часто меняется, а переобучать classifier под каждый
новый товар нереалистично.

## Что реально протестировано выполнением (не просто написано)

- `GET /snapshots/{id}/report`: одно сообщение «Отчёт ещё не готов или снимок не
  найден» разделено на «Снимок не найден» и «Отчёт ещё не готов» (`404` в обоих случаях);
- CORS: `allow_headers` теперь `["Authorization", "Content-Type"]` вместо `"*"`,
  `allow_methods` + `PATCH`;
- при `environment: production` отключены `/docs`, `/redoc`, `/openapi.json`;
- дашборд экранирует данные API перед вставкой в `innerHTML` (раньше — как есть);
- `POST /api/v1/auth/login` отвечает `429` + `Retry-After` после N неудачных попыток (см. ниже) —
  клиент, который в цикле ретраит логин, теперь упрётся в блокировку;
- `POST /api/v1/snapshots` в несуществующий магазин — `404` (раньше `500` на Postgres, с файлом-сиротой на диске);
  `POST /api/v1/users` при гонке за один логин — `409` (раньше `500`);
- новые эндпоинты F12 (`/review/*`) требуют право `review:manage` — есть только у
  `merchandiser`/`admin`; у `regional_manager`/`analyst` на них `403`, как и было
  задумано (см. раздел «F12»), но если это неожиданно — см. обоснование там же.

- `configs/config.yaml` содержит секцию `storage.images_bucket` /
  `raw_image_retention_days`, которая **нигде не читается** в
  `core/config.py::get_settings()` — похоже, задел на то же самое место,
  которое сейчас закрыто новой настройкой `media_root` (баг №4), но
  реализовано было под другим именем и так и не связано с кодом. Не стал
  трогать/объединять, чтобы не расширять правку — но при случае стоит
  либо убрать неиспользуемую секцию из config.yaml, либо перевести
  `media_root` на неё для единообразия.

## F13: как устроено и чего НЕТ

**Устройство.** Два независимых вопроса: право роли (`ROLE_PERMISSIONS`) и скоуп
магазинов (`admin`/`analyst` — вся сеть, `merchandiser`/`regional_manager` —
таблица `user_store_access`). Скоуп и роль читаются из БД на КАЖДЫЙ запрос, поэтому
смена роли/магазинов действует сразу, без перевыпуска токена. Токены opaque, в
БД только SHA-256 хеш; пароли — `scrypt` из stdlib (параметры в самом хеше, можно
повышать позже); при логине несуществующего пользователя scrypt считается против
хеша-пустышки (нет утечки «логин существует» по времени). Матрица прав — одно
место: `app/core/security.py`; новая роль без записи в матрице ловится тестом.
Новый эндпоинт без охранника ловится `test_every_route_requires_auth_except_explicitly_public`.

**Первый админ** — только скриптом `python -m scripts.create_user` (через API нельзя по построению).
**Миграции**: в проекте нет Alembic — новые таблицы создаёт `create_all` (скрипт
`create_user` вызывает его сам); существующие таблицы не менялись.

**Лимит неудачных входов** (`app/core/throttle.py`, настройки `auth.max_failed_logins_per_user`=5,
`auth.max_failed_logins_per_ip`=20, `auth.lockout_window_minutes`=15). Скользящее окно, два независимых
счётчика (логин / IP). Решения: счётчик ведётся и для НЕсуществующих логинов (иначе 429 выдаёт
существование логина); отказ отдаётся ДО проверки пароля и не записывается как неудача — блокировку
нельзя продлевать потоком запросов, и заблокированный не жжёт CPU на scrypt; успех сбрасывает счётчик
логина, но НЕ IP (иначе атакующий с одной валидной учёткой обнулял бы лимит); память ограничена (10 000 ключей).
`Retry-After` открыт для JS через `expose_headers` в CORS — без этого дашборд не покажет «через N мин».

**Не сделано / осознанные ограничения** (по убыванию важности перед выходом в сеть):
1. **Лимитер живёт в памяти ОДНОГО процесса.** При `uvicorn --workers N` или нескольких репликах API
   эффективный лимит умножается на N. Для боевой раскатки — общий счётчик в Redis (он уже есть в
   docker-compose). Плюс: за reverse-proxy запускать `uvicorn --proxy-headers --forwarded-allow-ips=<IP прокси>`,
   иначе `request.client` — адрес прокси, и лимит по IP накроет ВСЕХ пользователей разом
   (`X-Forwarded-For` вручную не читаем — клиент подделал бы его и обходил лимит).
2. **HTTPS обязателен вне localhost**: Bearer-токен по обычному HTTP читается сниффером
   (TLS терминировать на reverse-proxy; в самом приложении этого нет).
3. Лимит по логину позволяет постороннему временно «запереть» известную учётку (5 неудач → 15 мин) —
   плата за защиту от подбора; блокировка временная и сама снимается. Аналогично, много пользователей
   за одним NAT делят лимит по IP.
4. Нет самостоятельной смены пароля пользователем (только админ через `PATCH /users/{id}`).
5. Нет сущности «регион»: региональный менеджер = произвольный список назначенных магазинов.
6. Нет аудит-лога (кто и когда смотрел/менял; неудачные входы не логируются — стоит писать в лог
   IP + логин, это же основа для алертов).
7. Токен дашборда лежит в `sessionStorage` — при XSS утекает; смягчено экранированием,
   но вход по httpOnly-cookie был бы надёжнее (потребует CSRF-защиты и отказа от CORS `*`).
8. CORS всё ещё `allow_origins=["*"]` (см. комментарий в `main.py`) — сузить в проде.
9. `GET /health` отдаёт `environment` без авторизации (в RUNBOOK шаг 6.1 ожидает именно такой ответ).

## F14: как устроено и чего НЕТ

**Устройство.** Три независимых слоя: форматирование (`export_service.py`, чистое,
протестировано целиком — см. выше), сборка данных (`ReportService.build_export_payload`
раскрывает product_id → SKU/название одним запросом; `build_trend_rows` — дневная
динамика, ОДНА СТРОКА НА КАЖДЫЙ ДЕНЬ периода, включая дни без снимков, иначе ряд дат
съезжает и BI-инструмент/человек не сверит день-к-дню), HTTP (`routes_reports.py`,
права/скоуп — те же `_get_owned_report`, что и у обычного `GET .../report`, никакой
отдельной логики прав для экспорта не заводилось специально, чтобы не разойтись).

**CSV/XLSX-инъекция формул (OWASP CSV Injection)** — SKU/название/бренд в каталог
вводит человек через API (`routes_catalog.py`, доступно только `admin`, но сам каталог
мог быть скопирован из внешнего источника). Опасны строки, начинающиеся на `= + - @`
таб/CR. Для CSV — стандартный префикс `'` (Excel при ИМПОРТЕ CSV трактует ведущую `'`
как «дальше текст»). Для XLSX — эмпирически проверено (см. тесты), что `ws.append(["=1+1"])`
делает ячейку ФОРМУЛОЙ (`data_type == "f"`), а `cell.data_type = "s"` ПОСЛЕ записи убирает
это без изменения содержимого (без «уродливого» видимого апострофа, как в CSV) — сохраняется
и в самой XML (`t="inlineStr"`, без тега `<f>`), проверено вскрытием сгенерированного
xlsx-архива вручную перед тем, как класть логику в код.

**Не сделано / осознанные ограничения**:
1. **BI-интеграция по ТЗ (F14: «CSV/PDF/BI-интеграция»)** сведена к периодическому
   CSV/XLSX-экспорту дневной динамики (`GET .../osa-summary/export`) — это «BI умеет
   прочитать файл», а не настоящая интеграция (вебхук, прямой коннектор к
   Postgres/ClickHouse, автоматическая выгрузка по расписанию). Осознанное упрощение
   объёма на одну сессию; если нужна настоящая интеграция — начните с прямого доступа
   BI-инструмента (Metabase/PowerBI) к реплике Postgres, это меньше кода, чем API-выгрузка.
2. **Экспорт по снимку, не по периоду.** Нельзя одним запросом скачать отчёты по
   НЕСКОЛЬКИМ снимкам/полкам сразу (только текущий снимок дашборда или дневная динамика
   по одному магазину) — если понадобится «выгрузка по всей сети за неделю», это
   отдельная задача, вероятно с фоновой Celery-задачей (файл может быть большим), а не
   синхронным HTTP-ответом, как сейчас.
3. **Кнопки экспорта на дашборде** появляются только для полки, которая сейчас открыта
   (по `store_id`+`shelf_id` из URL) — нет общего «экспортировать всё» на уровне UI.
4. Шрифт DejaVu Sans не поддерживает **эмодзи/CJK** — не актуально для ru/uz, но если
   каталог когда-нибудь заведёт китайские SKU, PDF их не отрисует (пустые квадраты).
5. Экспорт больших отчётов (сотни строк) не проверялся на реальной производительности
   — `test_many_rows_do_not_crash_and_repeat_header_across_pages` гоняет только 80 строк,
   этого достаточно для «не падает и переносит заголовок таблицы», но не для замера
   времени генерации PDF на тысячах строк.

## F12: как устроено и чего НЕТ

**Устройство.** Три слоя, тот же принцип разделения, что и в F13/F14: решение —
чистая функция (`app/core/review.py:decide_review`, реально протестирована),
подготовка изображения — тоже чистая и реально протестирована
(`app/pipeline/review_crop.py`), БД+HTTP+Celery — не выполнялись, только вычитаны.
Ревью работает ТОЛЬКО со статусом `DetectionStatus.UNCERTAIN` (детектор нашёл
кандидата, но score между `unknown_threshold` и `match_threshold` — см.
`matcher.py:ProductMatcher.match`), ровно по формулировке ТЗ «очередь неуверенных
распознаваний». Три действия: `confirmed` (кандидат верный → `status="matched"`),
`corrected` (кандидат неверный, реальный товар — другой → `status="matched"` с новым
`matched_product_id` + Celery-задача `reindex_correction_task`), `marked_unknown`
(это вообще не товар из каталога → `status="unknown"`). После любого действия
статус меняется с `uncertain`, поэтому повторное ревью того же detection
автоматически отклоняется `decide_review` — двойной проверки статуса не нужно.

**«Дообучение на исправлениях»** реализовано НЕ как переобучение модели (это
дорого и не нужно — та же идея, что у F10 «добавление SKU без переобучения»):
crop, который человек пометил как `corrected`, становится ЕЩЁ ОДНИМ эталонным
фото для правильного `product_id` — эмбеддинг + `CatalogIndex.add()` + `save()`,
тем же кодом, что и `CatalogService.add_product`. Снимки полки часто реалистичнее
студийных эталонных фото (освещение, ракурс, соседство с другими товарами),
поэтому такие исправления особенно ценны.

**Кто может ревьюить**: `merchandiser` (только свои магазины) и `admin` (вся
сеть) — новое право `Permission.REVIEW_QUEUE`. `regional_manager`/`analyst`
получают `403` — это осознанный выбор (см. комментарий в `ROLE_PERMISSIONS`):
решение напрямую меняет общий эмбеддинг-индекс каталога, это операционное
действие человека на месте, а не управленческое. Если это неверная модель для
вашей организации (например, ревью должны делать региональные менеджеры, а не
рядовые мерчандайзеры) — это одна строка в `ROLE_PERMISSIONS`, не архитектурное
изменение.

**UI**: `frontend/review.html` — отдельная мобильная страница для мерчандайзера,
сознательно НЕ вкладка/секция `dashboard.html` (разная аудитория и разный контекст
использования: менеджер за монитором смотрит сводку по сети, мерчандайзер с телефоном
у полки разбирает очередь по одной карточке). Тот же дизайн-язык (CSS-переменные,
шрифт), что и у дашборда — визуально одна система, при этом два отдельных файла,
которые можно открывать/обновлять независимо. Кроп загружается авторизованным
`fetch`→`Blob`→`URL.createObjectURL` (тот же приём, что у скачивания экспорта в F14) —
обычный `<img src="...">` не отправил бы `Authorization`. Для действия "corrected"
понадобился НОВЫЙ эндпоинт `GET /catalog/products?q=` (его не было вообще — раньше
каталог можно было только пополнять, не читать) и новое право `CATALOG_READ`,
выданное всем ролям (просмотр каталога — не риск сам по себе, в отличие от записи).

**Не сделано / осознанные ограничения**:
1. **Разбирается только `uncertain`, не `unknown`.** Товар, которого детектор
   вообще не нашёл (например, каталог ещё не знает такой SKU) — это ДРУГАЯ
   задача (обнаружение пробела в каталоге, не проверка кандидата) и другой UX
   (нужен способ найти/создать правильный SKU с нуля, а не просто подтвердить/
   поправить готового кандидата). Сознательно не смешано с этой сессией.
2. **Переиндексация синхронная по одной записи** (`index.add()` + `save()` на
   каждое исправление) — при большом потоке исправлений `save()` (полная
   перезапись индекса на диск) станет узким местом. Для пилота нормально;
   для продакшена с активным потоком исправлений стоит батчить `save()`
   (например, раз в N исправлений или по таймеру), а не на каждое.
3. **Нет отмены ревью** (`undo`) — решение, применённое по ошибке, руками не
   откатывается; в БД остаётся аудиторский след (`reviewed_by`/`reviewed_at`/
   `review_action`), но обратной операции нет.
4. ~~Баг №8~~ — исправлен (файл на диске теперь размытый и выровненный кадр), см. сессию вычитки.
5. Переиндексация ничего не проверяет насчёт КАЧЕСТВА crop'а (размытый в движении
   товар, некорректный bbox от плохой детекции) — человек, нажавший "corrected",
   неявно ручается и за визуальное качество кропа, это не проверяется автоматически.
6. **`review.html` не обновляет очередь в реальном времени** между карточками, кроме
   кнопки "Обновить" — если за время работы мерчандайзера в очередь попали новые
   detections с другого снимка того же магазина, он их не увидит, пока не откроет
   страницу заново/не нажмёт "Обновить". Для одиночного мерчандайзера на смену
   это некритично; при нескольких людях, разбирающих одну очередь параллельно,
   стоит рассмотреть подгрузку по мере убывания локального списка.
7. **Поиск по каталогу — простой `ILIKE`**, без ранжирования по релевантности:
   результаты отсортированы по SKU, не по «похожести» на запрос. При каталоге
   в сотни SKU этого достаточно; при тысячах — понадобится полнотекстовый поиск.

  non-commercial purposes only" (цитата с официального репозитория). Годится
  для обучения/прототипирования, но веса на этих данных нельзя без отдельного
  разрешения Trax использовать в реальном коммерческом продукте. Для прода
  в итоге нужны собственные фото полок сети.
- **Железо пользователя**: Acer Predator Helios Neo 16S AI — Intel Ultra9
  275HX, 32GB DDR5, 1TB NVMe, **RTX 5060 8GB (архитектура Blackwell, sm_120)**,
  Windows. `training_guide.md` и `RUNBOOK.md` написаны конкретно под эту
  машину, включая нюансы совместимости PyTorch с Blackwell (нужен cu128+,
  риск несовместимости стабильных сборок) и известное ограничение Celery на
  нативном Windows (нужен `--pool=solo`).
- **Узбекский рынок**: единственное место в проекте, где страна реально
  имеет значение — язык OCR ценников. Подключены `uzb`/`uzb_cyrl`/`rus`
  языковые пакеты Tesseract с graceful fallback, если что-то не установлено.

   в `config.yaml` нигде не читается) и политика «сырых» снимков, если понадобится переанализ с нуля.
6. ~~Отчёт не пересчитывается после ревью~~ — исправлено (№13).
7. **Общий индекс каталога** вместо файла+копий в памяти (№14) — нужен перед горизонтальным масштабированием воркера.

   доступный сервер (VPS) или приватная сеть (например Tailscale) и HTTPS (reverse-proxy). Без HTTPS не заработают
   service worker/PWA и офлайн-очередь.
9. ~~Нативное приложение или PWA~~ — для курсовой не нужно (см. сессию №5); исходная формулировка: решать после пилота (критерии — в ответе пользователю): качество детекции на
   реальных фото, устоявшийся процесс съёмки, решение по хостингу.
10. **Лицензия SKU-110K — только академическое/некоммерческое использование** (`training_guide.md`, п. 0): веса,
    обученные на нём, нельзя без разрешения Trax использовать в коммерческом продукте; для прода нужны собственные
    размеченные фото полок.
