# 07. Распознавание товаров и ML

## 1. Цель

Надёжно определить **конкретный SKU**: Coca-Cola 0,5 л — не Coca-Cola Zero 0,5 л и не Coca-Cola 1 л. Если уверенности нет,
показать несколько кандидатов или честно сказать «не нашли». Демонстрационное распознавание не годится.

**Утверждено:** модели, веса, индексы и ML-конфигурация в рамках этой задачи не меняются. Сначала benchmark, потом решения.

## 2. Как работает сейчас (по коду)

```text
POST /catalog/identify (нужен токен)
  → normalize_photo (EXIF, 1600 px)
  → decode_image: штрихкод? известен → ответ by=barcode (без модели)
  → кадр во временный файл → Celery identify_product_task (API ждёт до 25 с)
  → DinoV2Embedder.embed(ВЕСЬ КАДР) → FaissCatalogIndex.search → rank_products (лучший счёт на товар)
  → decide_match(0.72 / 0.45 / margin 0) → matched | uncertain | unknown | empty_catalog
```

Наблюдения:

- **Детектор в распознавании не участвует**: YOLO загружается при старте воркера, но `identify` его не вызывает.
- **OCR отсутствует.** Tesseract с rus, uzb, uzb_cyrl стоит в образе, но кода нет.
- Процессор DINOv2 по умолчанию (`AutoImageProcessor`) уменьшает и **вырезает центральный квадрат**: края вытянутой упаковки
  могут обрезаться. Эталоны и запросы обрабатываются одинаково, поэтому это не ошибка, но влияет на качество. **Проверить в benchmark.**
- Индекс не хранит версию модели: подмена весов без пересборки молча ломает поиск.
- Публичная DINOv2-base **не дообучена** на товарах магазина.

## 3. Целевой процесс

```text
кадр
 │ 1. Нормализация: EXIF, размер, проверка формата, отказ от слишком тёмных и размытых кадров (подсказка «переснимите»)
 │ 2. Штрихкод (как сейчас) ─► найден, контрольная цифра верна, товар активен?
 │        ├─ да, и в кадре нет второго кода другого товара ──► КАНДИДАТ С ВЫСШИМ ПРИОРИТЕТОМ (см. 4.1)
 │        └─ нет / неизвестен / противоречие ──► дальше
 │ 3. Кадрирование: детектор находит товар(ы)
 │        ├─ одна рамка ──► кроп
 │        ├─ несколько ──► вернуть рамки, ПОЛЬЗОВАТЕЛЬ ВЫБИРАЕТ (не выбираем сами)
 │        └─ нет рамки ──► режим определяет benchmark: «весь кадр с пониженным доверием» или статус no_object
 │ 4. Визуальный поиск: эмбеддинг кропа → top-K товаров (группировка по товару, как сейчас)
 │ 5. OCR (только когда нужно): кандидаты близки (малый запас) ИЛИ это варианты одной линейки (бренд тот же, объём/вкус разные)
 │        → текст с упаковки → объём/масса, бренд, ключевые слова вкуса → сверка с карточками кандидатов
 │ 6. Решение (слияние признаков) ──► matched | candidates | unknown | no_object | empty_catalog
 └ 7. История запроса (документ 04), ответ — только публичные поля
```

### 3.1. Роль детектора

YOLO обучен на SKU-110K: плотные полки с десятками мелких товаров. Одиночный товар в руке крупным планом — другая картина.
Увидит ли его модель, **не измерено** (`ml/probe_detector.py` готов, фото владельца нет). Поэтому роль детектора решает замер:

- если на одиночных фото детектор надёжно даёт одну рамку — кроп по рамке;
- если часто молчит — детектор используется только для кадров с несколькими товарами, а одиночный кадр идёт целиком или
  центральным кропом (с пометкой в истории);
- порядок цветов: код отдаёт YOLO RGB, а Ultralytics для массивов numpy ожидает BGR. `probe_detector` сравнивает оба варианта.

### 3.2. Несколько товаров в кадре

Сервер возвращает рамки в долях кадра (0–1) и временный идентификатор кадра. Страница рисует рамки, покупатель нажимает
на нужную, клиент присылает **только номер рамки** (фото повторно не передаётся), и сервер режет кроп из кадра.
Кадр хранится **только в оперативной памяти** до 2 минут и удаляется сразу после выбора, после отмены или по истечении
времени; на диск и в резервные копии не попадает, после перезапуска не восстанавливается (уточнение D-10, подтверждено
владельцем; условия и реализация — документ 04, §4.2). Выбирать «самую
крупную» или «самую уверенную» рамку сами мы не будем: это ровно та ошибка, которую требование запрещает.

## 4. Слияние признаков (версия 1 — прозрачные правила)

### 4.1. Штрихкод

Штрихкод — самый сильный признак, но не безусловный:

| Ситуация | Решение |
|---|---|
| Один верный код, товар есть и активен | `matched`, `by=barcode` |
| Код верный, но визуально товар уверенно похож на **другой** SKU | `matched` по коду, запрос **отмечается для проверки** (возможна ошибка привязки кода в каталоге) |
| В кадре два кода разных товаров | `candidates` (оба), без автоматического выбора |
| Код верный, в каталоге нет | дальше по виду; сотруднику — предложение привязать код (уже есть) |
| Код в архивном товаре | дальше по виду; в истории пометка |

### 4.2. Вид + текст

1. Если лучший визуальный счёт ниже `unknown_threshold` и OCR не нашёл совпадений — `unknown`.
2. Если лучший счёт ≥ `match_threshold`, запас до второго товара ≥ `margin_threshold` и OCR **не противоречит** — `matched`.
3. Если кандидаты близки (или это одна линейка) и OCR **однозначно** поддерживает одного из них (совпал объём, вкус, название) —
   `matched` с `by=look+text`.
4. Если OCR противоречит лучшему кандидату (на упаковке «1 л», у кандидата «0,5 л») — `candidates`.
5. Иначе — `candidates` (3 лучших) с подписью «похоже на».

Пороги и правила подбираются на обучающей части benchmark и проверяются на контрольной. Версия 2 — откалиброванная модель
уверенности (например, логистическая регрессия на признаках: визуальный счёт, запас, совпадение текста, наличие кода).
Её стоит вводить, только если она даёт измеримый выигрыш на контрольных сессиях.

### 4.3. OCR

- **Утверждено:** OCR обязателен, Tesseract пока остаётся. Решение о замене — только после испытаний.
- Tesseract медленный на больших кадрах (оценка: от долей секунды до секунд на CPU). Поэтому OCR запускается **только на кропе
  и только когда нужно** (п. 4.2.3–4), с ограничением по времени.
- Разбор объёма и массы: регулярные выражения для «0,5 л», «0.5L», «500 мл», «500ml», «1,5 л», «250 г», «1 кг», «x6» с приведением
  к числу и единице. Сверка идёт с характеристиками типа `measure` из схемы категории (объём, масса, а у электроники — например, объём памяти), документ 06, §4.
- Сверка слов: нормализация (регистр, узбекская латиница и кириллица в общую форму, частые OCR-подмены 0/O, 1/l, 5/S),
  сравнение с текстами кандидатов на всех локалях и с брендом.
- Испытать: русский, узбекская латиница, узбекская кириллица, цифры, объём и масса, вкусы, мелкий текст, изогнутая и бликующая
  упаковка (отдельные срезы benchmark).

## 5. Benchmark (до любых крупных изменений)

### 5.1. Набор данных

| Параметр | Значение |
|---|---|
| SKU в каталоге | 30–50 |
| Похожие группы | не меньше 8 групп «один бренд — разные вкусы, объёмы, упаковки» (например, Coca-Cola / Zero / 1 л / 0,5 л / банка) |
| «Неизвестные» товары | 10–15 товаров, которых **нет** в каталоге (для проверки отказа) |
| Эталоны (каталог) | сессия A: 5–8 фото на SKU (спереди, сбоку, сзади, под углом), спокойный свет |
| Запросы (тест) | сессии B, C (и лучше D): **другой день, другое освещение, другой телефон, другое место**: в руке, на полке, с бликом, частично закрыт, издалека; 10–20 фото на SKU |
| Объём | около 500–1000 запросов известных товаров + 150–300 запросов неизвестных |

**Разделение по сессиям, а не случайное.** Ни одна сессия не попадает одновременно в эталоны и в запросы. Соседние кадры одной
серии почти одинаковы: случайное разделение дало бы завышенную точность. Запросы, используемые для подбора порогов (сессия B),
и контрольные (сессия C) тоже разные.

Структура папок (предложение): `benchmark/<сессия>/<артикул или unknown_N>/*.jpg` + `benchmark/sessions.csv`
(дата, телефон, место, свет, условия).

### 5.2. Что измерять

Обозначения: K — запросы известных товаров, U — запросы неизвестных, «уверенный ответ» — статус `matched`.

| Показатель | Формула | Цель |
|---|---|---|
| Top-1 accuracy | верный SKU первым среди K | записать факт |
| Top-5 recall | верный SKU среди 5 кандидатов (K) | записать факт; это потолок для режима «выберите из кандидатов» |
| Coverage | доля K с уверенным ответом | как можно выше **при соблюдении следующей строки** |
| Ошибки среди уверенных (selective risk) | неверные `matched` (в K и U) / все `matched` | **≤ 1 %** (целевая граница, не достигнутый результат) |
| Правильный отказ | доля U без `matched` | записать факт; близко к 100 % |
| Ложное принятие неизвестного | доля U с `matched` | записать факт |
| Скорость | p50 и p95 полного запроса (с OCR и без) | документ 11 |
| VRAM и RAM | пик и в покое | документ 11 |

Отдельно по срезам: похожие группы, блики, частичное закрытие, мелкий текст, каждый телефон, узбекские надписи.

**Статистическая честность.** На небольшом наборе нельзя доказать «≤ 1 %». Правило трёх: если среди n уверенных ответов
ошибок нет, верхняя граница доли ошибок с доверием 95 % — около 3/n. Чтобы утверждать «не больше 1 %», нужно не меньше
**300 уверенных ответов без единой ошибки** на контрольной сессии. При меньшем объёме в отчёте пишется честный интервал, а не «99 %».

### 5.3. Что сравнивать (по шагам, по одному изменению за раз)

| № | Конфигурация | Зачем |
|---|---|---|
| 0 | Текущая: весь кадр, DINOv2-base, пороги 0.72/0.45, без запаса | исходная точка |
| 1 | + кроп по YOLO (при одной рамке) | помогает ли детектор |
| 2 | + центральный кроп без YOLO | дешёвая альтернатива детектору |
| 3 | Предобработка без обрезки центра (дополнение до квадрата) | не теряем ли края упаковки |
| 4 | + подобранный запас (margin) | сколько уверенных ошибок убирает |
| 5 | + OCR-сверка | различение вариантов |
| 6 | + штрихкод (когда виден) | итоговая система |
| 7 | Альтернативные модели (раздел 6) на лучшей конфигурации | только если 0–6 не дают цели |

Инструмент: существующий `ml/evaluate_matching.py` рассчитан на размеченные фото полок (YOLO-разметка). Для одиночных
товаров нужен новый скрипт (например, `ml/benchmark_identify.py`), который **вызывает ту же функцию решения** `decide_match`
(и будущую функцию слияния) и пишет построчный CSV по каждому запросу. Тогда цифры benchmark соответствуют боевому поведению.

## 7. Коммерческий риск YOLO11 (Ultralytics)

- Текущий код использует пакет `ultralytics`, веса обучены его средствами.
- По заявлению Ultralytics, AGPL-3.0 распространяется и на обученные модели. Для продукта без открытия исходного кода
  нужна Enterprise-лицензия.
- Пока проект внутренний и не распространяется, вопрос не стоит остро. Перед **закрытым коммерческим дистрибутивом**
  нужна юридическая проверка. Варианты:
  1. купить Enterprise-лицензию;
  2. открыть исходный код по AGPL-3.0;
  3. заменить детектор моделью с разрешительной лицензией (RF-DETR N/S/M/L, RT-DETR) и переобучить;
  4. отказаться от детектора в сценарии одиночного товара, если benchmark покажет, что он не нужен.
- Здесь не делается категоричный юридический вывод. Решение принимается после консультации (документ 14, D-05).

| Тип индекса | `IndexFlatIP` (точный перебор) | Оставить: для 80 тыс. векторов точный поиск быстрый (документ 11), приближённые индексы не нужны |

## 9. Обучение на подтверждённых данных (позже)

- Исправления сотрудников («это не тот товар» → правильный SKU) попадают в очередь проверки, а **не сразу** в эталоны.
- Подтверждённые фото — кандидаты в эталоны (`product_images.role='reference'`) после проверки человеком.
- Дообучение модели (например, DINOv2 с метрическим обучением) — отдельный проект: разметка, разделение по сессиям, сравнение
  с базовой моделью на контрольной сессии, версия модели в манифесте, **откат** к предыдущей модели и индексу.
- Модель в рабочей системе не меняется без сравнения на benchmark и без пересборки индекса.

## 10. Универсальное распознавание (добавлено в 1.3)

### 10.1. Модель отделена от магазина

```text
   Модель признаков (общая)            Каталог и индекс (у каждого магазина или организации свои)
   ┌──────────────────────┐           ┌──────────────────────────────────────────────────┐
   │ кадр → эмбеддинг     │ ────────► │ индекс пространства имён «каталог X» + манифест   │ → кандидаты → проверка по каталогу X
   │ (DINOv2 и т. п.)     │           │ (модель, версия, предобработка)                   │ → matched / кандидаты / не найдено
   └──────────────────────┘           └──────────────────────────────────────────────────┘
```

- Модель извлекает **признаки изображения** и ничего не знает о структуре магазина, категориях и характеристиках.
- **Решение принимается по каталогу соответствующего магазина.** Товара нет в его каталоге — значит «не найдено», даже если
  в другом магазине такой товар есть. Совпадение не придумывается (open-set, §4).
- **Новый магазин с другим ассортиментом** = загрузить каталог и эталонные фото → построить **свой индекс** → работать.
  **Переобучение модели не требуется.** Индексы разных каталогов не смешиваются.
- Манифест индекса (§8) получает поле **пространства имён** (каталог или магазин). Индекс, построенный другой моделью или для другого
  каталога, не загрузится по ошибке.
- В сети с общим каталогом организации: один индекс на каталог организации + отбор кандидатов по ассортименту магазина (документ 17, §4.4).

### 10.2. Разные типы товаров — разная глубина распознавания

| Тип товара | Что можно узнать по фото | Что нужно ещё | `categories.recognition_level` |
|---|---|---|---|
| Упакованные продукты, бытовая химия | конкретный SKU (часто), похожие варианты различает OCR (объём, вкус) | штрихкод — лучший признак | `sku` |
| Одежда и обувь | модель и цвет; **размер — нет** | размер по этикетке или штрихкоду | `group` (модель), затем уточнение |
| Электроника в коробке | модель; конфигурация (8/16 ГБ) часто неразличима | штрихкод или OCR надписей на коробке | `group` или `sku` с обязательной OCR-сверкой |
| Цветы и растения | вид или сорт, цвет | высота и количество — не по фото | `group` |

Если `recognition_level = group`, результат — «Модель X, чёрная. Уточните размер (штрихкод или этикетка)», а не случайный вариант.
Это продолжение принципа «не выбирать за покупателя» (§3.2).

### 10.3. Компоненты, которые должны быть сменяемыми

- **Модель признаков:** DINOv2 сейчас; другие — только после benchmark на данных конкретного типа магазина (§5–6). Возможен «реестр моделей»:
  разные модели для разных типов магазинов, но **один индекс строится одной моделью** (это фиксирует манифест).
- **Детектор:** YOLO обучен на продуктовых полках (SKU-110K) и для одежды, цветов и электроники может не подойти. Поэтому детектор —
  необязательный помощник кадрирования (§3.1) с возможностью заменить или отключить его для типа магазина. Лицензионный вопрос — §7.
- **OCR:** работает для любого типа, но сверяет текст с характеристиками схемы категории (§4.3).
- **Штрихкод:** универсален и остаётся самым сильным признаком.

### 10.4. Что из этого делать когда

| Что | Группа |
|---|---|
| Поле «пространство имён» и версия модели в манифесте индекса; каждый вектор индекса помнит `product_id` **и** `group_id` (вариант и модель, документ 06, §4.6); распознавание не зависит от полей, специфичных для продуктов | **предусмотреть в архитектуре сейчас** |
| `recognition_level` у категорий; OCR-сверка с характеристиками `measure` | следующие этапы (вместе с универсальным каталогом) |
| Индексы для нескольких каталогов, отбор по ассортименту, реестр моделей по типам магазинов | при подключении сети или второго типа магазина |
| Дообучение моделей под одежду или цветы | не сейчас — только если benchmark на таких данных покажет необходимость |

### 10.5. Модель и вариант: распознавание не путает их (1.5)

**Правило:** распознавание по фото выдаёт **конкретный вариант** (SKU) только при наличии **различающего признака**. Иначе результат —
модель (группа) и просьба уточнить ось варианта.

| Признак | Достаточно для конкретного варианта? |
|---|---|
| Штрихкод варианта в кадре | **да** (штрихкод принадлежит ровно одному варианту, документ 06, §4.6) |
| OCR прочитал значение оси (например, «0,5 л», «16 GB») и оно совпало ровно с одним вариантом модели | да, если нет противоречий |
| Визуальный запас между вариантами одной модели выше порога **и** ось видна на фото (цвет, форма упаковки) | да — порог подбирается в benchmark для каждой оси отдельно |
| Только визуальное сходство, ось не видна (размер одежды, объём памяти в одинаковых коробках) | **нет** → результат «модель X» + уточнение |

Как это устроено:

1. Векторы индекса помечены `product_id` (вариант) и `group_id` (модель). Ранжирование кандидатов идёт **по моделям** (лучший счёт
   среди вариантов), затем — внутри модели по вариантам.
2. Если лучшие кандидаты — варианты **одной** модели и различающего признака нет, ответ — `matched` на уровне **модели** с полем
   `variant_unresolved` и списком осей для уточнения («Какой размер?», «Какой объём?»). Это не считается уверенным ответом о варианте.
3. Если лучшие кандидаты — **разные** модели, работают обычные правила (§4).
4. Уверенный ответ о неверном **варианте** считается ошибкой так же, как неверный товар.

**Метрики в benchmark (дополнение к §5.2):** точность на уровне модели; точность на уровне варианта; доля уверенных ответов
о варианте, оказавшихся **неверным вариантом той же модели**. Последняя входит в общую границу «ошибки среди уверенных ≤ 1 %».
В наборе benchmark — группы вариантов: продукты разных объёмов и упаковок одного вкуса; позже — одежда и электроника.
