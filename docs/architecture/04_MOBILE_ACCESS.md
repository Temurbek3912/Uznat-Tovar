# 04. Мобильный доступ через QR-код

## 1. Сценарий покупателя (утверждено)

Покупатель сканирует постоянный QR-код магазина → открывается мобильная страница → выбирает язык → фотографирует товар,
загружает фото или снимает штрихкод → видит результат и карточку. Регистрации нет, персональные данные не вводятся.

Сотрудник в настройках нажимает «Войти как администратор», вводит логин и пароль и получает функции по своим разрешениям.
Отдельного «скрытого» входа нет. Где именно доступен вход сотрудника — раздел 5 (в гостевой сети покупателей его нет).

## 2. Камера в браузере: что реально работает

| Способ | Нужен HTTPS? | Состояние в проекте |
|---|---|---|
| Живая камера `getUserMedia()` (видео на странице, съёмка кнопкой) | **Да.** API доступно только в защищённом контексте: HTTPS или `localhost` ([MDN](https://developer.mozilla.org/en-US/docs/Web/API/MediaDevices/getUserMedia)). По `http://192.168.x.x` на телефоне не работает | ✅ реализовано, показывает понятную ошибку на незащищённом адресе (`identify.js`: `error.camera_insecure`) |
| `<input type="file" accept="image/*" capture="environment">` — открывает приложение камеры телефона, снимок уходит как файл | **Нет**, работает по обычному HTTP | ✅ реализовано (`identify.html`) |
| Загрузка готового фото из галереи | Нет | ✅ |
| Штрихкод | Нет: сервер читает код со снимка (`app/services/barcode.py`) | ✅ (по снимку). Живое сканирование в видеопотоке — только с HTTPS |

**Утверждено для первой локальной версии:** покупатель снимает через `<input capture>`, сервер читает и штрихкод, и вид.
Живая камера — после появления HTTPS (раздел 3.4, вариант «свой домен»).

## 3. Адрес в QR-коде (D-07)

### 3.1. Требования владельца (уточнены 2026-11-06)

1. QR-код магазина **постоянный** и по возможности **не зависит от IP-адреса** конкретного компьютера.
2. Сначала исследовать постоянное локальное имя (например, `shop.local`). Если оно ненадёжно или требует слишком сложной настройки —
   закреплённый локальный IP через DHCP-резервирование.
3. В любом случае:
   - порт приложения фиксированный;
   - QR ведёт **только на публичный интерфейс** магазина;
   - административный доступ покупателям не открывается;
   - приложение показывает владельцу **текущий адрес и адрес, записанный в QR**;
   - при несовпадении — понятное предупреждение;
   - есть процедура смены адреса и обновления QR.
4. Не обещать, что QR останется рабочим при любой смене сети.

Ограничение на сейчас: только документация. Код, настройки сети и конфигурация приложения не меняются.

### 3.2. Важное свойство QR-кода

QR — это просто напечатанный текст адреса. **Изменить его после печати нельзя.** Поэтому «постоянный QR» означает одно:
адрес из QR должен продолжать вести на сервер магазина. Добиться этого можно двумя способами: сохранять сам адрес (IP) или
вписать в QR имя, которое при смене IP перенастраивается. Обходной путь через внешний сервис коротких ссылок («QR ведёт на
сайт, сайт перенаправляет на текущий адрес») **не подходит**: он требует интернета и стороннего провайдера, а это противоречит
local-first.

### 3.3. Исследование: постоянное локальное имя вместо IP

Есть два разных механизма локальных имён, и у них разные ограничения.

#### А. Имя через mDNS (`shop.local`, «Bonjour»)

Как работает: телефон рассылает в сеть вопрос «у кого имя `shop.local`?», компьютер магазина отвечает своим адресом.
Роутер не участвует. Зона `.local` зарезервирована именно за mDNS (RFC 6762) ([.local](https://en.wikipedia.org/wiki/.local)).

| Что проверяли | Результат | Источник |
|---|---|---|
| **iPhone / iPad** | имена `.local` разрешаются штатно (Bonjour встроен в iOS) | [.local](https://en.wikipedia.org/wiki/.local) |
| **Android 12 и новее** | системный DNS-резолвер Android поддерживает mDNS для `.local` с обновления модуля DNS Resolver (Mainline) от ноября 2021 года; на Android 10 и 11 изменение, по имеющимся данным, не перенесено | [Esper: Android adds mDNS support](https://www.esper.io/blog/android-dessert-bites-26-mdns-local-47912385) |
| **Chrome на Android** | для адресов `.local` Chrome по умолчанию обращается к системному резолверу, а защищённый DNS (DoH) для `.local` не применяет | [Chrome Host Resolution](https://chromium.googlesource.com/chromium/src/+/main/net/dns/README.md) |
| **Практика на Android** | есть сообщения, что Chrome и Edge на Android не открывают `.local` (ошибка `DNS_PROBE_FINISHED_NXDOMAIN`) — без указания версий; на рабочих (управляемых) Android 11–12 с VPN-туннелем `.local` работал нестабильно | [Home Assistant Community](https://community.home-assistant.io/t/detail-mdns-android-os-limitations-on-the-web-server-components-documentation/374099), [Technical Fellow](https://www.technicalfellow.com/2022/09/notes-from-the-field-the-one-that-android-said-no-more-local/), [Chromium issue](https://issues.chromium.org/issues/41127207) |
| **Компьютер Windows как отвечающая сторона** | Windows 10 (с версии 1703) и 11 сами отвечают на mDNS **для имени компьютера** (`<имя-компьютера>.local`). Произвольное имя вроде `shop.local` штатно не публикуется — нужна своя служба-ответчик (библиотека в backend или Bonjour). Брандмауэр должен пропускать UDP 5353 | [Windows mDNS/DNS-SD](https://slightfuture.com/technote/windows-mdns-dnssd/) |
| **Гостевая Wi-Fi сеть** | mDNS работает только **внутри одного сегмента сети**: многоадресные пакеты не проходят между подсетями и VLAN без специального ретранслятора (mDNS reflector), который есть далеко не у каждого роутера. Гостевая сеть обычно — отдельная подсеть или с изоляцией клиентов, поэтому **из гостевой сети `shop.local` не разрешится**, если компьютер стоит в основной сети | [OpenWrt forum](https://forum.openwrt.org/t/how-do-i-make-local-domain-work-across-ssid-networks-with-different-subnets/98440), [MikroTik forum](https://forum.mikrotik.com/t/reflector-cross-vlan-casting-mdns-ssdp-dial-as-a-routeros-container-10-mb-ram/271098) |
| Другие риски | конфликт имён (другое устройство с тем же именем — mDNS переименует одно из них, и QR молча перестанет вести куда нужно); фильтрация многоадресного трафика на некоторых точках доступа | — |

**Вывод по mDNS:** хорошо работает у iPhone и у новых Android в **одной** сети с компьютером. Для нашего главного сценария
(покупатели в **отдельной гостевой сети**, произвольные телефоны, в том числе Android 10–11) — **ненадёжно**.

#### Б. Имя в DNS роутера (например, `uznat.home.arpa`)

Как работает: в роутере заводится запись «имя → IP компьютера». Телефоны спрашивают DNS роутера, который выдаёт им DHCP.

- Для такого имени не используют `.local` — он зарезервирован за mDNS, и смешение вызывает сбои. Для домашних и малых сетей
  предназначен специальный домен `home.arpa` ([RFC 8375](https://www.rfc-editor.org/rfc/rfc8375)).
- **Плюс:** работает между подсетями, в том числе из гостевой сети, если гостевым клиентам разрешено обращаться к DNS роутера.
  При смене IP компьютера достаточно поправить запись в роутере — QR остаётся прежним.
- **Минусы:**
  - многие бытовые роутеры **не позволяют** заводить собственные DNS-записи (возможности конкретного роутера не подтверждены);
  - телефоны с включённым «Частным DNS» (Android, режим с указанным сервером) или с собственным DNS-профилем обращаются
    не к роутеру, а к внешнему серверу, и локальное имя у них не найдётся. На форумах описаны случаи, когда Android не разрешал
    локальные имена роутера без однозначной причины ([OpenWrt forum](https://forum.openwrt.org/t/manual-host-entry-openwrt-dns-prevents-android-from-resolving/147631));
  - имя всё равно указывает на IP, поэтому закрепление адреса (DHCP-резервирование) остаётся нужным.

**Вывод по DNS роутера:** может работать, но зависит от возможностей роутера и от настроек DNS на телефонах покупателей,
которые магазин не контролирует.

#### В. Свой домен в интернете, указывающий на локальный IP (для справки)

`shop.example.uz` → `192.168.1.50` в публичном DNS. Даёт постоянное имя **и** настоящий HTTPS (живая камера). Но требует
купленного домена, интернета у телефона для разрешения имени, а некоторые роутеры и DNS-серверы отбрасывают такие ответы
(защита от DNS rebinding). Это путь к HTTPS в будущем, а не решение для первой версии.

### 3.4. Сравнение и рекомендация

| Критерий | **Закреплённый IP** (DHCP-резервирование) | Имя mDNS `shop.local` | Имя в DNS роутера `*.home.arpa` |
|---|---|---|---|
| iPhone | ✅ | ✅ | ✅ (если телефон спрашивает DNS роутера) |
| Android 12+ | ✅ | ✅ в основном, есть сообщения о сбоях | ✅ (без «Частного DNS» со своим сервером) |
| Android 10–11 | ✅ | ❌ по имеющимся данным | ✅ (без «Частного DNS») |
| Из гостевой сети (другая подсеть) | ✅, если роутер пропускает к адресу и порту | ❌ без mDNS-ретранслятора | ✅, если гостям доступен DNS роутера |
| Зависимость от возможностей роутера | резервирование есть почти везде (подтвердить на конкретном) | ретранслятор — редкость | свои DNS-записи — не везде |
| Смена IP компьютера без перепечатки | ✅ только если вернуть **тот же** IP | ✅ (имя переезжает с компьютером) | ✅ поправить запись в роутере |
| Полная смена сети (другая подсеть) | ❌ перепечатка, если нельзя настроить ту же подсеть | ✅ только в одном сегменте | ✅ если в новом роутере завести ту же запись |
| Сложность настройки | низкая | средняя (своя служба-ответчик, UDP 5353) | средняя — зависит от роутера |

**Рекомендация (по правилу владельца: если имя ненадёжно — IP):**

- **В QR печатается закреплённый локальный IP и фиксированный порт:** `http://<закреплённый IP>:<порт>/s/<код магазина>`.
  Только этот вариант одинаково работает у всех типов телефонов, в том числе из гостевой сети, без зависимости от DNS телефона.
- Имя mDNS **в QR не используется**. Им можно пользоваться внутри основной сети: сотрудники открывают `<имя-компьютера>.local`
  на компьютерах и iPhone для удобства, но это не замена адресу в QR.
- Имя в DNS роутера — **запасной вариант для будущего**. Переходить на него стоит, только если конкретный роутер позволяет
  свои записи **и** проверка на телефонах (раздел 3.7) прошла без единого отказа.
- **Честное ограничение:** QR с IP останется рабочим, только пока сервер доступен по этому IP и порту. При полной смене сети,
  если нельзя настроить прежнюю подсеть, **QR придётся перепечатать**. Процедура — раздел 3.6.

### 3.5. Фиксированный порт и только публичный интерфейс

- **Порт** — часть адреса в QR, после печати его менять нельзя. Предложение: **оставить 8000** (используется сейчас, не требует
  особых прав, реже конфликтует с другими программами, чем 80). Окончательное значение **утверждает владелец** до печати QR
  (открытый вопрос, документ 14).
- **QR ведёт только на публичный интерфейс.** Рекомендуется разделить сервер на два «входа»:

| Вход | Где слушает | Что отдаёт | Кто видит |
|---|---|---|---|
| **Публичный** (порт из QR, например 8000) | сетевая карта магазина | только страницы покупателя и публичный API (`/s/<код>`, `/api/v1/public/*`, раздел 4). Маршрутов сотрудников **на этом входе нет вообще** (ответ 404) | покупатели (гостевая сеть) и все остальные |
| **Служебный** (другой порт) | `127.0.0.1` (окно программы на компьютере магазина); при решении D-08 — дополнительно только сеть сотрудников | интерфейс и API сотрудников, вход по паролю | компьютер магазина и, по желанию, сеть сотрудников |

  Брандмауэр Windows: входящие соединения разрешены только на публичный порт. Служебный порт и PostgreSQL снаружи закрыты.
  Тогда «административный доступ не открывается покупателям» обеспечивается дважды: маршрутов нет на публичном входе, и служебный
  порт не принимает соединения из гостевой сети. Пароли сотрудников по гостевому Wi-Fi не передаются.
- Публичная страница не содержит ссылки «Войти как администратор», если открыта через публичный вход. На компьютере магазина
  и в сети сотрудников ссылка есть.

### 3.6. Что видит владелец и процедура смены адреса

**Экран «Адрес для покупателей»** (Настройки, только владелец):

- адрес, записанный в QR (IP, порт, код магазина, дата печати, номер версии плаката);
- текущие адреса компьютера (все сетевые карты) и слушает ли сервер публичный порт;
- состояние: «✅ совпадает» или «⚠ не совпадает» с понятным текстом: «QR напечатан для 192.168.1.50:8000, а компьютер сейчас
  192.168.0.12. Покупатели не смогут открыть страницу. Что делать: …»;
- кнопка «Проверить с телефона»: на экране показывается **временный** QR текущего адреса, его сканируют своим телефоном
  из гостевой сети и видят «Связь есть»;
- «Паспорт сети»: IP, MAC сетевой карты, подсеть, адрес роутера, памятка «что ввести в новый роутер». Паспорт входит в резервную копию.

Предупреждение о несовпадении появляется также на главном экране владельца и в значке программы в трее.

**Процедура «Адрес изменился»** (мастер в программе):

1. **Понять причину.** Мастер показывает старый и новый адрес и подсеть.
2. **Попробовать вернуть прежний адрес** (тогда QR не меняется):
   - тот же роутер — проверить или восстановить DHCP-резервирование для MAC компьютера;
   - новый роутер — настроить ту же подсеть и то же резервирование по «Паспорту сети»;
   - новый компьютер — перенести резервирование на его MAC.
   После этого — «Проверить с телефона».
3. **Если вернуть нельзя** (другая сеть, другая подсеть):
   1. владелец подтверждает новый адрес (мастер требует, чтобы он был закреплён: резервирование или статический адрес вне пула DHCP);
   2. «Проверить с телефона» по временному QR;
   3. «Создать новый QR» — файл для печати (A4/A5) с адресом текстом под кодом, датой и номером версии;
   4. владелец печатает и заменяет плакаты; мастер напоминает, где висели старые (список мест владелец ведёт сам);
   5. запись в журнал действий и обновление «Паспорта сети».
4. **Переходный период (по желанию, если подсеть та же):** Windows позволяет назначить сетевой карте второй IP. Компьютер
   какое-то время отвечает и по старому адресу, пока висят старые плакаты. Это ручная сетевая настройка — только с согласия владельца.

### 3.7. Проверка перед печатью QR (обязательно)

До печати и при каждой смене сети — проверка на реальных телефонах из той сети, где будут покупатели:

| Устройство | Сеть | Что проверить |
|---|---|---|
| iPhone (актуальная iOS) | гостевая | QR открывает страницу, фото отправляется, ответ приходит |
| Android 12+ (2–3 разных производителя) | гостевая | то же |
| Android 10–11 (если есть) | гостевая | то же |
| Любой телефон с включённым «Частным DNS» | гостевая | то же (при IP в QR это не должно мешать) |
| Телефон в гостевой сети | гостевая | служебный порт **недоступен**, PostgreSQL **недоступен** |

Критерий: все устройства открывают публичную страницу, служебные порты из гостевой сети закрыты.

## 4. Публичный API покупателя (не реализован)

Сейчас `POST /api/v1/catalog/identify` и `GET /catalog/products/{id}/photo` требуют токен. Предлагается отдельный набор публичных
маршрутов (только на публичном входе, раздел 3.5):

| Метод | Назначение | Ограничения |
|---|---|---|
| `GET /s/<код магазина>` | страница покупателя | статическая страница |
| `GET /api/v1/public/store` | название магазина, языки, логотип | только публичные поля |
| `POST /api/v1/public/identify` | распознавание кадра | лимит размера (10 МБ, как сейчас), лимит частоты по IP, общий лимит одновременных распознаваний, таймаут |
| `POST /api/v1/public/identify/{frame_id}/select` | выбор товара из нескольких рамок в кадре **без повторной отправки фото** | кадр живёт только в памяти до 2 минут (раздел 4.2) |
| `DELETE /api/v1/public/identify/{frame_id}` | отмена выбора — кадр удаляется сразу | — |
| `GET /api/v1/public/products/{id}` | карточка товара | **только публичные поля** |
| `GET /api/v1/public/products/{id}/photo` | фото для карточки | только «витринные» фото, миниатюры |
| `GET /api/v1/public/search?q=` | поиск по названию | короткий ответ, лимит частоты, без выгрузки всего каталога |
| `POST /api/v1/public/feedback` | «это не тот товар» | без персональных данных, лимит частоты |

Правила:

- Публичные маршруты **не принимают токены** и не дают доступа к API сотрудников. Это отдельный набор схем ответа, а не
  «тот же ответ без проверки прав».
- Ответ для покупателя не содержит внутренних идентификаторов, баллов уверенности в сыром виде и служебной информации.
  Подписи «уверенно / похоже на / не нашли» формирует сервер.
- **Решение D-10 (принято владельцем 2026-11-06):** фото покупателей по умолчанию **не сохраняются**: они нужны только для
  обработки текущего запроса и удаляются после неё. В истории остаются обезличенные технические данные (раздел 4.1).
  Сохранение фото для улучшения распознавания — возможная будущая функция, которую владелец включает добровольно (раздел 4.3).

### 4.1. Что остаётся в истории запроса (обезличенно)

| Хранится | Не хранится |
|---|---|
| идентификатор записи, время (с точностью до минуты), канал (QR-телефон / компьютер магазина / сотрудник) | **фото и любые его копии**, миниатюры, вырезки |
| результат (узнан / кандидаты / не найден / нет объекта / каталог пуст / ошибка) и способ (штрихкод / вид / вид + текст) | IP-адрес (счётчики лимитов живут только в памяти и в журнал не пишутся) |
| найденный товар и до 3 кандидатов с баллами | сведения о браузере и устройстве, cookies, геолокация |
| прочитанный штрихкод товара (это номер товара, а не данные человека) | распознанный OCR-текст целиком (только признак «текст совпал / противоречит») |
| время обработки, версии программы, модели и индекса | имена, телефоны, любые данные покупателя |
| отзыв «это не тот товар» (без комментария в свободной форме) | |

Срок хранения истории — 30–90 дней (настройка владельца), удаление ежедневной задачей. Владелец может очистить историю вручную.

### 4.2. Временное хранение кадра при выборе товара (уточнение D-10, подтверждено владельцем 2026-11-06)

Если в кадре несколько товаров, покупатель выбирает нужный. Кадр нужен до выбора, и он хранится **только в оперативной памяти
сервера**. Выбор делается **без повторной передачи фото**: телефон присылает только номер рамки. Обязательные условия:

| Условие | Как обеспечивается (при реализации) |
|---|---|
| Фото **не записывается на диск** | кадр — объект в памяти процесса (байты нормализованного изображения); никаких временных файлов, файлов подкачки приложения и журналов с содержимым кадра. Обработка в Desktop идёт напрямую, без очереди и без брокера, поэтому кадр не попадает в Redis или базу. *Оговорка:* при нехватке памяти операционная система может сбросить часть памяти процесса в файл подкачки Windows; приложение этим не управляет. Шифрование диска (BitLocker) снижает этот риск |
| Удаляется **сразу после выбора** | обработчик выбора удаляет запись до отправки ответа |
| Удаляется **после отмены** | `DELETE …/identify/{frame_id}`; закрытие страницы тоже отправляет отмену (если браузер успеет) |
| Удаляется **через 2 минуты** автоматически | хранилище с ограничением времени жизни; фоновая очистка не реже раза в 10 секунд; при обращении к просроченному кадру — ответ «Кадр устарел, сфотографируйте ещё раз» |
| **Не попадает в резервные копии** | копии делаются из базы и файлов; кадров там нет по построению |
| **Не восстанавливается после перезапуска** | хранилище только в памяти; после перезапуска всех кадров нет |
| **Нет постоянной истории фото** | в историю пишутся только данные из раздела 4.1 |
| Ограничение объёма | не больше N кадров одновременно (например, 50; по замеру); при переполнении — отказ «система занята», старые кадры не вытесняют новые без уведомления |
| Идентификатор кадра | случайный и неугадываемый; связан с публичным входом; чужой кадр по идентификатору выбрать нельзя |

Текущий Docker-профиль работает иначе: API передаёт кадр воркеру через **временный файл** (`data/identify-tmp`, удаляется после
задачи, «забытые» чистятся через 15 минут). Это допустимо для одиночного распознавания в разработке, но **не соответствует
условию «не записывается на диск»** для выбора из нескольких товаров. Поэтому выбор товара реализуется на прямом вызове в процессе
API (как в Desktop, документ 08, §5), а не через очередь с файлом.

### 4.3. Будущая добровольная функция «сохранять фото для улучшения»

Включает только владелец. Для покупателей на странице появляется заметное уведомление («фото сохраняются на N дней для улучшения
распознавания»). Лица маскируются до записи (`privacy.py`). Срок хранения ограничен, есть удаление отдельного фото и «удалить все».
Такие фото **не попадают в резервные копии** (или копии хранятся не дольше этого срока): иначе удалённые фото продолжали бы жить
в старых копиях дольше обещанного срока.

## 5. Вход сотрудника с телефона

- «Настройки → Войти как администратор» → `POST /api/v1/auth/login` (уже есть) → интерфейс показывает разделы по `permissions`
  из `/auth/me` (уже есть).
- Кнопки скрываются **только для удобства**. Каждое действие проверяет сервер (уже так: `require_permission`).
- Временный пароль → обязательная смена при первом входе (документ 05).
- **Где доступен вход:** на служебном входе (раздел 3.5) — с компьютера магазина всегда; с телефонов сотрудников — только из сети
  сотрудников, если владелец это разрешит (D-08). **Из гостевой сети покупателей входа нет:** по HTTP пароль и токен шли бы
  по Wi-Fi в открытом виде.
- **Доверенное устройство не заменяет HTTPS (1.10).** На первом этапе доверенным может быть только компьютер магазина; телефоны сотрудников
  входят как обычные незарегистрированные устройства (документ 05, §12.12). Регистрация устройства не шифрует трафик и не защищает от
  перехвата и подмены: пока вход с телефона идёт по HTTP, пароль и токен в сети сотрудников передаются открытым текстом. Защита канала —
  отдельная задача (HTTPS, §3.3 В и §3.4; отдельная сеть сотрудников; решение D-08).

## 6. Сеть Wi-Fi для покупателей (В-5, решение владельца 2026-11-06)

**Предпочтительный вариант:** отдельная гостевая сеть Wi-Fi для покупателей с доступом только к необходимому интерфейсу приложения.

Модель роутера **не подтверждена**: предположений о его возможностях не делаем, сетевые настройки не меняем. Если гостевая сеть
полностью изолирована от сервера, QR работать не будет. Тогда нужна либо настройка роутера (разрешить гостям доступ к одному
адресу и порту), либо другое оборудование — решение владельца после проверки роутера.

Требования и меры:

| Требование владельца | Меры |
|---|---|
| PostgreSQL и Redis недоступны покупателям | слушают только `127.0.0.1` (в Docker уже так: порты `127.0.0.1:…`; в Desktop — обязательно); брандмауэр Windows закрывает их снаружи; проверка из гостевой сети (раздел 3.7) |
| Административные функции недоступны без авторизации | их нет на публичном входе (раздел 3.5); на служебном — вход по паролю и проверка прав на сервере для каждого действия |
| Ограничение доступа к локальному серверу | из гостевой сети разрешён только публичный порт (правило роутера, если поддерживается, плюс брандмауэр Windows); остальные порты компьютера закрыты |
| Защита от перебора паролей и чрезмерного числа запросов | вход сотрудников недоступен из гостевой сети; на служебном входе — ограничение неудачных попыток (хранить в базе, документ 05, §14); на публичном входе — лимиты по IP и общий лимит распознаваний (документ 10) |
| Распознавание через QR сохраняется | гостевая сеть должна иметь доступ к адресу и порту из QR; проверка перед печатью (раздел 3.7) |

### Риски локальной сети

Локальная сеть **не безопасна автоматически**:

| Риск | Что может случиться | Меры |
|---|---|---|
| Покупатели в одной сети с компьютером магазина | любое устройство в сети может сканировать порты компьютера и атаковать открытые службы | гостевая сеть; брандмауэр: снаружи открыт только публичный порт; PostgreSQL и Redis — только `127.0.0.1` |
| Перехват трафика по HTTP | в общей Wi-Fi сети трафик соседей можно подсмотреть (ARP-спуфинг, перехват рукопожатия WPA2-PSK) | через публичный вход идут только кадры товаров и карточки (паролей там нет); вход сотрудников — не из гостевой сети; в будущем HTTPS |
| Полная изоляция гостевой сети | QR «не работает» | разрешить гостям доступ к одному адресу и порту, если роутер умеет; иначе — решение владельца |
| Злоупотребление распознаванием | поток запросов загружает систему | лимиты по IP, общий семафор, очередь с ограничением, отказ с понятным сообщением |
| Загрузка вредных файлов | попытка уронить декодер изображений | уже: пересохранение через Pillow, лимит пикселей и размера, отказ от неизвестных форматов |
| Сбор каталога и цен | выгрузка всех карточек | цены и так публичны в магазине; поиск — с лимитом и без постраничной выгрузки |
| Компьютер магазина — ценная цель | на нём база сотрудников и резервные копии | отдельная учётная запись Windows, обновления ОС, резервные копии на другом носителе, пароль базы — не стандартный (документ 10) |

## 7. Универсальная платформа: влияние на мобильный доступ (добавлено в 1.3)

- **QR у каждого магазина свой:** путь `/s/<код магазина>` (§3.4) уже рассчитан на несколько магазинов. В сети каждый узел печатает
  QR своего адреса, а в облачном центре один адрес может обслуживать много магазинов по коду в пути. Решение D-07 не меняется.
- **ИИ-помощника на публичном входе нет** и не будет (документ 16, §5). Покупатель видит только распознавание и публичные карточки.
- **Карточка для покупателя строится из схемы категории** (документ 06, §5): у продукта — состав и аллергены, у одежды — материал
  и размеры, у ноутбука — характеристики. Публичный API отдаёт только характеристики с `is_public`.
- **Лимиты публичного входа** в сети считаются и по магазину (документ 17, §4.7): один магазин не должен отнимать ресурсы у других.
