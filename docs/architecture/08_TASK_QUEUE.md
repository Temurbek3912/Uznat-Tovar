# 08. Очередь фоновых задач

## 1. Что есть сейчас

Celery 5 + Redis 7 (брокер и результаты), один воркер с `--concurrency=1` (`app/worker.py`). Задачи: добавление товара,
добавление фото, распознавание. Повторы `max_retries=3`, `acks_late`, Redis с `appendonly`. API ждёт результат распознавания
синхронно до 25 секунд.

**Утверждено:** для Docker Compose (разработка и сервер) Celery и Redis сохраняются. Для Desktop нужна отдельная очередь без
обязательного Redis. Нельзя заменять Celery простыми фоновыми потоками или `BackgroundTasks` FastAPI без анализа надёжности.

## 2. Почему Celery и Redis не переносятся в Desktop

- **Celery:** проект не поддерживает Windows официально. На Windows работает только с ограничениями (пул `solo` или потоки),
  и проблемы там не считаются ошибками проекта. Точную формулировку проверить в актуальном FAQ Celery перед окончательным решением.
- **Redis:** официальной нативной сборки для Windows нет. Redis рекомендует Memurai Enterprise — совместимый порт, бесплатный
  90 дней пробного периода, дальше условия у поставщика ([redis.io](https://redis.io/blog/use-redis-natively-on-windows-with-memurai)).
  Это противоречит принципу «без сторонних платных зависимостей». WSL или Docker противоречат требованию «без Docker».
- В Desktop один процесс backend (документ 02): брокер между двумя процессами одного компьютера не нужен.

## 3. Какие задачи нужны и требования к ним

| Задача | Длительность | Нужна надёжность? | Где выполнять в Desktop |
|---|---|---|---|
| Распознавание кадра | доли секунды – секунды | **нет**: кадр устаревает через секунды, при сбое человек просто повторит | **напрямую в запросе**, с семафором (ограничение одновременных) и таймаутом — без очереди. Кадр не попадает ни в очередь, ни на диск (D-10, документ 04, §4.2) |
| Индексация фото товара | секунды на фото | **да**: товар без векторов не распознаётся | надёжная очередь |
| Импорт каталога (таблица или папка) | минуты | да | надёжная очередь |
| Пересборка индекса | секунды – минуты | да | надёжная очередь |
| Резервная копия по расписанию | минуты | да | надёжная очередь + планировщик |
| Экспорт каталога | секунды | желательно | надёжная очередь |
| Очистка старой истории (30–90 дней) | секунды | нет (идемпотентно) | планировщик |

Требования к надёжной очереди (из задания):

1. Работает на Windows.
2. Переживает перезапуск приложения (задания хранятся на диске, в базе).
3. Не теряет важные задания (запись в той же транзакции, что и данные, если возможно).
4. Повторы с задержкой и пределом попыток; после предела — статус «ошибка», видимый владельцу.
5. Защита от дублирования: ключ идемпотентности, повторная постановка того же задания не создаёт второе.
6. Отслеживание состояния: «в очереди / выполняется / готово / ошибка», процент для долгих задач (для интерфейса).
7. Без Redis.
8. Один писатель индекса: задачи, меняющие индекс, выполняются последовательно.
9. Восстановление после аварии: задание, «зависшее» в состоянии «выполняется» после сбоя, возвращается в очередь по истечении аренды.

## 5. Рекомендация

1. Ввести в коде **интерфейс** `TaskQueue` (поставить задание, узнать статус, отменить) и вынести тела задач в обычные функции
   без зависимости от Celery. Celery-задачи в `app/worker.py` становятся тонкими обёртками. Поведение в Docker не меняется,
   а тесты могут работать на локальной реализации.
2. Для Desktop — **очередь на таблице заданий в базе приложения** (рекомендовано), со схемой:

```text
jobs (id UUID, kind, payload JSON, idempotency_key UNIQUE, status ('queued'|'running'|'done'|'failed'|'cancelled'),
      attempts, max_attempts, next_run_at, lease_until, worker_id, progress, error_message, result JSON,
      created_at, updated_at, created_by)
```

   - Выборка: PostgreSQL — `SELECT … FOR UPDATE SKIP LOCKED`; SQLite — один обработчик и короткая транзакция.
   - Задание ставится **в той же транзакции**, что и данные (товар, записи фото). Либо всё сохранилось, либо ничего. Это закрывает
     нынешний риск «товар есть, индексации нет».
   - Аренда (`lease_until`): после сбоя «зависшее» задание возвращается в очередь.
   - Повторы с растущей задержкой, `max_attempts`, затем `failed` с понятным текстом (показывается в разделе «Состояние системы»).
   - Ключи идемпотентности: `index_image:<image_id>:<model_version>`, `import:<sha256 файла>`, `backup:<дата-слот>`.
   - Один поток-обработчик для заданий, меняющих индекс.
3. **Альтернатива:** Procrastinate, если PostgreSQL окончательно остаётся и в Desktop (решение после прототипа). Отказ от неё
   оправдан только сохранением возможности SQLite и транзакционной постановкой.
4. Распознавание в Desktop вызывается **напрямую**, без очереди: семафор на число одновременных распознаваний (по умолчанию 1–2
   на GPU), очередь ожидания с пределом и понятный ответ «система занята, повторите» при переполнении.

**Требует решения:** D-04 (своя таблица или Procrastinate) — после прототипа Desktop и выбора базы (D-02).

## 6. Тесты, без которых очередь не принимается

- перезапуск процесса во время задания → задание завершается после перезапуска ровно один раз;
- одно и то же задание поставлено дважды → выполнено один раз;
- ошибка в задании → повторы с задержкой → `failed` с текстом;
- откат транзакции данных → задания нет;
- два обработчика (для PostgreSQL) → каждое задание взято одним;
- задания, меняющие индекс, не выполняются параллельно.

## 7. Универсальная платформа: влияние на очередь (добавлено в 1.3)

- **Приоритеты:** интерактивное распознавание не ставится в очередь (§3). Фоновые задачи делятся на классы: индексация и импорт,
  отчёты и экспорт, резервные копии, **операции ИИ-помощника** (массовые изменения — как обычные задания: подготовка во временной
  области и одно атомарное применение, документ 05, §13.1; документ 16, §8).
- В схеме `jobs` предусмотреть `store_id` (чей магазин) и `kind`-класс приоритета. В узле магазина это почти ничего не меняет,
  а в центре сети нужно для **справедливости между магазинами**: квоты, чтобы тяжёлый импорт одного магазина не задерживал другие
  (документ 17, §4.5).
- В центре сети (профиль Server) — Celery и Redis с раздельными очередями по классам. Решение D-04 для узла не меняется.

### 7.1. Уточнение 1.4: запросы ИИ — своя очередь с низшим приоритетом

Запросы к языковой модели идут через **отдельную очередь** с ограничением одновременности (по умолчанию 1 на GPU) и допуском по нагрузке:
при росте времени распознавания запросы ИИ ждут или переходят на запасной путь (CPU, облако по согласию владельца). Распознавание
и задания каталога эту очередь не ждут (документ 16, §10.1). Выполнение подтверждённых планов помощника — обычные задания `jobs`
с ключом идемпотентности и атомарным применением (документ 05, §13.1).

### 7.2. Уточнение 1.6–1.8: задания, права, атомарное применение и передача

- `initiated_by` — пользователь, начавший задание (не меняется никогда); `executor_id` — от чьего имени оно сейчас выполняется; `system` —
  для системных заданий (резервная копия по расписанию, пересборка индекса, диагностика, очистка по срокам).
- **Изменения данных от имени сотрудника** (импорт каталога, импорт цен, массовое изменение, план ИИ) выполняются в два этапа (1.8):
  **подготовка** во временной области (`staging_rows`, `staged_files`; может идти частями, рабочие данные не меняются) и **применение одной
  транзакцией**: блокировка строки исполнителя на чтение и проверка прав → проверка версий записей → применение набором → журнал → задания
  индексации → одна фиксация. Отзыв доступа меняет ту же строку с блокировкой на запись, поэтому импорт либо применён целиком до отзыва,
  либо не применён вовсе; частично применённого импорта не бывает (документ 05, §13.1). Это заменяет описание 1.7 «проверка перед каждой
  партией, выполненные партии остаются».
- Предел строк на одну атомарную операцию — настройка (предложение 20 000, **оценка**, испытание Т-10); больше — явное деление на отдельные импорты.
- Остановленное задание не продолжается само; принять его может только сотрудник с `jobs.takeover` и правами на действие, явно, с новым
  предпросмотром; передачи — в `job_handovers` (документ 05, §13.2).
- Статусы задания изменений: `prepared` → `applying` → `applied` | `stopped` (`stop_reason`) | `expired`.
- **Фото и файлы (1.9, уточнено в 1.10):** файл записывается в основное хранилище и проверяется **до** транзакции, которая на него ссылается:
  запись о намерении `staged_files` (`writing`) → временный файл (с `FILE_FLAG_WRITE_THROUGH` или `fsync`) → переименование в имя по SHA-256 →
  повторное чтение и проверка хеша (`stored`); транзакция применения проверяет, что все фото `stored`. На Windows `fsync` и переименование
  **не дают документированной гарантии** сохранности после отключения питания, поэтому исходный файл задания хранится 24 часа после применения.
  **При запуске после нештатного завершения** до состояния «готово»: разбор записей `writing`, пересчёт хешей файлов, на которые сослались за
  последние 24 часа, восстановление из исходных файлов заданий; затем возврат в очередь заданий с истёкшей арендой. Очистка и проверка
  хранилища — системные задания с низким приоритетом (документ 05, §13.3).
- Системные задания от прав отдельных сотрудников не зависят.
- Результат (файл экспорта) выдаётся только тому, у кого право есть в момент скачивания.

## 8. Рабочая копия 2026-11-07: доставка заданий индексации без outbox

**Вопрос.** Товар записан в базу, процесс погиб до сохранения векторов, задача очереди потеряна. Как система это обнаружит и
восстановит?

**Решение — восстановление по состоянию, а не по журналу заданий.**
- Задание «проиндексировать фото товара» не нужно хранить отдельно: его можно **вычислить** из долговечного состояния.
  - Товары берутся из базы.
  - Фото — из файлов `data/catalog-uploads/`.
  - Что уже проиндексировано, говорит сам индекс: у каждого вектора записано его фото (`app/services/index_coverage.py`).
- Задача воркера `recover_index` ставится при **каждом** запуске воркера (сигнал `worker_ready`). Она добавляет векторы фото,
  у которых их нет, партиями по 200. Задача ставит себя снова, только если есть и остаток, и продвижение: непригодные фото
  её не зацикливают.
- Повтор безопасен: дублей товаров нет (артикул уникален в базе), дублей векторов нет (решает индекс).

**Почему не transactional outbox.** Outbox гарантирует доставку задания, записанного в той же транзакции, что и данные. Здесь
задание полностью выводится из данных, поэтому отдельная таблица заданий ничего не добавляет: она тоже потребовала бы
сверки при сбое между отметкой «выполнено» и сохранением индекса. Кроме того:
- API не пишет товар до постановки задачи (товар создаёт задача воркера), и разрыва «товар в базе — задачи нет» на стороне
  API нет;
- если очередь недоступна при добавлении фото, пользователь получает 503, а уже сохранённые фото подхватит `recover_index`.

**Ограничения:**
- восстанавливаются только фото, лежащие в `data/catalog-uploads/`. Товар без фото (добавлен по ссылкам, фото удалены)
  восстановить нечем — он виден в отчёте `scripts/reconcile_index.py`, нужны новые фото;
- `recover_index` выполняется при запуске воркера, а не по расписанию. Расписание (Celery beat) не используется: задачи с
  отложенным запуском дольше `visibility_timeout` Redis выдаются повторно и размножаются. При необходимости — вручную
  `scripts/reindex_uploads.py --apply`;
- в Desktop без Celery та же функция `recover_pending` должна вызываться при запуске приложения (этап 7).
