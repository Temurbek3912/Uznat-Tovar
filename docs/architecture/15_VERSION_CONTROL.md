# 15. Контроль версий кода (Git)

**Решение D-15 (предварительно принято владельцем 2026-11-06):** внедрить Git. Сначала достаточно **локального** репозитория;
GitHub и другие облачные сервисы не обязательны. Перед внедрением — проверить текущее состояние файлов и сохранить резервную копию.

**Это план, а не выполненное действие.** На 2026-11-06 разрешены только чтение, анализ и изменение документации: Git не
устанавливался, репозиторий не создавался, `.gitignore` не менялся.

## 1. Зачем

- Сейчас изменения приходят архивами и `apply_update.py`. Уже были путаница версий и конфликты (выпуск 2026-11-01b, папка копии
  внутри проекта, из-за которой pytest находил лишние тесты).
- Git записывает каждое изменение: что, когда и зачем поменялось. Любой файл или весь проект можно вернуть к проверенному состоянию.
- Git **не заменяет** резервные копии данных: база, фото, индекс и модели в Git не хранятся (документ 09).

### 3.1. Контрольный список исключений (проверить до первого коммита — требование владельца)

Перед внедрением сохранить резервную копию проекта и **особенно внимательно** проверить исключения. После `git init` и дополнения
`.gitignore` выполнить `git status --ignored` и `git check-ignore -v <путь>` для каждого пункта:

| Что должно быть исключено | Пример пути | Чем исключается | Как проверить |
|---|---|---|---|
| Модели и веса в любых подпапках | `models/detector/sku110k_yolo11n.pt` | `models/**/*.pt` (новое правило) | `git check-ignore -v models/detector/sku110k_yolo11n.pt` должен показать правило |
| Будущие веса эмбеддера | `models/embedder/…` | `models/embedder/` | то же |
| Индексы каталога | `models/index/catalog.faiss`, `catalog.faiss.ids.json` | `models/index/` | то же |
| Секреты | `.env` (сейчас отсутствует; может появиться) | `.env` (уже есть) | создать пустой пробный `.env` **не нужно** — проверить командой `git check-ignore -v .env` |
| Пользовательские данные | `data/…` (фото каталога, временные кадры) | `data/` (уже есть) | `git check-ignore -v data/catalog-uploads/x.jpg` |
| Временные файлы распознавания | `data/identify-tmp/…` | `data/` | то же |
| Журналы | `logs/…`, `docker-build.log` | `logs/`, `*.log` (новое) | `git check-ignore -v docker-build.log` |
| Кэши | `__pycache__/`, `.pytest_cache/` | уже есть | `git status` не показывает их |
| Виртуальное окружение | `.venv/` | уже есть | то же |
| Файлы конфликтов обновления | `*.from_update` | новое правило | — |
| Резервные копии | `backups/` (и любые копии — только вне проекта) | уже есть | — |

Если хотя бы один пункт **не** исключён — коммит не делать, сначала поправить `.gitignore`.

## 4. Порядок внедрения (когда владелец разрешит)

Рекомендуемый порядок: **сначала зафиксировать то, что есть, затем применить выпуск**. Тогда в истории будет видно, что именно
изменила уборка аудита, и её можно откатить одной командой.

1. **Резервная копия проекта** вне проекта (как в инструкции выпуска): `robocopy D:\retail-shelf-audit D:\retail-shelf-audit_copy_<дата> /E /XD .venv data ...`.
   Копия базы от 2026-11-03 уже есть; база при внедрении Git не меняется.
2. **Проверить, установлен ли Git для Windows:** `git --version`. Если нет — установить с официального сайта git-scm.com
   (бесплатно; это установка программы, **требует согласия владельца**).
3. Один раз указать имя для записей (только локально, никуда не отправляется): `git config --global user.name "Имя"` и
   `git config --global user.email "почта или любой адрес"`.
4. В папке проекта: `git init -b main`.
5. Дополнить `.gitignore` (раздел 3) — это первое изменение файла проекта в рамках D-15.
6. `git status` — **проверить список**: в нём не должно быть `.venv`, `data`, `.env`, весов, журналов. Прислать список разработчику.
7. `git add -A` → `git commit -m "Контрольная точка 2026-11-02 (до уборки аудита)"` → `git tag checkpoint-2026-11-02`.
8. Применить выпуск 2026-11-06b (`apply_update.py`), прогнать `pytest`, затем `git add -A` →
   `git commit -m "Выпуск 2026-11-06b: уборка аудита + архитектура"` → `git tag release-2026-11-06b`.
9. Копия репозитория одним файлом вне проекта: `git bundle create D:\backups_retail\repo-<дата>.bundle --all`.

## 5. Ежедневная работа после внедрения

- Перед любым обновлением: `git status` — изменений быть не должно (иначе сначала сохранить или выяснить, откуда они).
- После обновления и зелёного `pytest`: коммит с понятным сообщением и метка (`git tag`).
- Вернуть один файл к последнему коммиту: `git restore <файл>`. Посмотреть, что изменилось: `git diff`, история: `git log --oneline`.
- **Запрещённые команды** (могут удалить данные или работу):
  - `git clean -x` и `git clean -fdx` — удаляют **игнорируемые** файлы, то есть `data/`, `.venv`, `.env`, модели;
  - `git reset --hard` и `git checkout -- .` без проверки — стирают несохранённые изменения;
  - `git push --force` (когда появится удалённый репозиторий).
- Раз в неделю или после выпуска — новый `git bundle` во внешнюю папку копий.

## 6. Как это меняет поставку изменений

- Пока выпуски идут архивами, `apply_update.py` остаётся. После применения — коммит, и история становится полной.
- Позже изменения можно передавать как патчи Git (`git am` / `git apply --check`): та же проверка «применяется ли без конфликтов»,
  но стандартными средствами. Это отдельное решение после внедрения.
- Удалённый репозиторий (GitHub, свой сервер) — не нужен сейчас. Если понадобится, он должен быть **приватным**, без данных и весов.

## 7. Риски внедрения

| Риск | Мера |
|---|---|
| В первый коммит попадут лишние файлы (веса, данные, секреты) | шаг 6: проверка `git status` до коммита; дополнение `.gitignore` |
| Окончания строк «изменятся» на Windows | `.gitattributes` уже закрепляет нужные окончания; первые изменения проверить `git diff --stat` |
