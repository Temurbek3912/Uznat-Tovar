## 0. Главное коротко

1. **Ошибка в статусах (критично).** Документ решений называет «уже утверждённым» то, что утверждения не имеет.
   - Пакет 07.11 привязан к подэтапу 0Г. По генеральному плану 0Г — это **выпуск 11-06b**, и он требует отдельного согласования.
   - Р-7 и Р-16 не утверждены. Р-1 и Р-7 в порядке работ названы «исполнением принятого».
2. **D-10а не выполнено и быстрыми мерами Р-4(1) выполнено не будет.** Код хуже, чем описано в документе решений:
   - забытый кадр живёт 15 минут, а не 2;
   - при таймауте API не удаляет кадр;
   - задание без срока годности выполняется после перезапуска воркера;
   - разбор `multipart` не ограничивает размер файла до записи на диск.
3. **Порядок работ (раздел 9) опасен в двух местах.**
   - Пропущен этап 2А — проверенная резервная копия перед изменением схемы.
   - В этап 2Б положены сразу три крупные переделки: Alembic, `product_images`, цена. Это противоречит П-2.
4. **Оценки памяти и времени занижены, часть цифр ошибочна.** Ошибки мои:
   - пик загрузки индекса — вероятно ≈700 МиБ, а не ≈470;
   - поиск — ≈16 мс (облачный замер на numpy), а не «единицы мс»;
   - выигрыш Р-6а «10–50 мс» ничем не обоснован;
   - «float16 — потеря ~10⁻³» неточно.
5. **Лицензии.** Условия датасета SKU-110K найдены (по зеркалу исходного репозитория): **«solely for academic and non-commercial purposes»**.
   Вместе с позицией Ultralytics о весах (AGPL) это серьёзный вопрос для коммерческого выпуска. Юридического вывода я не делаю.
6. **Цена `NUMERIC(12,2)`.** Формулировка «float64 точно хранит суммы» неверна. Опыт на PostgreSQL 16 показал:
   - `NaN` проходит молча;
   - знаки после второго округляются;
   - слишком большие значения обрывают миграцию;
   - меняется формат цены в API.
   Тип цены нельзя выбирать до решения D-02 (SQLite не хранит `NUMERIC` точно).
7. **Прямая генерация узбекской кириллицы попала в «не рекомендуется» без опыта.** Это нарушает мой же П-1. Транслитерация тоже не
   безошибочна: русские заимствования пишутся иначе (`aksiya` → «акция», `oktabr` → «октябрь»). Нужен сравнительный опыт (раздел 6).

## 1. Проверка А. Приватность D-10а

**Текст D-10а** (документ 14, §2.2): «Кадр при выборе товара хранится только в оперативной памяти до 2 минут: не пишется на диск;

Документ решений опустил две вещи из этого текста:
- **2 минуты**;
- **выбор товара без повторной передачи фото** — кадр должен жить в памяти между запросами.

### А-2. Поднять порог буфера до 12 МБ

| Поле | Содержание |
|---|---|
| Пункт | Раздел 5 (мера), Р-4(1) |
| Текущая формулировка | «принимать кадр телом запроса (`application/octet-stream`) с пределом размера или поднять порог буфера выше предела кадра (12 МБ)» |
| Проблема | (1) Предел кадра в коде — **10 МБ**, а не 12. (2) В Starlette 1.7.0 порог — атрибут **класса**, отдельного параметра на запрос нет. Изменение действует на все маршруты с `multipart`, в том числе на добавление товара: до 8 фото × 25 МБ. (3) **Разбор не ограничивает размер файловой части.** `_read_limited` проверяет размер уже после того, как Starlette приняла всё тело: гигабайтный запрос сначала целиком ляжет на диск (или в память при поднятом пороге) и только потом получит 413. Это и приватность, и отказ в обслуживании. (4) Память на запрос определяет не буфер, а раскрытие изображения: при `MAX_PIXELS = 60 000 000` массив RGB занимает до ≈180 МБ, вероятная копия — ещё столько же. Число одновременных разборов ничем не ограничено |
| Доказательство | [код] `IDENTIFY_MAX_MB = 10` (`routes_catalog.py:44`); `max_upload_mb = 25` (`config.py`); `MAX_PHOTOS_PER_REQUEST = 8`; `MAX_PIXELS = 60_000_000` (`catalog_upload.py:38`); `_read_limited` читает `upload.file` после разбора. [код] Starlette 1.7.0: `max_part_size` действует только на нефайловые поля. [расчёт] 60 млн × 3 Б = 180 МБ |
| Уверенность | (1)–(3) — **подтверждено** (код); (4) — **вероятно** (расчёт, копия при `load_rgb` не измерена) |
| Исправление | Обязательные меры: (а) кадр — **тело запроса** `application/octet-stream` в асинхронном маршруте, чтение потоком со счётчиком и жёстким пределом 10 МБ — превышение обрывает запрос до записи куда-либо; (б) общий предел размера тела для всех маршрутов (промежуточный слой по `Content-Length` и по фактическому счёту байтов); (в) ограничение одновременных распознаваний (семафор, например 2–4) с ответом «занято»; (г) для кадра — свой предел пикселей ниже 60 Мп. Поднимать порог Starlette не нужно. Память: N одновременных × (10 МБ + до 360 МБ раскрытия) [расчёт] |
| Нужно ли решение владельца | Нет — техническая часть D-10а |

### А-3. Защищает ли `tmpfs` в Docker Desktop

| Поле | Содержание |
|---|---|
| Пункт | Р-4(1), раздел 5 (звенья «Windows-хост», «Память») |
| Текущая формулировка | «`tmpfs` в контейнере убирает файлы с диска Windows» |
| Проблема | Убирает **файлы в файловой системе Windows** — и только их. Это реальное снижение риска: теневые копии, OneDrive, «История файлов» и копия 0Б больше не видят кадры. Отсутствия записи на диск `tmpfs` **не гарантирует**: (1) память ВМ WSL может уходить в её файл подкачки `swap.vhdx` на диске Windows (по умолчанию 25 % памяти); (2) гибернация, аварийные дампы Windows и подкачка самой Windows для памяти ВМ — не проверено; (3) файл на `tmpfs` переживает сбой процесса и лежит до перезапуска контейнера; (4) `tmpfs` расходует память контейнера и ВМ, нужен `size=`. По риску `tmpfs` равен «кадру в памяти процесса» (R-19), но это **файл**: без уборки он не удалится через 2 минуты |
| Доказательство | [вторичный] описание `.wslconfig`: `swap` по умолчанию 25 % памяти, `swapFile` в `%USERPROFILE%\AppData\Local\Temp\...\swap.vhdx`. Документация Microsoft в этой сессии не открылась. Docker Desktop не запускался |
| Уверенность | п. 1, 3, 4 — **вероятно**; п. 2 — **неизвестно** |
| Исправление | «`tmpfs` убирает кадры из файловой системы Windows, копий и синхронизации. От подкачки ВМ, гибернации и дампов он не защищает: это тот же остаточный риск, что R-19. Нужен вместе с уборкой (А-4). Это временная мера, а не выполнение D-10а» |
| Нужно ли решение владельца | Да — принять ли R-19 (подкачка, гибернация, дампы) как допустимый остаток при толковании D-10а (см. А-6) |

### А-4. Достаточно ли удаления по таймеру в воркере

| Поле | Содержание |
|---|---|
| Пункт | Р-4(1) («удаление по таймеру в воркере»); раздел 5 («по таймеру в воркере и при старте») |
| Текущая формулировка | Удаление забытых кадров по таймеру в воркере |
| Проблема | Недостаточно, и документ решений не заметил трёх фактов кода. (1) **Кадр пишет API, а не воркер.** При таймауте `task.get` (воркер остановлен или занят) API отвечает 504 и **кадр не удаляет**. (2) У задания распознавания **нет срока годности** (`expires`). При `task_acks_late=True` оно лежит в Redis и выполнится после запуска воркера — когда клиент давно ушёл. Накопленные устаревшие задания задерживают новые. (3) Уборка вызывается только при следующем `/identify`, и только для файлов **старше 15 минут** (`IDENTIFY_KEEP_SECONDS = 900`), а D-10а разрешает 2 минуты. Таймер в остановленном воркере не сработает вовсе |
| Доказательство | [код] `routes_catalog.py:479–497`: `sweep_old_files` перед записью, нет `finally` с удалением после `task.get`; `IDENTIFY_KEEP_SECONDS = 900`; `worker.py:40` `task_acks_late=True`; `delay(ref)` без `expires` |
| Уверенность | **Подтверждено** (статически, не запускалось) |
| Исправление | Уборкой владеет тот, кто пишет: (а) API удаляет свой кадр в `finally` после ожидания при любом исходе — воркер, не нашедший файла, быстро завершает задание ошибкой; (б) задание с `expires` ≈ время ожидания; (в) уборка при старте API и периодически в API, а также при старте воркера; (г) срок жизни ≤ 120 с. Это малые изменения в нынешней схеме, без новой архитектуры |
| Нужно ли решение владельца | Нет (исполнение D-10а), но внедрение — отдельным разрешением, как всегда |

|---|---|
| Пункт | Р-6а, раздел 5 («Окончательно») |
| Текущая формулировка | «отдельный процесс распознавания: API передаёт байты по локальному соединению… кадр в памяти» |
| Проблема | Гарантия возможна только для **уровня приложения** и только при условиях, которых в документе решений нет. Весь путь кадра: телефон → Wi-Fi → (будущий обратный прокси для HTTPS, Р-15) → uvicorn → разбор тела → API → межпроцессная передача → процесс модели → журналы. (6) **Дампы памяти при падении** (torch, нативный код) могут содержать кадр — в контейнере `ulimit core=0`. (7) **Подкачка и гибернация** ОС — неустранимый остаток (R-19) |

| Уверенность | **Вероятно** (разбор устройства; ничего не запускалось) |
| Исправление | «Отдельный процесс гарантирует отсутствие записи кадра приложением при условиях (2)–(6). Не гарантирует отсутствие записи на уровне ОС (R-19). Пункты (1)–(6) — критерии приёмки Р-6а» |

### А-7. Удаление файла — не стирание

| Поле | Содержание |
|---|---|
| Пункт | Раздел 5, Р-4 |
| Текущая формулировка | «удаление по таймеру» как мера для D-10а |
| Проблема | Удалённый файл освобождает блоки, но данные в них остаются до перезаписи — на ext4 внутри диска ВМ, на NTFS, на SSD. `SpooledTemporaryFile` при переполнении создаёт безымянный файл, но байты всё равно пишутся на диск. Поэтому уборка сокращает **срок видимости** кадра, но не делает кадр, однажды записанный на диск, соответствующим «не пишется на диск» |
| Доказательство | Общее устройство файловых систем; доходит ли TRIM через `vhdx` до SSD — не проверялось |
| Уверенность | Остаток данных после удаления — **подтверждено** (устройство ФС); TRIM через `vhdx` — **неизвестно** |
| Исправление | Добавить в раздел 5: «Удаление уменьшает риск, но не превращает запись на диск в соответствие D-10а. Соответствие даёт только отсутствие записи» |
| Нужно ли решение владельца | Нет |

### А-8. Статус D-10 и D-10а в исходных документах

## 5. Проверка Д. База и миграции

### Д-1. `float` → `NUMERIC(12,2)`: безопасность и «точное сохранение»

| Поле | Содержание |
|---|---|
| Пункт | Р-9, «Переход» |
| Текущая формулировка | «значения до копейки сохраняются: `float64` точно хранит суммы до 15 значащих цифр» |
| Проблема | **Формулировка неверна.** `float64` не хранит точно даже 0,1. Верно другое: десятичное число не длиннее 15 значащих цифр переживает путь «десятичное → `float64` → десятичное». Опыт на PostgreSQL 16 (приведение `float8` → `NUMERIC(12,2)`): 9900.1 → 9900.10; 0.1+0.2 → 0.30; 12.345 → 12.35; 12.355 → 12.36; 1999.995 → 2000.00; 99 999 999.99 — без потерь; **`NaN` → `NaN` (проходит молча)**; `Infinity` → ошибка «cannot hold an infinite value»; 1e10 → ошибка переполнения (у `NUMERIC(12,2)` наибольшее значение 9 999 999 999.99). Итого: суммы с ≤2 знаками сохраняются; с большим числом знаков — молча округляются; `NaN` переносится в базу и сломает API; бесконечность и большие числа обрывают миграцию |
| Доказательство | [облако-PG16] опыт приведения (значения выше); база владельца не проверялась |
| Уверенность | **Подтверждено** на PostgreSQL 16 в облаке; данные владельца — **неизвестно** |
| Исправление | «Перед миграцией — отчёт на копии: `NaN`, бесконечности, значения ≥10¹⁰, значения с >2 знаками, отрицательные. Каждую группу владелец решает явно. Только после этого — приведение» |
| Нужно ли решение владельца | Да — что делать с найденными группами (после отчёта) |

### Е-2. Неоднозначности транслитерации латиница → кириллица

| Пункт | Раздел 7, «Известные трудности транслитерации» |

### 9.2. Важные замечания
1. **Б-4.** Пики памяти FAISS занижены (вероятно ≈700/≈940 МиБ на процесс); расчёт помечен как «статически».

   - нет правила «не удалять файл при неизвестном исходе фиксации»;
