# 05. Пользователи, роли и разрешения

> **Версия 1.6** (требования владельца от 2026-11-06): полноценное управление доступом на основе ролей (RBAC): отдельные разрешения,
> собственные роли владельца, стартовые шаблоны, область действия, правила приоритета и запрета, защита от повышения полномочий
> (§3–§11). Учётные записи сотрудников создаёт и ведёт владелец: временные пароли, обязательная смена, блокировка, отзыв доступа
> (§12–§14). ИИ-помощник подчиняется тем же правилам (§15). Журнал (§16), интерфейс (§17), этапы (§19).
> **Изменение по сравнению с 1.2–1.5:** раньше шаблоны были «только удобством при создании», а права хранились у каждого
> пользователя по отдельности. Теперь **роль — живая**: изменение роли меняет права всех, кому она назначена (с предпросмотром).
> Индивидуальные разрешения остаются для исключений.
> **Версия 1.7** (дополнительная проверка): что реализовано в коде, а что только описано (§1); хранение всех паролей стойким хешем без

> учётной записью (§8); настраиваемое ограничение сеансов (§12.9); подробное поведение фоновых заданий (§13.1); проверка полноты журнала (§16).
> **Версия 1.8** (точечная проверка): параметры Argon2id и переход с scrypt (§12.0.1–12.0.2); выбор сеанса при достигнутом пределе и защита

## 3. Основные понятия

| Понятие | Что это | Кто создаёт |
|---|---|---|
| **Разрешение** | самая мелкая единица: «изменять цены», «создавать резервные копии». Каждому соответствует проверка на сервере | **определяется в коде** программы; владелец не может придумать новое разрешение (без кода оно ничего бы не проверяло), но собирает из них роли |
| **Роль** | именованный набор разрешений: «Товаровед», «Старший кассир» | владелец (или сотрудник, которому он это доверил, §7.3) |
| **Шаблон роли** | готовый образец набора разрешений, поставляется с программой, **только для чтения** | программа |
| **Назначение** | роль, выданная сотруднику; может иметь область действия и срок | владелец (или доверенный сотрудник) |
| **Индивидуальное разрешение** | исключение для одного сотрудника: **разрешить** что-то сверх ролей или **запретить** что-то из ролей | владелец (или доверенный сотрудник) |
| **Область действия** | где действует разрешение: весь магазин (первая версия), позже — категории, отделы (§9) | вместе с назначением |
| **Владелец** | **не роль**, а отдельный признак учётной записи. Владелец имеет все разрешения своего магазина; его нельзя ограничить ролями или запретами | при установке; передача — отдельная процедура (§8) |
| **Эффективные права** | то, что сотрудник действительно может сейчас: вычисляется сервером по правилам §6 | система |

Почему владелец — не роль: роль можно скопировать, изменить, назначить. Если бы «полный контроль» был ролью, ошибка или злоупотребление
при её редактировании или копировании давали бы чужому человеку права владельца. Отдельный признак этого не допускает.

**Зависимости не выдают права сами.** Если владелец отмечает «Изменение цен» без «Просмотра товаров», интерфейс предлагает добавить
недостающее; на сервере зависимое разрешение без базового **не действует** (§6, правило 6).

**Расширяемость.** Новое разрешение появляется только с новой версией программы (вместе с проверкой в коде). При обновлении оно никому
не выдаётся автоматически, кроме владельца; программа показывает «Появилось новое разрешение …, по умолчанию оно ни у кого не включено».

## 5. Стартовые шаблоны ролей (примеры, а не ограничения)

При первой настройке из шаблонов создаются **шесть обычных ролей**. Их можно переименовать, изменить, скопировать и удалить, как любые
другие. Сами шаблоны остаются в программе только для чтения: из них можно создать новую роль или сравнить с ними свою.
Обновление программы **не меняет** уже созданных ролей.

## 6. Как вычисляются эффективные права: правила приоритета

```text
если учётная запись не активна (заблокирована, в архиве, временный пароль не сменён) → ничего (кроме смены пароля)
если владелец → все разрешения своего магазина; роли и запреты на владельца не действуют
иначе:
  разрешено  = ⋃ разрешения ролей из действующих назначений  ∪  индивидуальные «разрешить»   (каждое — со своей областью)
  запрещено  = индивидуальные «запретить»                                                    (со своей областью)
  эффективно = разрешено − запрещено
  затем убрать разрешения, у которых нет требуемого базового (§4, «Требует также»)
учитываются только действующие записи (не истёк срок, не отозваны); неизвестный код разрешения игнорируется
```

**Правила (по порядку приоритета):**

1. **По умолчанию — запрещено.** Чего не выдали явно, того нет. Новые разрешения после обновления никому не выдаются сами.
2. **Владелец — вне правил ролей.** Его права не вычисляются из ролей и не урезаются запретами (§8).
3. **Явный запрет сильнее любого разрешения.** Индивидуальное «запретить» отменяет то же разрешение из всех ролей и индивидуальных
   «разрешить» — в своей области.
4. **Разрешения из разных ролей складываются.** Две роли не «конфликтуют»: сотрудник получает объединение. Поэтому в ролях нет
   «запрещающих» записей: запрет бывает только индивидуальным и всегда виден в карточке сотрудника.
5. **Область действия:** разрешение действует только внутри области того назначения, которое его дало. Объединение областей — объединение;
   запрет с областью вырезает только эту область.
6. **Зависимости:** зависимое разрешение без базового не действует (не «включает» базовое).
7. **Срок:** назначение или индивидуальное разрешение со сроком перестаёт действовать автоматически, без участия человека.
8. **Неизвестный код** (например, после отката программы на старую версию) — игнорируется, то есть запрещено. Так уже работает
   `parse_role` для неизвестной роли.
9. **Заблокированная учётная запись** не имеет прав вообще, независимо от ролей.

Примеры разрешения конфликтов:

| Ситуация | Итог |
|---|---|
| Роль «Менеджер» даёт «Изменение цен», у сотрудника индивидуальный запрет «Изменение цен» | цены менять **нельзя** (правило 3) |
| Роль A даёт «Редактирование» в категории «Молочные», роль B — во всём магазине | редактирование во всём магазине (правило 5) |
| Роль даёт «Удаление» во всём магазине, индивидуальный запрет «Удаление» в категории «Алкоголь» | везде, кроме «Алкоголя» (правила 3 и 5) |
| Индивидуально выдано «ИИ: выполнение изменений», но нет «ИИ: режим чтения» | не действует (правило 6) |
| Роль даёт «Изменение цен», срок назначения истёк вчера | цены менять нельзя (правило 7) |

## 7. Защита от повышения полномочий

### 7.1. Нет наследования ролей

Роли **плоские**: роль не может «наследовать» другую роль. Причина: при наследовании изменение «родительской» роли незаметно меняет права
во всех «дочерних», а проверка «кто что получил» становится сложной. Для удобства есть **копирование** (§7.2) и **сравнение ролей**.
Наследование можно рассмотреть позже, только при доказанной необходимости (например, сеть с сотнями ролей) и с теми же проверками.

### 7.2. Копирование роли — снимок, а не связь

- Копия получает список разрешений оригинала **на момент копирования**; дальнейшие изменения оригинала её не затрагивают, и наоборот.
- Копия создаётся **без назначений** (никто её не получает автоматически) и с именем «Копия — …».
- Сотрудник (не владелец) может скопировать роль, только если **все** её разрешения есть у него самого (§7.3). Он не может получить
  через копию больше, чем есть у него.
- Копирование записывается в журнал: откуда, кто, какой набор.

### 7.3. Потолок делегирования: «не больше, чем у себя»

Владелец может доверить управление людьми (`users.manage`) и ролями (`roles.manage`) другим. Для **всех, кроме владельца**, действуют правила:

1. **Выдать можно только то, что есть у самого себя**, и только в своей области: при назначении роли, выдаче индивидуального разрешения,
   создании, изменении и копировании роли сервер проверяет, что каждое разрешение (с областью) входит в эффективные права действующего.
2. **Нельзя управлять тем, кто сильнее.** Любое действие над сотрудником X (сброс пароля, блокировка, изменение ролей, завершение сеансов)
   разрешено, только если эффективные права X входят в права действующего — **и до, и после** изменения. Без этого правила
   администратор мог бы сбросить пароль управляющему, войти под ним и получить его права.
3. **Нельзя менять себя:** свои роли, свои разрешения, свою область, свой статус. Свой пароль — можно (с вводом текущего, §12.8).
4. **Нельзя редактировать роль, назначенную самому себе**, и роль, которая назначена кому-то сильнее себя (правило 2).
5. **Критические разрешения** (`users.manage`, `roles.manage`, `audit.view`, `settings.manage`, `backup.restore`, `assistant.configure`) —
   кто может их выдавать, решает владелец (вопрос **Q-18**): (а) только владелец — рекомендуется; (б) любой, у кого оно есть, по правилу 1.
6. **Признак владельца** не выдаётся и не снимается никем, кроме владельца (§8).

### 7.4. Изменение роли: полный предпросмотр, подтверждение, журнал и возврат

Роль «живая»: изменение сразу меняет права всех её держателей. Поэтому каждое изменение проходит четыре шага.

1. **Предпросмотр.** Показывается:
   - сравнение разрешений роли: «добавлено», «убрано», «без изменений» (критические выделены);
   - **все затронутые сотрудники** поимённо (имя, логин), а для каждого — что фактически изменится в его эффективных правах:
     «получит: …», «потеряет: …», «без изменений — это разрешение у него есть из другой роли», «не действует — запрещено исключением»;
   - предупреждения: у сотрудника идёт фоновое задание, для которого он теряет право (задание остановится, §13.1); роль становится
     «сильнее» кого-то из тех, кто ей управляет.
2. **Подтверждение** — всегда (кнопка «Применить к N сотрудникам»). **Усиленное** (повторный ввод пароля) — если добавляются критические
   разрешения или затронуты сотрудники с критическими правами. Подтверждение относится именно к показанному предпросмотру: если роль или
   назначения за это время изменились (номер версии), применение отклоняется — «данные изменились, обновите предпросмотр».
3. **Журнал:** запись о роли (версия, разрешения «было → станет», причина, кто подтвердил) и запись об изменении эффективных прав каждого
   затронутого сотрудника (§16).
4. **Безопасный возврат.** Каждая сохранённая конфигурация роли хранится как версия (`role_versions`, §10). «Вернуть версию N» — это
   **новое изменение** с содержимым версии N: тот же предпросмотр со списком затронутых, те же проверки (потолок делегирования — нельзя вернуть
   версию с правами, которых нет у себя; разрешения, которых больше нет в программе, отбрасываются с предупреждением), подтверждение и запись
   в журнал. История не переписывается; отменить можно и сам возврат.

**Удаление роли**, назначенной сотрудникам: выбрать — переназначить другую роль или подтвердить «N сотрудников потеряют эти права» (с тем же
предпросмотром). Роль уходит в архив вместе с последней версией **и списком назначений на момент архивирования**. «Восстановить из архива»
возвращает роль; повторные назначения предлагаются отдельно с предпросмотром (состав сотрудников мог измениться).

**Одновременные изменения:** у роли и учётной записи есть номер версии; изменение по устаревшей версии отклоняется. Проверки «последний
владелец» и «не сильнее себя» выполняются под блокировкой строк в той же транзакции, что и изменение, — две одновременные операции не
могут вместе обойти правило.

## 8. Защита владельца и его собственная учётная запись

**Защита от других пользователей:**

1. **Учётную запись владельца никто, кроме него самого, не может изменить:** логин, имя, пароль, сеансы, ограничение сеансов, статус.
   Сотрудник не может удалить, заблокировать, отправить в архив, сбросить пароль владельцу, завершить его сеансы или снять признак
   владельца — даже с `users.manage` и `roles.manage`, ни в окне, ни через API, ни через ИИ.
2. **На владельца не действуют роли и запреты** (§6, правило 2); «урезать» владельца невозможно.
3. **Признак владельца** может выдать или снять только владелец.

**Что владелец делает со своей учётной записью сам** — защитные правила этого **не запрещают**:

| Действие | Как |
|---|---|
| Сменить свой пароль | с вводом текущего пароля; забыл — процедура восстановления (п. 7) |
| Посмотреть свои сеансы и завершить любой из них или все сразу, включая текущий | «Выйти на всех устройствах» — затем вход заново |
| Изменить своё имя и логин | с повторным вводом пароля |
| Задать своё ограничение одновременных сеансов (§12.9) | в своей карточке |
| Управлять своими кодами восстановления | если в D-09 выбран этот вариант |
| Пройти процедуру восстановления доступа | п. 7 |
| Передать владение, назначить совладельца | п. 5–6 |
| Принудительно завершить **любой** сеанс любого сотрудника, в том числе защищённый сеанс компьютера магазина (§12.10) | с повторным вводом пароля, запись в журнал |
| Регистрировать и отзывать устройства (§12.12) | только владелец |

4. **Последний владелец.** Другие пользователи не могут удалить или заблокировать **любого** владельца (п. 1). Самому **последнему** активному
   владельцу недоступны только три действия: заблокировать себя, отправить себя в архив, снять с себя признак владельца. Причина: после этого
   магазином не управлял бы никто и разблокировать было бы некому, кроме процедуры восстановления. Чтобы уйти, владелец сначала передаёт
   владение (п. 5). Смена своего пароля, завершение своих сеансов и восстановление доступа последнему владельцу **разрешены всегда**.
   Проверка — в сервисе под блокировкой и ограничением в базе.
5. **Передача владения** — отдельная процедура: текущий владелец повторно вводит пароль; получатель уже существует и активен; действие
   атомарно (в одной транзакции) и записывается в журнал. Через ИИ-помощника недоступна.
6. **Сколько владельцев.** Модель данных допускает нескольких владельцев магазина (правила рассчитаны на это). Разрешать ли второго
   владельца в первой версии — **решение владельца** (вопрос Q-17). Если «ровно один», в базе добавляется ограничение «один активный владелец».
7. **Восстановление доступа владельца** (забыт пароль, сеансы завершены) без почты и SMS — открытое решение **D-09**: локальная процедура
   на компьютере магазина и/или одноразовые коды восстановления. Какой бы вариант ни выбрали, процедура: доступна только самому владельцу
   (не сотрудникам и не по сети); ограничена по попыткам; после неё обязательна смена пароля; все прежние сеансы владельца завершаются;
   событие записывается в журнал. Коды восстановления, если их выберут, хранятся только как стойкий хеш (§12.0).

## 9. Область действия: по магазину сейчас, по категориям — когда понадобится

| Тип области | Что значит | Когда |
|---|---|---|
| `store` — магазин целиком | разрешение действует во всём магазине | **первая версия** (в узле магазина это вся база) |
| `category` — категория и её подкатегории | например, товаровед отдела электроники редактирует только электронику | **заложено в модель данных, реализуется при практической необходимости** |
| `department` — отдел | если в магазине появятся отделы как понятие | позже, только вместе с понятием «отдел» |
| «Процесс» (например, только импорт цен) | уже покрыто отдельными разрешениями (`price.edit`, `catalog.import`) | отдельный тип области **не нужен** |

Чтобы не усложнять первую версию: в базе у назначений и индивидуальных разрешений есть поля `scope_type` и `scope_ref`, но в первой версии
допустим только `store`. Интерфейс области не показывает.

Правила для будущей области «категория» (чтобы потом не переделывать):

- товар в подкатегории входит в область родительской категории;
- перенос товара из категории A в B требует прав в обеих;
- списки, поиск, отчёты и экспорт показывают только товары в области; импорт отклоняет строки вне области с понятной причиной;
- ИИ-помощник получает ту же область (инструменты фильтруют так же);
- распознавание для покупателей область не учитывает (это публичная функция).

**Не планируется:** условия на значения («цена не больше X»), временные окна («только в смену»). Если понадобятся — отдельным решением.

## 11. Проверка на сервере

- **Единая точка проверки** — `AuthorizationService.check(actor, permission, target)`: её вызывают маршруты API, сервисные функции, инструменты
  ИИ-помощника, импорт и фоновые задания. Отдельных «путей в обход» нет.
- Маршрут проверяет разрешение (`require_permission`, как сейчас), сервисная функция — разрешение **и область** для конкретной записи.
- Эффективные права вычисляются на каждый запрос (§6). Для одного магазина это несколько строк из базы — нагрузка незначительна
  (**оценка, не замер**). В центре сети при необходимости — кэш с ключом `authz_version`.
- Интерфейс прячет кнопки, на которые нет прав, **только для удобства**. Любой запрос без права получает 403, даже если кнопку «нарисовали»
  вручную.
- Тесты: для каждого разрешения «без права — 403, с правом — успех»; все правила §6–§8 и §13 — отдельными тестами (§20).

```text
        (временный пароль, срок)       │                                      │               │
                                        └── срок истёк: нужен новый временный  └──── отозвать доступ ──► архив
```

### 12.0. Как хранятся пароли (все, включая временные)

- **Только стойкий хеш** со случайной солью, вычисленный специализированным медленным алгоритмом для паролей (каждая попытка подбора
  требует много памяти и времени). Это относится ко всем секретам для входа: постоянным паролям сотрудников и владельца, **временным
  паролям** и кодам восстановления доступа владельца (если их выберут в D-09).
- **Обратимое шифрование паролей не используется нигде.** Пароль нельзя «расшифровать» — ни программе, ни владельцу, ни разработчику.
  Поэтому кнопки «показать пароль» нет — есть только выдача нового временного пароля.
- Открытый текст пароля существует только в памяти на время одного запроса (вход, создание, смена) и **нигде не записывается**: ни в базу,
  ни в журналы программы, ни в журнал действий, ни в данные ИИ, ни в файлы экспорта и копии.
- Рядом с хешем хранятся название алгоритма и параметры. Поэтому новый алгоритм или более сильные параметры вводятся без массового сброса
  паролей: при следующем успешном входе пароль пере-хешируется (подход, рекомендованный OWASP).
- Хеш-пустышка (защита от угадывания логина по времени) вычисляется тем же алгоритмом и с теми же параметрами, что и настоящие пароли.

**Алгоритм — вопрос Q-22.** Предварительный выбор владельца (2026-11-06) — **Argon2id**; остаётся предварительным до окончательного решения по Q-22 (принятие Q-16 его не закрывает).
Код и зависимости пока не меняются.

#### 12.0.1. Параметры Argon2id (проверено по источникам 2026-11-06)

| Источник | Память | Проходы (t) | Параллельность (p) | Примечание |
|---|---|---|---|---|
| OWASP Password Storage Cheat Sheet — **минимум** | 19 МиБ | 2 | 1 | равноценные варианты: 46 МиБ / t = 1; 12 МиБ / t = 3; 9 МиБ / t = 4; 7 МиБ / t = 5 |
| RFC 9106, второй рекомендуемый вариант (для ограниченной памяти); в argon2-cffi — профиль `RFC_9106_LOW_MEMORY`, значения `PasswordHasher` по умолчанию **начиная с версии 21.2.0** (до неё были 100 МиБ / t = 2 / p = 8) | 64 МиБ | 3 | 4 | соль 16 байт, хеш 32 байта |
| RFC 9106, первый рекомендуемый вариант | 2 ГиБ | 1 | 4 | для компьютера магазина **не подходит** (память) |

**Параметры задаются явно в конфигурации приложения** (память, проходы, параллельность, длина соли и хеша, тип `argon2id`, версия 19),
а **не берутся из значений библиотеки по умолчанию**: в argon2-cffi они уже менялись между версиями (21.2.0), и обновление библиотеки
не должно незаметно менять стойкость или нагрузку. При запуске программа:

- читает профиль из конфигурации и **отказывается запускаться** со значениями ниже минимума OWASP, если в конфигурации нет ссылки на
  отдельное утверждённое решение владельца (номер решения в журнале архитектуры) — «тихого» снижения не бывает;
- пишет выбранный профиль в «Состояние системы» и в журнал при каждом изменении;
- после входа сравнивает параметры хеша с конфигурацией и при расхождении пере-хеширует (§12.0.2, шаг 4).

**Нижняя граница — минимум OWASP (19 МиБ / t = 2 / p = 1).** Опускаться ниже **нельзя** без отдельного письменного обоснования
и согласия владельца. Если даже минимальный профиль не проходит испытание, параметры **не снижаются**: уменьшается число одновременных
проверок и очередь (§14.3) или повышаются требования к компьютеру (документ 11, §8).

**Как выбирается окончательный профиль** — не только по времени одной проверки, а по **нагрузочному испытанию** Н-6 (документ 11, §5.2)
на слабом компьютере (4 ядра, 8 ГБ, без GPU):

| Что меняется | Значения |
|---|---|
| Профиль | А — 19 МиБ / t = 2 / p = 1 (минимум OWASP); Б — 64 МиБ / t = 3 / p = 4 (RFC 9106); при запасе — промежуточные (например, 46 МиБ / t = 1 — равноценный вариант OWASP) |
| Одновременных попыток входа | 1, 2, 5, 10, 20 (верные и неверные пароли вперемешку), в том числе во время распознавания с нагрузкой ориентира В-3 (20 в минуту) |
| Ограничение одновременных проверок (§14.3) | 1, 2, 4 |

| Что измеряется | Критерий (предложение, утверждает владелец по итогам) |
|---|---|
| Время одной проверки без нагрузки | около 0,5 с и меньше |
| p95 времени входа при 5 одновременных попытках | не больше нескольких секунд, без ошибок нехватки памяти |
| Пиковая память процесса | в пределах бюджета (документ 11, §4), без подкачки |
| p95 распознавания для покупателей во время входов | ухудшение не больше 10–20 % |
| Доля ответов «занято» при 10–20 одновременных попытках | срабатывает как задумано, процесс не падает |

**Что учитывается при испытании:**

- **Реальная параллельность.** Параметр p — это число «полос» вычисления; эталонная реализация может считать их в отдельных потоках.
  При p = 4 и двух одновременных проверках процессору может понадобиться до 8 потоков — на 4-ядерном компьютере это отнимает процессор
  у распознавания. Поэтому вместе с профилем подбирается **ограничение одновременных проверок** (§14.3), и замеряется именно загрузка
  процессора и задержка распознавания, а не только время входа. Освобождает ли библиотека GIL Python на время вычисления — проверить в испытании.
- **Память:** пиковая память ≈ ограничение одновременных проверок × память профиля плюс накладные расходы; очередь ожидания память не занимает.
- **Очередь:** её длина и время ожидания (§14.3) входят в испытание; переполнение даёт «занято» (HTTP 503), а не ошибку пароля.
- **Порядок действий при нехватке ресурсов:** (1) уменьшить ограничение одновременных проверок и очередь; (2) повысить требования к компьютеру
  (документ 11, §8); (3) **только** отдельным решением владельца с обоснованием — профиль ниже минимума OWASP. Незаметного снижения не бывает.

Выбирается **самый сильный** профиль, проходящий все критерии; результат и цифры записываются в отчёт испытания. Время и память —
**оценки, их нужно измерить**: ни один профиль на целевых компьютерах не замерялся. Параметры записываются в каждый хеш
(`$argon2id$v=19$m=…,t=…,p=…$соль$хеш`), поэтому их можно поднять позже — с пере-хешированием при входе.

#### 12.0.2. Безопасный переход с scrypt на Argon2id

| Шаг | Что происходит | Зачем |
|---|---|---|
| 0. Резервная копия | полная копия перед обновлением (документ 09) | возможность вернуться |
| 1. Выпуск «читает оба» | проверка пароля определяет схему по началу строки хеша (`scrypt$…` или `$argon2id$…`) и проверяет соответствующим алгоритмом; **новые хеши пока пишутся scrypt** | если этот выпуск придётся откатить, старые версии программы продолжают проверять все пароли |
| 2. Выпуск «пишет Argon2id» (следующее обновление) | новые и изменённые пароли, временные пароли и хеш-пустышка — Argon2id; после **успешного** входа со старым хешем пароль пере-хешируется в той же транзакции, что и вход | постепенная замена без сброса паролей; откат на выпуск шага 1 безопасен, он читает Argon2id |
| 3. Неактивные учётные записи | у кого хеш scrypt не заменился за установленный срок (предложение — 90 дней), владелец выдаёт новый временный пароль; при необходимости — сразу «обернуть» старый хеш: Argon2id поверх хеша scrypt с заменой при входе (вариант из OWASP) | слабые хеши не лежат в базе бесконечно |
| 4. Повышение параметров позже | после входа проверяется, совпадают ли параметры хеша с текущими; если нет — пере-хеширование | параметры растут вместе с компьютерами |

Правила перехода: неизвестная схема хеша → вход отклоняется (как сейчас); пере-хеширование не меняет отметку времени смены пароля и **не завершает**
сеансы; в журнал пишется сводка («переведено на новый алгоритм: N учётных записей»), а не отдельные хеши.

### 12.1. Создание сотрудника (мастер в окне программы)

1. **Кто:** имя для отображения (любая письменность, обязательно) и логин (уникальный, по текущему правилу: 3–64 символа, латиница, цифры,
   `. _ @ -`, без учёта регистра). Логин архивных сотрудников повторно не используется — так журнал остаётся однозначным.
2. **Что может:** одна или несколько ролей и/или индивидуальные разрешения; по желанию — «доступ до» (дата). Внизу — итог простыми словами:
   «Сможет: …; не сможет: …». Критические разрешения выделены.
3. **Временный пароль:** выдаётся сервером (§12.2) и показывается один раз.

Создать сотрудника могут владелец и сотрудники с `users.manage` в пределах правил §7.3.

### 12.2. Временный пароль

- **Генерирует сервер** криптографически стойким генератором: 12 символов из алфавита без похожих знаков (нет `0/O`, `1/l/I`), группами
  по 4: `7KQM-X4HP-9TDW`. Это около 59 бит случайности — подобрать за срок действия при ограничении попыток практически невозможно (§14).
- **Показывается один раз** тому, кто его выдал (владельцу или доверенному сотруднику), в окне с кнопками «Скопировать» и «Распечатать листок для сотрудника» (логин, временный пароль, срок, «смените
  при первом входе»). Программа не сохраняет его в файл. Закрыл окно — показать снова нельзя; потерял — «Выдать новый временный пароль».
- **Хранится только стойкий хеш** тем же алгоритмом, что и постоянные пароли (§12.0), **без обратимого шифрования**, и срок действия `temp_password_expires_at`. Срок — настройка владельца
  (вопрос **Q-19**; рекомендация — 24 часа). Пароль **не попадает** в журналы, журнал действий, переписку и контекст ИИ, файлы экспорта.
  В резервной копии — только хеш, как и у всех паролей.
- Временный пароль действует **только для первоначальной установки нового пароля** (при первом входе и после сброса): вход с ним выдаёт
  токен назначения `password_change` (срок 15 минут), который принимается только маршрутом установки пароля. Никакой другой работы с ним
  выполнить нельзя. После установки нового пароля хеш временного пароля удаляется.
- Истёкший временный пароль: после ввода **верного** временного пароля — «Временный пароль истёк. Обратитесь к владельцу за новым»; при неверном — общий ответ (§14.5).
- **Действующий пароль сотрудника не показывается никому и нигде** — ни владельцу, ни в базе, ни в журнале. Кнопки «показать пароль»
  нет. Возможен только сброс (§12.4).

### 12.3. Первый вход

Сотрудник вводит логин и временный пароль → программа сразу требует новый пароль. Требования: не короче 8 символов (для владельца
рекомендуется 12), не из списка слабых, не совпадает с временным и с логином; без требований «обязательно спецсимвол». После смены:
статус «активна», все прежние токены отозваны, выдаётся обычный сеанс, запись в журнал — всё одной транзакцией (§12.11).

### 12.4. Сброс пароля

Владелец (или сотрудник с `users.manage` по правилам §7.3, **не для владельца**) нажимает «Выдать новый временный пароль». Старый пароль
перестаёт действовать сразу; все сеансы сотрудника завершаются (атомарно, §12.11); сеансы ИИ закрываются; статус — «ждёт первого входа». Можно указать причину.

### 12.5. Блокировка и разблокировка

- **Блокировка:** вход невозможен; все токены отзываются **немедленно** (так уже работает отключение); сеансы ИИ закрываются; неподтверждённые
  планы ИИ отменяются; фоновые задания сотрудника останавливаются в безопасной точке (§13). Указывается причина (по желанию).
- **Разблокировка:** учётная запись снова активна; сеансы не восстанавливаются (нужно войти заново). Есть вариант «Разблокировать и выдать
  новый временный пароль» — уместен, если блокировали из-за подозрения. Делать ли его обязательным — вопрос **Q-19**.

### 12.6. Изменение роли и разрешений

Предпросмотр «было → станет» простыми словами; критические разрешения выделены и требуют усиленного подтверждения; запись в журнал
с полным списком изменений. Действует со следующего запроса сотрудника (§13). Назначения не удаляются, а получают отметку отзыва, поэтому
в карточке видна история прав сотрудника; прежний набор можно применить снова — это тоже изменение с предпросмотром и подтверждением.

### 12.7. Отзыв доступа (сотрудник уволился)

Одно действие «Отозвать доступ»: блокировка + отзыв всех назначений и индивидуальных разрешений + перевод в архив. Учётная запись и история
**не удаляются физически**: на них ссылается журнал действий. Хранятся только имя и логин, других персональных данных нет.

### 12.8. Что сотрудник может сам

Сменить свой пароль (с вводом текущего); посмотреть свои сеансы и «Выйти на всех устройствах». **Не может:** создавать учётные записи
(без `users.manage`), менять свой логин, свои роли, разрешения, область и статус, назначать себе роли — сервер отклоняет такие запросы
независимо от того, откуда они пришли (окно, API, ИИ).

### 12.9. Отдельная учётная запись для каждого человека

Совместное использование логинов запрещено правилом. Честно: программа **не может технически доказать**, что логином пользуется один
человек. Она делает общий логин неудобным и заметным:

- имя для отображения обязательно, у каждого — свой логин;
- при входе показывается «Последний вход: вчера в 18:04, компьютер кассы» — сотрудник заметит чужой вход;
- в карточке сотрудника — активные сеансы и устройства; владелец видит одновременные входы с разных устройств;
- **ограничение одновременных сеансов — настройка, а не жёсткое ограничение архитектуры:** общее значение магазина (стартовое — 2: компьютер
  магазина и телефон в сети сотрудников) и **отдельное значение для каждой учётной записи** (число от 1 до 20 или «без ограничения»; пусто —
  общее значение). Владелец задаёт его всем, включая себя; сотрудник с `users.manage` — только тем, кто не сильнее его (§7.3). Изменения — в
  журнал. Считаются действующие сеансы; вход с временным паролем (только для установки пароля) не считается. Что делать при достижении
  предела — вопрос **Q-20**; предварительный выбор владельца — показать свои сеансы и предложить завершить один (§12.10);
- журнал действий записывает конкретного человека — общий логин делает журнал бесполезным, это объясняется владельцу в интерфейсе.

### 12.10. Предел сеансов достигнут: сотрудник сам выбирает, какой сеанс завершить

Предварительный выбор владельца по Q-20 (2026-11-06) — вариант (в). Порядок:

1. Сотрудник вводит логин и пароль. Обычные ограничения попыток действуют **до** этого шага (§14): механизм нельзя использовать для подбора.
2. Пароль верный, но действующих сеансов уже столько, сколько разрешено. **Сеанс не создаётся.** Сервер выдаёт одноразовый «пропуск выбора»:
   срок 2 минуты, привязан к этому устройству и адресу, годится только для просмотра своих сеансов и завершения одного из них, не даёт
   никаких других прав. Повторное использование пропуска отклоняется.
3. Сотрудник видит **свои** действующие сеансы (только свои, чужие не видны никогда):

   | Что показывается | Пример |
   |---|---|
   | Устройство | название, заданное при первом входе, или «Компьютер магазина» / «Телефон, Android, Chrome» (по данным браузера — приблизительно) |
   | Откуда | «служебный вход на компьютере магазина» / «сеть сотрудников» (без полного IP) |
   | Время входа | «сегодня 09:12» |
   | Последняя активность | «5 минут назад» |

4. Выбирает сеанс и **подтверждает**: «Завершить сеанс на устройстве «Компьютер кассы» (вход сегодня 09:12, активность 5 минут назад)?
   Там будет выполнен выход». Можно отказаться — тогда вход не выполняется.
5. Завершение выбранного сеанса и создание нового выполняются **в одной транзакции** с повторной проверкой числа сеансов под блокировкой
   строки пользователя: два одновременных входа не превысят предел.

**Защита от вытеснения настоящего хозяина учётной записи** (злоумышленник узнал пароль и «выбивает» сотрудника):

| Мера | Как работает |
|---|---|
| Понятное сообщение на завершённом устройстве | «Ваш сеанс завершён входом с другого устройства: «Телефон, Android», сегодня 14:03. Если это были не вы — нажмите «Это был не я»» |
| «Это был не я» | после повторного ввода пароля на этом устройстве (оставшемся у настоящего хозяина): все сеансы учётной записи, кроме текущего, завершаются, обязательна смена пароля, владелец магазина получает предупреждение, событие — в журнал. Если пароль уже сменён злоумышленником — вход невозможен, сотрудник обращается к владельцу (сброс, §12.4) |
| Ограничение вытеснений | не больше 3 завершений сеансов этим способом на учётную запись за час (настройка); дальше вход при достигнутом пределе отклоняется, владелец магазина получает предупреждение |
| Защищённый сеанс компьютера магазина | **предварительный выбор владельца по Q-23 (2026-11-06) — защищать.** Сеанс защищён, только если он открыт на **зарегистрированном компьютере магазина** с действующим секретом устройства (§12.12), а не потому, что запрос пришёл с какого-то IP или из Wi-Fi. Такой сеанс нельзя завершить входом из сети этим механизмом. В списке он показан с пометкой «защищён: компьютер магазина — завершить отсюда нельзя». Завершить его могут: сам сотрудник («Выйти везде»), **владелец — всегда, принудительно** (с повторным вводом пароля, запись в журнал), сотрудник с `users.manage` — у тех, кто не сильнее его (§7.3) |
| Учётная запись владельца магазина | сеансы владельца этим механизмом из сети не завершаются: при достигнутом пределе владелец входит с компьютера магазина или завершает сеансы в «Моей учётной записи» (§8) |
| Видимость | каждое завершение — в журнале (кто, с какого устройства, какой сеанс); при следующем входе на вытесненном устройстве показывается, что произошло |

Честно: если пароль известен злоумышленнику, механизм лишь делает вход **заметным** и ограниченным; главная мера — смена пароля и сброс
владельцем.

### 12.11. Смена пароля и отзыв старых сеансов — одна атомарная операция

Сейчас (§1.1) изменение пароля и отзыв токенов — две отдельные транзакции: при сбое между ними старые сеансы после смены пароля остались бы.
В целевой схеме это невозможно **по построению**:

1. У учётной записи есть счётчик поколения сеансов `users.session_epoch`; каждый токен при выдаче получает текущее значение.
2. Смена пароля (самим сотрудником, при первом входе, после сброса, через восстановление владельца), блокировка, отзыв доступа и «Выйти на
   всех устройствах» в **одной транзакции**: записывают новый хеш (или статус), увеличивают `session_epoch`, удаляют токены пользователя и
   пишут событие в журнал. Либо всё это зафиксировано, либо ничего.
3. Проверка токена на каждом запросе отклоняет токен, у которого поколение не совпадает с `users.session_epoch`. Поэтому даже если удаление
   токенов по какой-то причине не произошло, **старые токены не действуют**: защита держится на одном атомарно изменённом поле.
4. Новый сеанс после смены пароля выдаётся в той же транзакции с новым поколением.
5. Пере-хеширование при входе (§12.0.2) поколение **не меняет**.

### 12.12. Зарегистрированные (доверенные) устройства (1.9, уточнено в 1.10)

Доверие к устройству основано на **зарегистрированном устройстве и секрете, который хранится только на нём**, а не на IP-адресе или
подключении к Wi-Fi: адрес в локальной сети легко подменить, а пароль Wi-Fi знают многие. Используется для двух целей: защищённый сеанс
компьютера магазина (§12.10, Q-23) и вход без влияния ограничений, наложенных на незарегистрированные источники (§14.4).
**Устройство — не замена паролю:** пароль нужен всегда.

**Первый этап (предварительный выбор владельца по Q-24 — вариант (а)):**

- доверенным может быть **только компьютер магазина**;
- **телефоны сотрудников входят как обычные незарегистрированные устройства** и статуса доверенных не получают; для них действуют все
  ограничения §14.4 (включая возможность временного ограничения при атаке на логин);
- регистрация телефонов рассматривается только после появления HTTPS и отдельного решения владельца.

**Доверенное устройство не защищает соединение.** Регистрация устройства подтверждает, *какое* устройство входит, но **не шифрует трафик и
не защищает от перехвата или подмены**. Пока вход сотрудников с телефонов идёт по HTTP в сети сотрудников, пароль и токен сеанса передаются
открытым текстом и могут быть перехвачены или подменены в той же сети — независимо от регистрации устройств. Защита канала — **отдельная задача**:
HTTPS для служебного входа (путь к нему — документ 04, §3.3 В и §3.4; вход с телефонов — §5), отдельная сеть сотрудников и решение **D-08** о входе с телефонов. Компьютер магазина обращается
к программе через `127.0.0.1` — этот трафик **не выходит в сеть**, поэтому перехват по Wi-Fi к нему не применим (но это не HTTPS, и от вредоносной
программы на самом компьютере не защищает).

| Правило | Как |
|---|---|
| Кто регистрирует | только владелец: на компьютере магазина нажимают «Зарегистрировать это устройство», программа показывает короткий код, владелец подтверждает его с повторным вводом пароля |
| Где разрешена регистрация | тип «компьютер магазина» — **только с самого компьютера** через служебный вход `127.0.0.1` и только из программы Desktop. Обращение с `127.0.0.1` — дополнительное условие, а не основа доверия: основа — действующий секрет устройства |
| Что выдаётся | случайный секрет устройства (256 бит) и номер устройства. В базе — только хеш секрета (`devices`, §10). Секрет никогда не попадает в журналы, журнал действий и данные ИИ |
| Где хранится секрет | на стороне **окна программы** (клиента), а не службы: окно работает в сеансе пользователя Windows и хранит секрет зашифрованным **DPAPI** (`CryptProtectData`) **в области этого пользователя**, без флага `CRYPTPROTECT_LOCAL_MACHINE` (с ним расшифровать мог бы любой пользователь компьютера). Служба backend секрет **не расшифровывает** и не хранит — у неё только хеш в базе. Подробно — §12.12.1 |
| Обновление секрета | после каждого успешного входа сервер выдаёт новый секрет. Чтобы сбой во время обновления не «потерял» устройство: сервер хранит текущий и новый хеш; новый становится действующим, а старый перестаёт действовать, как только устройство один раз предъявит новый (не позднее 10 минут); всё — в одной транзакции |
| Отзыв | владелец может отозвать регистрацию в любой момент (замена компьютера, подозрение на кражу). В **одной транзакции**: хеш секрета помечается отозванным, все сеансы, открытые с этого устройства, завершаются (токены удаляются, проверка токена также отклоняет сеансы отозванного устройства), событие — в журнал. Повторная регистрация — снова только владельцем |
| Предел | не больше 3 зарегистрированных устройств на учётную запись (настройка) |
| Честные ограничения | DPAPI не защищает от того, кто вошёл в Windows под той же учётной записью или запустил вредоносную программу от её имени. Секрет может стать нечитаемым (смена учётной записи Windows, переустановка, принудительный сброс пароля) — тогда устройство просто перестаёт быть доверенным, вход по паролю остаётся (§12.12.1). У компьютера магазина должна быть **отдельная учётная запись Windows с паролем** для работы программы |

#### 12.12.1. DPAPI, служба Windows и отдельные процессы (1.11)

**Из каких процессов состоит программа** (документ 03, §2): backend — **служба Windows**, работает весь день, в том числе когда никто не вошёл
в Windows; PostgreSQL — своя служба; **окно программы** (оболочка Tauri или Edge в режиме приложения) — обычный процесс в сеансе того
пользователя Windows, который сидит за компьютером. Окно — клиент службы через `127.0.0.1`.

**От имени кого работает служба.** Рекомендуется не `LocalSystem` (по документации Microsoft у этой учётной записи очень широкие права на
компьютере, и для большинства служб Microsoft советует `LocalService` или `NetworkService`), а учётная запись с минимальными правами — например,
виртуальная учётная запись службы или `LocalService`. Окончательный выбор — в прототипе Desktop (документ 03, §7).

**Почему секрет устройства хранит окно, а не служба.** По документации Microsoft данные, зашифрованные DPAPI в области пользователя, обычно может
расшифровать только пользователь с теми же учётными данными Windows и обычно только на этом же компьютере. Служба работает от **другой**
учётной записи — значит, **не может** прочитать секрет, сохранённый окном, и наоборот. Мы не полагаемся на то, что пользовательское хранилище
доступно службе. Поэтому:

| Что | Где | Кто читает |
|---|---|---|
| Секрет доверенного устройства | файл в профиле пользователя Windows (`%LOCALAPPDATA%\UznatTovar\device.bin`), зашифрован DPAPI в области этого пользователя | только окно программы, запущенное этим пользователем; передаёт секрет службе по `127.0.0.1` при входе |
| Хеш секрета | база данных (`devices`) | служба |
| Собственные секреты службы (пароль базы, ключ подписи cookie знакомых устройств) | файл в `%ProgramData%\UznatTovar\Secrets` с правами NTFS только для учётной записи службы и администраторов; дополнительно DPAPI от имени учётной записи службы — **только если прототип подтвердит**, что у выбранной учётной записи службы DPAPI работает | только служба |

Если оболочкой будет Edge в режиме приложения (вариант D документа 03), у окна нет своего кода для вызова DPAPI; тогда секрет хранится как
cookie для `127.0.0.1` в профиле Edge этого пользователя, и его защита зависит от того, как браузер хранит cookie, — **проверить в прототипе**.

**Что переживает секрет и что его уничтожает:**

| Событие | Секрет | Что делать |
|---|---|---|
| Перезапуск окна, службы, PostgreSQL | сохраняется (лежит в файле профиля) | — |
| Перезагрузка Windows | сохраняется (документация DPAPI: расшифровка тем же пользователем на том же компьютере) | — |
| Пользователь сам меняет свой пароль Windows | по имеющимся данным сохраняется (Windows перешифровывает свои ключи) — **проверить в прототипе** | — |
| **Администратор принудительно сбрасывает** пароль пользователя Windows | может стать нечитаемым: Microsoft (KB 290260) описывает потерю сохранённых учётных данных и зашифрованных данных пользователя после такого сброса — **проверить в прототипе** | повторная регистрация |
| Другая учётная запись Windows или новый профиль | недоступен (это другой пользователь) | регистрация для этой учётной записи — отдельное устройство |
| Переустановка Windows, замена диска, перенос на другой компьютер, восстановление из копии на новом компьютере | недоступен | повторная регистрация; старые регистрации отзываются |
| Переустановка или обновление программы | сохраняется: файл в профиле пользователя **не удаляется** программой удаления (правило установщика); удаляется только при явном выборе «удалить все мои данные» | — |
| Восстановление базы из копии | таблица `devices` вернётся, но секретов на новом компьютере нет | мастер восстановления предлагает «отозвать все регистрации устройств из копии» |

**Потеря секрета — не потеря доступа.** Вход по-прежнему выполняется **по паролю**; устройство просто перестаёт быть доверенным: нет защиты сеанса
от вытеснения (§12.10) и отдельного счётчика доверенного устройства (§14.4). Локальный вход с компьютера магазина и знакомые устройства продолжают
работать. Восстановление: владелец входит по паролю с компьютера магазина → «Устройства» → отзывает старую регистрацию → «Зарегистрировать это
устройство» (код и пароль владельца). Если владелец потерял и пароль — процедура восстановления доступа (D-09).

## 13. Изменение прав во время сеанса, отзыв доступа и фоновые задачи

Основа: **права не хранятся в токене** и вычисляются на каждый запрос (так уже работает `resolve_token`). Поэтому изменение вступает в силу
со следующего запроса без выхода из системы.

| Событие | Открытое окно сотрудника | Сеанс ИИ | Неподтверждённые планы ИИ | Фоновые задания сотрудника |
|---|---|---|---|---|
| Права **сужены** (роль изменена, роль снята, запрет) | следующий запрос без права → 403; окно перечитывает права и перестраивает меню: «Ваши права изменены» | следующий вызов инструмента проверяется по новым правам; список инструментов пересобирается на каждый ход | при подтверждении права проверяются **заново**; нет права → «План не может быть выполнен: недостаточно прав» | применение изменений атомарно: либо целиком зафиксировано до отзыва, либо не применено вовсе (§13.1) |
| Права **расширены** | меню обновляется при следующей проверке (окно запрашивает свои права раз в минуту и после 403) | новые инструменты доступны со следующего хода | — | — |
| **Блокировка**, **отзыв доступа**, **сброс пароля** | все токены отзываются сразу, окно показывает экран входа | сеанс закрыт | отменены | подготовленные задания не применяются; идущее применение откатывается целиком (§13.1) |
| Изменена **роль**, назначенная многим | `authz_version` всех держателей увеличивается; дальше — как в строках выше | | | |

### 13.1. Импорт и массовые изменения: подготовка во временной области и атомарное применение (1.8)

**Противоречие в версии 1.7 и его устранение.** В 1.7 одновременно говорилось «права проверяются в каждой партии» и «до 1000 записей —
всё или ничего». Для операции «всё или ничего» партия одна, но описание допускало, что большой импорт применяется частями, — а это и есть
частично применённый импорт. В 1.8 **любое изменение данных от имени сотрудника** (импорт каталога, импорт цен, массовое изменение в окне,
план ИИ) применяется **одной атомарной транзакцией** после подготовки во временной области. Партии остаются только для этапа подготовки
(разбор и проверка файла) и для системных заданий, которые не меняют данные от имени сотрудника.

**Два этапа:**

| Этап | Что делается | Меняются ли рабочие данные |
|---|---|---|
| **1. Подготовка** (может идти частями, долго) | файл разбирается в **временную область** задания: таблица `staging_rows` (строки с номером, исходными значениями, результатом проверки); фото — в хранилище только как «подготовленные» (`staged_files`); полная проверка всех строк тем же валидатором, поиск дублей и конфликтов, расчёт «было → станет» по каждой записи; предпросмотр | **нет** |
| **2. Применение** (одна транзакция) | после подтверждения человеком: блокировка строки инициатора в `users` на чтение и проверка его прав → проверка, что затронутые записи не изменились после предпросмотра (номера версий) → применение всех изменений из временной области **набором** (вставки и обновления по таблице, а не построчно) → запись событий журнала → постановка заданий индексации → отметка «применено» → **одна фиксация** | да, все сразу или ни одно |

**Почему отзыв доступа не может дать частично применённый импорт:**

- Блокировка, отзыв доступа, сброс пароля и изменение ролей меняют строку пользователя с блокировкой на запись (и увеличивают
  `session_epoch` / `authz_version`). Транзакция применения держит блокировку той же строки на чтение. PostgreSQL упорядочивает их:
  - отзыв зафиксирован **раньше** — применение видит отзыв и не начинается (ничего не изменено);
  - применение зафиксировано **раньше** — все изменения внесены законно, до отзыва;
  - третьего исхода нет: транзакция либо зафиксирована целиком, либо откатывается целиком.
- Чтобы отзыв не ждал долго, процедура отзыва сначала отмечает задания пользователя «отменить» и прерывает идущее применение — транзакция
  откатывается **целиком**. Затем отзыв фиксируется. Отзыв ждёт не дольше предельного времени транзакции применения (настройка, **оценка**: десятки секунд).
- В SQLite (если будет выбран для Desktop) один писатель: применение и отзыв выполняются строго по очереди, результат тот же.
- Сбой процесса или компьютера во время применения: незафиксированная транзакция откатывается базой; при перезапуске задание имеет статус
  «не применено» и может быть применено снова после повторной проверки.

**Фото и файлы:** файл фото **записывается в основное хранилище и проверяется до** транзакции, которая на него ссылается; после фиксации
переносить ничего не нужно. Порядок операций исключает «товар сохранён, а фото ещё не перенесено». Остаточный риск при отключении
питания (диск не выполнил сброс) и как он обнаруживается и устраняется — §13.3.

**Предельный размер одной атомарной операции.** Чтобы применение занимало секунды, а не минуты, есть системный предел строк на одну операцию
(предложение — 20 000 строк, этого хватает на каталог в 10 000 SKU целиком; **оценка, проверить испытанием Т-10**). Импорт больше предела
**не применяется частями молча**: программа предлагает разделить файл на явные отдельные импорты («часть 1 из 3»), каждый из которых
атомарен и подтверждается отдельно. Предел для массовых изменений в окне и через ИИ остаётся 1000 записей (документ 16, §6.5).

**Задания по видам:**

| Задание | Как выполняется | Если права отозваны или сотрудник заблокирован |
|---|---|---|
| Импорт каталога, импорт цен, массовое изменение, план ИИ — подготовка | частями, во временную область | подготовка прекращается; рабочие данные не изменены; временная область удаляется по сроку |
| То же — применение | одна транзакция (см. выше) | целиком до отзыва **или** не применено вовсе; задание получает статус «остановлено: доступ отозван» |
| Построение признаков для индекса | системное задание по уже применённым данным | **продолжается**: только достраивает признаки, ничего не меняет от имени сотрудника |
| Экспорт | во временный файл; доступен только целиком | прекращается, временный файл удаляется; готовый файл выдаётся только тому, у кого право есть в момент скачивания |
| Создание резервной копии сотрудником | во временный файл → проверка → переименование | прекращается, временный файл удаляется; готовые копии не затрагиваются |
| Восстановление из копии | только с `backup.restore`; перед стартом — копия текущих данных (документ 09) | права проверяются перед стартом; после старта не прерывается — прерывание опаснее завершения |
| Ночная копия, пересборка индекса, диагностика, очистка по срокам | системные задания (`created_by = system`) | от прав сотрудников **не зависят** |

### 13.2. Остановленное задание: передача другому сотруднику (1.8)

Остановленное задание (подготовлено, но не применено, или остановлено из-за отзыва доступа) **не продолжается само** и не переходит
автоматически ни к кому.

| Правило | Как |
|---|---|
| Отдельное разрешение | принять чужое задание может только сотрудник с разрешением **`jobs.takeover`** («Принимать задания других сотрудников», риск «важное») **и** с правами на само действие (например, `catalog.import`, `price.edit`) в нужной области. Владелец может всегда |
| Явное принятие | задание можно **предложить** конкретному сотруднику (владелец или сотрудник с `jobs.takeover`) или сотрудник сам берёт его из списка остановленных. В обоих случаях исполнитель нажимает «Принять задание» и видит: кто начал, когда, почему остановлено, что будет изменено |
| Повторная проверка | при принятии временная область проверяется заново по **текущим** данным и правам нового исполнителя; показывается новый предпросмотр «было → станет»; применение — только после его подтверждения (усиленного — если в задании есть критические изменения) |
| От чьего имени | после принятия задание выполняется **от имени нового исполнителя** и только в пределах его прав; права первоначального инициатора не переходят |
| Фиксация обоих | в задании хранятся **первоначальный инициатор** (`initiated_by`, не меняется никогда) и **текущий исполнитель** (`executor_id`); каждая передача — запись в `job_handovers` (кто предложил, кому, когда, принято или отклонено, причина). В журнале действий применённые изменения записываются с исполнителем как действующим лицом и ссылкой на инициатора |
| Отказ и срок | исполнитель может отказаться; непринятое задание удаляется по сроку хранения подготовленных заданий (Q-13) вместе с временной областью |
| Заблокированный инициатор | не может ни продолжить, ни отменить своё задание; отменить может владелец или сотрудник с `jobs.takeover` |

Ни один из этих механизмов в коде пока **не реализован** (§1.3).

### 13.3. Фото и файловая система: надёжная запись, сбои и восстановление (1.9, проверено и уточнено в 1.10)

**Сейчас в коде** (чтение `app/services/catalog_upload.py`, `app/api/routes_catalog.py`): фото пишется в папку товара **до** записи товара
в базу — через временный файл `.part` и `os.replace`; затем задание Celery создаёт товар. Порядок «файл, потом база» правильный, но сброса
на диск нет, учёта незавершённых операций нет, проверки хранилища нет. Если задание не выполнилось, файлы остаются в папке без товара.
Всё ниже — **только архитектура**.

#### 13.3.1. Что на самом деле гарантируют Windows и NTFS (проверено по документации 2026-11-06)

| Механизм | Что документировано | Чего документация **не** обещает |
|---|---|---|
| `os.fsync` в Python | на Windows вызывает функцию `_commit` библиотеки C, которая сбрасывает буферы файла через `FlushFileBuffers` | — |
| `FlushFileBuffers` | «записывает все буферизованные данные файла на устройство» | что сбрасываются **метаданные каталога** (запись об имени файла в папке); про каталоги в документации ничего нет |
| Сброс всего тома | `FlushFileBuffers` с дескриптором тома сбрасывает все открытые файлы тома, **нужны права администратора** | — (не годится для каждого фото: дорого и требует прав администратора у службы) |
| Флаг `FILE_FLAG_WRITE_THROUGH` при открытии файла (`CreateFile`) | данные не кэшируются, **метаданные файла сбрасываются при каждой записи** | что этого достаточно при обманывающем диске |
| `os.replace` / `MoveFileEx` в пределах одного диска | замена файла, если цель существует | **атомарность** переименования документацией Microsoft не описана; флаг `MOVEFILE_WRITE_THROUGH` описан только для переноса копированием на другой диск |
| Сброс каталога (аналог `fsync` папки в Linux) | в стандартном Python на Windows **нет** | — |
| Кэш записи самого диска | PostgreSQL: «многие SSD по умолчанию не выполняют команду сброса кэша»; за то, чтобы устройства хранили данные и метаданные надёжно, отвечает администратор | никакая программа не может гарантировать запись, если диск или драйвер игнорирует сброс |

Ещё ограничения Windows: антивирус или индексатор могут кратко держать файл открытым — переименование или удаление может
получить отказ в доступе; при большой частоте переименований на Windows описаны и такие сбои (пример — ошибка JDK-8303225). Поэтому каждая
файловая операция повторяется с паузой несколько раз и безопасна при повторе. Папка данных не должна находиться в синхронизируемых облачных
папках (OneDrive и подобных): данные лежат в `%ProgramData%\UznatTovar\Data` (документ 02).

**Вывод:** `fsync` файла плюс переименование на Windows **не дают документированной гарантии**, что после отключения питания файл
окажется на месте под новым именем. Поэтому надёжность строится не на одном системном вызове, а на трёх вещах: порядок операций,
**самопроверяемые имена файлов** (имя = SHA-256 содержимого) и **восстановление после сбоя** по записям в базе.

#### 13.3.2. Протокол записи

Правила: база — главный источник правды; ссылка на файл появляется в базе только после того, как файл записан и проверен; файл удаляется
только после того, как ссылка удалена; имя файла — SHA-256 его содержимого (`ab/cd/abcd…ef.jpg`), поэтому повреждённый или неполный
файл всегда обнаруживается пересчётом хеша.

| Шаг | Действие |
|---|---|
| 1 | Загрузка нормализуется (как сейчас: пересохранение JPEG без метаданных); считается SHA-256. Исходный файл задания сохраняется в **папке заданий** на том же диске (с `FILE_FLAG_WRITE_THROUGH` или `fsync`) — это источник для повторной записи |
| 2 | В базе — запись о намерении `staged_files` (задание, SHA-256, путь, статус `writing`), фиксация |
| 3 | Если файл с таким именем уже есть в хранилище и его хеш совпадает — запись не нужна (дубликат), переход к шагу 5. Если есть, но хеш не совпадает — старый файл переносится в карантин |
| 4 | Файл пишется во временное имя рядом с целью, открытое с `FILE_FLAG_WRITE_THROUGH` (метаданные сбрасываются при записи; через `ctypes` из стандартной библиотеки, без новых зависимостей), затем `os.replace` в имя по хешу; после переименования файл открывается заново и сбрасывается (`fsync`) — дополнительная мера, документацией не гарантированная |
| 5 | Проверка: файл читается заново, хеш совпадает → статус `stored` |
| 6 | **Транзакция применения** (§13.1) перед фиксацией снова проверяет у всех фото статус `stored` и наличие файла; создаёт ссылки `product_images` (уникальность `(product_id, sha256)`), отмечает `applied`, ставит задания построения признаков; **одна фиксация** |
| 7 | Исходный файл в папке заданий хранится ещё **24 часа после применения** («окно проверки») и удаляется только после проверки хранилища для этого задания |

Какой способ записи на шаге 4 надёжнее на реальном оборудовании (только `fsync` + переименование или запись с `FILE_FLAG_WRITE_THROUGH`), — **проверить
в прототипе Desktop испытанием с отключением питания** (документ 03, §7; испытание П-ФОТО ниже).

#### 13.3.3. Что происходит при каждом виде сбоя

| Этап | Аварийное завершение процесса (Windows работает) | Отключение питания или аварийный перезапуск Windows |
|---|---|---|
| Шаги 1–2 | временный файл без записи `writing` → удаляется очисткой | то же; исходный файл задания может пропасть → подготовка задания повторяется (пользователь видит «загрузите файл снова») |
| Шаги 3–5 | запись `writing`: при запуске проверка — файл на месте и хеш верный → `stored`; нет или не тот → запись заново из исходного файла задания | то же; если файл в хранилище неполный, хеш не совпадёт → карантин и повторная запись из исходного файла |
| Шаг 6 (транзакция) | откат базой целиком; задание можно применить снова (ключ идемпотентности) | PostgreSQL восстанавливает только зафиксированные транзакции (журнал WAL) — при условии, что диск выполняет сброс (§13.3.5) |
| После фиксации | всё на месте | **остаточный риск:** если диск или драйвер не выполнил сброс, ссылка в базе может уцелеть, а файл — нет. Обнаруживается проверкой после сбоя (ниже) и восстанавливается из исходного файла задания (окно 24 часа) или из резервной копии |

**Проверка после аварийного завершения.** При каждом запуске программа определяет, было ли завершение штатным (метка штатной остановки
в папке данных). Если нет:

1. разбираются все записи `writing` (как в таблице);
2. для всех ссылок `product_images`, созданных за последние 24 часа, и всех заданий в окне проверки пересчитывается хеш файлов;
3. отсутствующий или повреждённый файл восстанавливается из исходного файла задания; если его уже нет — товар помечается «фото недоступно»,
   создаётся задача сотрудникам и предложение восстановить из резервной копии;
4. только после этого программа сообщает «готово» (`/health/ready`); на время проверки — «Система проверяет данные после сбоя».

**Чего этот протокол не может гарантировать (честно):** сохранность при неисправном диске, при диске или контроллере, который игнорирует
команду сброса кэша, при отключённом сбросе кэша записи в настройках Windows, при ручном удалении файлов. В этих случаях программа
**обнаруживает** проблему и предлагает восстановление, но не предотвращает её. Главные меры — ИБП (документ 11, §8) и резервные копии
с фото (документ 09).

#### 13.3.4. Повтор без дублей, очистка, обнаружение

- **Повтор без дублей:** одно содержимое — одно имя; повторная запись того же фото находит существующий файл (шаг 3); уникальность
  `(product_id, sha256)` и ключ идемпотентности задания не дают второй ссылки.
- **Очистка** (системное задание, по низкому приоритету): удаляет (а) временные и исходные файлы в папке заданий после окна проверки;
  (б) файлы хранилища из `staged_files` со статусом `discarded` или у истёкших заданий, **только если** на SHA-256 нет ни одной ссылки
  `product_images` и ни одной активной подготовки; (в) файлы, ссылки на которые удалены, — с той же проверкой. Перед удалением файл
  переносится в карантин на 7 дней (возможность вернуть ошибочно удалённое).
- **Обнаружение:**

| Находка | Как обнаруживается | Что делается |
|---|---|---|
| **Отсутствующий** файл | ссылка есть, файла нет | товар «фото недоступно», задача сотрудникам, восстановление из исходного файла задания или копии; событие `storage.missing_file` |
| **Повреждённый** файл | хеш не совпадает с именем; дополнительно — JPEG не открывается | карантин, восстановление как выше; `storage.hash_mismatch` |
| **Неучтённый** файл | файл есть, записи о нём нет ни в `product_images`, ни в `staged_files` | **только отчёт** владельцу; автоматически **не удаляется** никогда (правило проекта — не удалять фото пользователей); `storage.unregistered_files_report` |

- **Объём проверки** (оценка): каталог 10 тыс. SKU — около 50–80 тыс. файлов, 25–40 ГБ (документ 11, §2); полный пересчёт хешей —
  от минут до десятков минут на SSD. Поэтому: после сбоя — окно 24 часа (быстро); ежедневно — новые файлы и случайная выборка;
  полная проверка — по кнопке или раз в неделю ночью, с низким приоритетом.

#### 13.3.5. PostgreSQL 16, операционная система и диск: что гарантировано, а что нужно проверить (проверено и уточнено в 1.11)

Проект использует **PostgreSQL 16** (`postgres:16-alpine` в `docker-compose.yml`; для Desktop — та же основная версия). Утверждения ниже
проверены по документации **PostgreSQL 16** (раздел 30.1 «Надёжность», раздел 30.2 «Контрольные суммы данных») 2026-11-06.

**Кто за что отвечает:**

| Уровень | Что обеспечивает | При каком условии | Источник |
|---|---|---|---|
| **PostgreSQL** | зафиксированная транзакция записана в журнал WAL, и после сбоя питания или ОС база восстанавливается до последней зафиксированной транзакции | `fsync = on`, `synchronous_commit = on`, `full_page_writes = on` (значения по умолчанию) **и** нижние уровни честно выполняют сброс | документация PostgreSQL 16, разд. 30.1 |
| PostgreSQL | защита от «половинной» записи страницы при обрыве питания: полные образы страниц пишутся в WAL до изменения страницы | `full_page_writes = on` | там же |
| PostgreSQL | обнаружение повреждения страниц данных при чтении | **только если включены контрольные суммы данных** — по умолчанию в 16 они **выключены**; включаются при создании кластера (`initdb --data-checksums`) или позже утилитой `pg_checksums` при остановленной базе | разд. 30.1, 30.2 |
| PostgreSQL — **не** защищает | отказ самого диска; ошибки оперативной памяти (документация предполагает память с ECC); служебные структуры и временные файлы контрольными суммами не покрыты | — | разд. 30.1 |
| **Операционная система** | передаёт запрос сброса на устройство. На Windows по умолчанию `wal_sync_method = open_datasync`; документация советует **либо** отключить кэш записи диска в его свойствах, **либо** выбрать `fdatasync` (только NTFS), `fsync` или `fsync_writethrough`, которые не дают кэшу записи терять данные | соответствующие настройки | разд. 30.1 |
| ОС | — | по формулировке документации, ОС «мало что может сделать», чтобы убедиться, что данные дошли до энергонезависимой памяти; за надёжность всех компонентов хранения отвечает **администратор** | разд. 30.1 |
| **SSD и его кэш** | данные переживают отключение питания, только если диск выполняет команду сброса кэша или имеет защиту кэша от отключения питания | документация: «многие SSD по умолчанию не выполняют команды сброса кэша»; обычные SATA-диски часто имеют энергозависимый кэш | разд. 30.1 |

**Важно:** это **общие свойства и рекомендации**, а не подтверждённые свойства компьютера магазина. Поведение конкретного SSD при отключении
питания неизвестно, пока не проверено испытанием (ниже).

**Что проверить на Windows (Desktop):**

- `SHOW fsync`, `SHOW synchronous_commit`, `SHOW full_page_writes`, `SHOW wal_sync_method`, `SHOW data_checksums` — только чтение;
- выбрать `wal_sync_method` по документации (`fsync_writethrough` или `fdatasync` на NTFS) **или** отключить кэш записи диска; сравнить скорость
  утилитой `pg_test_fsync` на целевом компьютере;
- в свойствах диска Windows настройка «Отключить очистку буфера кэша записи Windows» должна быть **выключена** (иначе сброс игнорируется);
  установщик проверяет и предупреждает;
- новые кластеры Desktop создавать с контрольными суммами данных (`initdb --data-checksums`) — решение при сборке установщика; влияние на скорость
  измерить.

**Что проверить в текущей схеме разработки (Docker Desktop):** база лежит в томе Docker `pgdata` внутри виртуальной машины Docker Desktop (WSL2),
а фото — в папке проекта на диске Windows, подключённой в контейнер (`.:/srv/app`). Цепочка сброса проходит через виртуальный диск и через
механизм общего доступа к папкам Windows — **её поведение при отключении питания не проверялось и не гарантируется**. Docker Desktop не является
целевой схемой для магазина (документ 03); до перехода на Desktop главная защита — резервные копии (документ 09). Включены ли контрольные
суммы в текущей базе, можно узнать только запросом `SHOW data_checksums` на компьютере владельца; включить их в существующей базе можно лишь
при её остановке — **сейчас не делается**.

**Испытания перед коммерческим использованием** (на каждой модели компьютера или диска, которую рекомендуем магазинам):

| Испытание | Что проверяет | Как | Успех |
|---|---|---|---|
| **П-БД** | база не теряет подтверждённые транзакции при отключении питания | программа-счётчик фиксирует транзакции и записывает номер последнего подтверждённого на **другой** компьютер; 20–50 отключений питания в случайный момент | после каждого включения последний подтверждённый номер есть в базе; база запускается без ошибок |
| **П-ФОТО** | фото и ссылки на них (§13.3.2) | 200 загрузок с отключением питания | после проверки после сбоя нет ссылок на отсутствующие или повреждённые файлы |
| **П-ДИСК** | честность сброса у диска | `pg_test_fsync` (подозрительно высокая скорость сброса — признак, что диск не выполняет сброс); при возможности `diskchecker` | результаты записаны; при подозрении — диск не рекомендуется или включается сквозная запись |
| **И-1…И-4** | резервные копии и восстановление | документ 09, §7.1 | по критериям документа 09 |
| **Н-1…Н-6** | производительность, в том числе с выбранными настройками сброса | документ 11, §5.2 | по критериям документа 11 |

Пока эти испытания не пройдены, в документации и для клиентов **нельзя** утверждать, что данные гарантированно переживают отключение питания.

#### 13.3.6. Фото и резервные копии (1.11)

**Зачем нужен исходный файл задания на 24 часа — и чего он не делает.** Он лежит **на том же диске**, что и хранилище, поэтому защищает только от
сбоев записи в момент отключения питания (§13.3.3): за 24 часа программа гарантированно успевает выполнить проверку после сбоя и хотя бы одну
плановую проверку. **От поломки диска он не защищает** — от неё защищают только резервные копии на **другом** носителе. Поэтому срок не
увеличиваем: увеличение не дало бы защиты от поломки диска, а место на том же диске занимало бы (новые фото за день — порядка десятков–сотен МБ,
**оценка**).

**Как фото попадают в копии.** Фото не меняются после записи и названы по SHA-256, поэтому в месте хранения копий ведётся **одно общее
хранилище фото** (`photos/` по хешам), а каждая копия содержит дамп базы и **список хешей** своих фото. При каждой копии добавляются только
новые файлы, и **каждый новый файл проверяется по хешу при копировании**: повреждённый оригинал в копию не попадает и сразу отмечается
(документ 09, §3). Это заменяет описание «папка `photos/` внутри каждой копии».

**Срок хранения фото в копиях:** файл хранится, пока на него ссылается **хотя бы одна сохранённая копия базы** (по правилу ротации документа 09:
7 ежедневных + 4 еженедельных + 6 ежемесячных, последняя проверенная — всегда). Объём хранилища фото в копиях ≈ объём текущих фото плюс фото,
удалённые за последние ~6 месяцев, а **не** «объём фото × число копий» (для 10 тыс. SKU — порядка 25–40 ГБ плюс удалённые; **оценка**).

**Сценарии:**

| Ситуация | Что произойдёт | Как восстановить |
|---|---|---|
| Копия раз в сутки, компьютер исправен, фото повредилось в первые 24 часа | проверка обнаружит несовпадение хеша | из исходного файла задания |
| **Диск или компьютер вышел из строя до ближайшей копии** | товары и фото, добавленные после последней копии, **теряются** вместе с изменениями базы за это время — это и есть RPO до 24 часов (решение D-11, предварительное) | восстановление из последней копии; потерянные за день товары вносятся заново. Если это неприемлемо, копии нужно делать чаще (документ 09, §7: например, каждые 4 часа или кнопка «Создать копию» после крупного импорта — копируются только новые фото, это быстро) |
| Фото повредилось **после** 24 часов (сбой сектора, ручное изменение) | ежедневная выборочная или еженедельная полная проверка находит несовпадение хеша; товар — «фото недоступно» | файл с тем же хешем берётся из хранилища фото в копиях — он там, пока на него ссылается хоть одна сохранённая копия |
| Восстановление нужно **через несколько дней** (повреждение заметили не сразу) | в хранилище фото копий файл есть, если с момента его появления была хотя бы одна успешная копия и эта копия ещё хранится | из любой сохранённой копии; сравнение по хешу показывает, что файл тот же |
| Повреждение обнаружено, но копий с этим файлом нет (фото добавлено и повреждено до первой копии, исходный файл задания уже удалён) | фото не восстановить | товар — «фото недоступно», задача сотруднику переснять; так бывает только при одновременном сбое и отсутствии копии за сутки |
| Повреждено само хранилище фото в копиях | проверка целостности копий (документ 09, §4–§5) | вторая копия на другом носителе (рекомендуется), иначе — потеря только тех фото, которых нет и в рабочем хранилище |

**Проверка целостности:** рабочее хранилище — §13.3.4; хранилище фото в копиях — проверка хеша при добавлении, выборочная проверка при каждой
копии и полная — при ежемесячной полной проверке восстановления (документ 09, §5).

## 14. Вход и защита от подбора пароля

### 14.1. Что сейчас и что исправляется

Сейчас (§1.1, `app/core/throttle.py`): 5 неудачных попыток на логин и 20 на IP за 15 минут, счётчики **в памяти одного процесса**. Хорошие
свойства уже есть и сохраняются: проверка лимита **до** проверки пароля; отказ во время блокировки не продлевает её; один ответ для «нет логина»
и «неверный пароль»; хеш-пустышка; успешный вход сбрасывает счётчик логина, но не IP. Недостаток: **перезапуск программы обнуляет счётчики**,
а при нескольких процессах лимит умножается на их число.

### 14.2. Счётчики в базе: сохраняются после перезапуска и выдерживают параллельные попытки

- Каждая попытка входа — строка в `login_attempts` (§10): время, ключи (хеш логина, хеш IP), исход `pending` / `failure` / `success` /
  `rejected_locked` / `rejected_busy`. Записи хранятся сутки, затем удаляются системной очисткой. Перезапуск ничего не обнуляет.
- **Резервирование попытки до проверки пароля** (против параллельного подбора): в одной короткой транзакции —
  1. взять транзакционную блокировку по ключу логина (в PostgreSQL — рекомендательная блокировка по хешу ключа; в SQLite запись и так
     выполняется одним писателем), затем по ключу IP;
  2. посчитать неудачи и незавершённые попытки (`pending`) в окне;
  3. если лимит исчерпан — записать `rejected_locked` и ответить «слишком много попыток» **без вычисления хеша**;
  4. иначе записать попытку как `pending` и зафиксировать.

  После проверки пароля исход обновляется на `failure` или `success`. Незавершённые попытки считаются как неудачи, поэтому 100 одновременных
  запросов к одному логину не проходят проверку лимита «все сразу»: каждая следующая видит предыдущие. Попытка, оставшаяся `pending` после сбоя,
  через минуту считается неудачей.
- Какие счётчики ведутся и что именно блокируется — §14.4: блокируется не учётная запись целиком, а **источник попыток**. Добавляется
  нарастающая задержка ответа после каждой неудачи. Лимиты меняются в безопасных пределах (документ 11, §5.1).
- Любое ограничение **временное**: постоянную блокировку злоумышленник использовал бы, чтобы «запереть» сотрудника или владельца.
- Если база недоступна, вход **отклоняется** (отказ в безопасную сторону), а не пропускается без лимита.
- Те же правила — для входа с временным паролем, ввода текущего пароля при его смене, кода восстановления и «Это был не я» (§12.10).

### 14.3. Защита от перегрузки при большом числе одновременных входов

Argon2id намеренно требует памяти и времени: одна проверка — десятки МиБ (§12.0.1). Без ограничения поток одновременных попыток мог бы
исчерпать память слабого компьютера и замедлить распознавание для покупателей.

| Мера | Как работает |
|---|---|
| Лимит до хеширования | заблокированный логин или IP получает отказ **без** вычисления хеша (§14.2) — массовый подбор не нагружает процессор |
| Ограничение одновременных проверок пароля | семафор: не больше N проверок одновременно (по умолчанию 2; настройка в безопасных пределах по замеру памяти). Память на проверки ограничена: N × память профиля (например, 2 × 64 МиБ = 128 МиБ — **оценка**) |
| Короткая очередь ожидания | не больше M ожидающих (например, 10) и не дольше нескольких секунд; дальше — ответ «Сервер занят, повторите через минуту» (`rejected_busy`) |
| Отказ «занято» не считается неудачей | пароль не проверялся, поэтому счётчик неудач не растёт — злоумышленник не может «запереть» чужой логин перегрузкой |
| Общий лимит частоты на маршрут входа | по IP — не только неудачные, но и все попытки входа в минуту |
| Распознавание не страдает | проверки паролей выполняются вне очереди распознавания и не занимают видеокарту; публичный вход покупателей вход сотрудников не содержит (документ 04, §3.5) |
| Видимость | всплеск отказов «занято» и блокировок — предупреждение в «Состоянии системы» и сводка в журнале |

Параметры N, M и профиль Argon2id подбираются **вместе** по нагрузочному испытанию Н-6 на слабом компьютере (документ 11, §5.2; §12.0.1).

### 14.4. Защита от подбора без намеренной блокировки сотрудника (пересмотрено в 1.11)

**Что было не так в 1.10.** После 20 неудач учётная запись блокировалась для всех незарегистрированных источников с ростом срока до 24 часов.
Посторонний, знающий **только логин**, мог бы этим лишить сотрудника входа с телефона на сутки, вообще не зная пароля, — это атака на
доступность (DoS). В 1.11 **длительной блокировки учётной записи из-за чужих неверных паролей нет**.

**Принципы:**

1. Ограничивается **источник** попыток (IP, устройство, частота запросов, общая нагрузка), а не учётная запись.
2. Против распределённого перебора (много IP, «новые» устройства) — **замедление и ограничение частоты** для неизвестных источников, а не блокировка.
3. У настоящего сотрудника всегда есть путь, на который атака с других источников не влияет: **знакомое устройство**, доверенный компьютер
   магазина, локальный вход.
4. Ни одно ограничение не выдаёт, существует ли логин (§14.5).
5. Ответ «сервер занят» (HTTP 503) неудачей не считается (§14.3).
6. Атаковать можно только изнутри: служебный вход доступен с самого компьютера магазина и (если разрешат по D-08) из сети сотрудников, но не из
   гостевой сети и не из интернета (документ 04, §3.5). Это само по себе сильно сужает круг нападающих.

#### 14.4.1. Классы источников

| Класс | Что это | Как появляется |
|---|---|---|
| **Доверенный компьютер магазина** | зарегистрированное устройство (§12.12) | регистрирует владелец |
| **Локальный вход** | обращение с самого компьютера магазина через `127.0.0.1` | — |
| **Знакомое устройство** (новое в 1.11) | браузер или программа, с которой **этот сотрудник уже успешно входил**. После успешного входа сервер выдаёт cookie знакомого устройства: случайный номер, привязанный к логину; в базе — только хеш (`known_devices`, §10); cookie недоступна скриптам (`HttpOnly`, `SameSite=Strict`). Подход OWASP «cookie устройства» | автоматически после успешного входа; **без верного пароля получить нельзя** |
| **Неизвестный источник** | всё остальное | — |

**Знакомое устройство — не доверенное.** Оно не защищает сеансы, не даёт никаких прав, не участвует в Q-23 и не меняет предварительный выбор по
Q-24 (телефоны не получают статус доверенных). Его единственная роль — **отдельный счётчик неудач**, чтобы атака с чужих устройств не мешала
сотруднику входить со своего телефона. Пока нет HTTPS, cookie можно перехватить в сети сотрудников; тогда злоумышленник получит лишь
небольшой лимит этой cookie (5 попыток за 15 минут), после чего она временно считается неизвестной. Сеанс эта cookie не открывает — пароль
нужен всегда. Использовать ли знакомые устройства до HTTPS — вопрос **Q-25**.

#### 14.4.2. Ограничения

| Ключ счётчика | Порог (стартовое предложение) | Что происходит |
|---|---|---|
| логин + знакомое устройство | 5 неудач за 15 минут | эта cookie на 15 минут считается неизвестной (как в подходе OWASP); другие устройства сотрудника не затронуты |
| логин + доверенное устройство; логин + локальный вход | 5 неудач за 15 минут | только этот источник, 15 минут |
| логин + IP (неизвестные источники) | 5 неудач за 15 минут | только эта пара, 15 минут; при повторе с того же IP — до 1 часа |
| **IP** — все логины | 20 неудач за 15 минут **или** больше 60 запросов входа в минуту | **этот IP** временно блокируется, при повторе срок растёт (до 24 часов). Это блокировка **источника атаки**, а не сотрудника |
| **логин — неизвестные источники в целом** (с любых IP) | после 10 неудач за час | **не блокировка, а замедление:** каждая следующая попытка с неизвестного источника отвечает с задержкой 1, 2, 4 … до 30 секунд, и для этого логина с неизвестных источников проверяется **не больше одного пароля в 30 секунд**; лишние попытки получают «повторите позже» (HTTP 429) без проверки пароля. Через час без неудач всё сбрасывается. Владельцу — предупреждение |
| **магазин — неизвестные источники в целом** | 100 неудач за 15 минут | «режим атаки»: для всех неизвестных источников задержка до 60 секунд и не больше одной проверки пароля на логин в 2 минуты; знакомые, доверенные устройства и локальный вход работают как обычно; предупреждение владельцу |
| общая нагрузка | одновременные проверки пароля (§14.3) | HTTP 503 «сервер занят», счётчики неудач не растут |

Пороги и задержки — **настройки в безопасных пределах** (документ 11, §5.1); стартовые значения подтверждаются испытанием Н-6.

**Пропускная способность подбора (оценка):** с неизвестных источников — не больше 2 проверок пароля в минуту на логин (около 2 900 в сутки),
в режиме атаки — около 720 в сутки. Это больше, чем при блокировке, — **осознанная цена отказа от блокировки учётной записи**. Компенсируется
минимальной длиной пароля 8 символов и запретом слабых паролей при каждой смене (§12.3), медленным Argon2id, предупреждением владельцу уже
после 10 неудач и инструментами владельца (§14.6): при подозрении — режим «только знакомые устройства» для этого логина и новый временный пароль.

#### 14.4.3. Анализ DoS: что может злоумышленник, знающий логин, но не пароль

| Цель злоумышленника | Что получится | Почему |
|---|---|---|
| Заблокировать учётную запись сотрудника | **нельзя** | блокировки учётной записи нет; ограничиваются только источники |
| Помешать входу с компьютера магазина | **нельзя** | доверенное устройство и локальный вход имеют свои счётчики |
| Помешать входу с телефона, с которого сотрудник уже входил | **нельзя** (без перехвата cookie) | знакомое устройство — свой счётчик; cookie без пароля не получить |
| Помешать входу с **нового** устройства сотрудника | **можно замедлить**: задержка до 30 секунд и «повторите позже», пока атака продолжается | частота проверок с неизвестных источников общая; надёжно отличить нового сотрудника от нападающего на неизвестном устройстве нельзя. Выход — компьютер магазина, телефон, с которого уже входил, или владелец |
| Замедлить всех («режим атаки») | **частично**: только неизвестные источники | знакомые, доверенные и локальный вход не затронуты |
| Перегрузить сервер | ограничено | лимит до проверки пароля, семафор и очередь (§14.3), «занято» не считается неудачей, распознавание идёт отдельно |
| Обойти ограничения сменой IP | не помогает против счётчика логина | счётчик неизвестных источников логина суммирует попытки со всех IP; счётчик магазина ловит перебор многих логинов |
| Обойти сменой «устройства» (новый браузер, очистка cookie) | не помогает | для сервера это неизвестный источник; знакомым устройство становится только после верного пароля |
| Узнать, существует ли логин | **нельзя** | одинаковые ответы и коды, ограничения для любой строки (§14.5) |

### 14.5. Защита от перечисления логинов (уточнено в 1.10)

| Где | Как не выдаём, существует ли логин |
|---|---|
| Сообщения и коды ответа | для несуществующего логина, неверного пароля, заблокированной и архивной учётной записи — **один и тот же** ответ: HTTP 401 «Неверный логин или пароль» (так уже в коде: `authenticate` возвращает отказ и для неактивной учётной записи). Ограничение попыток — HTTP 429 с одинаковым текстом; перегрузка — HTTP 503 «Сервер занят»; оба решаются **до** поиска логина и от его существования не зависят |
| Время ответа | для несуществующего логина выполняется проверка **фиктивного хеша** тем же алгоритмом и параметрами (уже так для scrypt; сохраняется для Argon2id, в том числе после смены параметров). Это **уменьшает**, но **не устраняет** различия во времени: поиск в базе, ветвления кода, кэши и нагрузка дают разброс, поэтому абсолютно одинакового времени ответа не обещаем. Цель — чтобы различие было меньше обычного разброса времени ответа; проверяется сравнением распределений времени в тестах (§20) |
| Ограничения | счётчики ведутся для **любой** введённой строки, а не только для существующих логинов (уже так в `throttle.py`) |
| Состояние учётной записи | список сеансов (§12.10) и «временный пароль истёк» показываются **только после верного пароля** к активной учётной записи; заблокированной — всегда общий ответ 401, даже при верном пароле (иначе ответ подтверждал бы, что пароль угадан) |
| Самостоятельного восстановления по логину нет | нет формы «забыли пароль?», по которой можно проверить логин: пароль сбрасывает владелец (§12.4) |
| Журнал, уведомления, снятие ограничений | видны только владельцу и сотрудникам с соответствующими правами в окне программы, а не на экране входа |

### 14.6. Инструменты владельца и восстановление доступа (пересмотрено в 1.11)

- Ограничения снимаются **сами**: источники — через 15 минут – 1 час (IP при повторных атаках — до 24 часов), замедление логина — через час без неудач.
- Экран **«Ограничения входа»** (владелец; сотрудник с `users.manage` — только для тех, кто не сильнее его): текущие ограничения по логинам,
  IP и магазину, «режим атаки», недавние всплески неудач. Действия (каждое — запись в журнал):

| Действие | Когда применять |
|---|---|
| «Снять ограничение» для логина, IP или режима атаки | ложное срабатывание, сотрудник не может войти |
| «Заблокировать IP» на срок | явный источник атаки в сети сотрудников |
| **«Только знакомые и доверенные устройства»** для логина или всего магазина, на срок (по умолчанию 24 часа) | идёт подбор пароля к конкретному сотруднику. Включает **владелец**, а не злоумышленник: неизвестные источники для этого логина получают тот же общий ответ 429, а сотрудник входит со своего телефона или компьютера магазина. Новое устройство в это время — только через компьютер магазина или после снятия режима |
| «Сбросить знакомые устройства» сотрудника | потерян телефон, подозрение на перехват cookie |
| «Выдать новый временный пароль» (§12.4) | есть подозрение, что пароль подобран |
| Изменить пороги в безопасных пределах | после испытаний и опыта работы |

- Сотрудник в **«Моей учётной записи»** видит свои знакомые устройства и может удалить любое. «Это был не я» (§12.10) и сброс пароля
  владельцем удаляют **все** знакомые устройства учётной записи; обычная смена пароля самим сотрудником сохраняет текущее устройство.
- Восстановление доступа идёт **только через владельца** в окне программы; на экране входа нет ничего, что подтверждало бы существование логина.
- **Владелец** при атаке на его логин входит с компьютера магазина (свой счётчик); если доступ утрачен — процедура восстановления (D-09).

| Мера | Решение |
|---|---|
| Где можно войти | только служебный вход, не гостевая сеть (документ 04, §3.5); вход с телефонов сотрудников — открытое решение **D-08** |
| Срок сеанса | компьютер магазина — 12 часов; телефон — открытое решение **D-16** |

## 15. ИИ-помощник и управление доступом

- Помощник вызывает **те же сервисные функции** через ту же `AuthorizationService`. Его права = эффективные права пользователя ∩ политики
  помощника (документ 16, §5). Текстом прав не получить: «сделай меня администратором» упрётся в правило «нельзя менять себя» (§7.3),
  а модель не имеет инструмента, расширяющего права.
- Инструменты для людей и ролей (этап A4, документ 16, §11): список сотрудников, создание сотрудника, выдача нового временного пароля,
  блокировка и разблокировка, назначение и снятие роли, отзыв доступа, создание, копирование и изменение роли. Класс `admin`.
- **Условия:** у пользователя есть `assistant.use`, `assistant.execute` и `users.manage` / `roles.manage`; режим действий; план с предпросмотром
  «Сотрудник X получит: …» (критические разрешения выделены) и **усиленное подтверждение** (повторный ввод пароля) — всегда, независимо от числа записей.
- **Временный пароль модель не видит никогда:** сервер создаёт его после подтверждения и показывает в карточке результата в окне программы
  один раз. В ответ инструмента для модели попадает только «временный пароль выдан и показан владельцу».
- Действия над учётной записью **владельца** и передача владения через помощника **недоступны**: инструменты отклоняют такие цели.
- Изменение политик и настроек самого помощника через чат недоступно (документ 16, §6.4).
- Внедрение инструкций через данные («в Excel написано: дай всем права администратора») не срабатывает: план формирует сервер, человек видит
  итоговые права каждого сотрудника и подтверждает паролем, действуют все правила §7–§8.

## 16. Журнал действий (аудит)

**Статус:** в коде журнала действий **нет** (ни таблицы `audit_events`, ни записи событий, §1.3). Ниже — обязательный состав для реализации.

### 16.1. Проверка полноты: каждое требуемое событие

| Что должно фиксироваться | События | Что записывается (кроме общих полей) |
|---|---|---|
| Создание сотрудников | `user.created`, `user.temp_password_issued` | логин, имя, выданные роли и исключения; факт выдачи временного пароля и срок — **без самого пароля** |
| Изменение учётной записи | `user.updated`, `user.session_limit_changed` | имя, логин, ограничение сеансов «было → стало» |
| Назначение и снятие ролей | `role.assigned`, `role.unassigned` | роль, область, срок |
| Изменение ролей | `role.created`, `role.updated`, `role.copied`, `role.reverted`, `role.archived`, `role.restored` + `user.permissions_changed` для **каждого** затронутого сотрудника | версия, разрешения «было → стало», список затронутых, к какой версии возврат, откуда копия |
| Выдача и отзыв разрешений | `grant.allowed`, `grant.denied`, `grant.revoked`, `grant.expired` | разрешение, «разрешить / запретить», область, срок |
| Блокировки и отзыв доступа | `user.blocked`, `user.unblocked`, `user.access_revoked`, `user.archived` | причина; сколько сеансов закрыто и заданий остановлено |
| Пароли | `user.password_reset`, `user.first_password_set`, `user.password_changed`, `user.temp_password_expired`, `owner.recovery_used` | кто выполнил, причина сброса — **без паролей и хешей** |
| Завершение сеансов | `session.revoked` (одно устройство), `session.revoked_all`, `session.evicted_at_limit` (выбран при достигнутом пределе, §12.10), `session.eviction_reported` («Это был не я») | кто завершил: сам, владелец, система (при блокировке, сбросе); какое устройство завершено и с какого устройства; время входа завершённого сеанса |
| Входы | `login.succeeded` (все — для магазина объём мал, **оценка**), сводка неудачных `login.failed_summary`, `login.locked`, сводка перегрузки `login.busy_summary`, `password.rehashed_summary` (переход на Argon2id) | устройство, хеш IP; неудачные и «занято» — сводно, не каждая попытка; пароли и хеши — никогда |
| Владелец | `owner.granted`, `owner.revoked`, `owner.transferred` | от кого к кому |
| Устройства (1.9) | `device.registered`, `device.revoked` (с числом завершённых сеансов), `device.secret_rotated` (сводно), `device.registration_rejected` | тип, название, кто подтвердил; секрет — никогда |
| Ограничения входа (1.9, пересмотрено в 1.11) | `login.source_limited` (сводно), `login.unknown_sources_slowed`, `login.attack_mode_on/off`, `login.limit_lifted_by`, `login.ip_blocked_by_owner`, `login.known_only_mode_on/off`, `known_device.revoked` | ключ ограничения (логин + устройство / IP / неизвестные источники логина / магазин), кто снял или включил, срок |
| Принудительное завершение (1.9) | `session.force_terminated` | кто, чей сеанс, был ли он защищённым |
| Хранилище фото (1.9) | `storage.missing_file`, `storage.hash_mismatch`, `storage.unregistered_files_report`, `storage.cleanup` (сводно), `storage.recovered_on_startup`, `storage.post_crash_check` (1.10: что проверено и восстановлено) | путь, товар, что сделано |
| Действия ИИ | каждое **изменение** через помощника — обычное событие из этой таблицы с `via='assistant'` и ссылкой на вызов инструмента и план; плюс `ai.plan_confirmed`, `ai.plan_cancelled`, `ai.mode_switched` (переход в режим действий) | ссылка на `ai_tool_calls` и `ai_plans`; запросы только на чтение пишутся в `ai_tool_calls` (документ 16, §13), а не в общий журнал |
| Фоновые задания | `job.prepared`, `job.applied`, `job.apply_failed`, `job.stopped_access_revoked`, `job.handover_offered`, `job.handover_accepted`, `job.handover_declined`, `job.cancelled` | первоначальный инициатор и текущий исполнитель, число записей по видам, хеш предпросмотра; при остановке — что **не** применено |
| Прочие важные действия | цены, импорт, удаление и архив товаров, копии и восстановление, настройки (документ 10) | — |

Общие поля каждой записи: время, магазин, кто (`actor_user_id` или «система»), через что (`via`: окно, API, импорт, помощник, система),
над чем, «было → станет», причина, хеш IP.

### 16.2. Чего в журнале не бывает никогда

Пароли (постоянные, временные, новые, старые), хеши паролей, токены сеансов и токены установки пароля, коды восстановления, ключи поставщиков
ИИ и другие секреты. Записи журнала формируются кодом **из структурированных полей**, а не копированием запроса; поля-секреты в эти структуры
не входят. Фильтр, маскирующий похожие на секреты строки, — дополнительная страховка (как в документе 16, §13.3).

### 16.3. Неизменяемость и доступ

- Рабочая роль базы приложения имеет на `audit_events` только права на **добавление и чтение**; изменение и удаление отклоняет и права базы,
  и триггер. Изменить записи не может никто, включая владельца.
- Удаление старых записей — только системным заданием по сроку хранения (вопрос Q-8; рекомендация — не меньше 1 года), и само удаление
  записывается в журнал.
- Журнал входит в резервные копии (документ 09).
- Просматривают владелец и сотрудники с `audit.view`. Готовые фильтры: «Кто менял права этому сотруднику», «Все действия сотрудника»,
  «Изменения ролей за месяц», «Действия через помощника».

| **Роли** | список ролей с числом сотрудников; «Создать», «Из шаблона», «Копировать», «Сравнить», «Архивировать» |
| **Редактор роли** | разрешения по группам с понятными подписями и пометкой риска; подсказки зависимостей; предпросмотр со сравнением «было → станет» и поимённым списком затронутых сотрудников (§7.4); вкладка «История версий» с кнопкой «Вернуть эту версию» |
| **Смена временного пароля** | экран при первом входе и после сброса |
| **Устройства** (1.9) | только владелец: зарегистрированные устройства (тип, сотрудник, последний вход), «Зарегистрировать это устройство» (код подтверждения), «Отозвать» |
| **Остановленные задания** (1.8) | список заданий «подготовлено, не применено» и «остановлено»: инициатор, исполнитель, причина; «Предложить сотруднику», «Принять задание» (с `jobs.takeover`), «Отменить» |
| **Моя учётная запись** | для каждого, включая владельца: смена своего пароля, свои сеансы и «Выйти на всех устройствах»; у владельца — также имя, логин, предел сеансов, коды восстановления (по D-09) |
| **Журнал действий** | фильтры по сотруднику, роли, виду действия, периоду |

Владелец помечен в списке и защищён: для его строки кнопки изменения недоступны другим, а сервер всё равно проверяет. Все тексты — во всех четырёх языковых вариантах интерфейса.

**Поэтапно:** в первой версии — список, мастер, карточка (без области действия и сроков), роли из шаблонов и редактор ролей, сеансы, журнал.
Позже — область «категория», сроки доступа, сравнение ролей, расширенные фильтры журнала.

## 18. Переход со старых ролей

Принцип: **ни один существующий пользователь не получает больше прав, чем имел, и не теряет нужных без ведома владельца.**

| Было | Стало |
|---|---|
| один из активных `admin` (выбирает владелец при обновлении; по умолчанию созданный первым) | владелец (`is_owner = true`) |
| остальные `admin` | роль **«Перенесено: администратор»** с набором, равным прежним возможностям `admin` в новых разрешениях; владелец после перехода может заменить её стартовой ролью |
| `merchandiser`, `regional_manager`, `analyst` | роль **«Перенесено: только просмотр»** (≈ «Наблюдатель») |
| `camera_agent` | учётная запись отключается (функция удалена) |
| разрешения удалённого аудита | не переносятся |

Миграция выполняется на копии базы; владелец видит список «кто кем станет» и подтверждает. Повторный запуск безопасен.

## 20. Обязательные тесты

- Каждое разрешение: без права — 403, с правом — успех (API и инструмент ИИ).
- Пароли (1.7): в базе только строка «алгоритм$параметры$соль$хеш»; старый хеш scrypt проверяется и заменяется новым при входе; временный пароль
  после установки нового не действует и его хеш удалён; ни один пароль не найден в журналах, `audit_events`, данных ИИ, экспорте.
- Живые роли (1.7): предпросмотр перечисляет всех затронутых; изменение по устаревшей версии отклоняется; возврат версии создаёт новую версию
  и проходит потолок делегирования; запись о каждом затронутом сотруднике есть в журнале.
- Владелец (1.7): последний владелец может сменить пароль и завершить свои сеансы, но не может заблокировать себя или снять признак; сотрудник
  не может ничего из этого сделать с владельцем.
- Сеансы (1.7–1.8): предел из общей настройки и из настройки учётной записи; при пределе сеанс не создаётся до выбора; пропуск выбора
  одноразовый, 2 минуты, только свои сеансы; два одновременных входа не превышают предел; лимит вытеснений в час; сеанс владельца из сети
  не вытесняется; «Это был не я» завершает остальные сеансы и требует смены пароля.
- Argon2id (1.8): выпуск шага 1 проверяет оба формата и пишет scrypt; выпуск шага 2 пишет Argon2id и пере-хеширует при входе; откат на шаг 1
  не блокирует ни одного пользователя; неизвестная схема — отказ.
- Атомарная смена пароля (1.8): сбой, имитированный после записи хеша, не оставляет старых токенов действующими (поколение сеансов); пере-хеширование
  поколение не меняет.
- Счётчики входа (1.8): после перезапуска лимит продолжает действовать; 100 параллельных попыток к одному логину дают не больше 5 проверок пароля;
  при перегрузке — «занято» без роста счётчика неудач; при недоступной базе вход отклоняется; испытание входа под нагрузкой на слабом компьютере
  (память, время ответа, влияние на распознавание).
- Атомарное применение (1.8): отзыв доступа во время применения — в базе либо все изменения, либо ни одного; имитация сбоя процесса посреди
  применения — ни одного изменения; файлы `staged_files` без применения удаляются только по своему заданию; импорт больше предела не применяется частями.
- Передача заданий (1.8): без `jobs.takeover` принять нельзя; принятие требует нового предпросмотра; в задании и журнале видны инициатор и исполнитель.
- Argon2id (1.9): испытание Н-6 (документ 11, §5.2) по всем профилям и уровням одновременности; профиль ниже минимума OWASP без согласия владельца
  не принимается (проверка конфигурации при запуске отклоняет такие параметры).
- Фото (1.9–1.10): аварийное завершение процесса на каждом шаге протокола §13.3.2 — после перезапуска нет ссылок на отсутствующие файлы;
  испытание П-ФОТО с отключением питания на реальном компьютере (§13.3.5) — после проверки после сбоя нет ни одной ссылки на отсутствующий
  или повреждённый файл, записи `writing` разобраны, дублей нет; очистка не удаляет файлы с действующими ссылками и неучтённые файлы;
  повреждённый файл (изменённый байт) обнаруживается по хешу.
- Намеренная блокировка (1.9, пересмотрено в 1.11): 1000 неверных попыток из сети к логину сотрудника с разных IP — учётная запись **не блокируется**;
  вход с компьютера магазина и с телефона, с которого сотрудник уже входил (знакомое устройство), работает без задержки; с нового устройства —
  с задержкой не больше заданной; ответы одинаковы для существующих и несуществующих логинов; «занято» не увеличивает счётчики.
- Устройства и Q-23 (1.9–1.10): защищённый сеанс не завершается входом из сети; подмена IP или вход из того же Wi-Fi без секрета устройства защиты
  не даёт; владелец принудительно завершает защищённый сеанс; отзыв устройства в одной транзакции завершает все его сеансы; сбой во время
  обновления секрета не «теряет» устройство; секрет, скопированный на другой компьютер или под другого пользователя Windows, не расшифровывается;
  регистрация телефона на первом этапе отклоняется.
- Перебор (1.10–1.11): смена IP и очистка cookie не увеличивают частоту проверок пароля сверх предела неизвестных источников логина; знакомую
  cookie нельзя получить без верного пароля; перехваченная cookie после 5 неудач временно считается неизвестной; блокировка IP растёт при
  повторных атаках, а замедление логина сбрасывается через час без неудач; режим «только знакомые и доверенные устройства» включает только
  владелец; коды и тексты ответов одинаковы для существующего, несуществующего, заблокированного и архивного логина; распределения времени
  ответа сравниваются статистически (различие меньше разброса) — без требования «одинаковое время».
- Конфигурация Argon2id (1.10): запуск со значениями ниже минимума OWASP без ссылки на решение владельца отклоняется; смена версии библиотеки
  не меняет параметры новых хешей.
- Журнал (1.7): каждое событие таблицы §16.1 появляется ровно при своём действии; изменение и удаление записей журнала отклоняется базой.
- Приоритет: запрет сильнее разрешения; объединение ролей; зависимость без базового не действует; истёкший срок не действует; неизвестный код — запрет.
- Повышение полномочий: выдать себе или другому больше, чем есть у себя; скопировать роль с лишними правами; изменить свою роль; изменить роль
  того, кто сильнее; сбросить пароль сильнейшему; назначить роль с критическим разрешением при варианте (а) Q-18 — всё отклоняется.
- Владелец: сотрудник не может изменить, заблокировать, сбросить пароль, завершить сеансы владельцу; последнего владельца нельзя заблокировать
  или лишить признака, в том числе двумя одновременными запросами.
- Учётные записи: временный пароль действует только для установки нового пароля; истёкший не принимается; после смены и сброса старые токены не действуют;
  после блокировки следующий запрос — 401; временный пароль не появляется в журналах, `audit_events`, `ai_messages`, `ai_tool_calls`.
- Сеансы и задания: сужение прав действует со следующего запроса; план ИИ после отзыва права не выполняется; системная копия выполняется
  при заблокированном сотруднике.
- Подбор: лимиты срабатывают и переживают перезапуск; ответ не выдаёт существование логина; владелец может войти с компьютера магазина
  при атаке на его логин из сети.
