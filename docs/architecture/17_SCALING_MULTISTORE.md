# 17. Масштабирование и сеть магазинов

> **Версия 1.5:** сценарии утечек У-1…У-11 с проверками — §2.2. **Версия 1.4:** подробная схема изоляции магазинов — §2.1. **Версия 1.3 (новый документ).** Долгосрочное видение владельца: десятки, сотни магазинов и сеть; сотни и тысячи одновременных
> пользователей. **Первая версия остаётся на один магазин** (решение в силе). Здесь описано, что заложить сейчас, чтобы рост
> был возможен без переписывания, и что **не делать** до времени. Производительность не обещается без измерений.

## 1. Главный принцип: «узел магазина» + необязательный «центр организации»

```text
             ┌─────────────────────── Облако / сервер организации (будущее, по решению владельца) ───────────────────────┐
             │  Центр организации: общий каталог (по желанию), отчёты по сети, пользователи организации, резервные копии  │
             │  Многопользовательская база (organization_id / store_id + Row-Level Security), масштабируемые API и GPU     │
             └──────────────▲───────────────────────────▲───────────────────────────▲──────────────────────────────────────┘
                            │ необязательная синхронизация (документ 13)              │
   ┌────────────────────────┴───┐        ┌──────────────┴─────────────┐        ┌────┴───────────────────────┐
   │ Узел магазина №1 (= v1)    │        │ Узел магазина №2           │   …    │ Узел магазина №N           │
   │ своя база, свой индекс,    │        │ работает без интернета     │        │                            │
   │ свои сотрудники, свой QR   │        │                            │        │                            │
   └────────────────────────────┘        └────────────────────────────┘        └────────────────────────────┘
```

- **Узел магазина** — то, что строится в первой версии: программа на компьютере или сервере магазина, своя база, свой индекс,
  полностью автономная работа. Это требование «автономной работы отдельных магазинов», выполненное естественным образом.
- **Центр организации** — будущий необязательный компонент для сети: общий каталог, сводные отчёты, управление пользователями сети,
  копии. Узлы работают и без него.
- Тот же код работает в обоих режимах: различаются профиль запуска (документ 02, §3) и то, сколько магазинов в базе.

## 2. Изоляция данных: варианты

| Вариант | Как | Плюсы | Минусы | Где применять |
|---|---|---|---|---|
| **Отдельная база на магазин** | каждый узел — своя база | самая сильная изоляция; копия и восстановление магазина независимы; автономность | сводные отчёты — только через центр | **узлы магазинов (v1 и дальше)** |
| **Общая база + `organization_id`/`store_id` + Row-Level Security** | все магазины в одной базе, каждая строка помечена, политики PostgreSQL не дают видеть чужое | эффективно для сотен магазинов в облаке; сводные запросы простые | ошибка в политике — утечка между организациями; нужна дисциплина (владелец таблицы обходит политики без `FORCE ROW LEVEL SECURITY`) | **центр организации в облаке** |
| Схема на арендатора | отдельная схема PostgreSQL на организацию | средняя изоляция | миграции × число схем; плохо масштабируется на сотни | не рекомендуется |

Изоляцию проверяет **сервер**, а не интерфейс: даже при RLS приложение фильтрует по контексту магазина, а RLS — второй рубеж
([пример multi-tenant RLS](https://dev.to/software_mvp-factory/row-level-security-in-postgresql-multi-tenant-data-isolation-for-your-saas-without-a-query-change-57bb)).

### 2.1. Как предотвращается доступ одного магазина к данным другого (1.4)

**В узле магазина (первая версия)** изоляция физическая: у каждого магазина своя база, свой индекс, свои файлы и копии на своём компьютере.
Данных другого магазина в узле просто нет. Всё ниже относится к **будущему центру организации** с общей базой, но правила
закладываются в код уже сейчас (S-2, S-3, S-6, S-8), чтобы потом не переписывать.

**Принцип — несколько независимых рубежей.** Ошибка в одном не открывает данные: следующий рубеж её остановит.

| № | Рубеж | Как работает | Что ломается, если его нет |
|---|---|---|---|
| 1 | **Аутентификация** | токен → пользователь → организация. Токены разных организаций не пересекаются | — |
| 2 | **Контекст магазина** (`current_store`) | определяется **на сервере** для каждого запроса: магазин из пути или заголовка проверяется по праву пользователя с областью действия (S-3). Значение от клиента без проверки не используется. Нет контекста — нет доступа (кроме явно организационных операций для пользователей с правами на всю организацию) | подмена `store_id` в запросе дала бы доступ к чужому магазину |
| 3 | **Сервисный слой** | каждая сервисная функция получает контекст и фильтрует по `organization_id`/`store_id`. Общий базовый класс запросов добавляет фильтр автоматически; «голый» запрос без контекста запрещён правилом кода и проверкой в тестах | забытый фильтр в одном запросе |
| 4 | **PostgreSQL Row-Level Security** | политики на всех таблицах с данными организаций: строка видна, только если `organization_id = current_setting('app.org_id', true)` (и `store_id` — для данных магазина). Если контекст не установлен, `current_setting(…, true)` даёт пусто, и **не видно ничего** (запрет по умолчанию) | ошибка рубежа 3 сразу стала бы утечкой |
| 5 | **Отдельные роли базы** | приложение работает под ролью **без** прав владельца таблиц и **без** `BYPASSRLS`; на таблицах включён `FORCE ROW LEVEL SECURITY`, чтобы политики действовали и для владельца; миграции — отдельной ролью, которую приложение не использует; суперпользователь для приложения не применяется | владелец таблиц и суперпользователь обходят RLS |
| 6 | **Проверочные тесты** | для каждого маршрута, инструмента ИИ и фонового задания — тест «пользователь организации А не видит и не меняет данные Б»; «канареечные» строки в тестовой базе | регрессии остаются незамеченными |

**Особые места, где изоляцию легко нарушить:**

| Место | Риск | Мера |
|---|---|---|
| **Пул соединений** | `SET app.org_id` на уровне сессии «переезжает» к другому запросу на том же соединении; в PgBouncer в режиме транзакций сессионные настройки вообще непредсказуемы | контекст устанавливается **только внутри транзакции**: `SET LOCAL` / `set_config('app.org_id', …, true)` в начале каждой транзакции; после транзакции он автоматически сбрасывается; тест на «утечку контекста» при повторном использовании соединения |
| **Фоновые задания** | задание выполняется без пользователя — легко забыть контекст | каждое задание хранит `organization_id`/`store_id` (S-6, документ 08, §7); обработчик устанавливает контекст в транзакции задания; задание без контекста не выполняется. Служебные межорганизационные задачи (обслуживание) — отдельной ролью, явным списком и с записью в журнал |
| **Кэш** | ответ одного магазина отдан другому | ключи кэша всегда включают `organization_id`/`store_id` и версию; права не кэшируются дольше запроса; общий кэш результатов запросов без ключа арендатора запрещён |
| **Файлы и фото** | путь к чужому файлу угадан или подставлен | пути строит одна серверная функция с префиксом организации и магазина (S-8; сейчас `resolve_ref` уже защищает от `../`); прямых публичных ссылок на хранилище нет — фото отдаются через API с проверкой контекста (или по коротким подписанным ссылкам, если хранилище объектное) |
| **Индексы распознавания** | поиск по чужому каталогу | пространство имён индекса берётся из контекста на сервере, а не из запроса; индексы разных каталогов — разные файлы или разделы |
| **Представления и функции базы** | представление, созданное владельцем таблиц, может обходить RLS; функции `SECURITY DEFINER` выполняются с правами создателя | представления — с `security_invoker` (PostgreSQL 15+); `SECURITY DEFINER` — только по списку с ревью; проверка в тестах |
| **Побочные каналы через ограничения** | глобальная уникальность выдаёт существование: «этот штрихкод уже занят» — значит, он есть у другой организации | уникальность **в пределах организации** (D-26), ошибки уникальности не раскрывают чужие данные |
| **Резервные копии** | копия всей базы центра содержит все организации; восстановление одной организации перезаписывает чужие данные | доступ к копиям — только администраторам центра; копии шифруются; восстановление **всей** базы — на момент времени (PITR); восстановление **одной** организации — только логическим экспортом и импортом её данных в отдельной процедуре с проверкой, без затрагивания чужих строк |
| **ИИ-помощник** | модель «попросят» показать данные другого магазина | инструменты работают в контексте пользователя (рубежи 2–5 действуют так же); память и контекст — только текущего пользователя и магазина (документ 16, §9) |
| **Журналы и мониторинг** | в общих журналах видны данные клиентов | в журналах — идентификаторы, без содержимого карточек; доступ к журналам центра — только администраторам центра |
| **Отчёты по сети** | отчёт организации А включает строки Б | отчёты выполняются под той же ролью с RLS; для межорганизационной аналитики платформы — только обезличенные агрегаты отдельной ролью |

### 2.2. Сценарии утечек и как каждый перекрыт (1.5)

**RLS не является единственной защитой.** В каждом сценарии ниже срабатывает минимум два независимых рубежа из §2.1. Если отключить
RLS, утечку остановит сервисный слой и контекст; если ошибиться в сервисном слое, её остановит RLS.

| № | Сценарий утечки | Рубежи, которые его перекрывают | Проверочный тест |
|---|---|---|---|
| У-1 | **Пул соединений:** запрос магазина Б получает соединение, на котором остался контекст магазина А | контекст только через `SET LOCAL` в транзакции (сбрасывается при её окончании); RLS с запретом по умолчанию — без контекста не видно ничего; сервисный слой передаёт контекст явно | два параллельных потока разных организаций на одном соединении пула; после транзакции `current_setting('app.org_id', true)` пуст |
| У-2 | **Фоновое задание** обрабатывает данные не того магазина или выполняется без контекста | `organization_id`/`store_id` в самом задании; обработчик устанавливает контекст в транзакции задания; задание без контекста отклоняется; RLS | задание организации А пытается прочитать товар Б → пусто и ошибка; задание без контекста → не выполняется |
| У-3 | **Кэш** отдаёт карточку или результат другой организации | ключ кэша содержит организацию, магазин и версию; права не кэшируются; публичная карточка кэшируется по коду магазина из пути | одинаковые `product_id`-запросы от двух организаций дают разные ключи; подмена кода магазина в пути не даёт чужую карточку |
| У-4 | **Файлы** (импорт, экспорт, отчёты) другой организации доступны по пути | пути строит сервер с префиксом организации и магазина; отдача только через API с проверкой контекста; защита от `../` (`resolve_ref`) | запрос файла чужой организации по известному имени → 404 |
| У-5 | **Изображения товаров и миниатюры** видны по прямой ссылке | нет публичных прямых ссылок на хранилище; фото — через API с контекстом или короткие подписанные ссылки, привязанные к организации; миниатюры хранятся в том же префиксе | прямой адрес миниатюры другой организации → отказ; просроченная подписанная ссылка → отказ |
| У-6 | **Кадр покупателя для выбора товара** (D-10а) выбирается чужим идентификатором | кадр в памяти, идентификатор случайный и неугадываемый, связан с магазином и публичным входом; выбор проверяет совпадение магазина | выбор рамки с идентификатором кадра другого магазина → «кадр устарел» |
| У-7 | **Индекс распознавания** возвращает товары другой организации | пространство имён индекса берётся из контекста на сервере; индексы разных каталогов разделены; найденные `product_id` дополнительно читаются из базы через сервисный слой с RLS — «чужой» id просто не найдётся | поиск в контексте А по эталону товара Б → не найдено |
| У-8 | **Резервная копия** одной организации содержит или перезаписывает данные другой | копии центра — только для администраторов центра, шифрование; восстановление одной организации — логический экспорт и импорт только её строк; узлы магазинов копируют только себя | восстановление организации А в тестовой базе не меняет строки Б (сравнение контрольных сумм) |
| У-9 | **ИИ-помощник** показывает данные другого магазина | инструменты вызывают сервисный слой в контексте пользователя; память и история — только пользователя и магазина; RLS | запрос «покажи товары магазина Б» от сотрудника А → отказ или пусто |
| У-10 | **Отчёты и журналы** смешивают организации | отчёты под ролью с RLS; в журналах только идентификаторы; доступ к журналам центра — администраторам центра | отчёт организации А не содержит строк Б |
| У-11 | **Побочный канал уникальности** («штрихкод уже занят») | уникальность в пределах организации (D-26); тексты ошибок не раскрывают чужие данные | создание товара с штрихкодом, существующим только у Б, в организации А → успешно |

Тесты У-1…У-11 обязательны **до запуска центра организации**. В узле магазина (первая версия) большинство сценариев невозможно физически
(одна база, одна организация), но тесты контекста (У-1, У-2, У-6, У-7) имеют смысл уже там: они проверяют, что код не опирается на
«единственный магазин».

## 3. Модель организации (будущее) и что заложить сейчас

### 3.1. Будущая модель

| Уровень | Сущности |
|---|---|
| Организация | владелец организации, пользователи, шаблоны ролей, политики ИИ, **общий каталог** (если нужен), схема категорий и характеристик |
| Магазин | настройки, QR, ассортимент (`store_products`), цены (`store_prices`), остатки (`store_stock`), индекс распознавания, история распознаваний, сотрудники и их права в этом магазине |

Каталог в сети — два режима (выбор при подключении сети, сейчас не решается):

1. **Общий каталог организации + ассортимент магазина**: товар описан один раз, магазин выбирает, что продаёт, и задаёт свои цены.
   Подходит сети с похожим ассортиментом.
2. **Отдельный каталог каждого магазина**: независимые магазины под одной организацией.

### 3.2. Что заложить уже сейчас (дёшево, без реализации сети)

| № | Правило архитектуры | Проверка текущего кода | Действие |
|---|---|---|---|
| S-1 | Все идентификаторы — UUID | ✅ `_uuid` во всех таблицах | сохранить |
| S-2 | **Контекст магазина** определяется на запрос одной функцией (`current_store`), а не «первый магазин в базе» в разных местах кода | сейчас магазины перечисляются через `db.query(Store).all()` с проверкой доступа (`routes_stores.py`). Жёсткой привязки «магазин один» не найдено | правило для нового кода (документ 02) |
| S-3 | **Права сотрудника — с областью действия**: `store_id` (`NULL` = вся организация) в назначениях ролей `user_roles` и индивидуальных разрешениях `user_permission_grants` (1.6, документ 05, §10; раньше — `user_permissions`) | в плане 1.2 права были без магазина | **изменить план документа 05** до реализации прав (дешевле сейчас, чем потом) |
| S-4 | Уникальность артикула и штрихкода — **в пределах каталога** | сейчас глобальная (`products.sku UNIQUE`, `product_barcodes.barcode` — первичный ключ) | правило; менять схему не нужно, пока каталог один (документ 06, §7) |
| S-5 | Индекс распознавания имеет **пространство имён** (каталог или магазин) и манифест модели | индекс один глобальный | заложить в формат манифеста (документ 07, §8, §10) |
| S-6 | История распознаваний, журнал действий, сессии ИИ хранят `store_id` | история ещё не создана | создавать сразу с `store_id` (документ 02, §5) |
| S-7 | Настройки — «настройки магазина», а не глобальные константы | частично в `config.yaml` | новые настройки хранить на уровне магазина |
| S-8 | Пути к файлам строит одна функция (подкаталог каталога или магазина), а не склейка строк по коду | `catalog_upload.resolve_ref` уже централизует пути | сохранить и расширить |
| S-9 | `updated_at` и `version` в изменяемых таблицах | запланировано (документ 13) | сохранить |
| S-10 | Сервер без состояния в памяти, кроме явно оговорённого (кадр для выбора, кэш моделей) | ограничение попыток входа — в памяти процесса | перенести в базу (документ 05, §14) |

**Не делать сейчас:** таблицу организаций, столбцы `organization_id` во всех таблицах, RLS, центр организации, синхронизацию,
общий каталог, межмагазинные отчёты, биллинг. Всё это — отдельные этапы после первой версии и пилота.

## 4. Масштабирование: анализ по компонентам

### 4.1. API

- **Без состояния:** токены хранятся в базе (уже так), поэтому любой экземпляр API проверяет любой токен. Несколько экземпляров
  за балансировщиком возможны **после** переноса счётчиков попыток входа в базу или Redis (сейчас они в памяти процесса).
- **Кадр для выбора товара (D-10а)** хранится в памяти. При нескольких экземплярах запрос «выбрать рамку» должен попасть туда,
  где лежит кадр. Решение — **привязка к экземпляру распознавания**: идентификатор кадра содержит номер экземпляра, балансировщик или
  внутренний маршрутизатор направляет выбор туда. Если экземпляр перезапустился, ответ «кадр устарел, переснимите». Хранить кадры
  в общем Redis можно только **без сохранения на диск** (отключены RDB и AOF), иначе нарушается D-10а. Предпочтительна привязка.
- Медленные операции (импорт, отчёты, пересборка индекса) — только через очередь, не в запросе.

### 4.2. Распознавание как отдельно масштабируемый сервис

- Интерфейс `InferenceClient`: **локальная реализация** (в том же процессе — Desktop и узел магазина) и **удалённая** (пул GPU-воркеров для центра или крупного узла).
- Удалённый сервис: воркеры с загруженными моделями, пакетная обработка, приоритет интерактивных запросов, масштабирование по длине очереди.
- **Деградация при перегрузке:** штрихкод читается без GPU. Если сервис распознавания перегружен или недоступен, система продолжает
  отвечать по штрихкоду и честно сообщает «распознавание по фото временно недоступно».

### 4.3. PostgreSQL

| Тема | Решение |
|---|---|
| Пул соединений | пул SQLAlchemy в каждом процессе (размер пула × число процессов < `max_connections` с запасом); при многих экземплярах API — **PgBouncer** в режиме транзакций. Важно: psycopg 3 с PgBouncer — либо отключить подготовленные запросы (`prepare_threshold=None`), либо PgBouncer 1.22+ с `max_prepared_statements` и libpq 17+ ([psycopg: prepared statements](https://www.psycopg.org/psycopg3/docs/advanced/prepare.html)) |
| Индексы | в общей базе центра — ведущий столбец `organization_id`/`store_id` в составных индексах; по каталогу — GIN по `attribute_values`, индексная таблица характеристик (документ 06, §4.5) |
| Оптимизация запросов | без N+1 (загрузка связей пакетами), постраничная выдача по ключу, а не `OFFSET` на больших объёмах, `EXPLAIN` в нагрузочных тестах |
| Большие журналы | история распознаваний, `audit_events`, `ai_messages` — разбиение по месяцам в центре; срок хранения выполняется удалением старых разделов **по утверждённой владельцем политике хранения** |
| Отчёты по сети | реплика для чтения в центре — когда отчёты начнут мешать рабочей нагрузке |
| Восстановление | узел: ежедневные проверенные копии (D-11); центр: копии + архив журнала WAL (восстановление на момент времени) |

### 4.4. Поиск по векторам при многих магазинах

| Масштаб | Вариант | Комментарий |
|---|---|---|
| Узел магазина (до ~80 тыс. векторов) | FAISS `IndexFlatIP`, точный перебор (как сейчас) | около 246 МБ RAM на 10 тыс. SKU × 8 фото (документ 11) |
| Центр, десятки магазинов | индекс **на каталог**, загрузка по требованию (LRU), отбор по ассортименту магазина | 100 индексов по 246 МБ = около 25 ГБ, если держать все в памяти — значит, по требованию |
| Центр, сотни магазинов | pgvector с разбиением по каталогу или отдельная векторная база с фильтром | у pgvector HNSW с фильтром есть ловушка «фильтр после поиска»: результатов может стать слишком мало; в 0.8+ есть итеративное сканирование; для маленьких каталогов точный перебор по разделу быстрее и точнее ([ClickHouse: scale vector search in Postgres](https://clickhouse.com/resources/engineering/scale-vector-search-postgres)) |

Выбор — **по замеру**, интерфейс `CatalogIndex` уже существует (`FaissCatalogIndex`, `NumpyCatalogIndex`) и сохраняется.

### 4.5. Очереди и изоляция магазинов

- Раздельные очереди по приоритету: интерактивное (распознавание) ≠ фоновое (индексация, импорт, отчёты, копии) ≠ ИИ.
- **Справедливость между магазинами:** квоты одновременных фоновых задач на магазин; тяжёлый импорт одного магазина не задерживает другие.
- Профиль сервера — Celery и Redis (сохраняются); узел — очередь в базе (документ 08).

### 4.6. Кэширование — только где полезно

| Кэшировать | Не кэшировать |
|---|---|
| публичные карточки товаров (по магазину, сброс по `version`) | результаты распознавания (зависят от кадра, приватность D-10) |
| схемы категорий и характеристик (в памяти, сброс по `version`) | кадры покупателей |
| статические страницы, миниатюры фото (HTTP-кэш, ETag) | права пользователя дольше одного запроса (или короткий срок со сбросом при изменении) |
| загруженные модели (один раз на процесс) | ответы ИИ |

### 4.7. Защита от перегрузки

- Лимиты: по IP (публичный вход), по пользователю, **по магазину**; общий допуск к распознаванию; ограниченные очереди.
- Ответы `429` / `503` с `Retry-After` и понятным текстом, а не зависание.
- Таймауты на всё. Автоматическое отключение («предохранитель») обращений к распознаванию при массовых ошибках, деградация до штрихкода (§4.2).
- Плавная остановка: принятые запросы завершаются, новые не принимаются.

### 4.8. Восстановление после сбоев

Перезапуск API без потерь (нет состояния); задания идемпотентны и переживают перезапуск (документ 08); индекс пересобирается из кэша
эмбеддингов; проверки готовности не пускают трафик к неготовому экземпляру; копии и испытания восстановления (документ 09).

## 5. Уровни нагрузки (проектные допущения, не обещания)

| Уровень | Пример | Одновременных пользователей | Распознаваний в минуту (пик) | Каталог | Топология |
|---|---|---|---|---|---|
| **L0** | первая версия, один магазин | до 3 сотрудников + покупатели | до 20 (В-3) | до 10 тыс. SKU | один процесс на компьютере магазина |
| **L1** | крупный магазин | до 50 | до 100 | до 50 тыс. SKU | узел: API + отдельный процесс распознавания на GPU |
| **L2** | сеть 10–20 магазинов с центром | до 300 | до 500 суммарно | до 200 тыс. SKU в организации | центр: 2–3 экземпляра API, PgBouncer, Redis, 2–4 GPU-воркера; узлы автономны |
| **L3** | 100+ магазинов | тысячи | тысячи суммарно | миллионы строк | центр: автоматическое масштабирование API и GPU, разбиение журналов, векторная база, реплики для отчётов, наблюдаемость |

## 6. Когда и что масштабировать (по измерениям)

| Признак (по метрикам) | Что делать |
|---|---|
| p95 распознавания выше цели при нормальной загрузке CPU у API | вынести распознавание в отдельный процесс или GPU-воркер; добавить воркеры |
| Загрузка CPU у API стабильно выше 70 % | добавить экземпляры API (после S-10) |
| Соединения с базой упираются в предел | PgBouncer, уменьшение пулов, проверка долгих транзакций |
| Память под индексы растёт быстрее RAM сервера | загрузка индексов по требованию, затем pgvector или векторная база |
| Отчёты замедляют рабочие запросы | реплика для чтения |
| Один магазин мешает другим | квоты и отдельные очереди для этого магазина |
| Журналы растут и замедляют запросы | разбиение по месяцам и срок хранения |

## 7. Нагрузочные испытания (сценарии)

Для каждого уровня цели (p50 и p95, доля отказов) **записываются после первого замера** и только затем фиксируются как критерии.

| № | Сценарий | Уровень | Что измерить |
|---|---|---|---|
| Т-1 | Устойчивая нагрузка: ориентир уровня в течение 30 минут, смесь (штрихкод 30 %, вид 60 %, несколько товаров 10 %) | L0–L3 | p50, p95, отказы, CPU, GPU, RAM, VRAM, соединения с базой |
| Т-2 | Пик ×2 в течение 5 минут | L0–L3 | где начинаются `429/503`, нет ли падений |
| Т-3 | Всплеск: от 0 до пика за 10 секунд | L1–L3 | время реакции очередей и масштабирования |
| Т-4 | Длительная работа 8 часов (рабочий день) | L0–L2 | утечки памяти, рост времени ответа |
| Т-5 | «Шумный сосед»: один магазин ×10 от нормы | L2–L3 | другие магазины в своих целях |
| Т-6 | Отказ: остановить воркер распознавания, перезапустить базу, оборвать сеть узла | L1–L3 | деградация до штрихкода, восстановление, отсутствие потерь заданий |
| Т-7 | Холодный старт: запуск с загрузкой моделей и индексов | L0–L3 | время до «готово» |
| Т-8 | Импорт 10 тыс. товаров во время пика распознавания | L0–L2 | влияние фоновых задач на интерактивные |
| Т-9 | Одновременная работа ИИ-помощника (3–10 сессий) и распознавания на одном GPU; варианты: GPU, частичная выгрузка, CPU | L0–L1 | VRAM, время ответа покупателям с ИИ и без; срабатывание допуска по нагрузке (документ 16, §10.1) |
| Т-10 | Фильтры каталога по характеристикам на 1 млн товаров | L2–L3 | время запросов, использование индексов (`EXPLAIN`) |

Инструменты нагрузочного тестирования выбираются на этапе испытаний (например, k6 или Locust). Набор кадров — из benchmark (документ 07),
без фото покупателей.

## 8. Универсальное распознавание при многих магазинах

- Модель извлекает **признаки** изображения и не знает о структуре магазина. Решение принимается **по каталогу магазина** (или организации):
  отсутствует в каталоге — значит «не найдено».
- Новый магазин с другим ассортиментом: загрузить каталог и эталонные фото → построить **свой индекс** (пространство имён) → работать.
  **Переобучение модели не требуется** (подробно — документ 07, §10).
- Детектор, обученный на продуктовых полках (SKU-110K), может не подходить для одежды и цветов. Поэтому детектор — сменяемый
  компонент с ролью «помощник кадрирования», а не обязательное звено (документ 07, §3.1).

## 9. Риски чрезмерного усложнения (и защита от них)

| Риск | Как проявится | Защита |
|---|---|---|
| Строить сеть раньше первого магазина | месяцы на инфраструктуру, первый магазин не запущен | правило: в первой версии — только задел S-1…S-10; всё остальное — после пилота |
| Тестировать всё «на будущее» | матрица тестов растёт быстрее функций | тесты только на реализованное; задел проверяется ревью архитектуры |
| Преждевременная распределённость | Kubernetes, микросервисы, брокеры для одного магазина | узел — один процесс; разделение — только по метрикам §6 |
| Двойные пути кода (узел и центр) | расхождение поведения | общий сервисный слой; различаются только адаптеры (очередь, распознавание, хранилище) |
