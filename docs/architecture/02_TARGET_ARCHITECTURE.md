# 02. Целевая архитектура

## 1. Принципы (утверждено)

1. **Один магазин:** один владелец, один компьютер или сервер, один каталог, один постоянный QR-код, несколько сотрудников, анонимные покупатели.
2. **Local-first:** всё работает без интернета, без облака, без сторонних провайдеров. Фото покупателей никуда не отправляются.
3. **Backend не переписывается.** Развиваем существующий Python/FastAPI, меняем по частям.
4. **Одна бизнес-логика.** Windows-окно, телефон покупателя и телефон сотрудника — клиенты одного и того же API.
   Проверки прав и решения распознавания живут только на сервере.
5. **Честное распознавание:** система вправе отказаться от ответа. Пороги подбираются по замеру, а не на глаз.
6. **Без препятствий на будущее, но без лишней сложности сейчас:** UUID, `updated_at`, журнал изменений — там, где это действительно нужно (документ 13).
7. **Универсальная платформа (1.3):** ничего в ядре не привязано к продуктам питания; особенности типа магазина — данные
   (шаблоны категорий и характеристик), а не код (документ 06).
8. **Первая версия = «узел магазина» (1.3):** тот же код станет узлом сети; закладываются только правила S-1…S-10 (документ 17, §3.2).
9. **Каждое действие — сервисная функция с проверкой прав внутри (1.3):** HTTP-маршруты, импорт и будущий ИИ-помощник вызывают
   одни и те же функции; обходных путей к данным нет (документ 16, §3).

## 2. Общая схема

```text
   Телефон покупателя          Телефон сотрудника          Окно Windows (владелец, сотрудник)
   (QR → браузер, аноним)      (браузер, вход по паролю)   (Desktop-оболочка, документ 03)
            │                          │                              │
            └───────────── HTTP(S) в локальной сети ──────────────────┘
                                       │
                      ┌────────────────▼─────────────────┐
                      │  Backend «Узнать товар» (FastAPI) │  работает в фоне, пока магазин открыт,
                      │                                   │  независимо от окна программы
                      │  Публичный вход (порт из QR)      │  ← страницы и API покупателя, лимиты; маршрутов сотрудников нет
                      │  Служебный вход (127.0.0.1 / сеть │  ← каталог, пользователи, история, настройки (по правам)
                      │   сотрудников по D-08)            │
                      │  Сервис распознавания (ML Runtime)│  ← модели загружены ОДИН раз
                      │  Очередь фоновых задач            │  ← индексация фото, импорт, резервные копии
                      │  Журнал действий                  │
                      └──────┬─────────────┬──────────────┘
                             │             │
               ┌─────────────▼──┐   ┌──────▼──────────────────────────────┐
               │ PostgreSQL     │   │ Файлы данных (папка Data)            │
               │ (localhost)    │   │ фото товаров, индекс + манифест,     │
               └────────────────┘   │ резервные копии, журналы, экспорт    │
                                    └──────────────────────────────────────┘
```

## 3. Два профиля запуска одного кода

| | **Профиль Dev/Server** (как сейчас) | **Профиль Desktop** (цель) |
|---|---|---|
| Для кого | разработка, тесты, будущий сервер | владелец магазина |
| Запуск | Docker Compose | установщик Windows, ярлык; backend как фоновая служба |
| Процессы | `api` + `worker` (Celery) + `db` + `redis` | **один процесс backend** (API + ML + обработчик очереди) + PostgreSQL на localhost |
| Очередь | Celery + Redis (сохраняется) | очередь без Redis (документ 08) |
| ML | CPU в контейнере (GPU не настроен) | GPU NVIDIA, если есть, иначе CPU |
| Модели | кэш HuggingFace в томе | файлы моделей в установке, без скачивания при работе |
| База | PostgreSQL 16 в контейнере | PostgreSQL на localhost (SQLite — альтернатива после прототипа, документ 03) |

**Рекомендовано:** код приложения не должен знать, в каком профиле работает, кроме двух мест: фабрики очереди
(`TaskQueue` с реализациями «Celery» и «локальная») и путей данных (настройка `DATA_DIR`). Остальное — общий код и общие тесты.

### Почему в Desktop один процесс

- Модели (DINOv2 около 350 МБ весов, YOLO, OCR) загружаются один раз. Два процесса — двойная RAM и VRAM.
- Сейчас API ждёт воркер до 25 секунд (`task.get`). В одном процессе распознавание вызывается напрямую,
  без брокера, с ограничением одновременных запросов (семафор), чтобы не перегрузить GPU.
- Тяжёлые фоновые задачи (индексация, импорт, резервные копии) идут через надёжную локальную очередь в том же процессе
  (отдельный поток-обработчик), а не через «фоновые потоки без учёта».

Риск: зависание модели блокирует весь backend. Меры: таймауты на распознавание, сторожевой перезапуск процесса
супервизором (документ 03), healthcheck `/health/ready` с проверкой ML.

## 5. Принадлежность данных (без механического `store_id`)

Правило: поле магазина есть только там, где **смысл записи зависит от конкретного магазина**.
Каталог и всё, что описывает сам товар, — общие сведения о товаре.

| Сущность | Принадлежит | Поле магазина | Почему |
|---|---|---|---|
| `Store` | — | — | Ровно одна запись «этот магазин»; настройки магазина храним в ней или рядом |
| Товар (SKU), штрихкоды, тексты, состав, пищевая ценность, аллергены, фото | товару | **нет** | Описывают товар, а не магазин. Если появятся другие магазины, каталог можно сделать общим или копировать — решим тогда |
| Цена | товару в магазине | **рекомендуется** (`store_id` в будущей таблице цен) | Цена по смыслу всегда «цена в этом магазине». Сейчас `Product.expected_price` — оставить, позже переход на таблицу цен (документ 06) |
| Наличие (если будет) | магазину | да | То же, что цена |
| Сотрудники | магазину | через существующий `UserStoreAccess` | Уже есть, сохраняем |
| Запросы распознавания (история 30–90 дней) | магазину | да | Запрос пришёл через QR конкретного магазина; пригодится и для статистики |
| Журнал действий | установке | необязательное | Действие сотрудника; магазин выводится из пользователя |
| Резервные копии | установке | нет | Копия всей установки |
| Индекс и модели | установке | нет | Производные данные |

## 6. Ключевые потоки

### 6.1. Покупатель узнаёт товар (целевой)

```text
Телефон → POST /api/v1/public/identify (без входа, лимит частоты)
  → нормализация кадра (EXIF, размер, проверка формата)
  → штрихкод? ── да, известен, сверка с каталогом ok ──► карточка (by=barcode)
       │ нет / неизвестен
  → кадрирование товара (детектор или центр кадра; при нескольких объектах — вернуть рамки, покупатель выбирает)
  → эмбеддинг кадра → кандидаты по каталогу (группировка по товару)
  → OCR (если кандидаты близки или это варианты одной линейки) → сверка текста с карточками
  → решение: matched / candidates / unknown / no_object / empty_catalog
  → запись в историю (без личных данных; фото — только если владелец включил, с маскировкой лиц)
  → ответ: только публичные поля карточки
```

### 6.2. Сотрудник добавляет товар

```text
Форма (название на одном языке + фото + необязательные поля) → API проверяет права и данные
  → товар и записи фото в базе, файлы фото в Data/photos → журнал действий
  → задача «индексировать фото» в очередь (идемпотентно по SHA-256 фото и версии модели)
  → обработчик: эмбеддинги → кэш эмбеддингов → индекс (атомарная запись) → статус задачи «готово»
```

## 7. Структура папок Desktop (предложение, уточнить после прототипа)

```text
C:\Program Files\UznatTovar\        ← программа (заменяется при обновлении)
    shell\  backend\  python\  models\  frontend\  postgres\  migrations\
%ProgramData%\UznatTovar\Data\      ← данные (НЕ трогаются обновлением и удалением программы)
    db\  photos\  index\  backups\  logs\  exports\  config\
```

Данные нельзя хранить в папке программы: обновление или удаление программы не должно их затрагивать.
`%ProgramData%` (общая для всех пользователей Windows) подходит, потому что backend работает как служба.
Резервные копии по умолчанию — на **другой диск** или флешку (документ 09).

## 8. Универсальная платформа: влияние на целевую архитектуру (добавлено в 1.3)

| Решение 1.2 | Статус в 1.3 | Что меняется |
|---|---|---|
| Один магазин, один каталог (§1, п. 1) | **оставить** | первая версия не меняется; это «узел магазина» будущей сети |
| Принадлежность данных без механического `store_id` (§5) | **оставить и дополнить** | появляется будущий уровень «организация» (каталог организации, пользователи организации); в базе узла он не нужен. Правило «по смыслу» действует: цена, остатки, ассортимент, история — магазин; описание товара — каталог (магазина или организации) |
| Компоненты (§4) | **дополнить** | новые: справочник категорий и характеристик + `AttributeValidator` (документ 06); ИИ-подсистема (документ 16); интерфейс `InferenceClient` (распознавание в процессе или отдельным сервисом); контекст магазина `current_store` (документ 17, S-2) |
| Два профиля запуска (§3) | **оставить и дополнить** | профиль Dev/Server становится основой «центра организации»; профиль Desktop — узлом магазина |
| Один процесс в Desktop | **оставить** | для крупных узлов и центра распознавание выносится в отдельный сервис через тот же `InferenceClient` (документ 17, §4.2) |

Компоненты, которые добавляются в схему §2 в будущем:

```text
 Служебный вход ─► ИИ-помощник (оркестратор → адаптер модели → реестр инструментов → политика → предпросмотр → исполнитель)
                    │ вызывает тот же сервисный слой, что и API
 Сервисный слой ─► Каталог (категории, характеристики, AttributeValidator) │ Пользователи и права (с областью «магазин») │ Распознавание (InferenceClient)
```
