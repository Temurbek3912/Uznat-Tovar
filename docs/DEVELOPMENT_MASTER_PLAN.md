| Область | Готовность | Коротко |
|---|---|---|
| Архитектура | **высокая** | 1.11: ключевые механизмы описаны; часть решений ещё не утверждена (§3) |

### Этап 2. Фундамент данных и надёжность

**Правило:** ни одна миграция и ни одно серьёзное изменение данных (2Б) не начинается до **успешного** завершения 2А. Перед каждой миграцией
в 2Б — свежая полная копия по процедуре 2А с проверкой.

**2А. Минимальная полная резервная копия и реальное восстановление**
- **Цель:** доказать, что текущее состояние можно полностью восстановить **и что восстановленная копия работает**, — **до** любых изменений
  схемы и данных.
- **Состав копии:** база (`pg_dump -Fc`), фото (все файлы, на которые ссылается база, и каталог фото — сейчас по пути по умолчанию их нет,
  §2.0), индекс и его файлы, конфигурация (без секретов в открытом виде, документ 09, §6), **манифест** (версия программы, ревизия схемы,
  **точное** (`count(*)`) число товаров, штрихкодов, пользователей, фото, векторов индекса, SHA-256 каждого файла копии).
- **Модели в копии:**
  - если модели (веса детектора, файлы тома `hf_cache`) включаются в копию — SHA-256 каждого их файла в манифесте обязателен;
  - если не включаются — манифест явно говорит «модели в копию не включены» и указывает, какие модели и где лежат, и SHA-256 их текущих
    файлов для сверки (приложение В, В.3);
  - совпадение размера и времени изменения доказательством целостности не считается.
- **Инструмент:** разрабатывается и проверяется **вне проекта** на тестовых данных. Это не даёт разрешения на перенос: **перенос, установка
  и интеграция** инструмента в рабочий проект (в том числе изменение `scripts/backup_db.py`) — **отдельное изменение с предварительным
  разрешением владельца**. Запуск инструмента на рабочей системе для создания копии — тоже отдельное разрешение.
- **Где хранится копия:** вне проекта, по выбору владельца (лучше — другой диск); существующие копии не перезаписываются.

**Изоляция временной среды восстановления** (обязательно; рабочая база и рабочие данные не затрагиваются):

| Требование | Зачем |
|---|---|
| отдельное имя проекта Docker Compose, отдельные тома, отдельная папка данных вне `D:\retail-shelf-audit` | никакие файлы и тома рабочей системы не подключаются к временной среде |
| **отдельные** PostgreSQL **и Redis** | иначе рабочий воркер мог бы забрать задачи временной среды (и наоборот) |
| другие порты, только `127.0.0.1` | нет конфликта с рабочей системой и нет доступа из сети |
| веса моделей — только уже имеющиеся локально, копией **только на чтение**; без доступа в интернет за моделями | без скачивания моделей |
| временная среда удаляется после проверки; копия остаётся | не оставлять лишних данных |

**Критерии успешного восстановления** (все обязательны, кроме помеченных «если доступно»):

| № | Проверка | Успех |
|---|---|---|
| 1 | Целостность копии | SHA-256 всех файлов совпадают с манифестом; `pg_restore --list` читает дамп без ошибок |
| 2 | Восстановление базы | дамп восстановлен во временную базу без ошибок; ревизия схемы и **точное** число строк (`count(*)`, не статистика `n_live_tup`) в основных таблицах (товары, штрихкоды, пользователи, магазины) совпадают с манифестом |
| 3 | Восстановление файлов | все фото и файлы индекса на месте во временной папке, хеши совпадают |
| 4 | **Запуск приложения** на восстановленной среде | `/health` и `/health/ready` отвечают «готово» (база, схема, очередь) |
| 5 | **Вход** | вход проверочной учётной записью, созданной **только во временной среде**, или учётной записью владельца, если он сам введёт пароль; рабочая база не затрагивается |
| 6 | **Карточки товаров** | список товаров открывается; число совпадает с манифестом; выборочно 10 карточек (или все, если их меньше) открываются полностью: название, бренд, категория, цена, штрихкоды |
| 7 | **Фотографии** | для каждой выбранной карточки фото открываются через приложение (миниатюра и полный размер); число фото совпадает с манифестом |
| 8 | **Поиск** | поиск по названию, артикулу и штрихкоду находит заранее выбранные товары из манифеста |
| 9 | **Индекс** | файл индекса загружается; число векторов совпадает с манифестом; каждый идентификатор индекса соответствует товару в восстановленной базе (или отличие объяснено — индекс не умеет удалять векторы) |
| 10 | **Распознавание по штрихкоду** (если в базе есть штрихкоды) | тестовое изображение известного штрихкода даёт верный товар |
| 11 | **Распознавание по виду** — *если доступно* без скачивания моделей и без изменения рабочей системы | тестовые изображения товаров из копии (фото каталога) дают ожидаемый товар среди кандидатов; если весов локально нет — проверка **пропускается** и это записывается в отчёт, а не считается провалом |
| 12 | Отсутствие влияния на рабочую систему | по снимку **до и после** (приложение В), без файлов в рабочем проекте: контрольные суммы, размеры и время изменения всех файлов проекта (кроме `.venv`) совпадают; рабочие контейнеры не перезапускались; ни один контейнер временной среды не подключал рабочие тома и рабочую папку (В.4а); вывод «изменений нет» — только при полноте всех разделов снимка, иначе «проверка неполная» с перечнем непроверенного (В.5); рабочая база: если владелец отдельно разрешил полное хеширование (В.2в), — отпечатки содержимого всех объектов в границах В.2 совпадают; без В.2в в отчёте прямо указано, что содержимое базы не сравнивалось, а лёгкие признаки В.2б (структура, время запуска сервера, сброс статистики, файлы таблиц, счётчики) без отличий, что **не доказывает** отсутствие изменений; отличия допустимы только в таблицах, куда программа пишет сама, и каждое объяснено; SHA-256 файлов моделей в томе `hf_cache` совпадают; журналы рабочей системы не содержат обращений временной среды |

Если пустой раздел (например, фото или индекса нет) — соответствующая проверка отмечается «нечего проверять», а манифест это фиксирует.

- **Готово, когда:** все обязательные проверки пройдены, временная среда удалена, владелец подтвердил отчёт.
- **Что меняется на рабочей системе:** только новые файлы копии вне проекта (и, если владелец выберет вариант Б приложения В, файлы снимка

## 6. База данных для Windows Desktop: сравнение (решение D-02 не принято)

**Сейчас ничего не меняется:** серверный прототип остаётся на PostgreSQL (решение 2.1 п. 6), переход на SQLite не выполняется. Ниже —
сравнение для будущего Desktop. Подробная таблица — документ 03, §5.

| Критерий | PostgreSQL в составе установки (служба) | SQLite (файл, режим WAL) |
|---|---|---|
| Установка | бинарники PostgreSQL, `initdb`, служба, порт, пароль — делает установщик; больше точек отказа (порт занят, антивирус) | ничего не нужно: библиотека входит в Python |
| Обновление программы | обычно без изменений базы; **смена основной версии PostgreSQL** требует `pg_upgrade` или выгрузки и загрузки | миграции схемы — как у любой базы; версия библиотеки идёт с Python |
| Надёжность при сбое | журнал WAL, восстановление после сбоя; на Windows нужны настройки сброса (05, §13.3.5) | журнал WAL; при `synchronous=FULL` устойчива к сбоям; те же ограничения диска и Windows |
| Резервная копия | `pg_dump` — уже работает в проекте | встроенный API резервного копирования или `VACUUM INTO`; простое копирование файла — только при остановке |
| Производительность (10 тыс. SKU, до 10 сотрудников, 20 распознаваний в минуту) | с запасом | с запасом для чтения; **один писатель** одновременно — длинный атомарный импорт задерживает другие записи на его время |
| Совместимость с архитектурой | всё как описано: JSONB и GIN, диапазоны, блокировки строк для атомарного применения, частичные индексы | нет JSONB и GIN (есть JSON-функции), нет диапазонных типов (две колонки), нет блокировок строк (вся база блокируется на запись — атомарность сохраняется, но иначе), нет рекомендательных блокировок; поиск без учёта регистра для кириллицы — через FTS5 |
| Два диалекта | один диалект с серверным прототипом | два диалекта: тесты на обоих, часть кода (миграции, поиск, блокировки) — в двух вариантах |
| Обслуживание обычным пользователем | служба скрыта установщиком, но есть что ломаться (служба не запустилась, порт занят) | практически не требуется |
| Размер | около сотни МБ и больше (**оценка**) | ноль дополнительно |

Отклонены: SQL Server Express (тяжёлый, другой диалект, ограничения бесплатной версии), DuckDB (аналитическая, не для параллельной

### Б.1. Как открыть окно PowerShell для 0А

Не открывайте обычный PowerShell. Окно запускается **сразу** без профиля и с отключённым сохранением истории:

1. Нажмите **Win + R** — откроется окно «Выполнить».
2. Вставьте строку целиком и нажмите **Enter** (не **Ctrl + Shift + Enter**: это запуск от имени администратора):

```text
powershell.exe -NoProfile -NoLogo -NoExit -Command "Set-PSReadLineOption -HistorySaveStyle SaveNothing"
```

Что делает эта строка:
- `-NoProfile` — файлы профиля **не выполняются**;
- `-NoLogo` — без заставки;
- `-Command "…"` — отключает сохранение истории **до** ввода первой команды. Эта строка не набирается внутри окна, поэтому сама
  в историю PowerShell не попадает;
- `-NoExit` — окно остаётся открытым для ввода команд.

Настройка действует только в этом окне и исчезает после его закрытия. В папку проекта переходить не нужно: все команды используют
полные пути.

**П0** — убедиться, что окно открыто правильно и что диск `D:` локальный:
```powershell
(Get-PSReadLineOption).HistorySaveStyle
[Environment]::CommandLine
$PSVersionTable.PSVersion
(New-Object System.IO.DriveInfo 'D').DriveType
```

Ожидается:
- в первой строке — `SaveNothing`;
- во второй — строка запуска с `-NoProfile`;
- в последней — `Fixed`. Если там `Network` или другое значение, **0А останавливается**: проект лежит не на локальном диске, и чтение
  файлов означало бы обращение к сети.

Если первая строка не `SaveNothing`:
- выполните `Set-PSReadLineOption -HistorySaveStyle SaveNothing` и повторите П0;
- в историю тогда могли попасть только строка П0 и эта команда — секретов в них нет.

Если `-NoProfile` в строке запуска нет — закройте окно и запустите заново по шагам 1–2.

**Чего отключение истории НЕ обеспечивает** — чтобы не создавать ложного ощущения полной конфиденциальности:
- **вывод команд отправляется в чат**. Он сохраняется в переписке и попадает к Anthropic. В выводе есть имена и пути файлов,

### Б.2. Часть 0А-1: проект

**Ф — определения для П2, П4, П7, П8, П9а, П10.** Вставляются один раз в начале. Сами ничего не выполняют и ничего не читают.

`Get-TreeFiles` обходит папки сам, без `-Recurse`:
- в символические ссылки и точки соединения каталогов, в том числе если такой точкой является сам начальный путь, **не заходит**,
  а перечисляет их;
- ошибки доступа, слишком длинных путей и отсутствующие начальные пути **собирает** в `$global:WalkIssues`, а не скрывает.

Если список проблем не пуст, результат обхода имеет статус **INCOMPLETE**. `Show-PathValue` нужен для П9а.

```powershell
function Get-TreeFiles([string[]]$Roots, [string[]]$ExcludeDirs) {
  $ErrorActionPreference = 'Continue'
  $global:WalkIssues = New-Object System.Collections.ArrayList
  $stack = New-Object System.Collections.Stack
  foreach ($r in $Roots) {
    $ev = $null
    $ri = Get-Item -Force -LiteralPath $r -ErrorAction SilentlyContinue -ErrorVariable ev
    if (@($ev).Count -gt 0) {
      foreach ($e in $ev) {
        if ($e.Exception -is [System.Management.Automation.ItemNotFoundException]) { [void]$global:WalkIssues.Add("ROOT MISSING: $r") }
        else { [void]$global:WalkIssues.Add("ROOT ERROR: $r : $($e.Exception.Message)") }
      }
      continue
    }
    if (-not $ri) { [void]$global:WalkIssues.Add("ROOT MISSING: $r"); continue }
    if ($ri.Attributes -band [System.IO.FileAttributes]::ReparsePoint) { [void]$global:WalkIssues.Add("ROOT IS REPARSE POINT, NOT FOLLOWED: $r"); continue }
    if ($ri.PSIsContainer) { $stack.Push($ri.FullName) } else { $ri }
  }
  while ($stack.Count -gt 0) {
    $dir = $stack.Pop()
    $ev = $null
    $items = @(Get-ChildItem -Force -LiteralPath $dir -ErrorAction SilentlyContinue -ErrorVariable ev)
    foreach ($e in $ev) { [void]$global:WalkIssues.Add("LIST ERROR: $dir : $($e.Exception.Message)") }
    foreach ($it in $items) {
      if ($it.Attributes -band [System.IO.FileAttributes]::ReparsePoint) { [void]$global:WalkIssues.Add("REPARSE POINT NOT FOLLOWED: $($it.FullName)"); continue }
      if ($it.PSIsContainer) { if ($ExcludeDirs -notcontains $it.FullName) { $stack.Push($it.FullName) }; continue }
      $it
    }
  }
}
$pathLike = '^(?:\$\{[A-Za-z_][A-Za-z0-9_]*\}|(?:[A-Za-z]:[\\/]|\\\\|\.{1,2}[\\/]|/|~[\\/])?[A-Za-z0-9 _.\\/()-]*)$'
function Show-PathValue([string]$Where, [int]$Line, [string]$Label, [string[]]$Values) {
  if (@($Values | Where-Object { $_ -notmatch $pathLike }).Count -eq 0) { '{0}:{1} {2} {3}' -f $Where, $Line, $Label, ($Values -join ' -> ') }
  else { '{0}:{1} WITHHELD (value is not a plain path; line not shown)' -f $Where, $Line }
}
```

- буквы, цифры, пробел, `_ . - \ / ( )`;
- в начале — буква диска (`D:\`), `\\`, `./`, `../`, `/` или `~/`;

**Что извлекается:**
- из `config.yaml` — ключи с `root`, `dir`, `path`, `folder` в имени: в кавычках, с дефисом, элементом списка;
- из `docker-compose.yml`:
  - короткая запись подключения `- источник:путь[:режим]`;
  - длинная запись — `type`, `source`, `target`, `device`;
  - переменные `MEDIA_ROOT`, `INDEX_PATH`, `…_DIR`, `…_PATH`, `…_ROOT`.

**Остаточный риск:** значение, которое само выглядит как простой путь, но на деле является секретом, под ключом с `path`, `dir`, `root`,
`folder` в имени — например, `backup_dir: hunter2`. Оно будет выведено. Такие ключи для паролей не используются, но исключить это
полностью нельзя.

**Ограничения** (как в 1.8):
- это поиск по тексту, а не разбор YAML: многострочные значения, якоря, запись в фигурных скобках и файлы `env_file` не распознаются;

- содержимое файлов не исполняется.

- на 24 строках с паролями в разных формах, включая пароль с `/`, `#`, `@` и адреса в значениях путей: старый вариант (1.8) вывел

- шаблоны из этого блока побайтно совпадают с проверенными;
- проверка шла движком Python, а не PowerShell.

### Б.4. Часть 0А-2: Docker — только локальный и только уже запущенный

**Д0 — проверка контекста Docker. Выполняется первой, до любых других команд Docker.**

Команды `docker context show` и `docker context inspect` читают только локальные файлы настроек Docker в профиле пользователя и **к Docker
не подключаются**. Docker считается локальным, только если выполнены все три условия:
- переменные `DOCKER_HOST` и `DOCKER_CONTEXT` пусты;
- контекст определён;
- его адрес начинается с `npipe:////./pipe/` — внутренний канал Windows на этом компьютере (у Docker Desktop это `docker_engine` или
  `dockerDesktopLinuxEngine`).

Адреса `ssh://`, `tcp://`, `unix://` и любые другие считаются **нелокальными**: все команды 0А-2 и 0А-3 пропускаются автоматически, к удалённому
Docker обращений нет. Все дальнейшие команды Docker явно получают проверенный контекст (`--context $ctx`), поэтому не могут уйти
на другой адрес.

```powershell

if (-not $env:DOCKER_HOST -and -not $env:DOCKER_CONTEXT -and $ctx -and $ep -like 'npipe:////./pipe/*') {
  $dockerLocal = $true; 'DOCKER CONTEXT IS LOCAL: OK'
} else {
  'DOCKER CONTEXT IS NOT LOCAL OR UNKNOWN: 0A-2 AND 0A-3 ARE SKIPPED'
}
```

### Б.5. Часть 0А-3: внутри уже работающих контейнеров — **отдельное разрешение**

**Е0** — найти **работающие** контейнеры проекта по службам. Остановленные контейнеры **не запускаются**. Если у вас службы называются

```powershell
  "db=[$db] worker=[$worker] redis=[$redis]"

```

**Е1 — база данных, только чтение, без паролей.**

**Защита от изменений** — на трёх уровнях:
1. `PGOPTIONS="-c default_transaction_read_only=on"` — каждая транзакция сеанса по умолчанию только на чтение;
2. каждый запрос стоит внутри явной транзакции `BEGIN TRANSACTION READ ONLY; … COMMIT;` — в ней PostgreSQL отклоняет любые изменения;
3. в запросах только `SHOW` и `SELECT` из таблиц и системных представлений. Из функций — только функции чтения: `version()`, `count()`,
   `max()`, `now()`, `pg_database_size()`, `pg_size_pretty()`, `current_database()`.

**Защита от использования паролей.** Параметр `-w` лишь **запрещает интерактивный запрос пароля**. Сам по себе он не мешает `psql` взять
сохранённый пароль из переменной `PGPASSWORD`, из файла `.pgpass` или из файла служб. Поэтому `psql` запускается через `env`,
который для этого запуска:
- удаляет переменные `PGPASSWORD`, `PGSERVICE`, `PGSERVICEFILE`;
- направляет `PGPASSFILE` на **несуществующий** файл `/nonexistent/.pgpass`.

Кроме того, `-h /var/run/postgresql` задаёт подключение только через локальный сокет внутри контейнера.

**Итог:** подключение возможно, только если база пускает **без пароля** (в официальном образе `postgres` по умолчанию так настроены
локальные подключения внутри контейнера). Если база требует пароль, `psql` сразу завершится ошибкой
`fe_sendauth: no password supplied`. В этом случае:
- **0А-3 останавливается**;
- пароль **не ищется, не запрашивается и не проверяется** — это не D-19;
- присылается только текст ошибки.

**Прочие свойства:**
- `statement_timeout=60s` и `lock_timeout=5s` — любой запрос прерывается через минуту, а заблокированную таблицу ждёт не дольше 5 секунд.
  Это важно потому, что **Ctrl + C в окне PowerShell может не остановить запрос внутри контейнера**: прерывается клиент `docker`, а уже
  отправленный запрос PostgreSQL может выполняться до конца или до `statement_timeout`;
- `-X` — не читать файл настроек `psql`;
- в неинтерактивном режиме `psql` **не ведёт** файл истории;
- `-v ON_ERROR_STOP=0` — если какой-то таблицы нет (у вас версия проекта от 31.10), ошибка затронет только свою транзакцию;
- текст запросов — только латиницей: так PowerShell 5.1 передаёт его без искажений.

**Проверено заранее** на временном тестовом PostgreSQL 16 в рабочей среде Claude, **не** на компьютере владельца и не на его данных:
- точный текст Е1 выполняется, если одной таблицы нет — остальные запросы выполняются;
- попытка `INSERT` отклоняется: `cannot execute INSERT in a read-only transaction`;
- если база требует пароль, а пароль лежит и в `PGPASSWORD`, и в `.pgpass`: **обычный** `psql -w` подключается, а запуск через `env` с
  перечисленными настройками — **нет**, ошибка `fe_sendauth: no password supplied`.

Тестовая база удалена. Проверка шла с `env` из GNU coreutils; в образе `postgres:16-alpine` используется `env` из BusyBox с тем же синтаксисом
`-u ИМЯ` (по документации BusyBox; в самом образе не проверялось).

```powershell
COMMIT;

COMMIT;
```

**Как читать вывод:**
- первые две строки должны быть `on` и `on`; если это не так, результаты **не используются**, и об этом нужно сообщить;
- в конце должны быть `end-of-e1` и `exit=0`. Отметки нет или код не 0 — вывод **неполный**. Даже при `exit=0` строки `ERROR:`
  или `ROLLBACK` означают, что часть запросов не выполнилась: при `ON_ERROR_STOP=0` psql завершается с кодом 0 и после ошибок — проверено;
- `approx_rows` (`n_live_tup` из `pg_stat_user_tables`) — **приблизительная статистика**, а не точное число строк. Она не используется
  как доказательство количества. Точное число строк дают только запросы `count(*)` ниже;
- `newest_created_at` — значение поля `created_at` у **самой новой по этому полю** записи. Это **не** время последнего изменения таблицы:
  поле не отражает изменения и удаления существующих записей и зависит от того, как программа его заполняет.

**Е2** — какие модели уже скачаны в том `hf_cache` (важно для 1А и проверки 11 в 2А):

## Приложение В. Снимок состояния до и после 2А без файлов в рабочем проекте

**Не входит в 0А.** Снимок выполняется в рамках 2А и только по разрешению на 2А. **Полное хеширование рабочей базы (В.2в) в разрешение на 2А
не входит** — это отдельная операция с отдельным разрешением, которое владелец даёт после оценки В.2а. Цель снимка — проверка 12:
рабочая система не изменилась. В `D:\retail-shelf-audit` при этом ничего не создаётся.

**Отсутствие ошибок на тестовой базе в рабочей среде Claude не доказывает безопасность выполнения на рабочей системе владельца.** Тесты
показывают только, что запросы синтаксически верны и ведут себя так, как описано, на PostgreSQL 16 с тестовыми данными.

а не выполняют команду с пустым значением.

**Общие функции для команд Docker** (вставляются вместе с остальными определениями). `Invoke-DockerPart` выполняет одну справочную
команду Docker. Каждая строка, которую программа выдала в поток ошибок (stderr), сохраняется с пометкой `DOCKER STDERR [часть]`,
а в конце добавляется код завершения `DOCKER_EXIT [часть]=N`. `Test-PartsSnapshot` признаёт снимок полным, только если нет ни одной
строки stderr, все коды равны 0, есть отметка конца и обязательные строки. В Windows PowerShell 5.1 строки stderr внешней программы
при `2>&1` приходят как объекты `ErrorRecord`; функция распознаёт их по типу. Внутри функций `$ErrorActionPreference = 'Continue'`:
при значении `Stop` PowerShell 5.1 превращал бы stderr в прерывающую ошибку. Это по документации и известному поведению 5.1 —
**не запускалось**; проверяется тестом T3 (В.7):
```powershell
function Invoke-DockerPart([string]$Part, [string[]]$DockerArgs) {
  $ErrorActionPreference = 'Continue'
  $out = @(& docker --context $ctx @DockerArgs 2>&1)
  $code = $LASTEXITCODE
  foreach ($o in $out) { if ($o -is [System.Management.Automation.ErrorRecord]) { "DOCKER STDERR [$Part]: $o" } else { "$o" } }
  "DOCKER_EXIT [$Part]=$code"
}
function Test-PartsSnapshot([string]$Name, $Lines, [string]$EndMarker, [string]$MustHaveLike) {
  $text = @($Lines | ForEach-Object { "$_" })
  $p = New-Object System.Collections.ArrayList
  if ($text.Count -eq 0) { [void]$p.Add('no output') }
  if ($EndMarker -and -not ($text -contains $EndMarker)) { [void]$p.Add("MISSING: $EndMarker") }
  if ($MustHaveLike -and -not ($text | Where-Object { $_ -like $MustHaveLike })) { [void]$p.Add("MISSING: $MustHaveLike") }
  foreach ($l in $text) {
    if ($l -like '*DOCKER STDERR*' -or $l -like 'MISSING:*' -or $l -like 'STOP:*') { [void]$p.Add($l) }
    if ($l -match 'DOCKER_EXIT \[(.+)\]=(.+)$' -and $Matches[2] -ne '0') { [void]$p.Add($l) }
  }
  if ($p.Count -gt 0) { "INCOMPLETE: $Name"; $p } else { "OK: $Name" }
}
```

**Главное правило сравнения:** вывод «изменений нет» допустим, **только если** все проверки полноты (В.5, `Test-…`) дали `OK`, а списки
непроверенного пусты. Иначе итог — «проверка неполная», с перечнем того, что не проверено.

**Что учтено в функции:**
- **Обход** делает функция `Get-TreeFiles` из приложения Б (блок Ф); она вставляется первой. Начальные пути проверяются до обхода:
  отсутствующий путь, ошибка доступа к нему или путь-ссылка (точка повторной обработки) не обходятся и попадают в `$global:WalkIssues`.
  Ошибки доступа и слишком длинные пути внутри тоже не теряются молча.
- **Статус** даёт `Test-FileSnapshot`: **INCOMPLETE**, если есть хоть одна проблема обхода, нечитаемый файл или файл, изменившийся
  во время чтения.
- **Файлы, изменившиеся во время чтения.** Размер и время изменения файла сверяются до и после вычисления SHA-256. Если они разошлись,
  файл отмечается `StableDuringRead = False`. Его SHA-256 не считается достоверным, и его нужно снять повторно после завершения записи.
- **Файл, который нельзя прочитать** (занят другой программой, исчез, слишком длинный путь), получает в поле `Hash` текст `ERROR: …`,
  а не пропускается. Если файл не читается и «до», и «после», тексты ошибок совпадут, и `Compare-Object` отличия не покажет. Поэтому
  такие файлы выводятся **отдельным списком «не проверены»** (В.5). В версии 1.7 этого не было, и непрочитанный файл мог сойти за
  неизменный.
- **Ссылки и точки повторной обработки** не читаются и в снимок не попадают. Они перечисляются в `$global:WalkIssues` и делают
  снимок неполным.

```powershell
function Get-FileSnapshot([string[]]$Paths, [string[]]$ExcludeDirs) {
  $ErrorActionPreference = 'Continue'
  foreach ($f in @(Get-TreeFiles $Paths $ExcludeDirs)) {
    $h = try { (Get-FileHash -Algorithm SHA256 -LiteralPath $f.FullName -ErrorAction Stop).Hash } catch { 'ERROR: ' + $_.Exception.Message }
    $re = Get-Item -Force -LiteralPath $f.FullName -ErrorAction SilentlyContinue
    $stable = [bool]($re -and $re.Length -eq $f.Length -and $re.LastWriteTimeUtc -eq $f.LastWriteTimeUtc)
    [pscustomobject]@{ Path = $f.FullName; Length = $f.Length; LastWriteUtc = $f.LastWriteTimeUtc.ToString('o'); Hash = $h; StableDuringRead = $stable }
```

### В.2. Рабочая база

**Общий способ подключения** — как в Е1:
- без паролей (`env` удаляет `PGPASSWORD`, `PGSERVICE`, `PGSERVICEFILE`, а `PGPASSFILE` указывает на несуществующий файл);
- `-w` — без запроса пароля; если без пароля нельзя, операция останавливается;
- `default_transaction_read_only=on`, каждый запрос — в транзакции только на чтение.

**Ограничители длительности** — действуют только на этот сеанс:
- `statement_timeout=120s` — отдельный запрос прерывается через 2 минуты;
- `lock_timeout=5s` — блокировка ждётся не дольше 5 секунд;
- `idle_in_transaction_session_timeout=60s` — простой открытой транзакции не дольше минуты.

**Закреплённые параметры вывода** — нужны, чтобы текстовое представление строк было одинаковым в снимках «до» и «после»:
`TimeZone=UTC`, `DateStyle=ISO,YMD`, `IntervalStyle=postgres`, `extra_float_digits=1`, `bytea_output=hex`, `lc_monetary=C`.
Без них, например, смена `DateStyle` меняет отпечаток при неизменных данных — проверено. Параметры меняют только вывод этого
сеанса, а не данные.

**Сообщения об ошибках — всегда на английском:** `lc_messages=C` (на сервере, разрешено суперпользователю) и `LC_ALL=C` (для `psql`).
Иначе при русской настройке сервера ошибки выглядели бы как `ОШИБКА:` и не распознавались бы проверкой полноты. В тестовой среде
русской локали нет — это **по документации**, не проверено.

**Код завершения.** Функция добавляет в конец вывода строку `PSQL_EXIT=N`. Сам по себе код 0 полноту не доказывает: при
`ON_ERROR_STOP=0` psql завершается с кодом 0 и после ошибок в запросах — проверено. Поэтому `Test-SqlSnapshot` требует сразу всё:
- нет строк ошибок в форматах `psql:<stdin>:N: ERROR:`, `psql: error: …`, `FATAL:`, `WARNING:`, `PANIC:`, `ROLLBACK`, сообщений
  `env:` и Docker;
- `PSQL_EXIT=0`;
- есть **каждая обязательная строка** своего снимка (`$reqEstimate`, `$reqLight`, `$reqFull`), включая отметку конца.

**Ещё два параметра сеанса:**
- `row_security=off` — если для какой-то таблицы действуют правила защиты строк (RLS), а у роли нет права их обходить, запрос
  **завершится ошибкой**, а не вернёт молча часть строк. Проверено: без этого параметра роль без права обхода видела 1 строку из 2,
  а с ним получила ошибку. Роль `postgres` — суперпользователь, правила на неё не действуют; В.2а и В.2в выводят строку `role: …`
  для контроля;
- `max_parallel_workers_per_gather=0` — без параллельных процессов. Нагрузка на компьютер магазина ниже, хеширование медленнее.
  Проверено: по умолчанию план запроса использовал 2 параллельных процесса, с параметром — ни одного.

```powershell

  $ErrorActionPreference = 'Continue'

function Test-SqlSnapshot([string]$Name, $Lines, [string[]]$Required) {
  $text = @($Lines | ForEach-Object { "$_" })
  $p = New-Object System.Collections.ArrayList
  if ($text.Count -eq 0) { [void]$p.Add('no output') }
  foreach ($l in $text) {
    if ($l -cmatch '(^|\s)(ERROR|FATAL|PANIC|WARNING):' -or $l -ceq 'ROLLBACK' -or $l -match '^psql: (error|warning|fatal)|no password supplied|could not connect|server closed the connection|connection to server was lost|terminating connection|^Error|^env: |OCI runtime|executable file not found|^STOP:|^Killed$') { [void]$p.Add("BAD LINE: $l") }
  }
  $exit = @($text | Where-Object { $_ -like 'PSQL_EXIT=*' })
  if ($exit.Count -ne 1 -or $exit[0] -ne 'PSQL_EXIT=0') { [void]$p.Add("EXIT STATUS: $($exit -join ', ')") }
  foreach ($r in $Required) { if (-not ($text | Where-Object { $_ -like $r })) { [void]$p.Add("MISSING: $r") } }
  if ($p.Count -gt 0) { "INCOMPLETE: $Name"; $p } else { "OK: $Name" }
}
```

**Границы проверки базы** — какие объекты входят в полное хеширование. Список строится динамически по системному каталогу, без привязки
к 14 таблицам:

| Объект | `relkind` / признак | В отпечаток содержимого | Обоснование |
|---|---|---|---|
| Обычная таблица | `r` | **да** | основные данные |
| Секция секционированной таблицы | `r`, `relispartition` | **да**, каждая отдельно | строки хранятся в секциях |
| Секционированная таблица — родитель | `p` | **нет**, но входит в отпечаток структуры | своих строк не хранит; строки читаются через секции. Секция и родитель не учитываются дважды |
| Родитель в наследовании (`INHERITS`) | `r` с потомками | **да, только свои строки**: `FROM ONLY` | без `ONLY` запрос к родителю включает строки потомков, и они учитывались бы дважды. Это **исправлено**: в версии 1.6 `ONLY` не было, тест показал двойной счёт |
| Нежурналируемая таблица | `r`, `relpersistence = 'u'` | **да** | постоянная часть базы; входит в `pg_dump` |
| Материализованное представление | `m`, заполненное | **да** | хранит данные; меняется только при обновлении (`REFRESH`), а это тоже изменение |
| Материализованное представление, не заполненное | `m`, `relispopulated = false` | **нет**, указывается в оценке | чтение невозможно (ошибка «has not been populated») |
| Внешняя таблица | `f` | **нет**, никогда не читается; входит в отпечаток структуры | данные на другом сервере; чтение означало бы сетевое обращение |
| Представление | `v` | **нет**; столбцы входят в отпечаток структуры | своих строк нет. Текст определения представления не сравнивается — это граница проверки |
| Временные таблицы сеансов | `relpersistence = 't'`, схемы `pg_temp*` | **нет** | не часть постоянной базы. Чтение чужих временных таблиц невозможно (ошибка «cannot access temporary tables of other sessions»), а их появление и исчезновение дало бы ложные отличия. **Исправлено**: в версии 1.6 они попадали в список — проверено |
| Таблицы расширений | `r` в несистемной схеме, зависимость `e` в `pg_depend` | **да**, отмечаются в оценке | их содержимое может меняться (настройки расширений). В текущей схеме программы расширений с таблицами нет — по коду; на рабочей базе не проверено |
| Системные каталоги, TOAST-таблицы как отдельные объекты | схемы `pg_catalog`, `information_schema`, `pg_toast*` | **нет** | системные данные; длинные значения (TOAST) читаются через свою основную таблицу |
| Последовательности | `S` | **нет**, число показывается в оценке | это счётчики, а не строки данных; программа использует строковые идентификаторы |
| Большие объекты (`pg_largeobject`) | системный каталог | **нет**, число показывается в оценке | программа их не использует — по коду. Если оценка покажет число больше 0, это отдельный вопрос владельцу |
| Другие базы на том же сервере | — | **нет** | проверяется только `shelf_audit`; список баз показывается в оценке |

#### В.2а. Оценка размера и нагрузки — до любого хеширования

Читает **только системный каталог и настройки**. Строки таблиц не читаются; выполняется за доли секунды.

```powershell
$sqlEstimate = @'

SHOW transaction_read_only;
```

**Что показывает:**
- строку `role: … superuser=… bypassrls=…`. Если там не `superuser=true` или `bypassrls=true`, В.2в **не выполняется**: часть строк может
  быть недоступна;
- каждый объект с отметкой, входит ли он в полное хеширование, и почему;
- итог по хешируемым объектам: сколько их, сколько данных к чтению (`data_to_read_total`), самый большой объект, оценка общего числа строк;
- число больших объектов, последовательностей, временных таблиц сеансов, список баз на сервере;
- настройки, влияющие на нагрузку.

**Блокировки.** Функция размера `pg_table_size` на мгновение берёт самую слабую блокировку каждой таблицы. Если таблица в этот момент
заблокирована изменением структуры, оценка ждёт не больше 5 секунд (`lock_timeout`) и завершается ошибкой. Проверено: вся оценка
отменяется (`ROLLBACK`), её нужно повторить позже.

**Статистика — приблизительная.** `approx_rows_estimate` (`pg_class.reltuples`) — оценка планировщика, а не точное число строк. Значение
`-1` означает, что таблица ещё не анализировалась. То же относится к `n_live_tup` в Е1. Точное число строк дают только `count(*)`
в В.2в и при проверке копии в 2А.

**Время В.2в — только предварительная оценка, не гарантированная скорость.**
- **Опорный замер** на тестовой машине в рабочей среде Claude (процессор Xeon 2,1 ГГц, PostgreSQL 16, данные уже в памяти,
  без другой нагрузки): таблица из 1 млн строк и 131 МБ, похожая по составу на таблицу товаров, хешируется за 1,7 секунды.
  Это примерно 77 МБ/с или 600 тыс. строк/с. Из них:
  - около 0,4 секунды — получение текстового представления строк;
  - около 0,4 секунды — MD5;
  - около 0,85 секунды — суммирование.
- **Диапазон 20–100 МБ/с** для оценки — допущение, а не измерение на вашем компьютере. Верхняя граница близка к замеру выше, нижняя
  оставляет запас на медленный диск и нагрузку.
- **Реальное время зависит от:**
  - превращения строк в текст (сериализации);
  - числа строк: при множестве коротких строк важнее число строк, чем мегабайты;
  - типов данных: длинные тексты, JSON и двоичные значения (TOAST, распаковка; `bytea` в шестнадцатеричном виде вдвое длиннее);
  - вычисления хешей;
  - чтения с диска: на HDD и при холодном кэше — медленнее;
  - Docker Desktop: виртуальная машина WSL2;
  - одновременной нагрузки на диск и PostgreSQL;
  - скорости процессора.
- **Как оценивать:** брать **большее** из двух значений — `data_to_read_total` ÷ 20 МБ/с и `approx_rows_total` ÷ 100 тыс. строк/с.
  Если для самого большого объекта получается больше 2 минут, он прервётся по `statement_timeout` и будет отмечен «не проверен». Тогда
  отдельно решается: пропустить его или изменить ограничитель.

**Как ведут себя счётчики — проверено на PostgreSQL 16 в рабочей среде Claude:**

| Событие | Счётчики | Что ещё меняется | Вывод |
|---|---|---|---|
| Добавление, изменение, удаление с **откатом** транзакции | **растут** (+1, +1, +1), хотя данные не изменились | — | ложный признак изменения |
| `TRUNCATE` (все строки удалены) | **не меняются** | `filenode` | по одним счётчикам `TRUNCATE` не виден; поэтому добавлен `filenode` |
| Перезапись таблицы `ALTER TABLE … USING` (данные изменены) | **не меняются** | `filenode`; структура — если изменился тип | по одним счётчикам не видна |
| Сброс статистики одной таблицы (`pg_stat_reset_single_table_counters`) | **обнуляются** | `stats_reset` базы обновляется (так в PostgreSQL 16) | видно по `stats_reset` и уменьшению счётчиков |
| Сброс статистики базы (`pg_stat_reset`) | обнуляются | `stats_reset` | видно |
| **Аварийная остановка** PostgreSQL и запуск | **обнуляются**, изменения до аварии из статистики теряются | `stats_reset` становится **пустым (NULL)**, `server_started` меняется | одного `stats_reset` **недостаточно**: если он был пустым и до аварии, он не изменится. Поэтому добавлено `server_started` |
| Нормальный перезапуск | сохраняются | `server_started` | — |
| Пересоздание таблицы с тем же именем | начинаются с нуля | `relid`, `filenode` | видно |
| `VACUUM FULL`, `CLUSTER` (данные не меняются) | не меняются | `filenode` | ложный признак изменения |

Также, по документации PostgreSQL:
- статистика попадает в представления с задержкой: каждый процесс сервера передаёт накопленную статистику не чаще раза в секунду,
  а у простаивающих соединений бывает и позже. Поэтому снимок В.2б «после» делается **не раньше чем через 1 минуту** после
  удаления временной среды;
- изменения последовательностей, больших объектов и других баз счётчиками таблиц не учитываются.

**Что отпечатки структуры не охватывают** (граница проверки): комментарии к объектам, объекты расширенной статистики, событийные
триггеры, публикации и подписки, роли и прочие общие объекты сервера, настройки сервера, другие базы, значения последовательностей.

**Блокировки.** Функции, выдающие определения объектов, могут ждать снятия блокировки изменения структуры. Ожидание ограничено
5 секундами; после него вся транзакция В.2б отменяется. Проверено: при эксклюзивной блокировке таблицы другим сеансом вывод
содержит `ERROR: canceling statement due to lock timeout` и `ROLLBACK`. Такой снимок считается **неполным** (В.5) и повторяется.

**Итог: отсутствие отличий в признаках В.2б не доказывает отсутствие изменений в данных.** Признаки ловят часть изменений и дают
ложные срабатывания. Это не проверка целостности. Неизменность содержимого может показать только В.2в — в его границах.

#### В.2в. Полное хеширование — **отдельная операция с отдельным разрешением**

Автоматически не запускается и в разрешение на 2А не входит. Решение принимается по результату В.2а.

**Алгоритм:**
1. Объекты берутся из системного каталога по границам В.2: обычные таблицы, секции, родители наследования (только свои строки),
   нежурналируемые таблицы, заполненные материализованные представления. Временные, внешние, представления и секционированные родители
   не читаются.
2. У каждого объекта — **своя короткая транзакция** `BEGIN TRANSACTION READ ONLY; SELECT …; COMMIT;`. Одной длинной транзакции на всю
   базу нет: старый снимок данных удерживается только на время чтения одного объекта.
3. Для каждой строки вычисляется MD5 её текстового представления: `md5(x::text)`, все столбцы, при закреплённых параметрах вывода.
4. По объекту выводятся:
   - точное число строк `count(*)`;
   - две суммы — первых и вторых 64 бит MD5 строк (`sum1`, `sum2`).

   Сумма не зависит от порядка строк и учитывает одинаковые строки. Сортировка не нужна, поэтому память постоянна и временных файлов нет.

**Точный текст:**
- генератор строит на каждый объект четыре команды:
  - отметку `start: объект`;
  - `BEGIN TRANSACTION READ ONLY`;
  - `SELECT` с отпечатком;
  - `COMMIT`;
- команда `psql` `\gexec` выполняет их по очереди;
- в конце выводится `end-of-full-hash`;
- генератор и сгенерированные запросы содержат только `SELECT`, `BEGIN TRANSACTION READ ONLY` и `COMMIT`.

**Полнота результата.** Если объект прерван по `statement_timeout` или `lock_timeout`, сообщение об ошибке не всегда содержит его имя —
проверено. А если один и тот же объект прерывается и «до», и «после», `Compare-Object` отличия не покажет. Поэтому:
- отметка `start:` есть для каждого объекта;
- функция `Get-UnverifiedObjects` (В.5) перечисляет объекты, у которых есть отметка начала, но нет строки результата;
- отсутствие `end-of-full-hash` означает, что `psql` завершился раньше.

В версии 1.7 этих отметок не было, и непроверенный объект мог сойти за неизменный.

**Проверено** на тестовой базе в рабочей среде Claude:
- при эксклюзивной блокировке одной таблицы другим сеансом она прервана через 5 секунд, остальные объекты проверены, `end-of-full-hash`
  выведен;
- при очень малом `statement_timeout` большая таблица прервана, остальные проверены;
- роль без суперпользователя: строка `role:` это показывает, таблица с защитой строк даёт ошибку, а не часть строк.

**Одинаковое содержимое разных таблиц даёт одинаковый отпечаток.** Так и должно быть: отпечаток описывает содержимое, а сравнение идёт
по имени объекта.

```powershell
$sqlFull = @'
```

**Сколько данных читается:** все строки всех хешируемых объектов целиком, включая длинные значения (TOAST) — примерно
`data_to_read_total` из В.2а. Индексы не читаются.

**Оценка алгоритма и сравнение с потоковым SHA-256:**

| Свойство | Текущий: MD5 строк + две суммы | Вариант: SHA-256 строк + две суммы | Вариант: потоковый SHA-256 упорядоченной выгрузки |
|---|---|---|---|
| Обнаружение **случайных** изменений | изменение строки меняет её MD5. Шанс, что изменение не отразится ни на одной из сумм, — порядка 2⁻¹²⁸ на изменение. Для сравнения двух снимков этого достаточно | то же: слабое место — построение суммой, а не хеш | хеш всей таблицы целиком; практически абсолютная надёжность |
| Защита от **намеренной** подделки | **нет**: MD5 уязвим к коллизиям, а сумму хешей можно подобрать | **нет**: сумму можно подобрать и с SHA-256 | да, при защищённом хранении результата |
| Порядок строк | не важен | не важен | **нужен однозначный порядок**: первичный ключ или сортировка всей строки |
| Память и временные файлы | постоянная память, временных файлов нет (проверено) | то же | с первичным ключом — постоянная; **без него — сортировка, временные файлы в томе базы** (в тесте 136 МБ на 1 млн строк) |
| Время (тест, 1 млн строк, 131 МБ) | 1,7 с | MD5 и SHA-256 по 0,8 с — практически одинаково на этом процессоре; итог около 1,7 с | 1,3 с по первичному ключу, 3,8 с с сортировкой — плюс передача всех строк через `psql` |
| Сложность команды | одна команда на объект | одна команда | конвейер `psql … COPY … \| sha256sum` внутри контейнера, отдельный порядок для каждой таблицы |

**Вывод:**
- Текущего алгоритма **достаточно** для задачи В.2в — обнаружить **случайные** изменения между двумя снимками.
- Замена на SHA-256 **не требуется**. Вариант «SHA-256 + суммы» не повышает защиту от намеренной подделки: слабое место — сумма.
- Потоковый SHA-256 нужен только для защиты от **намеренной** подделки. Такой задачи у 2А нет, а без первичного ключа он требует
  временных файлов в рабочем томе.
- **Алгоритм не заменён.**

**Границы надёжности:**
- текстовое представление зависит от параметров вывода. Они закреплены, поэтому ложное **совпадение** из-за них невозможно; при незакреплённых
  было бы возможно ложное **отличие**;
- смена типа столбца при одинаковом тексте (например, `integer` → `bigint`) отпечатком содержимого не видна, но видна в отпечатке
  структуры (В.2б);
- `NULL` и пустая строка различаются: `(1,)` и `(1,"")`.

**Возможные последствия длительного выполнения:**

| Последствие | Почему | Как ограничено |
|---|---|---|
| Очистка старых версий строк (autovacuum) не может удалить версии, появившиеся после начала чтения объекта | открытая транзакция удерживает снимок данных | своя короткая транзакция на каждый объект; `statement_timeout=120s`; нерабочее время |
| Временный рост таблиц и индексов при активной записи в это время | следствие предыдущего пункта | то же; после завершения очистка продолжается сама |

| **Физическая запись на диск** возможна, хотя данные не меняются: при чтении PostgreSQL ставит отметки видимости строк и может очищать старые версии строк на странице. Временных файлов нет (проверено) |
| Сетевые обращения | не выполняются: внешние таблицы не читаются; материализованные представления читаются как сохранённые данные, их запрос не выполняется | — |

### В.3. Модели в томе `hf_cache` — SHA-256

```powershell
function Get-HfSnapshot {
  if (-not ($dockerLocal -and $ctx -and $worker)) { throw 'STOP: local Docker context or running worker container is not verified - run D0-D2 and E0 first' }
  Invoke-DockerPart 'hf_cache' @('exec', $worker, 'sh', '-c', "find /root/.cache/huggingface -type f -exec sha256sum '{}' + && find /root/.cache/huggingface -type l -exec ls -l '{}' + && echo end-of-hf-snapshot") | Sort-Object
}
```

- команда выполняется через `Invoke-DockerPart`: строки ошибок попадают в снимок с пометкой `DOCKER STDERR`, код завершения —
  строкой `DOCKER_EXIT`;
- части команды связаны `&&`: отметка `end-of-hf-snapshot` появляется, только если обе команды `find` завершились без ошибок. В версии 1.8
  части разделялись `;`, и отметка выводилась даже после ошибки;
- добавлен список символических ссылок кэша (какая ссылка указывает на какой файл);
- отметка `end-of-hf-snapshot` подтверждает, что команда дошла до конца;
- `find` и `sha256sum` — стандартные программы образа на основе Debian (`python:3.12-slim` в версии 11-06b). В вашем образе от 31.10 их
  наличие не проверено: если их нет, проверка полноты покажет ошибку.

**Что делает:** читает **полностью** все файлы моделей в томе. Для DINOv2-base это около 350 МБ — ориентировочно несколько секунд.
Если контейнер `worker` не запущен, сравнение моделей не выполняется, и в отчёте это указывается прямо.

**Модели в копии и манифесте** (действует для 0Б и 2А):
- **если модели включаются** в копию — в манифест записывается SHA-256 каждого файла;
- **если не включаются** — в манифесте явно указывается:
  - «модели в копию не включены»;
  - какие модели и где лежат;
  - SHA-256 их текущих файлов для сверки;
  - что восстановление скачиванием требует отдельного разрешения;
- совпадение размера и времени изменения **не считается** доказательством целостности.

### В.4. Рабочие контейнеры — только справочные команды

**Что сравнивается до и после** — для каждого контейнера с меткой проекта `retail-shelf-audit`:

| Характеристика | Поле `docker inspect` | Что означает отличие |
|---|---|---|
| Имя | `.Name` | контейнер переименован или заменён |
| **ID контейнера** | `.Id` | контейнер пересоздан |
| **ID образа** | `.Image` | контейнер пересоздан из другого образа |
| **Состояние** | `.State.Status` | контейнер остановлен или запущен |
| **Время запуска** | `.State.StartedAt` | контейнер перезапускался |
| Число перезапусков | `.RestartCount` | автоматические перезапуски |
| **Подключения к томам и папкам** | `.Mounts`: тип, имя тома или путь, точка подключения, разрешена ли запись | изменились подключения |

**Для каждого тома проекта** — какие контейнеры к нему подключены. Ни одного контейнера временной среды там быть не должно.

Используются только `docker ps`, `docker inspect`, `docker volume ls` — каждая через `Invoke-DockerPart`, со своими stderr и кодом
завершения. Частичный вывод (например, `inspect` с ошибкой, а `volume ls` без неё) снимок полным не делает. Ничего не запускается,
не останавливается и не меняется. Проверено на имитированных ответах Docker (логика на Python): в версии 1.8 три сценария из пяти давали
ложный «полный» снимок, в новой — ни одного. Настоящий Docker и PowerShell 5.1 не использовались.

```powershell
function Get-DockerSnapshot {
  if (-not ($dockerLocal -and $ctx -and $proj)) { throw 'STOP: local Docker context or project label is not verified - run D0-D2 first' }
  $ps = @(Invoke-DockerPart 'ps' @('ps', '-a', '-q', '--filter', $proj)); $ps
  $ids = @($ps | Where-Object { $_ -match '^[0-9a-f]{12,64}$' })
  if ($ids.Count -eq 0) { 'MISSING: no containers with the project label' }
  else { Invoke-DockerPart 'inspect' (@('inspect', '--format', '{{.Name}} | id={{.Id}} | image={{.Image}} | state={{.State.Status}} | started={{.State.StartedAt}} | restarts={{.RestartCount}} | mounts={{range .Mounts}}[{{.Type}} {{if .Name}}{{.Name}}{{else}}{{.Source}}{{end}} -> {{.Destination}} rw={{.RW}}]{{end}}') + $ids) }
  $vl = @(Invoke-DockerPart 'volume ls' @('volume', 'ls', '-q', '--filter', $proj)); $vl
  foreach ($v in @($vl | Where-Object { $_ -match '^[A-Za-z0-9][A-Za-z0-9_.-]*$' })) {
    Invoke-DockerPart "ps volume=$v" @('ps', '-a', '--filter', "volume=$v", '--format', '{{.Names}}') | ForEach-Object { "$v used by: $_" }
  }
  'end-of-docker-snapshot'
}
```

**В.4а. Подключения временной среды** — выполняется, пока временная среда ещё существует, до её удаления. Справочная команда только
по контейнерам временной среды. `$tempProj` — имя проекта временной среды; оно задаётся инструментом 2А и пока неизвестно:
```powershell
$tempProj = '<temporary environment project name>'
$tmpPs  = @(Invoke-DockerPart 'temp ps' @('ps', '-a', '-q', '--filter', "label=com.docker.compose.project=$tempProj"))
$tempIds = @($tmpPs | Where-Object { $_ -match '^[0-9a-f]{12,64}$' })
$wv = @(Invoke-DockerPart 'work volumes' @('volume', 'ls', '-q', '--filter', $proj))
$workVolumes = @($wv | Where-Object { $_ -match '^[A-Za-z0-9][A-Za-z0-9_.-]*$' })
$mounts = if ($tempIds.Count -gt 0) { @(Invoke-DockerPart 'temp inspect' (@('inspect', '--format', "{{.Name}}{{range .Mounts}}`t{{.Type}}`t{{.Name}}`t{{.Source}}`t{{.RW}}{{end}}") + $tempIds)) } else { @('MISSING: no containers of the temporary environment - check $tempProj') }
if ($workVolumes.Count -eq 0) { $mounts += 'MISSING: list of working volumes is empty' }
$violations = @(foreach ($line in $mounts) {
  if ($line -like 'DOCKER_*' -or $line -like 'MISSING:*') { continue }
  $parts = $line -split "`t"
  for ($i = 1; $i + 3 -lt $parts.Count; $i += 4) {
    $mName = $parts[$i + 1]; $mSrc = $parts[$i + 2]
    if (($workVolumes -contains $mName) -or ($mSrc -match '(?i)(^|[\\/])d:?[\\/]retail-shelf-audit([\\/]|$)')) { "VIOLATION: $($parts[0]) mounts working $($parts[$i]) [$mName$mSrc] rw=$($parts[$i + 3])" }
  }
})
Test-PartsSnapshot 'temporary environment mounts' ($tmpPs + $wv + $mounts + 'end-of-temp-mount-check') 'end-of-temp-mount-check' ''
if ($violations.Count -gt 0) { 'FAILED: working volumes or the working folder are mounted into the temporary environment'; $violations } else { 'No violations among the containers that were inspected' }
```

**Нарушение** — любое подключение рабочего тома или рабочей папки `D:\retail-shelf-audit` к контейнеру временной среды, даже только
на чтение: так требует таблица изоляции 2А. Шаблон пути распознаёт `D:\retail-shelf-audit`, `/run/desktop/mnt/host/d/retail-shelf-audit`
и `/host_mnt/d/…`, но не `D:\retail-shelf-audit_copy…` и не папки с таким именем в другом месте. Проверено движком Python, не в
PowerShell. Точный вид пути у вашего Docker Desktop не проверен.

**Шаг 3. Во время 2А, до удаления временной среды:** В.4а.

**Шаг 4. Снимок «после»** — после удаления временной среды и **не раньше чем через 1 минуту**, в том же окне; затем сравнение:
```powershell

$dbLightAfter  = Invoke-ReadOnlySql $sqlLight

# $dbFullAfter = Invoke-ReadOnlySql $sqlFull

$fd = Compare-Object @($filesBefore) @($filesAfter) -Property Path, Length, LastWriteUtc, Hash

'== FILES: expected-volatile (explain) ==';    $fd | Where-Object { $_.Path -match $volatile }
'== DB LIGHT (indicators only, not proof) =='; Compare-Object @($dbLightBefore) @($dbLightAfter)
'== HF_CACHE ==';                             Compare-Object @($hfBefore) @($hfAfter)
'== DOCKER ==';                               Compare-Object @($dockerBefore) @($dockerAfter)
# '== DB FULL =='; Compare-Object @($dbFullBefore) @($dbFullAfter)
```

**Как читать сравнение:**
- **сначала — раздел полноты «до» и «после»**. Если там есть `INCOMPLETE`, итог — «проверка неполная», с перечнем проблем, который
  выводит каждая проверка. Пустые разделы отличий в этом случае **ничего не доказывают** для непроверенной части;
- пустой вывод под заголовком отличий означает, что среди **проверенного** изменений нет;
- каждое отличие показывается строкой со стрелкой: `<=` — было только «до», `=>` — появилось только «после»;
- если оба снимка какого-то раздела пусты, `Compare-Object` может выдать ошибку о пустом значении: сравнивать нечего, и это тоже
  отмечается как «не проверено».

**Вариант Б** — сохранение вне проекта сразу после снимка «до». Папка создаётся только по разрешению 2А; путь внутри рабочего проекта
отвергается:
```powershell
$dir = 'D:\backups_retail\2A-<дата>'
$full = [System.IO.Path]::GetFullPath($dir)

$hfBefore      | Export-Clixml -LiteralPath "$full\hf-before.xml"
$dockerBefore  | Export-Clixml -LiteralPath "$full\docker-before.xml"
```
`New-Item … -ErrorAction Stop` завершится ошибкой, если папка уже существует, — существующие файлы не перезаписываются. Для сравнения
файлы читаются обратно: `$filesBefore = Import-Clixml -LiteralPath "$full\files-before.xml"`, так же остальные. `<дата>` заменяется

### В.7. Тест функций в настоящем Windows PowerShell 5.1 — отдельное разрешение

Ни одна функция приложений Б и В и сам тест в Windows PowerShell 5.1 **не запускались**. Подготовлены два файла:
- `protocol_0A_functions.ps1` — определения функций. Они побайтно совпадают с блоками плана: Ф, общие функции В.0, В.1, В.2, В.3, В.4.
  Совпадение проверено сравнением текста;
- `Test-Protocol0A.ps1` — тест.

**Защита данных** (реализовано в тесте):
- **Сначала проверка версии.** Если это не Windows PowerShell 5.1 (Desktop), тест сразу завершается с итогом `ABORTED`, ничего
  не создав.
- **Подготовка прерывается при первой ошибке** (`$ErrorActionPreference = 'Stop'`).
- **Функции загружаются до создания чего-либо.** Если файл не найден или какой-то функции нет, итог — `ABORTED`.
- **Папка `TEMP` проверяется заранее.** Она берётся из `GetTempPath()` и проверяется: не пустая, существует, не корень диска, не ссылка.
- **Временная папка.** Имя — `p0a-test-<32 шестнадцатеричных знака>`. Её не должно существовать заранее. Сразу после создания
  в неё записывается файл-метка с этим идентификатором.
- **Каждый создаваемый путь** проверяется функцией `Assert-InSandbox`: он должен быть строго внутри временной папки, с учётом границ
  каталогов и без `-like`.
- **Очистка проверяется независимо** функцией `Test-SandboxSafeToDelete`. Она использует только значения, записанные при создании
  (папку `TEMP`, идентификатор, путь), и метку. Путь должен совпасть с первоначально созданным; папка должна существовать, не быть
  ссылкой и содержать верную метку.
- **Если проверка безопасности не пройдена,** очистка не выполняется вообще, включая снятие запрета доступа. Это отражается в итоге
  как `CLEANUP INCOMPLETE`.
- **Запрет доступа** ставится по **SID** текущего пользователя (`icacls … /deny "*SID:(OI)(CI)(RD)"`), без поиска учётной записи
  по имени. Код завершения проверяется.
  - Признак попытки ставится **до** вызова `icacls`. Поэтому при безопасной очистке снятие запрета (`/remove:d *SID`)
    выполняется и тогда, когда `/deny` завершился ошибкой: он мог частично изменить ACL.
  - Код завершения снятия проверяется; ошибка даёт замечание очистки.
- **`cmd.exe`** используется только для очистки (`rmdir` точек соединения и `rd /s /q`), всегда с ключом `/d` — без пользовательского
  `AutoRun`.
- **Подставной Docker (T3) — `docker.exe` без `cmd.exe`:**
  - **Компилятор** — `csc.exe` из каталога .NET Framework, который возвращает `RuntimeEnvironment.GetRuntimeDirectory()`. Путь
    проверяется: абсолютный, лежит внутри `%WINDIR%\Microsoft.NET`, файл существует и не является ссылкой. Через `PATH` компилятор
    не ищется.
  - **Пути.** Исходник `fake-docker.cs`, программа `bin\docker.exe` и папка временных файлов компилятора `compile-tmp` проходят
    `Assert-InSandbox` до использования.
  - **Запуск компилятора** — отдельный процесс через `System.Diagnostics.Process`:
    - `UseShellExecute = false`, без окна;
    - параметры `/nologo /noconfig /target:exe /debug- /optimize+ "/out:…" "…"`;
    - рабочая папка — временная папка теста;
    - `TEMP` и `TMP` задаются **только дочернему процессу** и указывают в `compile-tmp`; у самого теста они не меняются.
  - **Без зависания.** stdout и stderr компилятора читаются одновременно (`ReadToEndAsync`). Ожидание завершения — не дольше 120 с;
    иначе процесс компилятора останавливается, итог `ABORTED`.
  - **После компиляции** проверяются: процесс завершён, код завершения 0, процесса с этим номером нет, `docker.exe` существует и не пуст.
  - **В процесс PowerShell ничего не загружается:** нет `Add-Type`, `Assembly.Load` и подобного. `docker.exe` запускается только
    как отдельный процесс.
  - **Сравнение TEMP.** Список верхнего уровня папки `TEMP` сравнивается до и после сборки, в блоке `finally`, — то есть и при ошибке
    компиляции. Новые записи печатаются как `NOTE`, **не удаляются**, а тест завершается с `ABORTED`. Это **вспомогательная**
    проверка, а не доказательство отсутствия временных записей:
    - не видит файлы, созданные и удалённые до конца сборки;
    - не видит вложенные папки и другие каталоги, например профиль пользователя;
    - даёт ложную тревогу, если в `TEMP` в это время пишет другая программа.
  - **Разрешение команды.** Перед запуском проверяется, что команда `docker` разрешается именно в тестовый `docker.exe` (тип
    `Application`, точный путь). Псевдоним, функция или другой файл — `ABORTED`.
  - **Любая ошибка** подготовки T3 — `ABORTED`, без запасного варианта. Настоящий Docker не вызывается; функция `Invoke-DockerPart`
    не изменена.
- **Оставшиеся временные папки.** Папки `p0a-test-*` от прерванных запусков перечисляются в начале и в конце, но **не удаляются**; команда удаления для них **не печатается**, потому что этот запуск их не проверял.

- `ALL TESTS PASSED` (код 0) — только если выполнены **все** 28 проверок из списка, ни одна не провалена, очистка прошла без замечаний
  и это Windows PowerShell 5.1;
- `NOT PASSED` (код 1) — есть проваленная или невыполненная проверка либо замечание очистки;
- `ABORTED` (код 2) — неподходящая версия PowerShell, ошибка подготовки (в том числе сборки и проверки `docker.exe`), ошибка
  загрузки функций или любое исключение во время теста. Признак — отдельный логический флаг, не зависящий от текста исключения.

**Если очистка неполная** (при любом итоге), печатаются строки `CLEANUP: …` с причинами и `CLEANUP INCOMPLETE`. Дальше — по результату
**независимой проверки пути** той же функцией `Test-SandboxSafeToDelete`. Наличие файла-метки при этом не требуется: частичная
очистка могла его удалить.

**Путь подтверждён:**
- печатается полный путь папки;
- печатается предупреждение, что `rd /s /q` удаляет **необратимо**, без корзины и без подтверждения, и что полный путь нужно сверить
  самому: имя `p0a-test-<32 знака>`, папка лежит прямо в `TEMP`, по возможности внутри есть `.p0a-sandbox-marker`;
- печатаются две команды:
  - `icacls "<путь>\project\locked" /remove:d "*<SID>"` — с настоящим SID, если он достоверно сохранён; иначе с заполнителем `"*<SID>"`
    и подсказкой `whoami /user`;
  - `cmd /d /c rd /s /q "\\?\<путь>"`.

**Путь не подтверждён:** команда удаления **не печатается вовсе**; предлагается осмотреть папки вручную.

Тест эти команды **не выполняет**.

**Следы вне песочницы** — тест их не создаёт намеренно, не удаляет и не изменяет:
- файлы ускорения запуска (Prefetch) для `csc.exe`, `docker.exe`, `icacls.exe`, `cmd.exe`;
- записи антивируса и систем защиты, проверяющих новые файлы и процессы;
- журналы событий Windows, в том числе журнал PowerShell;
- возможно, журнал использования .NET (CLR UsageLogs) в `%LOCALAPPDATA%\Microsoft\CLR_v4.0*\UsageLogs` при запуске управляемого
  `docker.exe`. Это известно только из сторонних источников и **не подтверждено** документацией Microsoft. Создаёт ли подобные следы
  сам `csc.exe`, тоже **не подтверждено**.

**Не проверяет** — тест это прямо выводит:
- **символические ссылки** — тест их не создаёт: для этого нужны права администратора или режим разработчика. Их обработка
  в `Get-TreeFiles` (тот же признак `ReparsePoint`, что у точек соединения) **не проверена**;
- `Invoke-ReadOnlySql`, `Get-HfSnapshot`, `Get-DockerSnapshot`, проверку временной среды В.4а;
- команды приложения Б в окне PowerShell, включая проверку контекста Д0;
- настройку истории PSReadLine;
- настоящий Docker и настоящий PostgreSQL.

**Python-проверки логики.** В версии 1.9 перенос `Get-TreeFiles` на Python в одном месте отличался от PowerShell. Отсутствующий
начальный путь там распознавался заранее, а в PowerShell `Get-Item` выдаёт ошибку `ItemNotFoundException`. Из-за этого функция
сообщала `ROOT ERROR` вместо `ROOT MISSING`, а проверка теста упала бы. В версии 1.10 функция распознаёт этот тип ошибки
и сообщает `ROOT MISSING`. Перенос на Python не заменяет запуск в PowerShell.

**Запуск** — только по отдельному разрешению владельца, в окне без профиля:
`powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\Test-Protocol0A.ps1`. Ключ `-ExecutionPolicy Bypass` действует только для
этого процесса и настроек не меняет. Оба файла должны лежать в одной папке. Вывод присылается в чат.

**Прерывание.** `PATH` (меняется на время T3), а также на всякий случай `TEMP` и `TMP` восстанавливаются во внешнем блоке `finally`
при штатном завершении и при исключении; у самого теста `TEMP` и `TMP` не меняются. Изменения через `$env:` действуют только внутри
процесса теста. По документации PowerShell выполняет `finally` и при Ctrl+C — это **не проверено**. Абсолютной гарантии нет:
повторное прерывание во время очистки, закрытие окна или принудительное завершение процесса могут оставить временную папку и не дать
выполниться очистке. Такая папка перечисляется при следующем запуске, но команда удаления для неё не печатается: её нужно
опознать и удалить вручную.

### А.1. Как определяется, что произойдёт с каждым файлом

`apply_update.py` сравнивает SHA-256 файла в проекте (у текстовых CRLF считается как LF) со списком известных версий:

| Состояние файла | Что делает скрипт |
|---|---|
| файла нет | **добавить** |
| лежит прежняя известная версия | **заменить**, старый файл копируется в `D:\retail-shelf-audit_before_update_2026-11-06b` |
| уже новая версия | ничего («уже применено») |
| **отличается от всех известных версий** (правил владелец) | **конфликт: файл не трогается**, новая версия кладётся рядом как `.from_update` |
| к удалению: лежит прежняя версия | **переносится** в папку копий |
| к удалению: правленный файл | остаётся на месте |

Без ключа `--apply` скрипт **ничего не пишет**. Ожидаемый итог из инструкции выпуска: «заменить 51, добавить 22, убрать 56, уже применено
48, конфликтов 0». Это **оценка** для состояния после предыдущих выпусков; фактические числа и конфликты покажет только проверка на
компьютере владельца (подэтап 0Г).
