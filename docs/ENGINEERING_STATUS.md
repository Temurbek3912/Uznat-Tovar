*Этап 2 (ниже) нашёл в этом исправлении недостатки и переделал хранение индекса; описание этапа 1 оставлено как история.*

1. **Потеря всех эталонов.** Существующий, но нечитаемый файл `catalog.faiss` отвергался одинаково в трёх местах: в воркере

3. **Неатомарная запись.** Оба файла писались прямо поверх прежних: обрыв портил индекс или разводил файлы.
4. **Затирание чужой записи.** Воркер держит индекс в памяти. Импорт при работающем воркере записывал файл, а следующее добавление
   товара воркером затирало его. Защищало только предупреждение в тексте скрипта.
5. **pickle в numpy-индексе.** Он читался с `allow_pickle=True`, а любой не-zip файл с именем `.npz` загружался как pickle.
6. **Размерность не сверялась.** Индекс от другой модели обнаруживался лишь падением FAISS при поиске.

- `app/pipeline/matcher.py`:

  - numpy-индекс пишется без pickle; старый формат с pickle читается только из настоящего `.npz`.
- `app/worker.py`, `scripts/add_product_from_local_file.py` — загрузчики стали тонкими обёртками над `open_catalog_index`.

**Новое устройство** (`app/pipeline/index_store.py`, `app/pipeline/matcher.py`):
- **Блокировка.** `<индекс>.lock` берётся на чтение и запись: `fcntl.flock` в Linux, `msvcrt.locking` в Windows; ожидание до 60 с,
  затем `IndexBusyError`. Если файловая система блокировки не поддерживает, работа идёт без неё с предупреждением; остаются сверка
  поколений и повторы чтения.
- **Поколение.** Случайный идентификатор пишется при каждом сохранении в `ids.json` (формат 2) и в `.npz`. Процесс перезаписывает
  файл, только если на диске поколение, которое он сам загрузил или записал, **и** файл индекса не сменился.
- **Одно чтение.** Файл индекса читается один раз; контрольная сумма и разбор (`faiss.deserialize_index`) — из одних байтов.
  Если такой функции нет — повторная сверка контрольной суммы файла после чтения.
- **Завершение прерванной записи.** Если новый индекс уже на месте, а список id нет, загрузка находит временный список с контрольной
  суммой текущего индекса и ставит его на место. Временные списки от других записей не трогаются.
- **Повторы замены в Windows.** `PermissionError` (файл держит антивирус) — до 6 попыток с нарастающей паузой.
- **Воркер:**
  - перед каждой задачей — `refresh_index_if_changed` (перечитать индекс, записанный другим процессом);
  - после сбоя добавления — `resync_index` (память заменяется сохранённым на диске);
  - если индекс с диска не загружается — компонент `matcher` помечается неготовым.
  - «+ фото» добавляет только фото, которых нет в журнале проиндексированных (`not_yet_indexed`).
- Векторы неверной размерности отклоняются до изменения индекса.

**Ответы на 8 пунктов:**
1. **Атомарность пары «индекс + список id + контрольная сумма».**
   - Обрыв до замены индекса — прежняя пара цела.
   - Обрыв между заменами — следующая загрузка завершает замену.
   - Обрыв после — новая пара.
   - Проверено гибелью процесса (не `Exception`), ошибкой ввода-вывода, первым в жизни сохранением, «занятым» списком id.
     ПРОВЕРЕНО ФАКТИЧЕСКИ (имитация в тестах; настоящая потеря питания не проверялась — НЕ ПРОВЕРЕНО).
2. **Рассинхронизация после перезапуска.** Загрузка сверяет SHA-256, число и тип id. При расхождении — завершение замены или отказ
   с причиной; пустой индекс вместо файла не создаётся. ПРОВЕРЕНО ФАКТИЧЕСКИ.
3. **Одновременная запись.**
   - **API** индекс не читает и не пишет (проверено поиском по `app/api` — ПРОВЕРЕНО СТАТИЧЕСКИ).
   - **Воркер** — один процесс (`--concurrency=1`).
   - **Скрипты импорта** — отдельные процессы.
   - Блокировка и поколения проверены на 4 процессах — ПРОВЕРЕНО ФАКТИЧЕСКИ на локальном диске Linux. Через общую папку Docker Desktop
     между контейнерами на Windows блокировка **НЕ ПРОВЕРЕНА**; без неё остаётся сверка поколений с коротким окном (п. 4).
4. **Гонка «проверка — замена».** При работающей блокировке её нет: проверка и замена под одной блокировкой. Без блокировки
   (файловая система её не поддерживает) остаётся окно в доли секунды. Гонка при загрузке (Н-1) закрыта полностью — одно чтение.
5. **Восстановление:**
   - частичная запись, повреждение, нехватка места (при записи индекса и при записи списка) — прежние файлы целы, временные удалены;
   - блокировка файла — повторы, затем прежние файлы целы.
   - ПРОВЕРЕНО ФАКТИЧЕСКИ имитацией ошибок. На настоящем Windows — НЕ ПРОВЕРЕНО.
6. **Повторное добавление и откат базы:**
   - в памяти — пересинхронизация (Н-6);
   - фото — защита от повтора (Н-8);
   - **остаётся:** если сохранение индекса прошло, а `commit` базы — нет, на диске остаются векторы несуществующего товара.
     Неверного ответа они не дают (п. 8), устраняются схемой этапа 2Б.
   - Повтор задачи «добавить товар» после удачного `commit` даёт сообщение «товар с таким кодом уже есть», хотя товар добавлен —
     неточность сообщения, не данных.
7. **Память и диск.** После удачного сохранения память = диск (поколение); после неудачного — перечитывание; изменения другого
   процесса подхватываются перед задачей; при непригодном диске — «не готов», а не работа с расходящейся копией. ПРОВЕРЕНО
   ФАКТИЧЕСКИ для функций; проводка в воркере — ПРОВЕРЕНО СТАТИЧЕСКИ (Celery и SQLAlchemy в среде нет).
8. **Неправильный товар:**
   - единственный найденный путь (Н-1) закрыт;
   - id без товара в базе отбрасываются при распознавании (тест);
   - расхождение id и векторов обнаруживается контрольной суммой.
   - **Остаточный риск:** старый формат списка id (до 07.11, без контрольной суммы) от другого сохранения с тем же числом векторов
     не обнаруживается — это касается только индексов, ни разу не сохранённых новым кодом. У владельца индекса нет (план, §2.0).

### 2026-11-07, этап 2. Импорт каталога из CSV

  с `errors="replace"`, и все кириллические названия **молча** становились «�����».

- `catalog_import._parse_price` использует ту же функцию, что форма (`parse_price`); тексты чистятся теми же `clean_name`
  и `clean_text`.
- `decode_products_csv`: UTF-8 (с BOM или без) читается как есть; иначе — Windows-1251 с предупреждением и советом сохранить

- **Тесты:** 20 новых случаев в `tests/test_catalog_import.py`; старый код не проходит 13.

### 2026-11-07, этап 2. Запись файлов фото

**Найдено:** `_atomic_write` писал во временный файл с одним и тем же именем `<файл>.part`. Два одновременных запроса с тем же фото

### 2026-11-07, этап 2. Заголовки безопасности

#### Восстановление индекса — `scripts/reconcile_index.py`

Ядро — `app/services/index_reconcile.py`. Без `--apply` скрипт только выводит отчёт:
- векторы товаров, которых нет в базе;
- товары без векторов (и есть ли у них фото на диске);
- устаревшие отметки журнала — фото отмечено проиндексированным, а у товара нет ни одного вектора; из-за них `reindex_uploads`
  пропускал бы фото.

С `--apply`:
1. Копия файлов индекса и журнала в `backup-<время>` под блокировкой индекса; копии сверяются по SHA-256.
2. Новый индекс — те же векторы без «призраков», байт в байт, в прежнем порядке. Модель не нужна.
3. Сохранение с проверкой поколения. Если индекс за это время записал другой процесс — отказ, ничего не изменено.
4. Проверка: индекс перечитан, id и векторы совпадают с ожидаемыми.
5. Из журнала снимаются отметки только у товаров без векторов.

Фото и товары скрипт не трогает никогда.

Отказ без изменений:
- база пуста при непустом индексе;
- «чужих» векторов больше 20 %. Так выглядит индекс, построенный `ml/build_catalog_embeddings.py` по папкам с артикулами
  вместо id товаров.

**Тесты:** 27, на FAISS и numpy, включая все отказы, копию и побайтную проверку. Мутационная проверка: 4 ослабления —
4 пойманы. ПРОВЕРЕНО ФАКТИЧЕСКИ.

**Найдено попутно:** `ml/build_catalog_embeddings.py` по умолчанию писал в рабочий путь индекса и молча заменял его целиком.
Векторы фото из браузера пропадали, а журнал продолжал считать их проиндексированными, поэтому `reindex_uploads` их пропускал.

#### Устойчивость к общим папкам Docker Desktop

Проверка «файл индекса — мой» сравнивала размер, время и номер файла. На общих папках время и номер могут меняться без изменения
содержимого (не проверено на Windows, но возможно). Тогда воркер отказывал бы в каждом сохранении. Теперь при расхождении
отпечатка решает SHA-256 содержимого; поколение старого формата тоже считается по содержимому. Тесты с искусственно «прыгающим»
номером файла: 4; код этапа 2 не проходит все 4.

#### Архитектурная оценка: несколько процессов и блокировки

**Кто пишет индекс:**
- **воркер** — один процесс (`--concurrency=1`);
- **скрипты** — `import_catalog`, `reindex_uploads`, `add_product_from_local_file`, `build_catalog_embeddings`, `reconcile_index`,
  `cleanup_temp`;
- **API** индекс не читает и не пишет (ПРОВЕРЕНО СТАТИЧЕСКИ).

**Что защищает от неправильного товара — независимо от блокировок:**
- ответ — только товары из базы;
- одно чтение файла при загрузке;
- контрольная сумма пары «индекс + список id»;
- атомарная замена.

**От потери чужой записи защищают** блокировка (если работает) и сверка поколения по содержимому (работает на любой файловой
системе).

| Конфигурация | Блокировка | Остаточный риск |
|---|---|---|
| Linux, локальный диск (облачная проверка) | `flock` работает | нет известного (4 процесса × 15 записей; контрольный опыт). ПРОВЕРЕНО ФАКТИЧЕСКИ |
| Docker Desktop на Windows: все процессы в контейнерах, общая папка `models/` | все контейнеры работают в одной Linux-машине, поэтому `flock` между ними **может** действовать; зависит от механизма общих папок (WSL2 / 9p / virtiofs). **НЕ ПРОВЕРЕНО** | если блокировка отклоняется (`ENOLCK` и т. п.) — работа без неё с предупреждением в журнале; если «проходит», но не действует между контейнерами — без предупреждения. В обоих случаях остаётся сверка поколения: окно в доли секунды, худший исход — потеря одной одновременной записи (векторы одного товара), **не** неправильный товар |
| Смешанно: скрипт в Windows-Python на хосте и воркер в Docker | `msvcrt.locking` на хосте и `flock` в Linux-машине друг друга **не видят** | как выше. Рекомендация: запускать скрипты внутри контейнера (`docker compose run --rm api python -m scripts.…`) |
| Windows: файл индекса держит антивирус | — | `os.replace` повторяется до 6 раз, затем ошибка; прежние файлы целы. На настоящем Windows **НЕ ПРОВЕРЕНО** |

Частичная потеря векторов (часть фото одного товара) сверкой не обнаруживается: в индексе нет записи «какой вектор из какого
фото». Обнаруживается только товар без единого вектора. Полное решение — источник фото в метаданных вектора или «фото в базе,
индекс — производные данные» (этап 2Б, документ 07, §8).

### 2026-11-07, этап 4. Независимая проверка: восстановление, связь фото и векторов, единая блокировка

#### 1. Товар в базе, векторов нет, задача потеряна

**Что было на самом деле (аудит):**
- **обнаружение** — только вручную, `scripts/reconcile_index.py` («товары без векторов»);
- **`reconcile_index --apply` недостающие векторы НЕ добавлял**: он только удалял лишние векторы и снимал отметки журнала;
- **добавление** — только вручную, `scripts/reindex_uploads.py --apply`, который доверял журналу `uploads_manifest.json`:
  если журнал ошибочно отмечал фото проиндексированным, фото пропускалось навсегда;
- **автоматически — ничего.** Если Celery выдаёт задачу повторно (`task_acks_late`), повтор сработает; но если задача потеряна
  совсем, товар остаётся без векторов до ручного вмешательства.

**Стало:**
- **Задача воркера `recover_index`** ставится при каждом запуске воркера. Товары берутся из базы, фото — с диска, а «есть ли
  вектор» решает сам индекс. Задача добавляет недостающие векторы партиями по 200 и ставит себя снова, только пока есть
  продвижение.
- **Почему не outbox.** Задание вычисляется из долговечного состояния, отдельная таблица заданий ничего не добавляет. Разбор —
  документ 08, §8.
- **Повтор безопасен:** повтор задачи после восстановления векторов не добавляет; второй запуск восстановления — тоже.
- **Фото недоступны:** товар показывается в отчёте как «без векторов и без фото — нужны новые фото»; восстановление
  не зацикливается.
- **Папка фото без товара в базе** (API сохранил фото, задача не дошла) не индексируется.
- **`reindex_uploads`** строит план по индексу, а не по журналу.
- **`reconcile_index --apply`** честно описан: убирает лишнее (теперь и повторы одного фото), недостающее не добавляет.

**Проверки.** 7 тестов сценария владельца в `tests/test_index_coverage.py` — ПРОВЕРЕНО ФАКТИЧЕСКИ на функциях. Задача Celery

#### 6.7. Четыре падения OpenCV: причина выяснена, решение без маскировки
- **Причина (проверено):** в облачной среде одновременно установлены `opencv-python`, `opencv-python-headless` и `opencv-contrib-python`
  5.0.0.93. Они пишут в одну папку `cv2/`, загружена сборка contrib: в её `getBuildInformation` есть модуль `xobjdetect`, и
  `cv2.CascadeClassifier` присутствует. Но **ни одно из трёх колёс 5.0 не содержит файлов каскадов**: в `RECORD` каждого 0 строк
  `haarcascade`, в `cv2/data` только `__init__.py`. Проект требует одну сборку `opencv-python-headless>=4.9,<5`
  (`requirements.txt`, `constraints-opencv.txt`); образ Docker проверяет это при сборке (`scripts/check_opencv`). Код приложения
  верен, среда не соответствует требованиям.
- **Неточность исправлена:** в `privacy.py` и `opencv_check.py` было написано «в 5.x нет `CascadeClassifier`». Точнее так: в 5.x нет файлов
  каскадов, а класс есть только в contrib.
- **Решение:**
  - два теста логики размытия (запас вокруг лица, обрезка по краю, неизменность входа, нечётное ядро) больше не зависят от файла каскада
    среды: они используют настоящие функции изображений cv2 и поддельный каскад;
  - два теста **соответствия окружения** помечены `@pytest.mark.environment` и в неподходящей среде **по-прежнему падают**;
    `tests/conftest.py` печатает в конце прогона диагноз (сборки, версия, файл каскада) и что делать.
  - Чтобы они прошли, нужна среда по `requirements.txt`: так собирается образ Docker. В облаке поставить OpenCV 4 нельзя: установка
    пакетов закрыта, и ни одного колеса 4.x на диске нет (проверено).
- **Не проверено:** что образ Docker действительно получает каскад (колёса 4.x его содержат — по документации пакета, здесь не запускалось).

### 2026-11-14. Вход покупателя из интернета: QR без Wi-Fi магазина (документ 04, §3; `docs/PUBLIC_ACCESS.md`)

**Решение владельца:** покупатели заходят по QR через свой мобильный интернет, без Wi-Fi магазина, без входа; программа
продаётся многим магазинам — у каждого свой адрес; для проверок сейчас — Tailscale; программисты магазинов настраивают свой
вход сами. Оспорено и принято: бесплатный тариф Tailscale — не для коммерческого использования, поэтому магазинам — Cloudflare
Tunnel со своим доменом (или свой прокси).

**Сделано:**
- Отдельный **внутренний вход покупателя** `127.0.0.1:CUSTOMER_PORT` (8100) в том же процессе, что API (`scripts/serve.py`:
  два сокета uvicorn, модели облегчённого режима грузятся один раз). `app/core/customer_gate.py`: на этом сокете (по
  `scope["server"]`, клиент не подделает) — только страница покупателя и `/api/v1/public/*`; вход сотрудников, каталог,
  управление, `/docs` — 404; `/` ведёт на страницу покупателя. Туннель подключается только к нему.
- **Найдено и исправлено до запуска:** за туннелем все запросы приходят с 127.0.0.1 — «12 снимков в минуту с телефона» стало бы
  «12 в минуту на весь магазин». Теперь адрес телефона берётся из заголовка туннеля (`CF-Connecting-IP`, `X-Forwarded-For`,
  `X-Real-IP`) — и только на внутреннем входе; заголовка нет — действует лишь общий предел 60 в минуту
  (`LoginThrottle.check/record_failure(skip_ip=...)`).
- `scripts/public_access.py` и `start_demo --public off|tailscale|cloudflare|manual` (или `PUBLIC_ACCESS` в `.env`):
  `tailscale funnel 8100` (без `--bg` — выключается вместе с программой; адрес `*.ts.net` — из `tailscale status --json`);
  `cloudflared tunnel --no-autoupdate run` (секрет — через переменную `TUNNEL_TOKEN`, не в командной строке; адрес —
  `PUBLIC_BASE_URL`, проверка `app/core/public_url.py` в режиме server: только https и имя, не IP); `manual` — свой туннель
  программиста. В QR — адрес из интернета; ссылку «включите Funnel» из журнала туннеля программа показывает в окне. Туннель —
  необязательная служба: его сбой или ошибка настройки не останавливают работу в сети магазина.
- Настройки — `.env.example` (`PUBLIC_ACCESS`, `PUBLIC_BASE_URL`, `CUSTOMER_PORT`, `CLOUDFLARE_TUNNEL_TOKEN`); инструкция для
  владельца и программистов — `docs/PUBLIC_ACCESS.md`; отметка о смене решения — документ 04, §3.

## 6. Технический долг и известные ограничения (новое)

- **Окно гонки без блокировки.** Если файловая система не поддерживает блокировку (общая папка Docker Desktop на Windows — не
  проверено), между сверкой поколения и заменой остаётся окно в доли секунды. Полная защита — единственный владелец индекса
  (очередь, этап 2Б).
- **Векторы-призраки от прежних версий** (до этапа 3 сохранение шло до `commit`). Неверного ответа не дают;
  убираются `scripts/reconcile_index.py --apply`.
- **Частичная потеря векторов** теперь обнаруживается и восстанавливается точечно (этап 4) — для векторов с записанным источником.
  Векторы версий до 07.11 (без источника) поштучно не проверяются.
- **`recover_index` выполняется при запуске воркера, а не по расписанию.** Товар, потерявший векторы при работающем воркере,
  восстановится при следующем перезапуске или вручную (`reindex_uploads`).
- **Изменённое после индексирования фото** обнаруживается только с `--verify-photos`; вектор не заменяется автоматически.
- ~~**Версия модели у векторов не записана**~~ — с 2026-11-14 индекс хранит паспорт модели и не загружается с другой
  моделью (§3, «Манифест индекса»). Индексы, построенные раньше, остаются «непроверенными» до полной пересборки.
- ~~**Индекс нельзя пересобрать без модели**~~ — с 2026-11-14 фото и их векторы в базе (`product_images`, `image_embeddings`),
  `scripts/rebuild_index.py` (§3, «Фото товаров в базе»). Векторы «непроверенных» индексов в кэш не переносятся.
- **Выведенные из эталонов фото исключаются по записи, а не удаляются из индекса** (§3, «Каталог: фото товара из базы»): их
  векторы остаются в файле индекса до пересборки (`scripts/rebuild_index.py --apply`). Векторы без источника (индексы до 07.11)
  так исключить нельзя.
- **Журнал проиндексированных фото** пишется без общей блокировки. Он больше не источник истины и учитывается только для старых
  векторов без источника.
- **Код с фото занят к моменту привязки** — видно только в журнале воркера, пользователю не сообщается.
- **Брошенные временные файлы индекса.** Обрыв до замены индекса оставляет временный файл индекса (до сотен МБ при большом
  каталоге). Предупреждение при загрузке индекса; удаление — `scripts/cleanup_temp.py --apply` (запускает человек; правила
  безопасности — этап 3). Автоматической очистки нет намеренно.
- **Блокировки в Windows не проверены** (`msvcrt.locking`), как и повторы замены при занятом файле на настоящем антивирусе.
- ~~CSP без `style-src`~~ — закрыто 2026-11-08 (§6.13).
- **Исправления этапа 3 в API и воркере не проверены на настоящих FastAPI, SQLAlchemy и Celery** — только логика на заглушках
  и статические тесты. Обязательно: полный `pytest` в Docker (0Д).
- **`ml/build_catalog_embeddings.py`** требует, чтобы имена папок были id товаров из базы; иначе распознавание по виду ничего не
  находит (сверка это покажет и откажет в изменениях). Для папок с артикулами — `scripts/import_catalog.py`.
- **pickle в старых индексах.** Индексы формата до 07.11 с pickle по-прежнему читаются (только настоящий `.npz`); следующее
  сохранение переписывает их без pickle.
- **Предупреждения тестов.** 1677 предупреждений `pytest` у владельца не разобраны. В облачной копии прогон без предупреждений
  (`Image.getdata` заменён совместимым вызовом, §6.13).

- **Кадр «Узнать товар» всё ещё файл на диске** (D-10а не выполнено): срок сокращён до 2 минут, уборка в API (этап 5), но
  multipart-буфер Starlette и файл в `data/identify-tmp` остаются. Окончательно — этап 6 (кадр только в памяти).
- **Полная копия: режим Docker и Windows не испытаны**; пробное восстановление занимает место на рабочем сервере PostgreSQL
  (временная база размером с рабочую) — перед запуском проверить свободное место.
