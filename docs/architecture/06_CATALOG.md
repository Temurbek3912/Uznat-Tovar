# 06. Универсальный каталог товаров

> **Версия 1.5** (заключительная проверка: аллергены §4.10, валидация в PostgreSQL и диагностика §4.11, варианты §4.6). **Версия 1.4** (уточнения к 1.3: §4.2–4.6, §4.8–4.9). **Версия 1.3:** Каталог переработан под **универсальную платформу**: продукты, одежда и обувь, электроника, цветы, бытовая химия и
> любая другая розница. Первый магазин остаётся продуктовым, но схема данных больше не привязана к продуктам питания.
> Что изменилось по сравнению с 1.2 — §9.

## 1. Исходные условия

**Утверждено ранее (действует):**

- В первой версии один магазин, до 10 000 SKU. Существующая модель `Product` — конкретный вариант (SKU). Не переименовывать, не ломать.
- Цены — вручную или импортом, без реального времени. Импорт и экспорт Excel/CSV, отдельный импорт только цен (В-4). Кассы — позже.
- Общая структура карточки и дополнительные разделы по категории; без отдельной сложной системы хранения на каждую категорию (В-2).

**Новое требование владельца (2026-11-06, вечер):**

- Платформа подходит для **любого типа магазина**.
- У каждого товара есть **общие характеристики**, а **дополнительные зависят от категории и типа магазина**.
- Владелец **через интерфейс, без изменения кода** создаёт категории, их характеристики, типы данных, обязательность и правила проверки.
- Гибридное хранение в PostgreSQL. Не одна огромная таблица с множеством необязательных столбцов и не «всё в JSONB без структуры».

## 2. Письменности и языки (без изменений)

Три языка и четыре языковых варианта интерфейса: русский; английский; узбекский (латиница); узбекский (кириллица). Коды локалей:

| Код локали | Что это | Интерфейс сейчас | Данные товара сейчас |
|---|---|---|---|
| `ru` | русский | ✅ | одно поле `name` |
| `uz-Latn` | узбекский, латиница | ✅ (`uz`) | ⬜ |
| `uz-Cyrl` | узбекский, кириллица | ⬜ | ⬜ |
| `en` | английский | ✅ | ⬜ |

- Переключатель «Русский / Oʻzbekcha / Ўзбекча / English». Код `uz` в `i18n.js` становится `uz-Latn`, добавляется словарь `uz-Cyrl`.
  Резервная цепочка: `uz-Cyrl → uz-Latn → ru → en` и `uz-Latn → uz-Cyrl → ru → en`.
- **Автотранслитерация** латиница ↔ кириллица для узбекского — только **черновик** с пометкой «авто», пока человек не подтвердит.
- **Поиск** нормализует запрос: узбекская латиница и кириллица приводятся к общей форме, регистр, апострофы (`oʻ`, `o'`, `o‘`).
- Список локалей — данные, а не код: в будущем магазин в другой стране добавит свою локаль без изменения схемы.

## 3. Сравнение способов хранения характеристик

Требование: общие поля + характеристики, которые владелец определяет сам. Рассмотрены четыре подхода
(источники: [EAV и JSONB](https://raz-samuel-blog.pages.dev/postgresql-jsonb-vs-eav-dynamic-data),
[GIN для jsonb](https://postgresql.org/docs/%EF%BC%99.6/gin-builtin-opclasses.html),
[Leapcell: sparse columns, EAV, JSONB](https://leapcell.io/blog/storing-dynamic-attributes-sparse-columns-eav-and-jsonb-explained)).

| Критерий | **1. Широкая таблица** (столбец на каждую характеристику) | **2. Классический EAV** (строка на каждое значение) | **3. Только JSONB** (всё в одном поле) | **4. Гибрид** (рекомендуется) |
|---|---|---|---|---|
| Новая характеристика без изменения кода | ❌ нужна миграция схемы | ✅ | ✅ | ✅ |
| Чтение карточки | один ряд | много рядов, сборка «разворотом» | один ряд | один ряд |
| Типы и проверка | сильные (типы столбцов) | частично (столбцы по типам) | слабые без внешней схемы | сильные: схема характеристик в таблицах, проверка на сервере |
| Фильтры по нескольким характеристикам | простые | сложные (много соединений) | `@>` через GIN — хорошо для равенства, хуже для диапазонов | равенство — через GIN; диапазоны и подсчёт фасетов — через узкую индексную таблицу |
| Объём и скорость | много пустых столбцов | больше всего строк и индексов | компактно | компактно + небольшая индексная таблица только для фильтруемых характеристик |
| Целостность ссылок (варианты списков) | да | да | нет | на уровне сервера + индексная таблица с внешними ключами |
| Конкурентная запись | обычная | отдельные строки — меньше конфликтов | правка одной характеристики переписывает всё поле | как JSONB; для каталога одного магазина это приемлемо |
| Риск «каши» | столбцы-призраки | «база данных внутри базы данных» | разнородные ключи и типы | ограничен: ключи только из справочника, значения проверяются |
| Вывод | отклонено (прямо запрещено требованием) | отклонено как основное хранилище | отклонено (прямо запрещено требованием) | **принять** |

Замер в одном из источников (10 млн строк, 7 характеристик) показал, что JSONB компактнее EAV в 2 раза и быстрее на подсчётах
и сортировке с фильтром. Это чужой замер, не наш. Для нашего каталога его нужно повторить, но направление совпадает
с общей практикой.

## 4. Рекомендуемая модель данных (гибрид)

### 4.1. Общие поля товара — обычные столбцы

```text
products (есть, дополняется миграциями; существующие столбцы не трогаем)
  id (UUID), sku, name, brand, category (текст, как сейчас), expected_price, created_at       ← есть
  + category_id (FK на categories; переход с текстовой category)                                ← новое
  + status ('active' | 'archived'), updated_at, version                                          ← новое
  + attribute_values JSONB NOT NULL DEFAULT '{}'                                                 ← новое: значения характеристик
  + attribute_schema_version INT    (с какой версией схемы категории проверены значения)         ← новое
  + group_id (FK на product_groups, NULL)  (модель с вариантами — §4.6)                           ← новое, позже
product_barcodes (есть)        — штрихкоды (несколько на SKU)
product_texts (новое)          — название, краткое и полное описание по локалям (общие тексты любого товара)
product_images (новое)         — фото: эталоны для распознавания и витринные (как в 1.2)
```

Только то, что есть **у любого товара в любом магазине**: идентификатор, артикул, название, бренд, категория, статус, штрихкоды,
фото, тексты, цена. Всё остальное — характеристики.

### 4.2. Справочник характеристик — обычные таблицы (редактирует владелец)

```text
categories                    -- дерево категорий
  id, parent_id, code (неизменяемый), names {локаль: текст}, sort_order, status ('active'|'archived'),
  recognition_level ('sku' | 'group')   -- до какого уровня различаем товар по виду (§4.6), updated_at, version

attribute_definitions         -- что за характеристика
  id, code (неизменяемый, латиница, например 'ram_gb'), names {локаль: текст}, help {локаль: текст},
  data_type, unit_kind (масса | объём | длина | память | …, для типа measure),
  is_localized (значение на нескольких языках), is_filterable, is_searchable, is_public (видно покупателю),
  validation JSONB (декларативные правила — §4.4), status ('active'|'archived'), updated_at, version

attribute_options             -- варианты для списков (цвет, сезон, аллерген)
  id, attribute_id, code (неизменяемый), labels {локаль: текст}, sort_order, status

category_attributes           -- какие характеристики у категории
  category_id, attribute_id, is_required, section ('Основное', 'Состав', 'Уход', …), sort_order,
  inherited (действует ли для подкатегорий)

category_templates            -- готовые наборы («Продукты питания», «Одежда», «Электроника», «Цветы», «Бытовая химия», «Прочее»)
  code, names, store_types, definition JSONB (категории + характеристики), version     -- поставляются с программой как данные
```

**Типы данных** (`data_type`): `text`, `localized_text`, `integer`, `decimal`, `measure` (число + единица, например 16 ГБ, 0,5 л),
`boolean`, `enum` (один вариант), `multi_enum` (несколько вариантов), `date`, `range` (от–до, например «высота 40–60 см»), `url`.
Набор типов задаётся кодом и расширяется только разработкой: свободных «формул» и пользовательского кода нет.

**Системные составные типы (1.4)** — для данных, где важна строгая внутренняя структура и единые правила. Структура задаётся
**кодом программы**, владелец не может её поменять, но может подключить такую характеристику к любой категории:

| Тип | Что внутри | Зачем отдельный тип, а не набор простых характеристик |
|---|---|---|
| `nutrition_facts` | основа (на 100 г / на 100 мл), по желанию порция; энергия (ккал и кДж), жиры, в т. ч. насыщенные, углеводы, в т. ч. сахара, клетчатка, белки, соль — каждое число ≥ 0 в фиксированных единицах | связи между полями проверяются вместе: насыщенные жиры ≤ жиров, сахара ≤ углеводов, сумма на 100 г ≤ 100 г; энергия сверяется с белками, жирами и углеводами (предупреждение, а не ошибка); единая таблица в карточке для всех продуктов |
| `allergen_profile` | по каждому аллергену из **системного справочника**: **статус** (содержит / может содержать следы / производитель заявляет «без …» / в маркировке не указан / нет данных) и **происхождение** сведений (источник, подтверждено ли сотрудником, когда) — §4.10 | статус без источника опасен; нужно различать отсутствие данных, неподтверждённые сведения, заявление производителя и возможные следы (§4.10) |

**Справочник единиц (1.4)** — системные данные, не редактируются владельцем:

```text
unit_kinds  (code: mass | volume | length | data_size | energy | count | screen_size …, base_unit)
units       (code: g, kg, mg, ml, l, cl, mm, cm, m, in, MB, GB, TB, kcal, kJ, pcs …, kind, factor_to_base, symbols {локаль: текст})
```

`measure` и `range` хранят исходную единицу (для показа) и значение в базовой единице (для сравнения и фильтров). Для объёма памяти
явно фиксируется соглашение (ГБ = 10⁹ байт, как на упаковках), чтобы 512 ГБ и 0,5 ТБ сравнивались одинаково.

### 4.3. Значения характеристик — JSONB с жёсткой структурой

`products.attribute_values` — объект, где **ключи — только коды из справочника**, а форма значения определяется типом:

```json
{
  "ram_gb":       {"v": 16, "u": "GB"},
  "cpu_model":    "Intel Core i5-13420H",
  "color":        "black",
  "sizes_fit":    ["m", "l"],
  "care":         {"ru": "Поливать раз в 3 дня", "uz-Latn": "Har 3 kunda sug‘oring"},
  "height":       {"min": 40, "max": 60, "u": "cm"},
  "nutrition":    {"basis": "100ml", "energy": {"kcal": 42, "kJ": 180}, "fat": 0, "carbs": 10.6, "sugars": 10.6, "protein": 0, "salt": 0},
  "allergens":    {"items": {
                     "milk":   {"status": "contains",         "source": "label_photo", "verified_by": "u-17", "verified_at": "2026-11-06"},
                     "nuts":   {"status": "may_contain",      "source": "label_photo", "verified_by": "u-17", "verified_at": "2026-11-06"},
                     "gluten": {"status": "free_from_claim",  "source": "label_photo", "verified_by": "u-17", "verified_at": "2026-11-06"},
                     "soy":    {"status": "not_listed",       "source": "label_photo", "verified_by": "u-17", "verified_at": "2026-11-06"}
                   }}
}
```

Правила, которые не дают JSONB превратиться в «кашу»:

1. **Писать значения можно только через один серверный компонент** (`AttributeValidator` в сервисе каталога). Любой путь записи
   проходит через него: форма, импорт, API, ИИ-помощник. Прямых обновлений JSONB в обход сервиса нет.
2. Ключ, которого нет в справочнике категории, — ошибка. Неверный тип — ошибка. Значение `enum` — только код варианта.
3. Единицы `measure` приводятся к базовой единице для сравнения (0,5 л = 500 мл), исходная единица сохраняется для показа.
4. Проверка в базе как страховка: `CHECK (jsonb_typeof(attribute_values) = 'object')`.
5. Коды характеристик **неизменяемы**. Переименование меняет только подписи (`names`), поэтому существующие данные не ломаются.

### 4.4. Правила проверки (декларативные, без кода)

`attribute_definitions.validation`:

| Правило | Для типов | Пример |
|---|---|---|
| `required` (в `category_attributes`) | все | размер обязателен для «Обувь» |
| `min`, `max`, `step` | числа, `measure`, `range` | ОЗУ 1–256 ГБ |
| `allowed_units` | `measure` | масса: г, кг |
| `max_length` | тексты | 500 символов |
| `pattern` | `text` | только из **безопасного ограниченного набора** шаблонов: буквы, цифры, артикул производителя. Произвольные регулярные выражения не разрешаются: плохое выражение может «повесить» сервер (ReDoS) |
| `options` | `enum`, `multi_enum` | из `attribute_options` |
| `unique_in_catalog` | `text` | серийный номер модели (редко) |
| `min_date`, `max_date` | `date` | — |

Что происходит при изменении схемы владельцем:

| Действие | Поведение |
|---|---|
| Добавить характеристику (необязательную) | сразу доступна; у существующих товаров пусто |
| Сделать характеристику **обязательной** | существующие товары **не блокируются**: помечаются «не заполнено обязательное», появляются в отчёте и в фильтре; новые и изменяемые — проверяются |
| Ужесточить правило (например, `max`) | то же: существующие нарушения показываются в отчёте, не удаляются |
| Изменить тип | только безопасные превращения (`integer` → `decimal`, `enum` → `multi_enum`, `text` → `localized_text`) с предпросмотром; остальное — «создать новую характеристику и перенести» мастером |
| Удалить характеристику | **архивирование**: значения сохраняются, из форм и фильтров убирается; окончательное удаление — отдельное действие владельца с предпросмотром и записью в журнал |
| Удалить вариант списка | архивирование; товары с этим вариантом показываются в отчёте |

Каждое изменение схемы увеличивает `version` категории или характеристики и пишется в журнал действий.

### 4.5. Фильтрация, поиск и индексы

| Задача | Как | Индекс |
|---|---|---|
| Карточка товара | одно чтение `products` (+ тексты, фото, штрихкоды) | первичный ключ |
| Фильтр по равенству: «цвет = чёрный», «аллерген содержит молоко», «сезон = зима» | `attribute_values @> '{"color":"black"}'` | GIN по `attribute_values` с классом `jsonb_path_ops` (поддерживает только `@>`, зато быстрее и компактнее `jsonb_ops`) |
| Диапазоны и сортировка: «ОЗУ ≥ 16 ГБ», «высота 40–60 см», «сахар < 5 г на 100 мл» | узкая **индексная таблица** только для характеристик с `is_filterable` | `product_attr_index (product_id, attribute_id, sub_key, num_value, num_range, option_code, bool_value, date_value, presence, text_norm)`: `sub_key` — поле составного типа (`sugars`, `milk`); индексы `(attribute_id, sub_key, num_value)`, `(attribute_id, option_code)`; для `range` — `num_range numrange` с индексом GiST и поиском пересечения `&&` |
| Подсчёт фасетов («чёрный — 12, белый — 8») | группировка по индексной таблице | то же |
| Полнотекстовый поиск | название, бренд, артикул, штрихкод, тексты и характеристики с `is_searchable`, с нормализацией узбекских письменностей | `tsvector` (конфигурация `simple`) + `pg_trgm` для опечаток — в последующих этапах |

Индексная таблица строго типизирована на уровне базы: числа — в числовых столбцах, `option_code` — внешний ключ на `attribute_options`,
`presence` — `CHECK` из трёх значений. Поэтому всё, по чему идёт фильтр, проверено и самой базой, а не только сервером.

Индексная таблица — **производные данные**. Её заполняет тот же сервис каталога в той же транзакции, что и `attribute_values`.
Её можно пересобрать из JSONB в любой момент: источник истины один. Индексы по отдельным ключам JSONB **не создаются динамически
по действию владельца**: изменение схемы базы во время работы опасно.

**Масштаб:** для 10 тыс. SKU фильтры работают быстро даже без индексов. Индексы нужны для сети: 100 магазинов × 10 тыс. = 1 млн
строк. Цифры подтверждаются замером (документ 17).

### 4.6. Варианты товара — архитектурная поддержка сейчас, полный интерфейс позже (уточнено в 1.4)

Одна «модель» товара выпускается в нескольких вариантах. У каждого варианта свой штрихкод и часто своя цена.

| Тип магазина | Модель | Оси вариантов (примеры) |
|---|---|---|
| Одежда | футболка «Basic» | размер (XS…XXL), цвет |
| Обувь | кроссовки «Run 2» | размер (EU / US / см стельки), полнота, цвет |
| Электроника | ноутбук «X15» | память (8/16/32 ГБ), накопитель, цвет |
| Продукты | Coca-Cola | объём (0,33 / 0,5 / 1 / 1,5 л), упаковка (одна / упаковка ×6), вкус (Classic / Zero) |

**Схема (входит в этап 5 вместе с универсальным каталогом; интерфейс полного управления вариантами — позже):**

```text
product_groups                -- «модель»
  id, category_id, name, brand, attribute_values JSONB (общие характеристики модели), status, updated_at, version
group_variant_axes            -- по каким характеристикам различаются варианты
  group_id, attribute_id, sort_order            (ось — обычная характеристика категории: size, color, ram_gb, volume, pack_size)
products (= вариант, SKU)
  + group_id (NULL = самостоятельный товар без модели; так у всех нынешних товаров)
  + attribute_values — только характеристики варианта (размер, цвет, объём); общие наследуются от модели
product_images
  + group_id (фото модели) или product_id (фото варианта: например, фото именно красного цвета)
```

Правила:

- **SKU остаётся единицей учёта**: у **каждого** варианта свой `products`, свой **уникальный артикул (SKU)**, своя цена и наличие.
- **Штрихкод — у варианта, а не у модели**: `product_barcodes.product_id` указывает конкретный вариант. У варианта может быть один
  или несколько штрихкодов, а может не быть ни одного (цветы поштучно, весовые товары, товары без маркировки). У модели
  (`product_groups`) **нет** ни артикула, ни штрихкода, ни цены: это только объединение.
- Штрихкод однозначно указывает **один** вариант; если штрихкод из кадра принадлежит варианту, результат — этот вариант без угадывания.
- **Эффективные характеристики** варианта = характеристики модели + характеристики варианта. Вариант не может переопределить ось
  чужой модели; проверяет `AttributeValidator`.
- **Уникальность комбинации осей** внутри модели: два варианта «M, чёрный» в одной модели — ошибка.
- **Миграция безопасна:** `group_id` необязателен, нынешние товары остаются самостоятельными. Модель можно создать позже и «собрать»
  в неё существующие SKU.
- **Импорт:** колонки `group_key` (общий для вариантов одной модели) и колонки осей. Без `group_key` — самостоятельный товар.
- **Распознавание** (`categories.recognition_level`, документ 07, §10.2 и §10.5): индекс помнит и `product_id`, и `group_id`. Если по фото различима
  только модель (размер одежды, объём памяти в одинаковой коробке), результат — модель и уточнение оси: штрихкод, OCR (объём «0,5 л»
  на этикетке) или выбор покупателем («Какой размер?»). **Размер и конфигурация не угадываются.**
- **Карточка покупателя** показывает модель и доступные варианты (оси), выбранный вариант — с его ценой и штрихкодом.

### 4.8. Достаточно ли JSONB для всех категорий: проверка (добавлено в 1.4)

| Требование | Как обеспечено | Достаточно? |
|---|---|---|
| **Строгие типы** | **проверка при записи** — основной механизм: единственный путь записи — `AttributeValidator` по схеме категории; база проверяет структуру и всё, что попадает в индексную таблицу (типы столбцов, внешние ключи, `CHECK`); **периодическая диагностика** — дополнительная, инкрементальная (§4.11) | да; что именно проверяет сама PostgreSQL, а что — приложение, разобрано в §4.11 |
| **Пищевая ценность** | системный тип `nutrition_facts` (§4.2): фиксированные поля и единицы, проверка связей, фильтры по полям через `sub_key` | да |
| **Аллергены** | системный тип `allergen_profile` + системный справочник аллергенов (коды неизменяемы, подписи во всех четырёх языковых вариантах интерфейса); пять статусов + происхождение сведений | да, при правилах §4.10 |
| **Единицы измерения** | справочник единиц, хранение «исходная + базовая», допустимые единицы у характеристики | да |
| **Диапазоны** | тип `range` → `numrange` в индексной таблице, поиск пересечения через GiST | да |
| **Быстрый поиск и фильтры** | равенство — GIN `jsonb_path_ops` по `attribute_values`; диапазоны, сортировка, фасеты — индексная таблица; текст — `tsvector` + `pg_trgm` | да для 10 тыс. SKU; для 1 млн строк — подтвердить испытанием Т-10 (документ 17) |
| **Варианты** | `product_groups` + наследование характеристик (§4.6) | да |
| **Отчёты по сети** (например, средний сахар по категории) | агрегаты по индексной таблице; при необходимости — материализованное представление «пищевая ценность в табличном виде» (производные данные) | да |

**Аллергены — особые правила безопасности:** §4.10 (версия 1.5 заменяет правило 1.4: вывод «не содержит» из «список проверен
полностью» **отменён** как создающий ложное ощущение безопасности).

### 4.9. Почему отменены отдельные таблицы пищевой ценности и аллергенов (обоснование, 1.4)

| Критерий | А. Отдельные таблицы `product_nutrition`, `product_allergens` (план 1.2) | Б. Системные составные типы в общем механизме характеристик (рекомендуется) |
|---|---|---|
| Строгость типов и связей | высокая (столбцы, `CHECK`) | такая же: структура фиксирована кодом, проверка связей в валидаторе, фильтруемые поля — в типизированной индексной таблице |
| Подходит не продуктовым магазинам | таблицы пустуют, а в коде появляются ветки «если это еда» | один механизм для всех: магазин одежды просто не подключает эти характеристики |
| Владелец может подключить к любой категории (например, корм для животных, косметика с аллергенами) | только изменением кода и схемы | да, через интерфейс |
| Импорт, экспорт, ИИ, карточка, проверка полноты | отдельная логика для двух таблиц | общая логика для всех характеристик |
| Фильтр «сахар < 5 г» | обычный индекс по столбцу | индекс `(attribute_id, sub_key, num_value)` — такой же по скорости класс запроса |
| Сложность миграций в будущем | изменение состава полей = миграция схемы | изменение системного типа = версия типа и миграция данных JSONB с предпросмотром |
| Риски | — | ошибки валидатора; смягчается тестами на каждый системный тип, проверкой при записи и периодической диагностикой (§4.11) |

**Вывод:** вариант Б даёт ту же строгость, но без привязки ядра к продуктам питания. **Когда вернуться к варианту А:** если появятся
обязательные регламентные отчёты по пищевой ценности с тяжёлой аналитикой, которую индексная таблица не обслужит. Тогда добавляется
**производная** таблица или материализованное представление, а источник истины остаётся прежним.

### 4.7. Тип магазина и готовые шаблоны

- `stores.store_type` (продукты, одежда и обувь, электроника, цветы, бытовая химия, другое) заменяет нынешнее поле `stores.format`
  (сейчас «гипермаркет / супермаркет / у дома» — это формат продуктового магазина). Поле `format` не удаляется, оно становится вторичным.
- При первой настройке программа предлагает **шаблоны категорий** под тип магазина. Владелец их копирует и меняет, шаблоны не навязываются.
- В программу входят шаблоны (данные, а не код):

| Шаблон | Примеры характеристик |
|---|---|
| Продукты питания | состав (`localized_text`), пищевая ценность (`nutrition_facts`), аллергены (`allergen_profile`), срок хранения (`text`), масса или объём (`measure`, нужна OCR-сверке) |
| Напитки | объём (`measure`, нужна OCR-сверке), состав, пищевая ценность (`nutrition_facts`, на 100 мл), газированный (`boolean`) |
| Бытовая химия и гигиена | назначение, способ применения, меры предосторожности (`localized_text`), объём или масса |
| Одежда и обувь | размер (`enum` по размерной сетке), цвет (`enum`), материал (`multi_enum`), сезон (`enum`), пол (`enum`) |
| Электроника и компьютеры | процессор (`text`), видеокарта (`text`), ОЗУ (`measure`, ГБ), накопитель (`measure`), диагональ (`measure`), совместимость (`multi_enum`) |
| Цветы и растения | сорт (`text`), цвет (`enum`), высота (`range`, см), условия ухода (`localized_text`), сезонность (`enum`) |
| Прочее | описание и основные характеристики |

**Решение В-2 сохраняется по смыслу**: «продукты / напитки / бытовая химия и гигиена / прочее» становятся первыми четырьмя
**шаблонами**, а не жёстко зашитым перечнем `card_type`. Отдельные таблицы `product_nutrition` и `product_allergens` из версии 1.2
**отменяются**: пищевая ценность и аллергены — системные составные характеристики (`nutrition_facts`, `allergen_profile`) шаблона «Продукты питания». Обоснование — §4.9.

### 4.10. Аллергены: статусы, происхождение сведений и интерфейс без ложной безопасности (1.5)

**Главный принцип:** программа **ни в каком состоянии не утверждает, что товар безопасен для аллергика.** Она передаёт сведения
из маркировки и честно показывает, откуда они и проверены ли они. Решение остаётся за покупателем, который читает упаковку.

**Статус по каждому аллергену:**

| Код | Что означает | Что это **не** означает | Что видит покупатель |
|---|---|---|---|
| `no_data` (или аллерген не заполнен) | сведений нет | не означает «не содержит» | «Нет данных об аллергенах. Проверьте упаковку» |
| `contains` | аллерген входит в состав или выделен в маркировке | — | «Содержит: молоко» — заметно, первым |
| `may_contain` | производитель предупреждает о возможных следах («может содержать следы…») | не означает «не содержит» | «Может содержать следы: орехи» — заметно, рядом с «содержит» |
| `free_from_claim` | производитель **явно заявляет** на упаковке «без глютена», «не содержит лактозы» | **не гарантия** магазина; не медицинская безопасность | «Производитель указывает: без глютена» — нейтрально, **без** зелёных галочек и слов «безопасно» |
| `not_listed` | маркировка проверена, этот аллерген в ней не упомянут | **не** означает отсутствия; не равен `free_from_claim` | «В маркировке не указан» — мелко, только в подробном разделе, с пояснением «это не гарантия отсутствия» |

**Происхождение сведений** (`source`, `verified_by`, `verified_at`) — у каждого аллергена:

| Источник | Показывается покупателю? |
|---|---|
| `label_photo` — переписано с фото маркировки, фото сохранено в карточке | да, после подтверждения сотрудником |
| `supplier_doc` — документ поставщика | да, после подтверждения сотрудником |
| `staff_entry` — внесено сотрудником без указания документа | да, после подтверждения с отметкой проверившего |
| `ai_suggestion` — предложение ИИ-помощника (OCR, текст) | **нет**, пока сотрудник не подтвердит; после подтверждения источник меняется на фактический документ |
| `import_unverified` — пришло импортом без проверки | **нет**, пока сотрудник не подтвердит |

Неподтверждённые сведения **никогда не показываются покупателю** — для него такой товар выглядит как `no_data`. Сотрудники видят
неподтверждённые сведения с явной пометкой и в отчёте «Аллергены требуют проверки».

**Правила интерфейса покупателя:**

1. Блок аллергенов **всегда** заканчивается фразой: «Сведения из маркировки производителя. Состав может измениться. При аллергии
   обязательно проверьте упаковку». Фраза — во всех четырёх языковых вариантах интерфейса, не скрывается.
2. **Нет** слов «безопасно», «подходит аллергикам», «гипоаллергенно» от имени магазина; **нет** зелёных значков «✓ без …».
   Только заявления производителя дословным смыслом и с указанием, что это заявление.
3. `contains` и `may_contain` показываются **первыми и заметно**; `free_from_claim` — нейтрально; `not_listed` — только в подробностях.
4. **Фильтров вида «безопасно для аллергиков» нет.** Возможный фильтр «Производитель заявляет: без глютена» (только `free_from_claim`,
   только подтверждённые) — **решение владельца** (вопрос Q-15, документ 14): даже он может восприниматься как гарантия.
5. Если в сведениях противоречие (например, `free_from_claim` по глютену и `contains` пшеница) — карточка показывает «Сведения
   противоречивы, проверьте упаковку», а сотрудники получают задачу проверки.
6. Распознавание по фото **не влияет** на аллергены: даже уверенно узнанный товар может быть другой партией с изменённым составом —
   поэтому фраза из п. 1 обязательна всегда.

**Изменение по сравнению с 1.4:** отменено правило «если список проверен полностью и аллергена в нём нет — показывать как
отсутствующий». Это и было «ложным ощущением безопасности». Теперь такой аллерген получает статус `not_listed` с пояснением.

### 4.11. Как проверяются динамические характеристики: что делает PostgreSQL, что — приложение (1.5)

Владелец создаёт характеристики через интерфейс, поэтому их схема **хранится в таблицах как данные**. PostgreSQL сама по себе
не знает, что `ram_gb` должна быть числом от 1 до 256: это правило записано в строке `attribute_definitions`, а не в схеме таблицы.
Честное разделение обязанностей:

| Что проверяет | Кто | Как |
|---|---|---|
| Значение — правильный JSON, верхний уровень — объект | **PostgreSQL** | тип `jsonb` + `CHECK (jsonb_typeof(attribute_values) = 'object')` |
| Ключи только из схемы категории, типы, единицы, диапазоны, обязательность, варианты списков, связи полей составных типов | **приложение** (`AttributeValidator`) при **каждой** записи — форма, импорт, API, ИИ | один модуль; запись в обход сервиса не предусмотрена |
| Всё, что участвует в фильтрах (числа, диапазоны, коды вариантов, статусы аллергенов) | **PostgreSQL** | индексная таблица: числовые столбцы, `numrange`, внешний ключ на `attribute_options`, `CHECK` для статусов; если валидатор ошибся, вставка в индексную таблицу не пройдёт и **вся транзакция откатится** |
| Ссылочная целостность схемы (характеристика существует, категория существует) | **PostgreSQL** | внешние ключи в `category_attributes`, `attribute_options`, индексной таблице |

Варианты усиления проверки в самой базе (рассмотрены):

| Вариант | Плюсы | Минусы | Вывод |
|---|---|---|---|
| Триггер PL/pgSQL, проверяющий JSONB по таблицам схемы | вторая независимая проверка в базе | вторая реализация тех же правил (риск расхождения с валидатором), затраты на каждую запись, сложнее сопровождать | **не сейчас**; можно добавить лёгкий триггер «ключи только из `category_attributes` категории», если диагностика будет находить нарушения |
| Расширение `pg_jsonschema` (схема JSON, генерируемая из справочника) | декларативно | внешнее расширение: его нужно собрать и поставлять с PostgreSQL в Desktop; схема меняется при каждом изменении характеристик | не сейчас |
| Отдельная роль базы с правом записи `attribute_values` только через функцию | закрывает обход сервиса | усложняет код и миграции | не нужно: обход сервиса и так не предусмотрен; проверяется ревью и тестами |

**Периодическая диагностика — дополнительная, не основная.** Она нужна не для «второй проверки всего», а для случаев, когда правила
изменились после записи (владелец сделал поле обязательным, ужесточил диапазон) или в коде была ошибка.

- **Инкрементально:** проверяются только товары, у которых `attribute_schema_version` меньше текущей версии схемы их категории, и товары,
  изменённые после последней диагностики. После изменения схемы категории диагностика запускается для этой категории.
- **Полная проверка** — по кнопке владельца и после обновления программы, а не каждую ночь.
- Низкий приоритет в очереди, партиями, в нерабочее время; результаты — отчёт «Качество каталога».

**Оценка нагрузки (не измерена, проверить в испытании Т-10):** 10 тыс. товаров × около 20 характеристик ≈ 200 тыс. проверок значений
в Python. При порядке десятков микросекунд на значение это **секунды**, а с чтением из базы — **десятки секунд**: для узла магазина
нагрузка несущественна даже при полной проверке. Для 1 млн товаров в центре сети полная проверка — порядка **минут–десятков минут**,
поэтому там только инкрементальный режим и партии. Цифры — оценка порядка, а не результат замера.

## 5. Карточка товара (структура для любого типа)

Карточка строится **из схемы категории**, а не из жёстко свёрстанного шаблона.

```text
┌──────────────────────────────────────────────┐
│ [фото]   Название (на языке покупателя)       │  1. Сразу: фото, название, бренд, категория, цена (если ведётся),
│          Бренд · Категория                     │     2–4 «главные» характеристики категории (у продуктов —
│          Цена                                  │     объём и предупреждения «Содержит / Может содержать следы», у одежды — цвет и размеры,
│          ★ главные характеристики              │     у ноутбука — процессор и ОЗУ)
├──────────────────────────────────────────────┤
│ ▸ Раздел 1 (например «Состав» / «Материал»)    │  2. По нажатию: разделы из category_attributes.section,
│ ▸ Раздел 2 («Пищевая ценность» / «Уход»)       │     только публичные (is_public) и заполненные
├──────────────────────────────────────────────┤
│ Штрихкод · Артикул · [Это не тот товар]        │  3. Мелко: служебное, «Сообщить об ошибке»
└──────────────────────────────────────────────┘
```

Пустые разделы не показываются. Покупателю — только характеристики с `is_public`; внутренние (закупка, заметки) — только сотрудникам.
Пример карточки продукта (Coca-Cola Zero 0,5 л) из версии 1.2 — частный случай этой схемы. Блок аллергенов в карточке покупателя —
по правилам §4.10 (обязательная фраза «проверьте упаковку», без слов «безопасно»).

| Импорт Excel (.xlsx) | ⬜ | ✅ через `openpyxl` (уже в зависимостях) |
| Экспорт CSV/Excel | ⬜ | ✅ (по категории — с колонками её характеристик) |
| Предпросмотр и проверка до записи | ✅ для папки (`--validate-only`) | ✅ «что будет добавлено, изменено, какие ошибки» |
| Ручное добавление и правка цены | ✅ `PATCH /catalog/products/{id}` (`expected_price`) | ✅ отдельное право `price.edit`, журнал изменений |
| **Импорт только цен** | ⬜ | ✅ по штрихкоду или артикулу (§6.1) |
| Интеграция с кассой | ⬜ | не реализуется (решение В-4) |

**Формат таблицы — общий для любого магазина:** общие колонки (`sku; barcode; name_ru; name_uz_latn; name_uz_cyrl; name_en; brand;
category_code; price; status`) + колонки характеристик, где **заголовок — код характеристики** (`ram_gb`, `color`, `energy_kcal`),
а для локализуемых — код с локалью (`care@ru`). Шаблон таблицы скачивается **для конкретной категории** с её колонками и подсказками
(тип, единицы, допустимые варианты).

Правила импорта:

- Ключ строки — `sku`. Если его нет, ищем по штрихкоду. Обновляются **только заполненные ячейки**.
- Каждое значение проходит тот же `AttributeValidator` (§4.3). Ошибки показываются по строкам и колонкам до применения.
- Неизвестная колонка — предупреждение «такой характеристики нет в категории» с предложением её создать (только у кого есть право
  менять схему).
- Два шага: подготовка и проверка во временной области с отчётом → применение по подтверждению **одной атомарной транзакцией** (1.8, документ 05, §13.1); повтор безопасен; импорт больше предела делится на явные отдельные импорты.
- Цены требуют `price.edit`. Фото импортом таблицы не загружаются.
- **Экспорт ≠ резервная копия** (документ 09).

### 6.1. Импорт только цен (решение В-4, без изменений)

Ручная правка цен; импорт и экспорт каталога; **отдельный импорт только цен** по штрихкоду или артикулу; проверка и предпросмотр.
Касс нет. Архитектура **не привязана к формату кассы**:

1. Загрузка любого CSV (разделитель `;`, `,`, табуляция; UTF-8 или Windows-1251) или Excel.
2. Сопоставление колонок: штрихкод или артикул (одно обязательно) и цена; догадка по заголовкам («штрихкод», «barcode», «EAN», «артикул»,
   «SKU», «цена», «price», «narx»); сопоставление сохраняется как шаблон.
3. Проверка и предпросмотр «было → станет»: не найденные коды; пустые, нечисловые и отрицательные цены; ноль (предупреждение); резкое
   изменение (порог настраивается); дубли; конфликт «штрихкод одного товара, артикул другого»; разбор чисел `12 000`, `12000,50`, `12,000.50`.
4. Применение по подтверждению, право `price.edit`, одна транзакция, повтор безопасен. Журнал: файл (имя и SHA-256), число изменённых цен, кто.
5. Отчёт можно скачать.

## 7. Цены, остатки и принадлежность данных (задел на сеть магазинов)

| Данные | Первая версия (один магазин) | Будущее (сеть, документ 17) |
|---|---|---|
| Товар, тексты, характеристики, фото, штрихкоды | каталог магазина | каталог **организации** (общий для её магазинов) или отдельный каталог магазина — решается при подключении сети |
| Цена | `products.expected_price` | `store_prices (store_id, product_id, price, currency, valid_from)`: цена всегда принадлежит магазину |
| Наличие и остатки | не ведутся | `store_stock (store_id, product_id, qty, updated_at)` — по решению владельца |
| Ассортимент (что продаётся в этом магазине) | весь каталог | `store_products (store_id, product_id, is_active, локальные отличия)` |
| Схема категорий и характеристик | своя | организация; магазин может добавлять свои характеристики, не ломая общих |

**Ограничение уникальности — важный задел.** Сейчас `products.sku` и `product_barcodes.barcode` уникальны **во всей базе**. В одной базе
магазина это верно. Но в общей облачной базе у двух независимых организаций может быть один и тот же штрихкод Coca-Cola и одинаковые
артикулы. Архитектурное правило: **уникальность артикула и штрихкода — в пределах каталога (организации)**. В первой версии это
равносильно нынешней глобальной уникальности, менять схему сейчас не нужно. Переход — при появлении облака (документ 17, §3).
