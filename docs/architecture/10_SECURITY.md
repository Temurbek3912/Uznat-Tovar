# 10. Безопасность

## 1. Модель угроз (кратко)

| Кто | Чего может хотеть | Где граница |
|---|---|---|
| Покупатель (аноним в сети магазина) | бесплатно пользоваться, иногда — перегрузить, собрать данные, атаковать компьютер | публичный API, лимиты, брандмауэр |

### 2.1. Пароль базы данных: проверка фактической конфигурации

**Почему это важно.** Доступ к базе «только с этого компьютера» (порт `127.0.0.1`) — нужная мера, но **недостаточная защита**:

- к базе может подключиться любая программа на этом компьютере, в том числе вредоносная или установленная другим пользователем Windows;
- при ошибке в настройках (например, порт опубликован не на `127.0.0.1`) стандартный пароль сразу становится доступен из сети;
- стандартный пароль `postgres` известен всем и первым проверяется любыми средствами подбора;
- в базе — хеши паролей сотрудников, журнал действий и весь каталог.

**Что известно сейчас (только чтение файлов, 2026-11-06):** файла `.env` в папке проекта нет. В `docker-compose.yml` пароль задан
как `${POSTGRES_PASSWORD:-postgres}`: если переменная `POSTGRES_PASSWORD` не задана ни в `.env`, ни в переменных окружения Windows,
используется `postgres`. Кроме того, пароль применяется **только при первом создании тома базы** (`pgdata`). Если когда-то база
создавалась с другим значением, действует оно. Поэтому фактический пароль по файлам установить нельзя — **нужна проверка**.

**Как проверить, не показывая пароль на экране** (выполнять только после отдельного разрешения владельца; эти команды ничего не меняют):

1. Задана ли переменная в Windows (выводит только «задана / не задана»):
   `if ($env:POSTGRES_PASSWORD) { "POSTGRES_PASSWORD задана" } else { "не задана" }`
2. **Контрольный запуск с заведомо неверным паролем** — убедиться, что база вообще проверяет пароль при сетевом подключении:
   `docker compose exec -e PGPASSWORD=zavedomo-nevernyj db psql -h db -U postgres -d shelf_audit -tAc "SELECT 1"`
   - ожидается ошибка `password authentication failed` — проверке можно доверять, переходить к шагу 3;
   - если ответ `1` — база пускает **без пароля**. Это отдельная серьёзная находка: сообщить разработчику, шаг 3 не имеет смысла.

   Подключение идёт по имени сервиса `db`, а не по `127.0.0.1`: в стандартном образе PostgreSQL подключения изнутри контейнера
   к `127.0.0.1` могут пропускаться без пароля, и проверка была бы ложной.
3. Принимает ли база стандартный пароль (только чтение, запрос `SELECT 1`):
   `docker compose exec -e PGPASSWORD=postgres db psql -h db -U postgres -d shelf_audit -tAc "SELECT 1"`
   - ответ `1` — **база принимает стандартный пароль** (нужно планировать смену);
   - ошибка `password authentication failed` — пароль другой (стандартный не подходит).

   Имя пользователя и базы — значения по умолчанию из `docker-compose.yml`; если они переопределены, подставить свои.
   Пароль в этих командах — только проверяемые значения; настоящий пароль на экран не выводится.

**Если пароль стандартный — план смены (не выполнять без разрешения):** резервная копия базы → новый длинный случайный пароль →
`ALTER ROLE` внутри базы → тот же пароль в `.env` (файл вне Git, документ 15) → перезапуск `api` и `worker` → проверка `/health/ready`.
Порядок важен: если поменять только `.env`, а пароль в базе оставить прежним, приложение перестанет подключаться к базе.

## 3. Риски для телефона покупателя в сети магазина

Подробно — документ 04, §6. Главное:

1. Подключая телефоны покупателей к той же сети, где стоит компьютер магазина, мы открываем компьютер для **любого** устройства
   этой сети. Локальная сеть не является доверенной.
2. По HTTP логины и токены сотрудников видны тому, кто перехватывает трафик в этой сети.
3. Перегрузка распознавания запросами делает систему недоступной для всех.
4. Покупателю нельзя ничего устанавливать (сертификаты, приложения) — значит, нужен либо HTTP с ограничениями,
   либо настоящий сертификат на доменное имя.

## 4. Проверки безопасности (что тестировать)

- Публичные маршруты не принимают токен и не возвращают служебных полей (снимок схемы ответа в тесте).
- Каждое разрешение: без права — 403, с правом — 2xx.
- Самоповышение, изменение владельца сотрудником, отключение последнего владельца — запрещены.
- Повышение через роли (1.6): выдача больше своего, копирование роли с лишними правами, изменение своей роли и роли более сильного сотрудника,
  сброс пароля более сильному, одновременные запросы против правила «последний владелец» — отклоняются (полный список — документ 05, §20).
- Временный пароль: действует только для установки нового пароля, истекает, не появляется ни в журналах, ни в `audit_events`, ни в данных ИИ.
- Вход и сеансы (1.8): лимит попыток после перезапуска; параллельные попытки не обходят лимит; «занято» не увеличивает счётчик неудач; сбой
  после смены пароля не оставляет старых токенов; при пределе сеансов — только свои сеансы и одноразовый пропуск.
- Атомарность (1.8): отзыв доступа во время применения импорта — ни одного частичного изменения (документ 05, §20).
- 1.9–1.11: перебор из сети не блокирует учётную запись и не мешает входу с компьютера магазина и знакомого устройства; смена IP и очистка cookie не дают проверок сверх предела; ответы не выдают существование логина;
  защищённый сеанс не завершается входом из сети и подменой IP; отключение питания на каждом шаге записи фото не оставляет битых ссылок.
- Загрузка: файл-«бомба», HEIC, не-изображение, путь с `../` — понятный отказ, процесс не падает.
- SSRF: адреса `127.0.0.1`, `169.254.169.254`, `10.x`, `192.168.x`, `[::1]`, редирект на частный адрес — отказ.
- Лимит частоты публичного распознавания срабатывает и не мешает сотрудникам.
- На публичном входе нет ни одного маршрута сотрудников (перебор списка маршрутов в тесте); служебный вход не слушает внешний интерфейс.
- Кадр для выбора товара: не появляется на диске, удаляется после выбора, отмены и через 2 минуты, отсутствует после перезапуска (документ 04, §4.2).
- Резервная копия не содержит секретов в открытом виде.
