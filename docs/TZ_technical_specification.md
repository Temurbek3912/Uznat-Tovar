# Техническое задание
## Система автоматического учёта и классификации товаров на полках магазина по изображению
### (Retail Shelf Audit AI — рабочее название)

Версия 1.0 · Черновик для проработки командой разработки

---

## 1. Цель и область применения

Создать систему компьютерного зрения, которая по фотографии (или серии фото) торговой полки автоматически:

1. **Обнаруживает** все товарные позиции на полке (детекция объектов).
2. **Классифицирует/распознаёт** каждую позицию как конкретный SKU (артикул) из каталога сети — включая товары, добавленные в каталог уже после обучения моделей.
3. **Сверяет фактическую выкладку с планограммой** (эталонной схемой выкладки) и находит нарушения.
4. **Оценивает наличие товара на полке (On-Shelf Availability, OSA)** — находит пустые/почти пустые места.
5. Формирует **отчёт и алерты** для товароведов/мерчандайзеров и агрегированную аналитику для менеджмента сети.

Система рассчитана на сети с каталогом от нескольких тысяч до десятков тысяч SKU, у которых каталог обновляется еженедельно/ежемесячно — то есть **переобучение классификатора под каждый новый товар неприемлемо**. Это ключевое архитектурное ограничение, определяющее выбор ML-подхода (см. раздел 5).

## 3. Нефункциональные требования

- **Точность**: детекция позиций mAP@0.5 ≥ 0.90 на удержанной выборке; top-1 точность распознавания SKU ≥ 0.92 при закрытом каталоге, ≥ 0.85 при появлении новых SKU без дообучения детектора.
- **Латентность**: обработка одного снимка полки (до ~120 facings) — не более 5 сек. в облачном режиме (p95), не более 15 сек. на edge-устройстве среднего класса.
- **Пропускная способность**: пилот — 50 снимков/мин; целевая нагрузка сети — 5 000+ снимков/мин в часы пиковых обходов.
- **Масштабируемость**: горизontal scaling инференс-воркеров, очередь заданий, stateless API-слой.
- **Доступность**: 99.5% для облачного сервиса; локальная деградация на edge при потере связи (буферизация и досылка результатов).
- **Приватность/комплаенс**: автоматическое размытие лиц людей, попавших в кадр (сотрудники/покупатели); хранение сырых фото — конфигурируемый срок (retention policy), шифрование at-rest.
- **Наблюдаемость**: метрики инференса, дрейф качества модели, алертинг по деградации точности.
- **Обновляемость каталога**: добавление нового SKU — операция «добавить эталонные фото → построить эмбеддинг → проиндексировать», без даунтайма, без переобучения основной модели детекции.

## 4. Рекомендация по архитектуре развёртывания

Вопрос «где должна работать система» был явно оставлен на моё усмотрение — вот рекомендация и почему.

**Рекомендуемая модель: гибридная, capture-on-edge / heavy-inference-in-cloud.**

- **Захват изображения**: два равноправных сценария в зависимости от того, что есть у сети:
  - Стационарные камеры на стеллажах (лучшее качество, автоматизация, но требует CAPEX и не окупается на всех форматах магазинов) — подходит для крупных гипермаркетов и пилотных «flagship»-точек;
  - Мобильное приложение мерчандайзера/товароведа с обходом по маршруту (низкий CAPEX, быстрый rollout на всю сеть) — рекомендуемая точка входа для MVP и большинства форматов (супермаркет, магазин у дома).
- **Тяжёлый инференс (детекция + эмбеддинги + матчинг + сверка с планограммой) — в облаке.** Причины: модели детекции/эмбеддинга требуют GPU для приемлемой задержки при пиковой нагрузке; каталог эмбеддингов (десятки тысяч SKU) удобнее держать в едином централизованном векторном индексе, а не тиражировать по тысячам точек; так проще выкатывать обновления моделей (canary/A-B) сразу на всю сеть.
- **Лёгкий edge-компонент (опционально, фаза 2+)**: для точек со слабым/нестабильным интернетом — компактная модель на устройстве (например, Jetson-класс) делает только детекцию «есть товар / пусто» и локально показывает алерт по критичному OOS, полный матчинг по каталогу и точный compliance-отчёт досчитывается в облаке при синхронизации. Это защищает от двух рисков сразу: зависимости от связи и необходимости держать полный каталог-индекс на каждом устройстве.
- **Почему не «полностью on-premise/edge»**: обновление модели и каталога на тысячах локальных устройств операционно дорого и медленно; also нельзя простым способом добавлять новые SKU «на лету» без пересинхронизации индекса на каждой точке.
- **Почему не «только облако без edge вообще»**: годится как стартовая точка (и её достаточно для MVP/пилота), но для сети с точками в местах с плохим интернетом облачный-only вариант надо будет расширить edge-буферизацией на фазе роста.

**Вывод**: начинать с чисто облачной обработки фото с мобильного приложения (самый быстрый путь к MVP и pilot), закладывая в архитектуру интерфейсы так, чтобы edge-инференс можно было добавить позже без переписывания ядра (детектор/матчер как отдельные заменяемые сервисы за общим API).

## 5. ML-подход: почему open-set retrieval, а не классический классификатор

Классический softmax-классификатор на N классов (N = число SKU) не подходит: каталог сети — это десятки тысяч позиций, регулярно меняющихся (новые вкусы, сезонные SKU, редизайн упаковки). Переобучать сеть под каждое изменение каталога нереалистично.

**Принятый подход — двухэтапный pipeline, стандартный для промышленных задач fine-grained retail recognition:**

1. **Class-agnostic детекция** — модель находит рамки объектов класса «товар» (без знания, какой именно SKU), обучена один раз на разнородных данных полок (аналог задачи, публично представленной в датасетах вроде SKU-110K для плотной ритейл-детекции).
2. **Metric learning / эмбеддинги** — каждый вырезанный объект прогоняется через модель, обученную выдавать вектор так, чтобы одинаковые товары были близки в векторном пространстве, а разные — далеки (архитектуры уровня DINOv2/CLIP как база, с fine-tuning на собственных фото полок и эталонных фото каталога).
3. **Векторный поиск (kNN) по каталогу-эмбеддингов** — вместо переобучения classifier, для нового SKU достаточно добавить несколько эталонных фото → посчитать эмбеддинг → положить в индекс (FAISS/pgvector/Milvus). Порог по расстоянию отделяет «уверенно узнан» / «похож, но не уверен → в очередь на ручную проверку» / «совсем не похож на каталог → чужеродный объект».

Это открытый, общеизвестный в академической и индустриальной практике паттерн (используется во множестве систем ритейл-аналитики), а не копия конкретного проприетарного продукта — мы реализуем его самостоятельно поверх открытых моделей и открытых библиотек.

## 6. Технологический стек (рекомендация)

| Слой | Технологии |
|---|---|
| Детекция объектов | Ultralytics YOLOv8/v11 (или RT-DETR), дообученная на собственном датасете полок |
| Эмбеддинги/распознавание | DINOv2 или CLIP (HF `transformers`) с fine-tuning под fine-grained retail |
| Векторный индекс | FAISS (self-hosted) или pgvector в PostgreSQL для простоты инфраструктуры на старте; Milvus — при росте до сотен млн векторов |
| Backend API | Python, FastAPI, Pydantic v2 |
| Очереди/асинхронная обработка | Celery + Redis (или RabbitMQ/Kafka при большем масштабе) |
| БД | PostgreSQL (метаданные, планограммы, отчёты) |
| Хранилище изображений | S3-совместимое объектное хранилище |
| Контейнеризация/оркестрация | Docker, Kubernetes (HPA под GPU-инференс-воркеры) |
| MLOps | MLflow (registry/experiments), DVC (версионирование данных), собственный retraining-пайплайн по human-in-the-loop правкам |
| Мониторинг | Prometheus + Grafana, алертинг по деградации точности/латентности |
| Мобильное приложение | Flutter или React Native (кросс-платформенность, offline-очередь загрузки фото) |
| Дашборд | React + графики (Recharts/ECharts) |

## 7. Модель данных (ключевые сущности)

- **Store** — магазин (id, адрес, формат).
- **Product (Catalog SKU)** — товар: id, штрихкод, название, бренд, категория, эталонные фото, эмбеддинги.
- **PlanogramSlot** — ячейка планограммы: store_id/shelf_id/секция/ряд/позиция → ожидаемый product_id, ожидаемое число facings.
- **ShelfSnapshot** — загруженное фото: store_id, shelf_id, timestamp, автор, путь к изображению(ям).
- **Detection** — одно обнаружение на снимке: bbox, snapshot_id, matched_product_id (nullable), confidence, статус (matched/uncertain/unknown/empty-slot).
- **ComplianceReport** — агрегат по снимку: compliance_score, список нарушений, список OOS-слотов, ссылки на detections.

## 8. API (верхнеуровневый контракт)

```
POST /api/v1/snapshots                → загрузить фото, поставить в очередь на обработку
GET  /api/v1/snapshots/{id}           → статус обработки
GET  /api/v1/snapshots/{id}/report    → отчёт по снимку (compliance, OOS, детекции)
GET  /api/v1/stores/{id}/osa-summary  → агрегированный OSA по магазину за период
POST /api/v1/catalog/products         → добавить/обновить SKU (+ эталонные фото → пересчёт эмбеддинга)
GET  /api/v1/planograms/{shelf_id}    → текущая планограмма полки
PUT  /api/v1/planograms/{shelf_id}    → обновить планограмму
```

## 9. Метрики качества и приёмочные критерии MVP

- mAP@0.5 детекции ≥ 0.85 на pilot-датасете.
- Top-1 retrieval accuracy ≥ 0.85 по каталогу пилотного магазина.
- OOS detection F1 ≥ 0.80.
- Расхождение compliance-score с ручным аудитом ≤ 10 п.п. на выборке из 50 снимков.
- End-to-end время от загрузки фото до отчёта ≤ 10 сек. (p95) в облачном сценарии.

## 10. Дорожная карта

1. **Фаза 0 (2–4 недели)** — сбор датасета фото полок пилотного магазина, разметка bbox, описание планограмм в структурированном виде, baseline: pretrained YOLO + zero-shot CLIP эмбеддинги без fine-tuning.
2. **Фаза 1 — MVP (6–8 недель)** — дообучение детектора, построение векторного индекса каталога, backend API, простой веб-дашборд, пилот на 1 магазине.
3. **Фаза 2 — Масштабирование (8–12 недель)** — модуль планограмм и OSA, алертинг, мобильное приложение для обхода, rollout на несколько магазинов.
4. **Фаза 3 — Зрелость** — human-in-the-loop дообучение, OCR ценников, edge-режим для точек со слабым интернетом, BI-интеграции, полноценный multi-store rollout.

## 11. Риски

- **Визуально похожие SKU** (вкусы/объёмы одной линейки) — главный источник ошибок matching'а; митигируется fine-grained fine-tuning эмбеддера и, при необходимости, доп. сигналом (штрихкод/ценник рядом).
- **Вариативность освещения и ракурса** — требует репрезентативного датасета для обучения и/или нормализации на этапе препроцессинга.
- **Приватность** (люди в кадре) — обязательное автоматическое размытие лиц до сохранения/показа фото.
- **Дрейф каталога** — мониторинг доли «unknown»-детекций как индикатор устаревания индекса.
- **Интеграция с ERP/WMS** заказчика — уточняется индивидуально на этапе пилота.
