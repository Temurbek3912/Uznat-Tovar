# Независимый итоговый аудит архитектуры «Узнать товар» (2026-11-07)

**Что это.** Критическая оценка всей архитектуры как единого проекта:
- 18 документов `docs/architecture/` (версия 1.11);
- генеральный план 1.12;
- журнал решений (документ 14);
- `ENGINEERING_STATUS.md` (этапы 1–4);
- фактический код облачной рабочей копии.

Включены дополнительные требования владельца к трёхъязычному ИИ-помощнику (раздел 11).

**Чего здесь нет.** Ни одно решение, документ, код, настройка, база или модель по итогам аудита не изменены. Все предложения —
рекомендации; принятые решения меняются только по согласованию владельца.

**Как помечены источники:**
- **(код)** — проверено чтением кода рабочей копии;
- **(документы)** — следует из архитектурных документов;
- **(оценка)** — суждение архитектора, не измерение;
- **(проверить)** — нужны исследование или испытание.

Облачная среда не содержит FastAPI, SQLAlchemy, Celery, PyTorch, FAISS, Docker и Windows. Поэтому всё, что касается их
поведения, — только чтение кода и документов.

## 1. Общая оценка

**Архитектурная документация — сильная, местами избыточная (7/10).**

Плюсы:
- редкая для проекта такого размера честность: ✅/🟡/⬜ по коду, «оценка» против «измерено», журнал решений с основаниями;
- правильный порядок «сначала измерить распознавание, потом выбирать модели»;
- продуманная безопасность и приватность;
- реалистичная модель роста «узел магазина + необязательный центр».

Минусы:
- объём проектирования далеко обгоняет код;
- часть механизмов спроектирована с запасом, который первой версии не нужен (роли, ИИ-помощник, протокол 0А);
- три важные темы проработаны слабо: многоязычие на сервере и в помощнике, версии моделей, хранение векторов.

**Готовность реализации к коммерческому пилоту — низкая (3/10).**
- Работает прототип: штрихкоды, добавление товаров, распознавание по всему кадру, вход сотрудников.
- Фундамент коммерческой версии почти целиком на бумаге (код): миграций нет, роли фиксированные, резервная копия — только
  базы, нет публичного входа покупателя, нет OCR, нет Desktop.
- Качество распознавания не измерено ни разу.

**Главный вывод.** Переписывать проект не нужно, но до реализации этапов 2Б–7 стоит пересмотреть шесть решений (раздел 3).
Иначе возникнет технический долг, который потом придётся убирать дорого:
1. где живут векторы;
2. одна очередь вместо двух;
3. многоязычие на сервере;
4. обязательность компонентов распознавания;
5. закрепление версий зависимостей;
6. версия модели у векторов.

## 3. Критические проблемы (исправить до соответствующего этапа)

### К-1. Код нарушает принятое решение D-10а: кадр покупателя пишется на диск
- **Факт (код).** `POST /identify` сохраняет кадр в `data/identify-tmp/`; воркер читает файл и удаляет его, забытые файлы
  удаляются через 15 минут. D-10а (принято владельцем): кадр только в памяти, на диск не пишется.
- **Почему важно.** При публичном входе покупателей это нарушение принятой политики приватности. Кадр попадает на диск, а значит
  в теневые копии Windows и, возможно, в резервные копии.
- **Предложение.** Передавать кадр воркеру или процессу распознавания в памяти: байты в задаче — до 2 МБ после нормализации — или
  прямой вызов в процессе (К-8).
- **Этап.** До публичного API покупателя (этап 8), желательно в 2Б. **Требует согласования:** нет — исполнение уже принятого
  решения.
- **Если оставить.** Нарушение D-10 и D-10а с первого дня пилота.

### К-2. Векторы — единственная копия в файле вне базы
- **Факт (код).** Векторы хранятся только в `catalog.faiss` + `ids.json`. Этапы 1–4 сделали файл надёжным: атомарная запись,
  поколения, блокировки, источник фото у вектора, восстановление. Но цена — около 3000 строк кода и тестов вокруг индекса (подсчёт по файлам этапов 1–4), и всё равно
  остаются неустранимые на файлах ограничения: блокировки в Docker Desktop на Windows не проверены, между Windows-хостом и
  контейнером они не действуют.
- **Почему текущее недостаточно.** База и индекс — два хранилища без общей транзакции. Отсюда все сценарии этапов 3–4:
  «призраки», товары без векторов, гонки.
- **Предложение.**
  - Таблица `image_embeddings (image_id → product_images, model_version, vector BYTEA/REAL[])` — **источник истины**, в той же
    транзакции, что товар и фото.
  - FAISS — только ускорение в памяти, собирается из базы при старте. Оценка: 80 тыс. векторов × 768 × 4 байта ≈ 245 МБ — чтение
    за секунды.
  - Документ 07, §8 уже предлагает `image_embeddings`, но как «кэш». Предлагается сделать её главной, а файл индекса — необязательным.
- **Плюсы:** одна транзакция, резервная копия через `pg_dump`, нет файловых блокировок, разделение по магазинам — обычный
  `store_id`.
- **Минусы:**
  - холодный старт дольше (секунды);
  - память ×2 при пересборке;
  - при SQLite в Desktop (D-02) — `BLOB`, это работает.
- **Альтернатива.** `pgvector`: поиск прямо в PostgreSQL. Минусы — сборка расширения под Windows-установку и скорость точного
  поиска (проверить); для 10 тыс. SKU FAISS в памяти проще.
- **Этап.** Схема — 2Б (вместе с `product_images`); перевод распознавания — 6. **Требует согласования** (меняет модель данных
  распознавания).
- **Если оставить.** Механизмы этапов 1–4 придётся сопровождать и проверять на каждой ОС; сеть магазинов потребует пространств
  имён файлов; потеря файла = пересчёт всех векторов моделью.

### К-3. Нет миграций схемы
- **Факт (код).** Alembic в зависимостях, но не используется; `create_all`.
- **Предложение.** Базовая ревизия по фактической схеме владельца (после 0А-3); каждая миграция — на копии базы (план 2А/2Б).
- **Этап.** 2Б, уже в плане. **Согласовано** (план).
- **Если оставить.** Любое расширение каталога или ролей — ручной риск для данных.

### К-4. Распознавание по виду не работает без компонентов, которые оно не использует
- **Факт (код).** Воркер не объявляет готовность без весов YOLO (`preflight`) и без каскада лиц, хотя «Узнать товар» использует
  только DINOv2 + индекс. Детектор — `ultralytics` (AGPL-3.0, или платная лицензия) — обязательная зависимость образа.
- **Почему важно.** Лишняя точка отказа (нет файла весов — нет распознавания) и лицензионный риск в закрытом дистрибутиве (R-03),
  даже если детектор не вызывается.
- **Предложение.** Компоненты распознавания — по фактическому конвейеру: детектор и размытие лиц — необязательные, пока они не в
  рабочем пути; `ultralytics` — необязательная зависимость до решения D-05. Решение о детекторе — по benchmark (план §4).
- **Этап.** До пакета Desktop или коммерческого выпуска; удобно в этапе 6. **Требует согласования** (меняет требования к составу
  образа; размытие лиц объявлено обязательным в коде).
- **Если оставить.** AGPL-зависимость в коммерческом продукте; отказ распознавания из-за файла, который не используется.

### К-5. Версии зависимостей не закреплены
- **Факт (код).** `requirements.txt`: `torch>=2.3`, `transformers>=4.42`, `ultralytics>=8.3.0`, `faiss-cpu>=1.8` и т. д.; файла
  блокировки версий нет (кроме ограничений OpenCV).
- **Почему важно.** Две сборки одного выпуска могут отличаться; обновление `transformers` или `torch` меняет векторы — а значит,
  совместимость индекса — без ведома владельца.
- **Предложение.** Файл точных версий с хешами (`pip-compile --generate-hashes` или `uv lock`), отдельные наборы CPU и GPU;
  обновление зависимостей — отдельный выпуск с прогоном тестов и benchmark.
- **Этап.** До первого выпускного пакета после 0Г — сейчас. **Требует согласования** (установка и обновление зависимостей — §10
  плана).
- **Если оставить.** Невоспроизводимые сборки, «у меня работает» при поддержке.

### К-6. Многоязычие не доходит до сервера, профиля пользователя и помощника
- **Факт (код).**
  - около 70 текстов ошибок в `HTTPException` и исключениях сервисов (подсчёт по коду) — только на русском; страница показывает их как есть
    (`describeApiError` в `products.js`);
  - язык хранится только в `localStorage` браузера;
  - поля языка у пользователя нет.
- **Почему важно.** Требование владельца — три языка (а для интерфейса — четыре варианта) во всех сообщениях, включая ошибки и
  результаты действий помощника (раздел 11). Сейчас узбекский пользователь видит русские ошибки.
- **Предложение.** Раздел 11, Р-1…Р-4: коды ошибок с параметрами вместо готовых фраз, перевод на клиенте и в шаблонах сервера,
  `users.preferred_locale`, порядок выбора языка.
- **Этап.** Коды ошибок — до этапа 3 (вместе с переделкой входа); язык в профиле — этап 3; помощник — 7А. **Требует согласования.**
- **Если оставить.** Переводить придётся задним числом во всех маршрутах; помощник унаследует русские ошибки инструментов.

### К-7. У векторов нет версии модели
- **Факт (код).** В индексе нет имени, ревизии и хеша весов эмбеддера, предобработки; сверяется только размерность.
- **Почему важно.** Смена модели или даже версии библиотеки с той же размерностью (768) даст несовместимые векторы без ошибки —
  тихое падение точности.
- **Предложение.** `model_version` у каждого вектора (К-2) и в манифесте индекса; при старте — сверка с загруженной моделью; новая
  модель — пересчёт рядом со старой и переключение после проверки на benchmark.
- **Этап.** 2Б (схема), 6 (сверка и переключение). **Согласовано по сути** (документ 07, §8 «Предложение»), не реализовано.
- **Если оставить.** Невозможно безопасно обновить модель — главное средство улучшения качества.

### К-8. Распознавание — синхронный вызов через очередь
- **Факт (код).** API ставит задачу в Celery и блокирует поток до 25 с (`task.get`); маршрут синхронный, то есть занимает поток из
  ограниченного пула.
- **Почему важно.** Для ориентира В-3 (20 распознаваний в минуту) хватает. Но для публичного входа это поверхность отказа
  в обслуживании: медленные запросы занимают потоки API, лишние звенья (Redis, результаты в Redis) добавляют задержку и точки
  отказа (оценка).
- **Предложение.** Распознавание — прямой вызов через `InferenceClient` (D-27 уже предлагает) в отдельном процессе распознавания
  с семафором и ограниченной очередью ожидания; очередь — только для фоновых заданий. В Desktop так и задумано (документ 02, §3);
  предлагается то же в серверном профиле.
- **Этап.** До публичного API (этап 8), лучше вместе с К-1. **Требует согласования** (меняет утверждённое «Celery и Redis — для
  Docker»; см. Р-6).
- **Если оставить.** Два разных пути распознавания в двух профилях; задержка и отказы под нагрузкой.

## 4. Существенные недостатки (чтобы не накопить долг)

### С-1. Роли и разрешения избыточны для первой версии (документ 05)
Свои роли, индивидуальные «разрешить / запретить», области, защита от повышения полномочий, доверенные и знакомые устройства — для
одного владельца и ≤10 сотрудников. Это много кода, тестов и сложный экран (R-33).

**Предложение:**
- модель данных оставить расширяемой (D-38…D-42);
- в первой версии реализовать 4–6 шаблонов ролей, которые владелец меняет галочками, без индивидуальных запретов и доверенных
  устройств;
- остальное — по факту потребности.

**Требует согласования** (Q-16 принято).

### С-2. Протокол 0А непропорционально тяжёл
Около 1300 строк плана на чтение состояния, 12 редакций. Риск уже исчерпан наполовину: ничего не меняется, чтение идёт только
командами из списка.

**Предложение** для будущих операций такого рода: сначала проверенная копия (0Б), затем короткий автоматический сценарий отчёта,
запускаемый одной командой.

Решение владельца уважается; это замечание о стоимости процесса.

### С-3. Две очереди и два процесса в двух профилях
Celery + Redis в Docker; таблица заданий в Desktop (документ 08, §5); разные пути распознавания. Риск R-29 признан.

**Предложение:** Р-6 — одна реализация (таблица заданий + процесс распознавания) для обоих профилей.

### С-4. Каталог и привязка к PostgreSQL
`numrange`, GIN по JSONB, RLS (документы 06 и 17) делают SQLite в Desktop (D-02) почти невозможным, хотя решение D-02 формально
открыто.

**Предложение:** честно связать решения — либо D-02 = PostgreSQL (тогда спокойно пользоваться его возможностями), либо ограничить
каталог переносимыми конструкциями. Раздел 8.

### С-5. Фото хранятся в папках по артикулу
Артикул нельзя переименовать без переноса файлов; у фото нет id в базе.

**Предложение:** `product_images` (этап 2Б, в плане) с путём хранения по `image_id` (`ab/cd/<uuid>.jpg`), а не по артикулу; артикул —
только данные.

### С-6. Цена — `float`
Решение в плане есть (этап 4), но цена влияет на импорт цен и будущую сверку. Перевести в `NUMERIC(12,2)` + валюту в той же
базовой миграции 2Б, а не позже.

### С-7. Сотрудники входят по HTTP
Пароль и токен по Wi-Fi магазина открытым текстом (R-40 признан).

**Предложение:** локальный HTTPS с собственным центром сертификации, установленным на устройства сотрудников, — или вход
сотрудников только с компьютера магазина до появления HTTPS. Это заодно даёт живую камеру на телефоне.

**Требует решения D-08.**

### С-8. Нет журналов для поддержки
Нет структурированных журналов с ротацией, метрик (время распознавания, очередь, ошибки) и «пакета диагностики» одним нажатием
для отправки разработчику (без персональных данных).

Для владельца-непрограммиста и удалённой поддержки это главный инструмент.

**Этап:** вместе с этапом 7 (Desktop), основа — раньше.

### С-9. Тесты API проверяются в основном заглушками вне Docker
В облачной среде нет FastAPI и SQLAlchemy; настоящие API-тесты идут только у владельца.

**Предложение:** локальная команда «прогон всех тестов в Docker» как обязательная проверка каждого выпуска; для Desktop — тестовая
виртуальная машина Windows.

### С-10. ИИ-помощник спроектирован шире, чем нужно для пилота
A4 (сотрудники и роли через чат) и пакетные операции повышают риск и объём.

**Предложение:**
- первая версия — A1 (только чтение и объяснения) + A2 (черновик карточки);
- управление доступом через ИИ не делать вовсе (у владельца есть экран).

**Требует согласования** (D-31, D-45).

### С-11. Перевод на узбекский — черновой
Нужен носитель языка до пилота (R-11). Для помощника качество узбекского у локальных моделей — отдельный риск (раздел 11).

### С-12. Лицензия Redis
Образ `redis:7-alpine`: начиная с 7.4 Redis распространяется под RSALv2/SSPL. Для внутреннего сервера это, как правило, не мешает;
при поставке в составе продукта нужна проверка — или замена на Valkey (BSD).

**(проверить)** — какая именно 7.x используется у владельца.

### С-13. Подпись установщика (D-14)
Без подписи SmartScreen пугает пользователя. Нужно заранее выяснить доступные варианты сертификата для организации в Узбекистане
(OV/EV, облачная подпись) и их стоимость.

**(проверить)**

## 8. Сравнение альтернатив (только где есть реальный выбор)

| | Файл FAISS (сейчас) | Таблица в базе + FAISS в памяти (рекомендация) | `pgvector` |

| Скорость поиска | лучшая (память) | лучшая (память) | хуже на точном поиске, нужны индексы (проверить) |
| Desktop | файлы | работает и с SQLite (BLOB) | только PostgreSQL + сборка расширения под Windows |
| Сложность | высокая (блокировки, поколения) | низкая | средняя |

|---|---|---|---|

| Дополнительные сервисы | Redis | нет | нет |

**База Desktop (D-02):** PostgreSQL в установке — один диалект, все возможности каталога, но служба, пароль и смена основной версии
у клиента. SQLite — проще установка, обновление и копии, но второй диалект и отказ от части возможностей каталога. Рекомендация
плана (склоняться к PostgreSQL) разумна **при условии**, что прототип 1Г проверит тихую установку, обновление и смену основной
версии. Если нет — каталог придётся упрощать. Решить до этапа 4.

**Детектор (D-05):**
- YOLO11 — AGPL или платная лицензия;
- RF-DETR и RT-DETR — Apache-2.0 (проверить лицензию конкретных весов);
- без детектора — центральный кроп для одиночного товара в руке.

Решение — по benchmark. Для сценария «один товар в руке» вариант без детектора может оказаться достаточным, и он самый дешёвый.

**Язык ответа помощника на узбекской кириллице:** модель пишет сразу кириллицей (качество моделей хуже, проверить) — против
«модель пишет латиницей, приложение транслитерирует детерминированно» (рекомендация, раздел 11).

## 10. Итоговая оценка

**Архитектура — 7/10. Реализация для пилота — 3/10.**

**Сильные стороны (документы и код):**
- честный учёт состояния и решений;
- правильный порядок «измерить, потом выбрать»;
- образцовые принципы безопасности и приватности;
- local-first без обязательного интернета;
- реалистичная модель роста;
- аккуратный и хорошо протестированный код существующих частей;
- после этапов 1–4 — надёжная запись данных и восстановление индекса.

**Слабые стороны:**
- проектирование местами избыточно для первой версии: роли, помощник, процессы;
- три важных механизма спроектированы слабо: где живут векторы, версия модели, многоязычие сервера и помощника;
- две параллельные инфраструктуры (Docker с Celery и Redis против Desktop);
- код нарушает одно принятое решение (D-10а);
- распознавание не измерено ни разу — это по-прежнему главный неизвестный риск всего продукта.

**Честное заключение.** Проект можно доводить до коммерческого пилота без переписывания, если до этапов 2Б–7 принять Р-4…Р-9
и не расширять объём первой версии сверх необходимого. Самый ценный следующий шаг не меняется: проверенная копия (0Б), затем
небольшой реальный benchmark распознавания (этап 1). Без него остальные оценки качества продукта остаются предположениями.

| Системные сообщения и ошибки на выбранном языке | сервер отдаёт готовые русские фразы; страница показывает их как есть | код |
| Тесты сохранения и переключения языка | есть JS-проверки переключателя (`i18n_smoke_test.js`); тестов профиля, повторного входа и обновления нет | код |

### 11.2. Предлагаемый порядок выбора языка (рекомендация, требует согласования)

1. **Язык интерфейса пользователя** — `users.preferred_locale` (ru, uz-Latn, uz-Cyrl, en):
   - меняется переключателем;
   - сохраняется на сервере и применяется на всех устройствах после входа;
   - для анонимного покупателя — только `localStorage` на его телефоне, на сервере ничего.
2. **Язык помощника по умолчанию = язык интерфейса.** Смена языка программы сразу меняет язык помощника (п. 7 требований).
3. **Отдельный язык помощника** (п. 8):
   - необязательная настройка `assistant_locale` со значением по умолчанию «как в программе»;
   - в окне чата видна метка «Помощник отвечает: Oʻzbekcha (как в программе)»;
   - сброс — одной кнопкой.
   - Так нет путаницы: по умолчанию одна настройка; отдельная видна и подписана.
4. **Ответ на сообщение на другом языке.** Помощник понимает запрос на любом из трёх языков. Отвечает на выбранном языке, а не на
   языке сообщения, чтобы не прыгать между языками; одна оговорка-подсказка «ответить по-русски?» допустима.
5. **Порядок при старте:** профиль → `localStorage` (если профиль пуст, например до первого входа) → язык браузера → русский.
   Ключ `localStorage` версионируется, чтобы обновление программы не сбрасывало выбор.

### 11.3. Что делает приложение, а что — модель

- **Тексты интерфейса, ошибки, подтверждения, итоги действий** формирует приложение по коду сообщения и параметрам из каталогов
  перевода — не модель. Тогда они всегда на нужном языке и не искажаются (п. 10).
- **Инструменты помощника** возвращают структурированные результаты (коды, числа, id), а не фразы. Модель объясняет их на нужном
  языке; критичные формулировки (предупреждения, подтверждения) берутся из каталога перевода.
- **Данные каталога** (названия товаров, бренды) показываются как записаны и моделью не переводятся: перевод названия — источник
  выдумки и ошибок поиска.
- **Узбекская кириллица.** Модель отвечает на узбекской латинице, приложение детерминированно транслитерирует в кириллицу, если
  выбран `uz-Cyrl`. Транслитерация латиница → кириллица для узбекского почти однозначна (оценка; исключения — слова на «е»/«э»,
  «ц», заимствования — проверить носителем). Запросы на кириллице нормализуются для поиска (документ 06, §2).

### 11.4. Риски и что проверить

- **Качество узбекского у локальных моделей 7–8 млрд параметров** — главный риск требования (оценка; **проверить**).
  - Выбор модели (документ 16, §10.2) должен включать отдельный набор контрольных задач на каждом языке: ru, uz-Latn, en,
    плюс проверку транслитерации uz-Cyrl.
  - Нужен порог качества для узбекского. Если локальная модель его не проходит: модель крупнее на отдельном компьютере, облако
    по согласию владельца (Q-5) или ограниченный режим, где на узбекском — только шаблонные ответы приложения.
- **Смешение языков в ответах** — проверка в наборе задач: доля ответов с фрагментами другого языка, цель — меньше 2 %
  (предложение).
- **Тесты (п. 11):**
  - сохранение в профиле;
  - смена на одном устройстве — применение на другом после входа;
  - повторный вход;
  - перезапуск сервера;
  - обновление программы (миграция ключа `localStorage`);
  - анонимный режим без сервера;
  - отдельный язык помощника и сброс;
  - каждое сообщение об ошибке на каждом языке (как сейчас `tools/test_texts.js` для интерфейса).
- **Вопрос владельцу:** в новом тексте требований «узбекский» — один язык, а принятое требование интерфейса — четыре варианта
  (с узбекской кириллицей). Нужен ли помощник на узбекской кириллице? Рекомендация: да, через транслитерацию (дёшево).
